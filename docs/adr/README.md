## 運用ルール

- 承認済みADRは原則として**書き換えない**。決定が変わったら新しいADRを起こし、古い方の状態を「棄却(ADR-XXXXで置き換え)」に変える
- 実装がADRと食い違ったら、コードを直すかADRを改訂するかを必ずどちらか選ぶ。放置しない
- **「書き換えない」の範囲**:状態欄の更新と、日付つきの**註記・追記**は書き換えに含めない。守るべきは**本文の文言を変えないこと**であり、後から分かった事実とその評価は註記として足してよい(足さないと、崩れた前提の上に決定だけが残る)。註記は日付を明記し、本文と視覚的に区別する
- **却下理由の前提が崩れたら、代替の却下理由を註記する。** ADRの価値は却下した選択肢とその理由が残ることなので、前提だけ崩れて理由が空白になると、再検討時にその選択肢を評価できない
- **帰結は2節に分ける。**「**帰結(引き受けるトレードオフ)**」はADR内で完結するもの、「**波及(反映先)**」は更新して初めて決定が完了する文書のチェックリストである。**反映先が決まらないものは帰結ではなく issue に書く** — チェックできない行を並べると、完了の判定ができなくなる(ADR-0006 は残る2件を [#9](https://github.com/stama72/visionary/issues/9) / [#10](https://github.com/stama72/visionary/issues/10) へ明示的に逃した)。**波及が空になるADRでは節ごと省く**
- **形の適用は新規起案から。既存ADRは次に触るときに揃える。** 0001〜0003 への遡及は行わない — 単一論点で読み替えも無く、ステータス行も波及節も効かないため、凍った文書を触るコストだけが残る([issue #15](https://github.com/stama72/visionary/issues/15))
- **多論点ADRは、論点ごとにステータス行を持つ。** 「1決定1ファイル」の「1決定」は**独立して覆せる単位**であり、1つのADRが複数の論点を持つなら覆されるのも論点ごとである。各論点の見出し直下に引用行を置く:

  ```
  > ステータス: 承認 / WIP 上限は ADR-0006 論点4 で読み替え
  ```

  **索引の状態欄は「この ADR に読み替えがあるか」だけを示し、どの論点がどうなったかは本文が持つ。** 状態欄1つでは表現できなくなるため(現に ADR-0004 は3件の読み替えを抱えていた)。ステータス行の追加は上の「書き換えない」の対象外である([issue #12](https://github.com/stama72/visionary/issues/12))

### ADRか他文書かの切り分け

起案時に3つの問いで判定する:

1. **却下した選択肢に価値があるか。** 後から覆す人が、選択肢の再発見と再検討からやり直す必要があるならADR。「他に選びようがなかった」ものは単なる仕様であってADRではない
2. **これは決定か、それとも予測か。** 予測は運用で反証されるのが正常。凍る文書に予測を書くと、外れたときにADRを起こすしかなくなる。ADRに予測を書くなら「これは仮説であり◯◯で検証する」と明示する
3. **読者は「なぜ」を知りたいのか、「今どうなっているか」を知りたいのか。** 現行の状態を答える責務を負った時点で、その文書はADRではない

**不採用にした候補:「これは機械で守れるか」。** ADR-0002 の決定論規約のように、機械で守れない技術的決定は存在する。この問いは規約を設計するときには有効だが、ADR/他文書の切り分けには使えない。

### テンプレート

**[TEMPLATE.md](TEMPLATE.md) が形の正である。** 起案時にコピーして使う。

### その他

- **決定と予測を区別する。** 理由に書いた経験的な予測は運用で反証されうる。**予測が外れた結果として決定を変えるなら新ADR、決定が変わらないなら追記**([ADR-0004](0004-ai-driven-development-workflow.md) 論点4 の追記が例)。ADRに予測を書くなら「これは仮説であり◯◯で検証する」と明示する
- **現行仕様をADRに持たせない。** ADRが答えるのは「なぜそうしたか」であって「今どうなっているか」ではない。現行の状態を答える責務を負った時点で、それはADRではなく育てる文書(GDD / TDD / [process/](../process/))の仕事である
- **番号の予約は master へ直接コミットする。状態欄の更新は当該ADRのPRで行う。** 予約が master にあるのは worktree をまたいで番号衝突を防ぐためであり、承認/棄却の反映はそのADRを含むPRのマージと同時でよい
- **他に活きている worktree があるときは、番号を着手時に予約する。** 起案を始めた時点で、この表に「起案中」の行だけを先に master へコミットする。承認後にしか載らない運用では、worktree で並行作業したときに番号が衝突する([ADR-0004](0004-ai-driven-development-workflow.md) 論点3)
- **`git worktree list` が自分の1本だけを返すなら、予約しない。** 衝突しようがなく、予約コミットは空振りになる。**実態が既にこうなっている** — 0007・0008・0010 は並行が無く予約せず、0009・0011 は予約した。無条件の規則にすると、守られない行が残り続ける([issue #55](https://github.com/stama72/visionary/issues/55))
