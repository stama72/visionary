# ADR-0001: ゲームエンジンとシミュレーション層のアーキテクチャ

- 日付: 2026-08-19
- ステータス: 承認
- 決定者: stama

## 背景

2Dトップダウンのピクセルアート表現で、エージェントベースの経済シミュレーションを中核とするPCゲームを個人・12ヶ月で開発し、Steamで配信する。就活ではWeb・一般ソフトウェア業界向けに、設計力・テスト・開発プロセスをアピールしたい。

開発はAIコーディングエージェント(Claude Code等)の活用を前提とするため、**AI駆動開発への適性**も評価軸に含める。具体的には (a) LLMの学習データ量(生成精度)、(b) プロジェクトファイルのテキスト編集性(エージェントが直接読み書きできるか)、(c) ヘッドレス/CLI実行(エージェントが自律的にビルド・テスト・実行して検証できるか)の3点。

## 検討した選択肢

1. **Godot 4 + C#(シム部を純C#クラスライブラリに分離)**
2. Unity + C#
3. Godot 4 + GDScript
4. 自作フレームワーク(MonoGame等)

## 決定

**選択肢1: Godot 4 + C#。経済シミュレーションはエンジン非依存の純C#クラスライブラリ(`Visionary.Sim`)として実装し、Godot側は描画・入力・UIのみを担う。**

## 理由

- 2D機能がネイティブで、ピクセルアート×トップダウンに最適。無料でライセンスリスクもない
- 就活先がゲーム業界ではないため、Unityのエンジン経験価値よりも、C#での設計・テスト経験の汎用性を優先する
- シム部の分離により:
  - tickベース・シード付き決定論的にでき、リプレイ・デバッグが容易
  - ヘッドレス実行で「ゲーム内100年分回して物価が発散しないか」等の検証をxUnit+CIで自動化できる
  - 万一エンジンを乗り換えても中核資産が生き残る
- MonoGame等の自作は柔軟だがUI・アセットパイプラインの工数が1年スコープに収まらない
- AI駆動開発適性の評価:
  - 学習データ量ではUnityが優位(Godot 4 C#は作例が薄い)。ただしこれはチャット型のコード生成で効く差であり、エージェント型開発では自律検証ループで吸収可能
  - エージェント型開発で支配的なのはテキスト編集性とCLI実行であり、ここはGodotが明確に優位:`.tscn`/`.tres`は人間可読テキストでエージェントが直接読み書き・diffできる(UnityのシーンはGUID参照だらけのYAMLで実質GUI操作前提)。`godot --headless`でインポート・テスト・エクスポートまでCLI完結する
  - 複雑さの中心である`Visionary.Sim`は標準.NET + xUnitの世界で、LLMの最も得意な領域。シム分離設計はAI駆動開発の観点でも最適配置になる

## 帰結(受け入れるトレードオフ)

- GodotのC#サポートはGDScriptよりドキュメント・作例が少ない。詰まった場合はGDScript作例をC#に読み替えるコストを払う
- Godot経験は国内ゲーム業界の求人ではUnityほど通用しない(ターゲット外のため許容)
- シム層とエンジン層の境界設計(状態の同期、イベント通知)に初期コストがかかる。M0プロトタイプでこの境界を検証する
- Godot 4 C#の学習データの薄さにより、AIが古いGodot 3系APIやGDScript流儀のC#を生成するリスクがある。緩和策:
  - Godotのマイナーバージョンを固定し、CLAUDE.md にバージョン・C#規約・既知の間違いパターンを明記する
  - AIには公式クラスリファレンスの参照を前提とした実装を求める運用にする
  - gdUnit4によるエンジン側テストとヘッドレス起動チェックをCIに入れ、幻覚APIをコンパイル・実行段階で機械的に検出する
