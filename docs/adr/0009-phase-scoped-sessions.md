# ADR-0009: タスクをフェーズで切り、フェーズ境界でセッションを捨てる

- 日付: 2026-09-15
- ステータス: 承認
- 決定者: stama

## 背景

[ADR-0008](0008-review-scope-narrowed-to-unnoticeable-defects.md) はレビュー1巡あたりの単価を下げたが、**セッションの持ち方には触れていない**。1タスクを1つのコンテキストで通す運用は [ADR-0004](0004-ai-driven-development-workflow.md) のまま残っている。

W2-01([#32](https://github.com/stama72/visionary/issues/32) / [PR #64](https://github.com/stama72/visionary/pull/64))を1セッションで設計から PR まで通した結果、2つのことが起きた。

- **1つのコンテキストが、仕様・実装・レビュー3巡・文書更新・PR 説明のすべてを抱えた。** PR 時点で保持していた情報のうち、PR 説明を書くのに要ったものは一部である
- **実装エージェントを使わなかった**([#65](https://github.com/stama72/visionary/issues/65))。[02-task-spec](../process/02-task-spec.md) の先行指標(仕様の穴の数)が1回分採れず、1巡目の I-b-1(仕様が TDD01 §3.8 の訂正を許可しておらず、判定の基準表が偽のまま残った)は**仕様の穴**でありながらレビューまで持ち越された

**ADR-0004 論点1 の基準「そのコンテキストは捨てられるか」は、役割(設計 / 実装 / レビュー)には当てたが、1タスクの中の時間軸には当てていなかった。** 本 ADR はその基準を時間軸に当てる。

## 論点1: セッションをどの単位で捨てるか

### 検討した選択肢

1. **タスク単位**(現行)。1タスク = 1セッション。肥大したらコンパクションに任せる
2. **フェーズ単位**。設計 / 実装とレビュー / 文書更新と PR の3つに切り、境界で開発者が `/clear` する
3. コンパクション任せ。境界を決めず、ハーネスの自動圧縮だけに頼る

### 決定

**選択肢2。** 境界は次の3つとする。

| | フェーズ1 設計 | フェーズ2 実装とレビュー | フェーズ3 文書更新と PR |
| --- | --- | --- | --- |
| 成果物 | タスク仕様の凍結 | 緑のコードとコミット | PR と切り出した issue |
| 主 | 開発者 + 設計セッション | オーケストレータ(コードを読み書きしない) | — |

### 理由

- **ADR-0004 論点1 の基準をそのまま時間軸に当てた結果である。**「設計は途中経過が成果物であり、却下した案とその理由が次の判断の入力になる」は**設計フェーズの中では**真だが、**仕様が凍った時点で成果物は `docs/tasks/` に出ている**。同 ADR 論点2 が「タスク仕様はセッションを捨てて作り直すコストを下げる」と書いたのは、まさにこの器のことである
- 実装とレビューのコンテキストは捨てられる。最終物はコードとコミットであり、**指摘の内容と対応理由はコミット本文が既に持っている**(実例: [`3f2c0a7`](https://github.com/stama72/visionary/commit/3f2c0a7) は指摘・なぜ気付けないか・変異2件の結果・採った規則自身が残す穴まで持つ)
- 文書更新と PR は、diff と引き継ぎメモ(論点2)から組める
- **選択肢3は捨てるものを選べない。** 自動圧縮は新しい情報を残すため、**フェーズ1 の設計意図がフェーズ3 で最初に消える** — 最も要るものから消える順序になる
- 境界を3つにしたのは、境界ごとに引き継ぎメモを書くコストが載るためである。2つでは実装とレビューのコンテキストが文書更新まで残り、4つ以上では書く手間が節約を食う

## 論点2: フェーズ境界で消える情報をどう渡すか

W2-01 を実測し、フェーズをまたいで要る情報が今どこに残るかを棚卸しした。

| 情報 | 今どこに残るか | 判定 |
| --- | --- | --- |
| 型・シグネチャ・テスト表・編集してよい文書・スコープ外の判断 | タスク仕様 | 残る |
| **採った**設計の理由 | コードの doc コメント・TDD([`HouseholdState.cs:96`](../../src/Visionary.Sim/World/HouseholdState.cs) が実例) | 残る |
| **却下した**設計案と理由 | ADR に載る大きさのものだけ | **消える** |
| implementer の「止まった / 決めて報告した」件数 | なし | **消える** |
| 直したレビュー指摘 | コミット本文 | 残る |
| **直さないと決めた**指摘と理由 | なし(コミットが発生しない) | **消える** |
| **指摘0件の巡**・打ち切りの理由 | なし(同上) | **消える** |
| 変異と結果 | doc コメント・コミット | 残る(02-task-spec が規約化済み) |
| 検証コマンドの結果 | — | フェーズ3で再実行できる |

### 検討した選択肢

1. 渡さない。消えてよいものとして受け入れる
2. **ブランチ上の引き継ぎメモ**。`docs/tasks/W*-<スラッグ>.handoff.md` に各フェーズの末尾で追記し、フェーズ3で PR 説明へ転記して削除する
3. issue のコメントに追記する
4. フェーズ1末に draft PR を立て、その説明を各フェーズで育てる

### 決定

**選択肢2。** 上表で「消える」と判定した4件**だけ**を書く。既にどこかに残るものは書かない。

### 理由

- **欠落は非対称である。「直した指摘」はコミットになるので残るが、「直さないと決めた指摘」はコミットが発生しないので消える。** 消えるのは悪い側である — [01-review](../process/01-review.md) は指摘への対応を「直す / **直さないと決めて理由を残す** / issue へ落とす」の3択と定めており、2つ目の記録先が構造的に無い
- **却下案の消失は二次被害を持つ。** レビュアー憲章 §4 の I-b-4「却下理由の空洞化」は、**却下理由が書かれていて初めて検査できる**。設計セッションの文脈にしか無いなら、この観点は最初から空振りする。フェーズ分割はこの既存の穴を顕在化させるだけで、作り出すわけではない
- 選択肢1を**部分的に採った**。上表で「残る」と判定した5件は書かない。器を作ると全部書きたくなるため、**書かないものを先に決めてある**
- 選択肢3・4 は `gh` 経由で読み書きが重い。4 は実装前に空コミットで PR を立てる必要がある。選択肢2 は `cat` 一発で読め、PR の差分でレビューでき、**文書の四層の「使い捨て」層にそのまま収まる**
- 削除するのは、PR 説明が正になったあと master に複製を残さないためである(add → delete なので PR の差分には現れない)

## 論点3: 実装をメインセッションが書くことを許すか

### 検討した選択肢

1. **規模で使い分ける**(現行の実態)。小さければメインが書く
2. **実装タスクは必ず implementer に渡す**
3. 実装は implementer、レビュー指摘の修正だけメインに許す

### 決定

**選択肢2。** ただし象限I-b(仕様そのものの欠陥)への対応は、**メインが仕様を直してから** implementer に渡す。仕様の訂正は設計判断だからである。

### 理由

- **書いた本人が実装すると、仕様に穴があっても自分の頭から埋めてしまい表面化しない**([ADR-0005](0005-reviewer-scope-includes-spec-defects.md) が認めた経路)。W2-01 の I-b-1 がその実例である
- **先行指標が採れない。** 02-task-spec の「仕様の穴の数」は implementer が止まった件数で定義されており、止まる主体が居なければ発生しない
- implementer は Sonnet なので、実装の読み書きがメインのコンテキストから外れる
- **選択肢1 は境界の判定自体が節約を食う。** 「小さいか」を判断するにはメインがコードを読む必要があり、読んだ時点で節約は消えている。加えて「小さいから今回は」は後付けできるため、原則が形骸化する
- **選択肢3 を採らないのは、指摘の修正こそ実装だからである。** 実際 W2-01 でレビュー由来の変更は 1,625 行の追加のうち小さくない部分を占めた。ここをメインに許すと、フェーズ2 のメインがコードを読む経路が常設される

## 決定(まとめ)

- タスクを**3フェーズ**に切り、境界で開発者が `/clear` する(論点1)
- 境界で消える**4件だけ**を `docs/tasks/W*-<スラッグ>.handoff.md` に残し、フェーズ3で PR 説明へ転記して削除する(論点2)
- **実装タスクの実装は必ず implementer が書く。** レビュー指摘の修正も含む(論点3)

運用の正は [docs/process/05-phase-sessions.md](../process/05-phase-sessions.md)、フェーズ2・3 の枠づけは [`.claude/commands/impl.md`](../../.claude/commands/impl.md) と [`.claude/commands/wrap.md`](../../.claude/commands/wrap.md) が持つ。

## 帰結(受け入れるトレードオフ)

- **フェーズ境界ごとに、次のフェーズがタスク仕様を読み直す往復が載る。** 差し引きで減るというのは**予測であって決定ではない**
- **これは仮説であり、「W2 の残りタスクで、引き継ぎメモの書き漏れにより後のフェーズが判断をやり直した回数が0か」で検証する。** 1回でも起きたら、メモの項目が足りないか境界の位置が悪い。0 のまま W2 を終えたら決定として固定する
- **フェーズ2 のメインは自分でコードを読まないので、implementer の報告が唯一の窓になる。** 報告が薄いと、レビュアーに渡る前に気付く機会が無い。憲章の報告項目を強くすることで補うが、完全には補えない
- **`/clear` は機械で守れない。** 忘れても何も壊れないが、節約も起きない。守られたかどうかを後から確かめる手段も無い
- **フェーズ3 を Sonnet で回せるのは、実態合わせと転記に限る。** 文書側に新しい判断が要ると分かったら、それはフェーズ1 に戻すべき仕事である
