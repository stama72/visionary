# ADR-0006: issue駆動のタスク管理と、スコープ・優先順位の器

- 日付: 2026-09-14
- ステータス: 承認
- 決定者: stama

## 背景

W2(仮経済 + Trade)の設計工程が期限を超過し、スコープが M2 相当まで膨張した。症状ではなく測定できる形で書く。

- **M0 が M1 より大きくなった。** [企画書 §6](../02-project-proposal.md) の M1 垂直スライスは「1地区・品目5種・NPC20体」である。[TDD01 §3.6](../04-tdd/01-sim-core-and-m0.md) はもともと「品目5種・職業3類型」を持っており、**M0 ≤ M1 という関係が成立していた**。現在の M0 は 9区画・11品目・20世帯・NPC 80体に加えて財政・貿易商・破産・機会費用を含む。区画9倍・品目2.2倍・NPC 4倍であり、**マイルストーンの順序が反転している**
- **レビューが自分の修正で次のレビューを生んでいた。** [GDD02](../03-gdd/02-economy.md) のレビュー5〜8巡目のブロッカーは 9 → 7 → 3 → 4 件。このうち**6巡目の7件と7巡目の3件は、前巡の修正が新たに作った、または不十分だったもの**である(GDD02 §14 の見出し自身がそう書いている)。停止則が「ブロッカー件数の減衰」という**品質の基準**だったため、自己触媒的なループに効かなかった。最終的に v0.15 は「ここで打ち切り、凍結する」と**宣言で**止めている
- **未決事項が115件、時間軸も優先順位も持たずに分散している。** 数え方は「`docs/` 配下の `.md` で行頭が `- [ ]` のもの」、測った時点は `docs/gdd02-draft` ブランチ(GDD02・GDD06・GDD08 を含む唯一の状態)である。内訳は GDD02 が41件(本文1,234行)、GDD08 10件、GDD01 7件、GDD06 6件、TDD01 6件、ほか
- **マイルストーン計画([docs/README.md](../README.md) の 05)とリスク管理表(同 06)は未着手のまま**であり、スコープを管理する器が存在しない

**原因は WIP ではない。** W2 は [ADR-0004](0004-ai-driven-development-workflow.md) 論点3 の WIP = 1 の規律下で、単一タスク・単一セッションのまま膨張した。WIP は「同時に何個か」を縛る装置であって、「**1個がどこまで膨らむか**」を縛らない。

ADR-0004 は方針を「速さより質」に置いたうえで、前提としてこう書いていた:

> その時決めるべきことを高い質で決め、決めなくてよいことは未決定事項として切り出す

**前半は機能した。後半を実行する器を与えなかった。** 切り出した未決事項の行き先は同じ文書の末尾しかなく、そこには優先順位も期日も持てない。115件という数はその帰結である。

## 論点1: スコープと優先順位をどの器が持つか

### 検討した選択肢

1. **GitHub の issue / milestone が持つ。文書は定義だけを持つ**
2. `docs/05-milestones.md` と `docs/06-risks.md` を書く(docs/README.md の当初計画)
3. 両方持つ(文書に一覧、GitHub に実体)

### 決定

**選択肢1**。

### 理由

- 進捗・優先順位・依存関係は**状態**であり、「今どうなっているか」を答える責務を負う。[docs/adr/README.md](README.md) の切り分けの3つ目の問い(読者は「なぜ」を知りたいのか、「今どうなっているか」を知りたいのか)に照らせば、これは凍る文書の仕事ではない。加えて**最も頻繁に変わるものを、最も更新コストの高い場所に置く**ことになる — ADR-0004 論点2 が「TDD の分冊として詳細設計を常設する」を却下したのと同型の理由である
- **マイルストーンの定義と Exit Criteria は [企画書 §6](../02-project-proposal.md) が既に持っている。** 05 を書くとその複製になり、2つの表が食い違う日が来る。定義は企画書、期日と進捗は GitHub Milestone に分ける
- **リスクは閉じる条件を持つ。** 「売り手2世帯間の相互参照が発散しうる」は W2 の [GDD02 §12-1](../03-gdd/02-economy.md) で観測して閉じる。閉じる条件と担当の実験を持つものは、表の行ではなく issue である
- 選択肢3は二重管理になる。W1 で `docs/tasks/README.md` の状態一覧を **master へ直接コミットする**という迂回が必要になったのは、ブランチをまたいで状態を共有する手段が無かったからである(ADR-0004 論点3)。**issue はブランチ非依存なので、この迂回そのものが要らなくなる**

## 論点2: 既存の未決事項115件をすべて issue に移すか

### 検討した選択肢

1. **4種に仕分け、issue になるのは2種だけにする**
2. 全件 issue 化する(「未決事項を持つのは issue のみ」を純粋に守る)
3. M0 に関わるものだけ先に issue 化し、残りは後回しにする

### 決定

**選択肢1**。仕分けは次の表による。

| 種別 | 例 | 行き先 |
| ---- | -- | ------ |
| **値・閾値の初期値** | 許容乖離‰、季節市の開催日数3日、視界半径 R | **文書に残す。`- [ ]` をやめ、「調整軸」の表に書き換える** |
| **他分冊へのルーティング** | 「妥結価格 → 分冊06」「ギルド → 分冊07」 | **文書に残す。所在を述べるリンク1文にする** |
| **疑い(実データ待ちの予測)** | 「相互参照が発散しうる」「貿易商が資金枯渇しうる」 | **それを観測する実験 issue の受入条件**に畳み込む |
| **決定待ち・拡張案** | 腐敗、複数都市、耐久財の拡大、ADR テンプレートの標準化 | **issue** |

### 理由

- 全件 issue 化(選択肢2)は、**単独では閉じられない issue を大量に残す**。係数の初期値だけで約20件あり、これらは W2 の実データが出るまで1件も閉じられず、しかも実質的に同時に閉じる。**優先順位の信号はノイズの量で薄まる** — 文書の官僚主義を issue に引っ越させるだけになる
- **「値だけが残っている」ものは、そもそも未決事項ではない。** CLAUDE.md は既に「数値(閾値・係数)は初期値であり調整対象。固定すべきは構造と依存関係」と決めている。これは**仕様が調整軸として書かれている状態**であって、`- [ ]` というチェックボックスの文法が誤っているだけである。同様に「→ 分冊06」は所在の宣言であって決定待ちではない
- 仕分けを済ませると、**育てる文書から「未決定事項」節を全廃できる**。そこで初めて「docs に未決事項を置かない」が `grep` で機械的に守れる規約になる(CLAUDE.md「これは機械で守れるか」)。選択肢2でも同じ規約は作れるが、issue 側の信号を犠牲にして買うことになる。**凍る文書(ADR)の未決事項節は対象外とする** — 中身は issue へ移すが、節は起案時点の記録として残る。ADR は凍るので溜まらず、規約が守りたい対象ではない
- 選択肢3は着手が速いが、`- [ ]` を全廃できないため機械的な規約が作れない。**規約が無ければ半年後に同じ状態へ戻る**

## 論点3: issue の粒度と階層

### 検討した選択肢

1. **Milestone = 週 / 親 issue = 関心事 / sub-issue = 1タスク = 1 PR(3層)**
2. Milestone = M0〜M4、週はラベル
3. 階層を作らず、全てフラットな issue に milestone とラベルだけ付ける

### 決定

**選択肢1**。粒度は **1 issue = 1機能 = 1タスク仕様書 = 1 PR**。実装タスクは、タスク仕様書の作成からレビュー完了までを1 issue に含める。

### 理由

- **GitHub Milestone は期日を持てる唯一の器である。** 今回の失敗は「週の期限超過」なので、期日を週に付けなければ同じ失敗を二度目も検出できない。選択肢2では週次の締切が GitHub 上に存在しなくなる
- M0〜M4 の定義と Exit Criteria は企画書 §6 が持つので、**Milestone を週に使ってもマイルストーンの定義は失われない**
- 当初案の4層(M / W / 機能 / 未決事項)は GitHub が素で持てず、手で同期することになる。3層に落とし、最下層は sub-issue かタスク本文のチェック項目として吸収する
- 選択肢3は最も軽いが、「W2 の全体設計」のような**束ねる単位**を持てず、関心事ごとの進捗が見えない
- **タスク仕様書の寿命は PR とともに終わる**(ADR-0004 論点2)まま変えない。issue はその外側の器であり、仕様書より長く生き、コードより短く死ぬ

## 論点4: WIP の上限

### 検討した選択肢

1. **「開発者の判断を要するタスクの WIP = 1」に読み替える**
2. WIP = 1 を維持する
3. 上限を撤廃し、Projects の優先順位だけで管理する

### 決定

**選択肢1**。判断を全工程で要するタスク(設計・ADR・ゲームデザイン)は WIP = 1。**仕様が凍結済みの実装タスクに限り2本まで**許す。

### 理由

- **ADR-0004 論点3 の決定は覆さない。** ボトルネックが開発者のレビュー帯域であるという認識は正しく、今回の遅延も WIP が原因ではなかった(背景を参照)
- ただし ADR-0004 は「レビュー帯域」を**一枚岩として**扱った。実際には二種類ある — 開発者の判断を**全工程で**食うタスク(設計は途中経過が成果物であり、却下した案が次の入力になる)と、**末尾でだけ**食うタスク(仕様が凍結済みの実装は、前段をレビュアーエージェントが吸う)である。後者を1本に縛る根拠は ADR-0004 の理由付けの中に無い
- 上限を2に留めるのは、3本以上にすると「同時に文脈を保持すべき設計の数」が増える側へ戻るためである。ADR-0004 論点3 が挙げた却下理由はその範囲でまだ有効である
- **これは決定ではなく予測を含む**([docs/adr/README.md](README.md) の2つ目の問い)。**仮説は「実装タスクの並行は開発者の判断を増やさない」であり、検証は「2本目が『レビュー中』のまま1週間を超えるか」で行う。** 超えたら選択肢2へ戻す
- 選択肢3は、ADR-0004 論点3 が挙げた却下理由(上限を緩めても止まったタスクが増えるだけ)をまだ反証していない。反証なしに撤廃はしない

## 論点5: 膨張を止める停止則をどこに置くか

### 検討した選択肢

1. **レビュアーの指摘にスコープの分類を義務づけ、レビューの巡に出自ベースの停止則を置く**
2. スコープの判断は開発者のレビューが担う
3. マイルストーンの Exit Criteria を厳密化して防ぐ

### 決定

**選択肢1**。2点をセットで入れる。

- **分類の義務**: レビュアーは指摘ごとに「**今のマイルストーンの Exit Criteria を脅かすか**」を分類する。脅かさないものは「直す」ではなく「**issue へ落とす**」を既定の処置とする
- **出自ベースの停止則**: **前巡の修正が原因のブロッカーが2巡続いたら、その文書のレビューを打ち切り、実装へ渡す**

### 理由

- [`.claude/agents/reviewer.md`](../../.claude/agents/reviewer.md) の観点は**すべて「正しいか」**であり、「今のマイルストーンに要るか」を問う観点が1つも無い。したがって正しい指摘はすべて「直す」対象になる。**正しい指摘を無限に出せる文書では、この憲章は原理的に収束しない**。GDD02 の6〜8巡目がその実例である
- **停止則は件数ではなく出自で置く。** 「ブロッカーが減れば収束」は自家生成ループに効かない(9 → 7 → 3 → 4 は減衰しているのに止まらなかった)。出自で置けば、GDD02 は**7巡目で止まっていた**
- 選択肢2は、ADR-0004 論点4 が消そうとしたボトルネックに仕事を戻す。「これは M0 に要るか」は参照点さえあれば**分類であって判断ではない**ので、エージェントが担える。判断が要るのは分類が割れたときだけである
- **ただし M0 の Exit Criteria は定性的である。** 「GO判断3項目に答えが出ている」(企画書 §6)は、[01-review.md](../process/01-review.md) が「開発者にしか判定できない」と明記したゲームデザインの妥当性そのものであり、参照点としては弱い。**したがって分類軸を2本にする** — (a) Exit Criteria を脅かすか、(b) この変更自体が誤った記述を凍らせるか。**(b) は文書間の照合で判定できるので、定性的な (a) に依存しない。** M1 以降は Exit Criteria が定量化される(「第三者が15分遊んで『もっと遊びたい』と言う」「通しプレイ10時間」)ため、(a) 単独でも機能するようになる
- 選択肢3は必要だが十分ではない。Exit Criteria を厳密にしても、**指摘を落とす先が無ければ「直さない」を心理的に選べない**。[01-review.md](../process/01-review.md) は既に3択(直す / 直さないと決めて理由を残す / 別タスクとして切り出す)を持っていたが、切り出し先が「別タスク」としか書かれておらず、実体が無かった。**選択肢1は選択肢3の不足を埋める形で働く**

## 決定(まとめ)

**3つの駆動を役割で分ける。**

| 駆動 | 器 | 持つもの |
| ---- | -- | -------- |
| **issue 駆動** | GitHub issue / milestone | 進行・スコープ・優先順位・依存関係・未決事項・更新履歴 |
| **ドキュメント駆動** | ADR / GDD / TDD / process | 設計と意思決定。「なぜ」と「今の仕様」 |
| **仕様駆動** | `docs/tasks/` のタスク仕様書 | 実装の要件。「どう作るか」 |

**切り分けルール**(境界で迷ったときの正):

- **未決事項と更新履歴を持つのは issue だけ。**
- **設計と意思決定を持つのはドキュメントだけ。**
- **実装の要件を持つのはタスク仕様書だけ。**
- **議論の過程は「そのコンテキストは捨てられるか」で割る**(ADR-0004 論点1 の基準を再利用する)。**却下した案とその理由が次の判断の入力になるならドキュメント。ならないなら issue / PR のコメント**

運用の現行仕様は [docs/process/04-issue-driven.md](../process/04-issue-driven.md) が持つ。本 ADR は理由だけを持ち、ラベル体系・テンプレート・粒度の具体は持たない。

## 帰結(引き受けるトレードオフ)

- **GitHub への依存が増える。** 進捗をオフラインで読めなくなり、リポジトリのホスティングを移すと履歴の移送が要る(`gh issue list --json` で機械的に取り出せる範囲に限る)。**設計と意思決定は文書側に残る**ので、失われても再構築可能なのは進行管理だけである、という線引きが依存の上限になっている
- **issue が新しい官僚主義になりうる。** 文書で起きたことは issue でも起きる。抑止は3つ — **本文は箇条書き15行以内、閉じる条件を1行で書けないものは issue にしない、テンプレートは2種に限る**。これらは [04-issue-driven.md](../process/04-issue-driven.md) が持つ
- **文書の寿命が四層になる。** ADR(永続)/ GDD・TDD・process(育てる)/ **issue(閉じるまで)** / タスク仕様(PR とともに終わる)。issue は「育てる」と「使い捨て」の中間にあり、ADR-0004 論点2 の三層表に1行増える
- **「判断を要するタスクの WIP = 1」は自己申告に依存する。** 「これは判断を要さない」と誤って分類すれば、設計が2本走る。**機械では守れない規約であり、ADR-0004 の帰結(機械で守れない規約を増やすほど委ねられる範囲が狭まる)を1つ引き受けている**
- **停止則は品質を犠牲にする方向にも働く。** 打ち切られた文書は不完全なまま実装へ渡る。これを受け入れられるのは、**落とした指摘が消えるのではなく issue として残る**からである。issue に落とさずに打ち切れば、この帰結は受け入れられない
- **レビュアーがスコープを分類するには、今のマイルストーンの Exit Criteria を知る必要がある。** 憲章に参照先を書くぶん、レビュアーの前提知識が増える
- **状態一覧を master へ直接コミットする運用が消える。** ADR-0004 の帰結を1つ解消する
