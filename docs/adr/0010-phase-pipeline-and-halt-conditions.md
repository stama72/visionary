# ADR-0010: フェーズ境界を機械が握り、停止則に当たったときだけ開発者を呼ぶ

- 日付: 2026-09-16
- ステータス: 承認
- 決定者: stama

## 背景

[ADR-0009](0009-phase-scoped-sessions.md) の3フェーズは、W2-02([#33](https://github.com/stama72/visionary/issues/33))・W2-03([#34](https://github.com/stama72/visionary/issues/34))で実測した。**同 ADR の帰結節が「差し引きで減るというのは予測であって決定ではない」と保留した点は、減る側で確定した。**

3タスクは差分規模がほぼ同一(+1625 / +1784 / +1826 行、18 / 18 / 19 ファイル)で、比較に耐える。

| タスク | 形 | API 等価コスト | 実時間 |
| --- | --- | ---: | --- |
| W2-01([#32](https://github.com/stama72/visionary/issues/32)) | 1セッション通し・implementer なし | $89.21 | 2時間52分 |
| W2-02([#33](https://github.com/stama72/visionary/issues/33)) | 3フェーズ | $47.39 | 53分 |
| W2-03([#34](https://github.com/stama72/visionary/issues/34)) | 3フェーズ | $62.43 | 83分 |

**減った理由はターン数ではなく、1ターンあたりの単価である。** メインのターン数は 156 → 104 / 118 とほぼ変わらない。変わったのはコンテキストの深さで、1本通しは終盤 353k トークンを毎ターン読み直していた(1ターン $0.50)のに対し、フェーズを切ると各セッションが 120〜220k で終わる(1ターン $0.29〜$0.33)。フェーズ境界の読み直しコストは実測で各フェーズの最初の5ターン $1.1〜$1.7、追加2フェーズで**タスクの約5%**であり、節約 $27〜$42 を食わない。

**残った問題は、節約ではなく待ち時間である。** 境界は開発者が `/clear` して次を開く形なので、**開発者が画面を見ていない間は進まない。** 1タスクの実時間1時間のうち、実際に開発者の判断が要ったのは2〜3回だった。残りは「終わったので次を開く」だけの待ちである。

## 論点1: フェーズをどう繋ぐか

### 検討した選択肢

1. **現行。** 開発者が `/clear` し、`/impl` `/wrap` を手で開く
2. **`claude -p` のプロセス連鎖。** フェーズ1 のセッション(または素のシェル)がスクリプトを起動し、`claude -p "/impl 35"` → `claude -p "/wrap 35"` を順に回す
3. **サブエージェント連鎖。** フェーズ1 がフェーズ2 を subagent として起動する
4. **1セッションに戻し、停止点だけ減らす**

### 決定

**選択肢2。**

### 理由

- **別プロセスは別コンテキスト窓であり、ADR-0009 が `/clear` に負わせていた隔離と意味論が完全に一致する。** 隔離が「運用の約束」から「プロセス境界」に変わるだけで、決定の中身は動かない
- **選択肢3 は隔離が半分になる。** 親は子の最終報告を読むので親のコンテキストが育つ。加えて implementer / reviewer を孫として立てる必要があり、深さ2の可否が未検証である
- **選択肢4 はターン単価 $0.29〜$0.33 を $0.50 に戻す。** 停止点は減るが、ADR-0009 が取った −38% を捨てる
- 選択肢1 を残さないのは、**待ちがトークンでは買えないためである。** Max プランへ移っても、開発者が画面を見ていない時間は縮まない

### 実測で確かめた前提(この決定はこれに依存する)

| 事実 | 確かめ方 |
| --- | --- |
| `claude -p "/impl 35"` はスラッシュコマンドとして解決される | 使い捨てコマンドを置いて `PROBE_OK` を返させた |
| **プロンプトは可変長フラグ(`--allowedTools`)より前に置く。** 後ろだと引数として吸われ、`Input must be provided` で落ちる | 前後を入れ替えて再現 |
| **Git Bash からは呼べない。** MSYS が先頭の `/` を `C:/Program Files/Git/...` へ変換し、コマンドとして解決されない | 同じプロンプトが PowerShell では通り Git Bash では化けた |
| コマンドの `model:` frontmatter はモデルを切り替える。ただし CLI の `--model` が勝つ | 走ったセッションの記録上のモデル名を照合(frontmatter だけなら haiku、`--model opus` 併用なら opus) |
| `--allowedTools "Bash(git status:*)"` は無人でも効く | 許可した1コマンドだけを実行させた |

## 論点2: 何を停止条件にするか

**既定が反転する。** いまは「止まる」が既定で、開発者が見ていなければ止まる。パイプラインでは「進む」が既定になるので、**必ず止まる条件を明示しないと、[ADR-0004](0004-ai-driven-development-workflow.md) 論点1 が防いでいた失敗(仕様に穴があっても自分の頭から埋めて表面化しない)が、フェーズ境界で再発する。**

### 決定

**次の4つで止まり、デスクトップ通知を出す。**

| コード | 条件 | 誰が判定するか |
| --- | --- | --- |
| `SPEC-OUTSIDE` | 象限I-b の訂正が**タスク仕様の外**(GDD / TDD / ADR)に及ぶ | **機械**(フェーズ2 の後の差分検査)+ 自己申告 |
| `IMPL-BLOCKED` | implementer が「止まって報告」した | 自己申告 |
| `REVIEW-EXHAUSTED` | レビュー4巡目到達 / implementer が2回試して緑にならない | 自己申告 |
| `RED` | build / test / format が赤のまま先へ進みそう | 自己申告 |

**逆に、次では止まらない。**

| 止まらないもの | W2-02 / W2-03 の実測 |
| --- | --- |
| implementer の「決めて報告」 | 4件 / 0件。**すべて後から追認できた** |
| レビュー1〜3巡の指摘と修正 | I-a 3件・I-b 4件。**すべて実装の内側で閉じた** |
| 気付いたことの issue 化 | PR 時にまとめる |

### 理由

- **`SPEC-OUTSIDE` が4つの中心である。** W2-03 は GDD02 §5.2 の「所要労働」の定義そのものを訂正した。これは仕様の誤りではなく**ゲームデザインの訂正**であり、止めないパイプラインは **GDD をエージェントが黙って書き換えるパイプライン**になる。[ADR-0009](0009-phase-scoped-sessions.md) 論点3 が仕様の訂正をメインに残した理由を、そのまま境界へ延長したものである
- **`IMPL-BLOCKED` は件数が0のまま止めどころとして置く。** [02-task-spec](../process/02-task-spec.md) の先行指標そのもので、**発生したときにこそ開発者が見るべき**種類の情報である
- 止まらない側を実測から選べたのは、W2-02・W2-03 の PR 説明が件数と対応を残していたからである。**[ADR-0009](0009-phase-scoped-sessions.md) 論点2 の引き継ぎメモが無ければ、この論点は勘で決めるしかなかった**

### `SPEC-OUTSIDE` だけ機械で判定する

**4つのうち `SPEC-OUTSIDE` だけは差分に現れるので、自己申告に委ねない。** CLAUDE.md の「新しい規約を作るときは『これは機械で守れるか』を必ず問う」に照らして、守れるものを守らせる。

フェーズ2 が `PIPELINE: DONE` を出しても、**`docs/03-gdd/` / `docs/04-tdd/` / `docs/adr/` に差分があれば `SPEC-OUTSIDE` として止める。** [`impl.md`](../../.claude/commands/impl.md) は以前から「ADR / GDD / TDD を触らない」と書いていたが、パイプラインの `--allowedTools` は `Edit` / `Write` を無条件で渡すので、**GDD を書き換えたうえで `DONE` を出すセッションが素通りできた。**

**基準は `master` ではなく、フェーズ2 起動直前の `HEAD` である。** フェーズ1 が仕様を凍らせるときに GDD を直すのは正当な仕事で、その変更は既にブランチ上にある(W2-03 の GDD02 §5.2・GDD03 §2.1 が実例)。`master` 起点にすると、それを毎回 `SPEC-OUTSIDE` として誤検出する。

事後検出だが、**`git push` はフェーズ3 の仕事なので、開発者が見る前に外へ出ることはない。**

残る3つが自己申告に留まるのは、いずれも**差分に現れない事象**だからである。implementer が止まったこと、レビューが何巡目か、テストが赤だったことは、コミットの形を取らない。

### 合図は機械が読める1行にする

各フェーズは最後に `PIPELINE: DONE` か `PIPELINE: HALT <コード> <理由>` を出す。**どちらも出さずに終わったら停止扱いにする(`NO-SENTINEL`)。**

fail-closed にするのは、**踏んだか判らないまま次のフェーズへ渡すほうが高いため**である。止めすぎの代償は通知1回で済む。

## 論点3: 無人実行の権限をどこに置くか

無人の `claude -p` は、`dotnet` / `git` / `gh` を回し、ファイルを書き、サブエージェントを立てる。許可が無ければプロンプトが出て、**答える主体がいないので黙って落ちる。**

### 検討した選択肢

1. `.claude/settings.json` に許可を書く
2. **パイプラインのスクリプトの `--allowedTools` に書く**
3. `--dangerously-skip-permissions`

### 決定

**選択肢2。**

### 理由

- **選択肢1 は開発者自身の対話セッションまで緩める。** 無人実行のために取ったリスクが、無人でない場面にも常設される
- **選択肢2 は緩む範囲がパイプライン経由の実行だけに閉じ、しかも `scripts/pipeline.ps1` の差分としてレビューできる。** 権限の変更が git に残る
- 選択肢3 は無人のシェルに無制限を与える。`git push` と `gh pr create` を無人で通す以上、**それ以外は絞れるだけ絞る**

## 決定(まとめ)

- フェーズ2 → フェーズ3 を `claude -p` の別プロセスで連鎖させる(論点1)。運用の正は [05-phase-sessions](../process/05-phase-sessions.md)、実装は [`scripts/pipeline.ps1`](../../scripts/pipeline.ps1)
- **停止則は4つ**(論点2)。合図は `PIPELINE: DONE` / `PIPELINE: HALT <コード>`、合図が無ければ停止扱い
- 無人実行の許可はスクリプトの `--allowedTools` に置き、`settings.json` には置かない(論点3)

## 帰結(受け入れるトレードオフ)

- **`git push` と `gh pr create` が無人で走る。** 「そのまま PR まで行く」を選んだ時点の帰結である。ブランチは常に `feat/<issue>-<スラッグ>` で master ではないこと、PR はマージされないことが歯止めになる
- **フェーズ1 は自動化しない。** 設計は開発者の判断そのもので、仕様の凍結が境界である。**パイプラインは凍った仕様を入力として受け取る**
- **開発者がレビュー指摘を読む機会が、PR まで無くなる。** いまは巡ごとに目に入っていた。代償として、**見落としたものは PR レビューで拾うことになる**。W2-02・W2-03 のレビュー指摘が実装の内側で閉じていたことを根拠に受け入れる
- **`.pipeline/` にフェーズごとの生ログが残る。** git 管理しない。停止したとき、開発者が最初に読むのはここである
- **[ADR-0009](0009-phase-scoped-sessions.md) の検証条件は汚染されない。** 「引き継ぎメモの不足で後のフェーズが判断をやり直した回数」はフェーズ3 が PR 説明に書く形のままで、むしろ `.pipeline/` のログが裏取りの材料を増やす
- **これは仮説であり、W2-04([#35](https://github.com/stama72/visionary/issues/35))の1本で検証する。** 検証項目は3つ — (a) 無人の許可範囲が足りたか、(b) 停止則が「止まるべきでないところ」で止まらなかったか、(c) 止まったとき通知が届いたか。**1本目は開発者が画面を見たまま回す。** 無人で回してよいと決めるのは、この3つが確かめられてからである
- **デスクトップ通知は Windows のフォーカスアシストに抑制されうる。** 通知はあくまで補助で、届かなくても停止の判定は変わらない(スクリプトは終了コード 2 を返す)
