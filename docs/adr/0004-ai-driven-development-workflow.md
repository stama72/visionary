# ADR-0004: AI駆動開発におけるエージェントの役割分担と作業単位

- 日付: 2026-08-27
- ステータス: 承認
- 決定者: stama

## 背景

[ADR-0001](0001-engine-and-simulation-architecture.md) は AI コーディングエージェントの活用を前提としてエンジンを選定したが、**どう使うか**は決めていない。M0 の進行に伴って次の5点が表面化した。

- **並行作業の事故**。複数セッションが1つのワーキングツリーを共有しており、未コミットの暦の作業を別セッションが消しかける寸前まで進んだ。[ADR-0003](0003-calendar-structure.md) の番号が既に取られていることも、コード中のコメントを読むまで分からなかった。未コミット作業の消失は Git の履歴に残らないため、マージ競合より危険である
- **開発者のレビューがボトルネックになっている**。全体を読み込んでから整理された2000〜3000字の指示を書いており、1往復に数時間かかる。開発全体の速度がこの工程で決まっている
- **レビュー相手が居ない**。個人開発のため第三者レビューがない。AI をレビュアーに使えるが、実装と同じコンテキストで見せてもレビューにならない
- **TDD の粒度では実装を切り出せない**。TDD01 §3.3 は「Trade は相手選好→約定→記帳」までしか書いておらず、そのまま実装エージェントに渡せる形ではない
- **学習と設計の混線**。開発者は Java の経験はあるが C#/.NET/Godot は未経験であり、初歩的な質問が設計の対話に混ざるとコンテキストが汚れる

開発方針は**速さより質**とする。設計とドキュメントの質が AI 駆動開発の成否を分け、開発者自身が理解していない設計は判断もできない(理解負債)。

ただしこの方針は、**すべての判断に等しく時間をかけることを意味しない**。開発者は深い思考に適性がある反面、横道で悩んで時間を失う、あるいは全体像を見失って頓挫するリスクを持つ。したがって「その時決めるべきことを高い質で決め、決めなくてよいことは未決定事項として切り出す」ことを、速さと質を両立させる手段として本 ADR の前提に置く。

## 論点1: どの作業をエージェントに切り出すか

### 検討した選択肢

1. **設計はメインセッション。実装とコードレビューのみサブエージェント**
2. メインを PM 役とし、設計もサブエージェントに切り出す
3. すべてメインで行う(サブエージェントを使わない)

### 決定

**選択肢1**。

### 理由

- 切り出しの可否は「**そのコンテキストは捨てられるか**」で決まる。設計は途中経過が成果物であり、却下した案とその理由が次の判断の入力になる。実装は最終物がコードなので、途中の試行錯誤を捨ててよい。この基準は将来エージェントを追加すべきかを判断するときにも使う
- 選択肢2は伝言ゲームが挟まるうえ、開発者が設計役と直に対話できなくなる。判断の質は開発者の理解を超えられないため、理解負債を溜める方向に働く
- 選択肢3ではレビューが成立しない。実装したエージェントは自分の意図を知っているため、**コードがその意図を表現できていなくても読めてしまう**。独立したコンテキストのレビュアーは docs とタスク仕様しか持たないので、「ドキュメントから読み取れない実装」が自然に浮かぶ。レビューはドキュメント品質の検査を兼ねる
- サブエージェントは「大量に読んで少量返す」仕事に向く。実装・レビュー・探索がこれにあたる。少量読んで少量返す仕事では起動コストのほうが高くつく

## 論点2: 実装エージェントに渡す仕様と、その文書の寿命

### 検討した選択肢

1. **タスク単位の使い捨て仕様を `docs/tasks/` に置く**
2. TDD の分冊として詳細設計を常設する
3. TDD をそのまま渡す

### 決定

**選択肢1**。`docs/tasks/` に置き、**実装完了時点で凍結する**。以後の正はコードと TDD であり、実態合わせ改訂(TDD01 §5.4 W6)の対象外とする。

### 理由

- 選択肢3は粒度が足りない。TDD は「何を作るか」であって「どう作るか」ではない
- 選択肢2は**最も腐りやすい文書を最も維持コストの高い場所に置く**ことになる。GDD/TDD が「育てる文書」たりうるのは、そこに決定があるからである。メソッドのシグネチャに決定はなく、コードが正になる。常設すれば実態合わせの対象が3層に増える
- したがって文書を**寿命で三層に分ける**:

  | 層 | 例 | 寿命 | 実装と食い違ったら |
  | ---- | ---- | ---- | ---- |
  | 決定 | ADR | 覆るまで永続 | ADRを改訂、または新ADRで置き換え |
  | 仕様 | GDD / TDD | 育てる | 両方直す |
  | 作業指示 | タスク仕様 | PRとともに終わる | 直さない(コードが正) |

- タスク仕様には**緑にすべきテストの一覧**を書く。TDD01 §5.3 の7プロパティ表がその形である。仕様をテストのリストとして書くと、実装が仕様から逸れにくく、レビュアーが仕様↔テストの対応を機械的に確認でき、完了条件が曖昧にならない
- 副次的な効果として、タスク仕様は**セッションを捨てて作り直すコストを下げる**。コンテキスト肥大化への対処としてセッションをタスク単位で切る運用は、これがあって初めて成立する

## 論点3: 作業単位とセッションの遷移

### 検討した選択肢

1. **WIP = 1(シングルスレッド)。メインセッション + 一時的なサブセッション。タスクは worktree に切り出す**
2. worktree でタスクごとにツリーを分け、設計セッションを複数並行させる(WIP 上限 2)
3. 単一のワーキングツリーを複数セッションで共有する(現状)

### 決定

**選択肢1**。以下を規律とする。

**タスクの規律**

- **同時に取り組むタスクは1つ**。既存タスクのレビューを放置して次に移らない
- **レビューを終えて初めて、次に取り組むタスクを自由に選べる**
- レビューが難航した場合、または前提として別タスクの実行が必要だと判明した場合は、**承認せずに凍結してよい**。これがないとデッドロックする

**セッションの規律**

- 新しいタスクで**勝手にセッションを開かない**。まずメインセッションに相談する
- コンテキストや専門性(技術・ゲームデザイン・マーケティングなど)の違いからセッションを分けるべきと判断されたときだけ、サブセッションを開いて一時的に移る。**その間メインセッションは凍結**する
- **メインセッションに戻るときは、サブセッションのタスクを完了か凍結して閉じる**

**作業ツリーの規律**

- 1 worktree = 1 ブランチ = 1 タスク = 1 PR
- タスクの状態(進行中 / レビュー中 / 凍結 / 完了)を `docs/tasks/README.md` の一覧で明示する

### 理由

- 選択肢2・3は並行度を上げるが、**ボトルネックは並行度ではなく開発者のレビュー帯域**である。上限を2に緩めても、止まったタスクが増えるだけで開発速度は上がらない
- 開発者はマルチタスクに適性がなく、集中が切れると効率が落ちる。並行タスクは同時に文脈を保持すべき設計の数を増やし、理解負債を溜める方向にも働く。速さより質という方針と正面から衝突する
- 「レビューを終えるまで次を選べない」を規律にすると、放置されたタスクが積み上がらない。ただし**凍結という逃げ道**がなければ、難航したレビューがそのまま開発全体を止める
- **worktree は並行実行の器ではなく、凍結の器である。** タスクを凍結すると、作業は未コミットの中途半端な状態で残る。単一ツリーではそれが次のタスクの邪魔になるか失われる。worktree は状態をその場に置いたまま別の場所で作業させる。WIP = 1 でも worktree が要るのはこのためである
- 選択肢3は既に事故を起こしかけた(背景を参照)
- **docs はコードより競合しやすい**。1ファイルが大きく、複数タスクが同じ節に触るためである(TDD01 は264行で、W1〜W6 のどのタスクも触る)。タスク仕様に「編集してよい文書」を明記し、他タスクはそこを触らない
- ADR 番号は着手時に予約する。承認後にしか採番表へ載らない運用では、番号衝突を防げない

## 論点4: 開発者のレビューの粒度

### 検討した選択肢

1. **欠けている論点の指摘と、自分の方針との違和感の共有に絞る。解決策はエージェントと一緒に作る**
2. 現状維持。全体を読み込み、整理された指示を書く
3. 開発者のレビューを省略し、機械的ガードとレビュアーエージェントに委ねる

### 決定

**選択肢1**。あわせて、設計セッションは判断を求める前に「**これは今決める必要があるか**」を提示し、決めなくてよいものは未決定事項として切り出す。

### 理由

- ボトルネックは判断そのものではなく、**判断を言語化して整理する工程**にある。整理はエージェントが担える。1往復に数時間は適正範囲を超えており、継続の障害になる
- **論点の指摘と違和感の共有は開発者にしかできない。** プロジェクトの意図を持っているのは開発者だけである。一方、解決策の生成はエージェントにもできる。「AIにできることはAIで」をレビュー工程にも適用する
- 選択肢3は成立しない。機械的ガードは規約違反しか見ておらず、レビュアーエージェントも仕様との一致しか見ない。**仕様そのものが間違っている**ことを検出できるのは開発者だけである。レビューは省略できないが、粒度は下げられる

  > **【2026-08-31 追記:この予測は外れた】**
  > W1-02・W1-03 の実運用で、レビュアーエージェントは仕様の欠陥を繰り返し検出した(過大な約束、規範文と理由の不一致、上位文書との矛盾、曖昧な順序)。しかもそれが最も重い指摘だった。
  > 原因は「仕様の誤り」を一枚岩として扱ったことにある。実際には2種類あり、**内部破綻**(文書間の食い違い)は docs しか持たない読者に最もよく見えるため、レビュアーが検出できる。**作るべきものが正しいか**は予測どおり開発者にしか判定できない。
  > 決定(選択肢1)は有効なまま、この理由に書いた予測だけが外れた。憲章の変更は [ADR-0005](0005-reviewer-scope-includes-spec-defects.md) が扱う。
  > *(追記は事実の記録のみ。上の本文は当時のまま変更していない)*
- 理解が追いつかない段階では、学習セッションを相談役として使う(論点5)。理解から論点の言語化までをそちらで済ませ、整理された論点だけを設計セッションに持ち込む
- 開発者の熟達に伴って速度は自然に上がる。**継続を妨げないこと**を短期的な質より優先する

## 論点5: 学習(C#/.NET/Godot)の置き場所

### 検討した選択肢

1. **開発に関与しない専用セッション。読み取り専用とし、スラッシュコマンドで枠づけする**
2. 学習専用のサブエージェント
3. メインセッションで随時聞く

### 決定

**選択肢1**。レビューの相談役(論点4)も兼ねる。

### 理由

- 選択肢2は目的を達成しない。サブエージェントの呼び出しと結果はメインのコンテキストに残るため、汚染を避けられない。メインからの呼び出しを禁じるなら、そもそもサブエージェントである必然性がない
- 選択肢3は設計の対話に初歩的な質問が混ざる
- 学習セッションはコードを書かないので worktree を必要としない。むしろ書き込みを許さないほうが安全である
- **還流のルール**を設ける。学習で得た知見のうち「このプロジェクトで C# のこの機能をこう使うと決めた」というものだけを CLAUDE.md か docs に戻す。**言語一般の解説を docs に書かない** — 混ぜると docs が入門書になる。判断が入ったものだけが docs の対象である

## 決定(まとめ)

| 役       | 形態                       | コンテキスト   | 起動               | 主な仕事                                               |
| -------- | -------------------------- | -------------- | ------------------ | ------------------------------------------------------ |
| 設計     | メインセッション           | 継続           | 開発者が直接       | 仕様検討、アーキテクチャ設計、タスク仕様の作成、ADR起草 |
| 設計(専門) | サブセッション(一時的)   | 分離           | メインでの相談を経て | 専門性が違うタスク。開いている間メインは凍結           |
| 実装     | サブエージェント           | 使い捨て       | 設計セッションから | タスク仕様に沿った実装とテスト                         |
| レビュー | サブエージェント           | 使い捨て・独立 | 設計セッションから | 規約順守、仕様との過不足、文書との乖離                 |
| 学習     | セッション(読み取り専用)   | 完全分離       | 開発者が直接       | C#/.NET/Godot の解説、レビューの相談役。開発に関与しない |

**同時に取り組むタスクは常に1つ**(論点3)。開発者のレビューは「欠けている論点の指摘」と「違和感の共有」に絞り、解決策はエージェントと作る(論点4)。

レビュアーエージェントの憲章は、**機械が判定できない範囲に限る**:

1. 機械が捕まえない決定論の破れ(変数に入らない一時値の浮動小数点、系統をまたいだ乱数借用、列挙順への依存、‰係数の単位コメント欠落)
2. タスク仕様との過不足(仕様にない実装、仕様にある未実装)
3. 実装と文書の乖離(コードだけ直すのは禁止。文書側も直す)
4. プレースホルダ宣言の妥当性(M0限りの仮置きが正式仕様のふりをしていないか)

## 帰結(受け入れるトレードオフ)

- **開発速度は開発者のレビュー速度そのものになる。** WIP = 1 のため、並行度で速度を買えない。M0 のスケジュール(TDD01 §5.4)が厳しくなった場合、上げるのは並行度ではなくスコープ削減で対応する
- **粗いレビューは見落としを増やす。** これを受け入れられるのは、機械的ガード(ADR-0002)とレビュアーエージェントが下支えしているからである。**開発者のレビュー精度を下げられる範囲は、その2層が守れている範囲までである**。守れていない領域(ゲームデザインの妥当性、仕様そのものの誤り)では粒度を下げない
- **凍結したタスクは worktree とブランチを占有し続ける。** ディスクと、どこに何が置いてあるかの記憶コストがかかる。`docs/tasks/README.md` の状態一覧で緩和するが、凍結を溜めれば管理コストが増える
- **状態一覧は master へ直接コミットする。** worktree をまたいで共有する必要があり、ブランチ上で更新すると他のツリーから見えないため。ADR 番号の予約と同じ扱いになる
- **タスク仕様は実装後に腐る。** 凍結後の文書を読んで実装を理解しようとすると誤る。正はコードと TDD であることを各タスク仕様の冒頭で宣言する
- **サブエージェントに委ねられる範囲は、機械的ガードの範囲に依存する。** 決定論規約はビルドとテストで強制されている(ADR-0002 / `BannedSymbols.txt` / `DeterminismConventionTests`)ため実装を委ねられる。機械で守れない規約を増やすほど委ねられる範囲は狭まるので、**新しい規約を作るときは「これは機械で守れるか」を必ず問う**
- **実装に安いモデルを使うと、仕様の曖昧さがレビュー往復として跳ね返る。** レビュー往復が2回を超えたらモデルではなく仕様を疑う。往復回数をタスク仕様の品質の指標として扱う
- **レビュアーには機械の判定結果を渡さない。** ビルド・テストで確定することを AI に再判定させるのはトークンの浪費であり、レビュアーの注意も逸れる
