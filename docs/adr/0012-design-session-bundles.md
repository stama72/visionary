# ADR-0012: 設計セッションを「決定の束」で切り、モデルはセッションではなく仕事で決める

| 項目 | 内容 |
| ---- | ---- |
| 状態 | 起案中 |
| 日付 | 2026-09-20 |
| 決定者 | stama |

## 背景

[ADR-0009](0009-phase-scoped-sessions.md) と [ADR-0010](0010-phase-pipeline-and-halt-conditions.md) は実装タスクを3フェーズに切り、フェーズ2・3 を機械に繋いだ。**設計工程には工程の切り方が無い**([#104](https://github.com/stama72/visionary/issues/104))。[ADR-0004](0004-ai-driven-development-workflow.md) 論点1 は「設計は途中経過が成果物であり、却下した案とその理由が次の判断の入力になる」として設計のコンテキストを「継続」と置いたまま、いまに至る。

あわせて Max プランで `fable` が選べるようになり、フェーズ・エージェントごとのモデル配分を決める必要が出た。

### 実測 — 設計セッションはどう回っていたか

`.claude/projects/` の生ログから集計した(2026-09-20)。活動時間は30分超の空白を除く。「文書の書き込み」は `Write` / `Edit` で `docs/` を書いた文字数が assistant の出力に占める割合。

| セッション | 活動時間 | 開発者ターン | 開発者の思考・入力 | AI の作業 | 最大コンテキスト | 文書の書き込み |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| [#85](https://github.com/stama72/visionary/issues/85) GDD02 洗い直し(fable) | 415 分 | 21 | 296 分(71%) | 119 分 | 580K | 8% |
| [#8](https://github.com/stama72/visionary/issues/8) M0 スコープ分割(opus) | 142 分 | 13 | 102 分(72%) | 40 分 | 625K | 21% |
| [#101](https://github.com/stama72/visionary/issues/101) 追随表(fable) | 56 分 | 3 | 17 分 | 39 分 | 544K | 27% |
| 実装のフェーズ1(#35〜#97、5本) | 46〜127 分 | 2〜4 | — | — | 250〜510K | 45〜49% |
| issue 作成だけのセッション(4本) | 3〜13 分 | 1〜2 | — | — | 87〜114K | — |

- **設計のボトルネックは AI ではなく開発者の時間である。** 開発者の1ターンは平均14分の読解と入力
- **#85 の開発者ターン 21 のうち 4 は `/advise` の指摘を手で運ぶ転記だけだった**
- **仕事5(文書化)は 1〜4 と分離していない。** #85 は分冊ごとに「決める → 書く → `/advise` → 直す」を4周し、コミットは 23:34 から翌 20:10 まで散っている
- 文書の書き込みは出力の 8〜27%。**コンテキストの重さは読み込みが作る**(assistant の出力文字数の 78% がツール呼び出し)
- 大きな設計セッションは 580K〜625K に達し、起動時の読み直しは約 60K

### 仕事の5分割

#104 が置いた整理をそのまま使う — 1 スコープ決め / 2 論点出し / 3 案とトレードオフ / 4 決定 / 5 文書化。分担の現行は [06-design-sessions](../process/06-design-sessions.md) が持つ。

## 論点1: 設計セッションをどの単位で切るか

> ステータス: 承認

### 検討した選択肢

1. **決定の束ごと。** 1束 = 論点の集まりを決め、文書に書き、コミットするまで(sub-issue があればそれが束)。境界は文書のコミット。引き継ぎメモは書かない
2. 1〜4 と 5 で切る(#104 の当初の見立て)。5 を別プロセスの下位モデルに出す
3. 切らない。コンパクション任せ

### 決定

**選択肢1。** 束の終わりで3条件(文書がコミット済み / 決定ログが issue にある / 残る論点と、開発者が述べてまだ決定に消費されていない「重視すること」が issue にある)を満たす。満たしたら切ってよく、切るかは束ごとに開発者が選ぶ。

### 理由

- **ADR-0009 論点1 の基準「そのコンテキストは捨てられるか」を設計に当てた結果である。** 捨てられる点は「仕事5 の前」ではなく「**文書をコミットした直後**」に来る。採った案は文書に、却下した案は決定ログ(issue の番号付きコメント。#85 の「決定 1〜20」が形)に出ているので、境界で消える情報が無い。ADR-0009 論点2 と同じ棚卸しをした:

  | 情報 | どこに残るか |
  | ---- | ------------ |
  | 採った案 | 文書(コミット済み) |
  | 却下した案と理由・前提 | 決定ログ(ADR 級なら ADR) |
  | 残る論点 | issue |
  | 開発者が述べた「何を重視するか」で、まだ決定に消費されていないもの | issue(境界の条件3)。**これだけは文書にも決定ログにも無い** — 書き忘れると消える |
  | `/advise` の指摘と対応 | コミット本文 |
  | 決めて / 止まって報告の件数 | 決定ログ |

- **選択肢2 は実測が否定した。** 5 は 1〜4 と分離しておらず、**書いた差分が開発者と `/advise` の検証媒体になっている。** 5 を末尾へ寄せると、その検証が末尾へずれ、指摘の戻りのたびに 1〜4 を開き直す(#85 では4回)
- **選択肢3 は ADR-0009 が退けた理由がそのまま当たる。** 自動圧縮は新しい情報を残すので、最も要るもの(設計の意図)から消える。#85 は 580K、#8 は 625K に達した
- **決定ログを「文書を書く前」に書かせるのは、セッションが途中で死んでも決定が残るためである。** ラップトップでの開発は移動中に頻繁に止まる([#106](https://github.com/stama72/visionary/issues/106))
- **これは ADR-0004 決定(まとめ)の「設計 = コンテキスト継続」の読み替えである。** 決定(設計はメインセッションで開発者と直に対話する)は動かさない。動くのは「継続」の単位で、タスク全体から束へ縮む

## 論点2: 仕事5(文書化)を誰が書くか

> ステータス: 承認

### 検討した選択肢

1. **設計セッション自身が本文を書く。機械的な波及だけ Sonnet のサブエージェント**
2. 別プロセスの Sonnet が決定ログから書く(#104 の「下位モデルで足りる」)
3. writer サブエージェントに全部書かせ、設計セッションが差分を見る(implementer と同じ構造)

### 決定

**選択肢1。** 「機械的」の判定は「**却下した選択肢を知らなくても正しく書けるか**」。参照の付け替え・追随表の候補列挙・件数の更新がこれに当たる。

### 理由

- **「気付けない × 影響大」の4類型(広い保証 / 参照点の誤り / 上位文書との矛盾 / 却下理由の空洞化)は文言の中で生まれる。** #85 で `/advise` が4巡にわたって拾ったのは、いずれも書いた文言の欠陥だった。却下案を持たない書き手に本文を書かせると、この型が増える
- **選択肢2 は節約にならない。** 文書の書き込みは出力の 8〜27% で、これを逃がしても設計セッションの重さ(読み込み)は変わらない
- 選択肢3 は実装と違って**文言そのものが決定**である点で implementer と条件が異なる。試すなら1タスクで計測してからで、いまは根拠が無い

## 論点3: モデルをどう配分するか

> ステータス: 承認

### 検討した選択肢

1. **仕事で決める。** `docs/` の設計 = fable / 機械的な波及 = sonnet / `/advise` と専門家アドバイザーは [#105](https://github.com/stama72/visionary/issues/105) / フェーズ2・3 は [05](../process/05-phase-sessions.md) のまま
2. 設計セッションは全部 fable(実装のフェーズ1 も含む)
3. 全部 opus のまま

### 決定

**選択肢1。ただし実装のフェーズ1(凍った GDD からタスク仕様を書く)は決めない。** 現状は `~/.claude/settings.json` の既定(`claude-fable-5-1[1m]`)で走っており、opus に落とす機構は無い。落とすかは帰結の検証条件で決める。

### 理由

- **開発者の1ターン14分を縮めるのは案とトレードオフの質である。** そこに最上位モデルを当てる
- **フェーズ1 を opus に落とす案は根拠も機構も無かった。** 当初の起案は「タスク仕様は凍った GDD の転記に近い」を根拠に opus と書いたが、単価も差し戻し回数も未実測で、既定のセッションを opus にする機構も無い(`/advise` の指摘)。**根拠の無い規約を機械で守れない形で置かない**
- 選択肢3 を採らないのは、実装側の節約(ADR-0010)がターン単価で効いたのに対し、設計側の時間は開発者が 7 割を占め、モデル単価の節約が効く場所ではないためである。**ただしモデル単価がターン単価にどう効くかは未実測である**

### 実測で確かめた前提

| 事実 | 確かめ方 |
| --- | --- |
| コマンドの `model:` frontmatter は `claude -p` で settings の既定に勝つ | 既定が fable の環境で `model: haiku` の使い捨てコマンドを置き、記録上のモデルが `claude-haiku-4-5` になった(2026-09-20)。**最初の実測は `model: fable` で行い、既定と同じなので証拠にならなかった** — frontmatter の効き方は既定と違うモデルで測る |
| 対話セッションでの frontmatter の効き方 | **未実測。** いまは既定が fable なので、`/design` の `model: fable` はどちらでも同じ結果になる |

## 論点4: 何を「設計タスク」と呼ぶか

> ステータス: 承認

### 検討した選択肢

1. **`docs/` の規則・仕様・設定を書き換える仕事の全層**(docs 直下のコンセプトシート・企画書・世界観設定書 / GDD・TDD / ADR / process)
2. GDD / TDD / ADR / process に限り、docs 直下はケースバイケース(当初の起案)
3. docs 直下だけ別枠「コンセプト作業」(決定ログだけ必須、束と `/advise` は任意)

### 決定

**選択肢1。** 層が違っても進め方は変えない。変わるのは規則を変えたとき何が追随するかだけで、docs 直下なら「変えた規則 → 追随する GDD / TDD の節 → 引き取る design issue」、GDD / TDD なら「→ 実装している既存コード → 引き取る impl issue」([04-issue-driven](../process/04-issue-driven.md))。

### 理由

- **[#68](https://github.com/stama72/visionary/issues/68)(世界観と正式タイトル)が枠の外に落ちていた**(開発者の指摘)。同 issue のブランチは世界観設定書と ADR-0011 を起案し、「領主 → 市参事会」という規則の反転を企画書・コンセプトシート・GDD01 / 02 / 09 に波及させる。構造は GDD の設計タスクと同じで、違いは層と追随の向きだけである
- **選択肢2 は追随表の規則が当たらない。** ADR-0011 の波及節は「読み替えを企画書・コンセプトシート・GDD へ反映する(別 issue)」とだけ書き、どの節が追随するかも引き取る issue も無い。master の GDD01 / 02 / 09 には「領主」が 3 / 4 / 7 箇所残っている。[#101](https://github.com/stama72/visionary/issues/101) が GDD → コードで踏んだ「反転した規則に追随表が無い」が、一段上で起きていた
- 選択肢3 は開発者のクリエイティブな比重が大きい工程には合うが、枠が2つになり判定が増える。実測は #68 の1本(12分)しか無く、別枠が要る根拠がまだ無い。次の直下タスクで束と `/advise` が重いと分かってから足す

## 論点5: 設計セッションが自分で決めてよい範囲をどう定めるか

> ステータス: 承認

### 検討した選択肢

1. **2条件(却下する選択肢が無い / 開発者が置いた数値・優先順位・スコープを動かさない)を満たすものは自分で決め、束の終わりに列挙する。開発者が事後に却下できる**
2. 3条件(上の2つ + 上位文書の規則を反転・削除・新設しない)を事前の許可条件にする(当初の起案)
3. 3つ目の条件を GDD / TDD に限る

### 決定

**選択肢1。** implementer の「決めて報告 / 止まって報告」と同じ2種に分け、決めて報告は事前の許可ではなく事後の拒否権として置く。規則の反転・削除・新設は「常に選択肢がある」ので条件1 の例として残す。

### 理由

- **選択肢2 は初回適用で自分に当たった。** #104 の決定ログで「決めて報告」と数えた3件のうち2件が、3つ目の条件に自分で当たっていた(`/advise` の指摘)。**process 文書は全文が規則なので、「規則を新設しない」の形にすると常に発火し、件数が指標にならない**
- 選択肢3 を採らないのは、process の設計にも選択肢があり、条件1「却下する選択肢が無い」が既に規則の反転・新設を捕まえるためである。3つ目の条件は条件1 の特殊例であって独立した条件ではない
- 事後の拒否権にするのは、実態がそれだからである。設計セッションは決めた件を列挙して報告し、開発者はレビューで却下する

## 決定(まとめ)

| 論点 | 決定 |
| ---- | ---- |
| 1 切り方 | 決定の束ごと。境界は文書のコミット + 3条件。引き継ぎメモは書かない |
| 2 文書化 | 設計セッション自身が本文を書く。機械的な波及だけ Sonnet |
| 3 モデル | 仕事で決める。設計 = fable。実装のフェーズ1 は未決(現状 fable) |
| 4 範囲 | `docs/` の全層。追随表の向きは層で変わる |
| 5 決めてよい範囲 | 2条件 + 事後の拒否権 |

運用の正は [06-design-sessions](../process/06-design-sessions.md)、枠づけは [`/design`](../../.claude/commands/design.md)。

## 帰結(引き受けるトレードオフ)

- **これは仮説であり、次の設計タスク(#105 か #68)で検証する。記録先はそのタスクの PR 説明で、0 件でも「0 件」と書く**(ADR-0009 帰結の教訓。0 を沈黙から導かせない)。検証条件は6つ:
  - 束の数と、切った回数
  - **切った後に、却下案を再検討した・決定をやり直した回数。** 1 でも起きたら境界の3条件が足りない
  - **開発者が既に言ったことを言い直した回数。** 境界の条件3 の「重視すること」が書き漏れたときに出る
  - 開発者ターンのうち、転記だけのターン数(#105 の後は 0 が期待値)
  - 決めて報告 / 止まって報告の件数と、決めて報告のうち開発者が却下した件数
  - **実装のフェーズ1 の API 等価コスト(fable のまま)。** 次の実装タスクの PR 説明に書き、opus に落とすかの判断材料にする
- **境界の3条件は機械で守れない。** 文書のコミットは git に残るが、決定ログと残る論点が issue にあるかは人が見る。守られなかったときは上の「やり直した回数」に出る
- **`/advise` の指摘を開発者が運ぶターンは、#105 まで残る。** #85 で 21 ターン中 4
- **フェーズ1 のモデルは決めていない。** 現状の fable が続く。落とすかを決める材料が揃うのは次の実装タスクの後である
- **対話セッションでの frontmatter の効き方は未実測のまま置く。** 既定が fable である限り結果は変わらないが、既定を変えたときに `/design` の `model: fable` が効く保証は無い
- **ADR-0004 決定(まとめ)の「設計 = コンテキスト継続」を読み替える。** 決定そのものは動かさない
