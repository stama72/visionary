# ADR-0005: レビュアーの守備範囲に仕様の欠陥を含め、憲章の正を `.claude/` に移す

- 日付: 2026-08-31
- ステータス: 承認
- 決定者: stama
- **[ADR-0004](0004-ai-driven-development-workflow.md) 決定(まとめ)のレビュアー憲章リスト(4項目)を棄却し、本ADRで置き換える。** ADR-0004 の他の決定(論点1〜5の各決定、WIP=1、三層の文書運用)は変更しない

## 背景

W1-02・W1-03 の実運用で、レビュアーエージェントが**仕様の欠陥**を繰り返し検出した。しかもそれが最も重い指摘だった:

| タスク | 検出された仕様の欠陥 | 影響 |
| ------ | -------------------- | ---- |
| W1-02  | 「借用を型で不可能にする」という達成できない約束 | 実装は約束を満たせず、残る穴が誰にも見えていなかった |
| W1-02  | 参照ベクトルの入力の縮退を仕様が制約していない | 鍵導出を書き換えても全テストが素通り |
| W1-03  | 規範文「同じ `entityId`」と理由「同じ**組**」の食い違い | 実装は文面に忠実で、日次フェーズが動かない状態になった |
| W1-03  | 仕様の `List<PriceObservation>` が TDD01 §3.2「Actor別」と矛盾 | M0検証項目#5(誤爆率)が実行不能になる形 |
| W1-03  | 「`Now` は処理の前に更新する」が2通りに読める | エポックが永久に処理されない |

いずれも**実装は仕様に忠実**であり、直すべきは仕様だった。開発者のレビューを待たずに検出されている。

これを憲章に反映しようとしたところ、2つの構造的な問題に当たった。

1. ADR-0004 の決定(まとめ)がレビュアー憲章を**4項目のリストとして持っている**。項目を足すと、承認済みADRと `.claude/agents/reviewer.md` が食い違う
2. 反映先の文書が体系に無かった。プロセスの「育てる文書」が存在せず、ADR を起こす以外の置き場所が構造上なかった

2 は本 ADR の対象外とし、[docs/process/](../process/) の新設で解決した。本 ADR は 1 を扱う。

## 検討した選択肢

1. **憲章に項目を追加し、あわせて憲章の正の所在を `.claude/agents/reviewer.md` に移す**
2. ADR-0004 を書き換えて憲章リストを参照に置き換える
3. ADR-0004 を棄却し、新 ADR で全体を置き換える
4. 憲章を変えず、仕様の欠陥は開発者のレビューで拾う

## 決定

**選択肢1。** 次の2点を決める。

### (a) レビュアー憲章に「タスク仕様そのものの欠陥」を加える

対象は**仕様の内部破綻に限る**:規範文と理由の不一致、達成できない約束、上位文書との矛盾、曖昧な順序・境界。

**「作るべきものが正しいか」(ゲームデザインの妥当性、ニーズ設計の是非)は引き続き開発者にしか判定できない。** ADR-0004 帰結の安全弁は「守れていない領域(**ゲームデザインの妥当性、仕様そのものの誤り**)では粒度を下げない」と書いている。このうち**ゲームデザインの妥当性はそのまま有効**であり、**仕様そのものの誤りは、内部破綻に限って本 ADR が覆す**。

### (b) 憲章の正は `.claude/agents/reviewer.md` とする

**ADR-0004 決定(まとめ)の憲章リスト(4項目)を棄却する。** 以後の正は `.claude/agents/reviewer.md` であり、ADR-0004 のリストは起案時点(2026-08-27)のスナップショットとして読む。

ADR-0004 の本文は書き換えず、当該箇所に日付つきの註記を入れる(運用ルールが追記を認めているため)。

## 理由

- **本 ADR は ADR-0004 の決定の一部を覆している。** したがって「プロセスについて新たに ADR を起こすのは、過去の ADR の決定を覆すときに限る」というルールを満たす。覆しているのは決定(まとめ)の憲章リストであって、論点4 の決定(選択肢1:開発者のレビュー粒度を絞る)ではない
- **選択肢2は運用ルールに反する。** 承認済み ADR の書き換えにあたる([docs/adr/README.md](README.md))
- **選択肢3は損失が大きい。** ADR-0004 の他の4論点は生きている
- **選択肢4は、既に検出できているものを捨てることになる。** W1-03 の仕様欠陥は開発者のレビュー前に出ており、往復1回分を節約している
- **設計セッションの自己点検では代替できない。** 仕様を書いたのは設計セッション自身であり、書いた本人には食い違いが見えない。W1-02 の過大な約束も W1-03 の規範文の誤りも、設計セッションは自分では見つけられなかった
- **(b) は ADR の自己完結性を損なわない。** ADR が守るべきは「当時の判断が再現できること」であって「現行仕様が読めること」ではない。ADR-0004 のリストは 2026-08-27 時点の憲章として完全に自己完結している。問題はそれが「現行」と読めてしまうことであり、**ADR-0004 の当該箇所に註記を入れる**ことで解消する
- **憲章は「実行される仕様」である。** ハーネスが読んで動くのは `.claude/agents/reviewer.md` であり、内容を別文書に複製すれば必ずドリフトする(位置づけの詳細は [docs/process/README.md](../process/README.md#実行される仕様という位置づけ))
- ADR-0004 論点1 は既に「レビューはドキュメント品質の検査を兼ねる」と書いている。仕様も docs の一部であり、**(a) は論点1の帰結を論点4に反映させたにすぎない**とも読める

## 帰結

### 引き受けるトレードオフ

- **現行の憲章を知るには `.claude/agents/reviewer.md` を読む必要がある。** ADR だけを読んでも現行は分からない。これは意図した設計であり、ADR は「なぜ」を、`.claude/` は「今」を持つ
- **レビュアーの注意が分散する。** 見る対象がコードから仕様へ広がるぶん、1件あたりの深さは落ちうる。往復回数と見落としの発生で観察する
- **設計セッションが仕様を書き飛ばす誘因になりうる。** 「レビュアーが見つけてくれる」は、機械的ガードに対する「守ってくれる」と同じ堕落の形である。[タスク仕様の書き方](../process/02-task-spec.md)の規則はレビュアーに渡す前に自分で潰すためのものであり、レビュアーはその後段である
