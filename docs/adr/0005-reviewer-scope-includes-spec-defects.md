# ADR-0005: レビュアーの守備範囲に仕様の欠陥を含める

- 日付: 2026-08-31
- ステータス: 起案中
- 決定者: stama
- 関連: [ADR-0004](0004-ai-driven-development-workflow.md) 論点4 の一部を棄却する

## 背景

[ADR-0004](0004-ai-driven-development-workflow.md) は、レビュアーエージェントの守備範囲を4項目に限定し、その理由として次を挙げた:

> 機械的ガードは規約違反しか見ておらず、レビュアーエージェントも**仕様との一致しか見ない**。**仕様そのものが間違っている**ことを検出できるのは開発者だけである。(論点4 理由)

帰結でも、開発者のレビュー粒度を下げられる範囲を「機械的ガードとレビュアーが守れている範囲まで」とし、**仕様そのものの誤りをその外**に置いた。

**この予測は、W1-02 と W1-03 の実運用で外れた。** レビュアーは実際に仕様の欠陥を検出しており、しかもそれが最も重い指摘だった:

| タスク | レビュアーが検出した仕様の欠陥 | 影響 |
| ------ | ------------------------------ | ---- |
| W1-02  | 「借用を型で不可能にする」という達成できない約束 | 実装は約束を満たせず、残る穴が誰にも見えていなかった |
| W1-02  | 参照ベクトルの入力の縮退を仕様が制約していない | 鍵導出を書き換えても全テストが素通り |
| W1-03  | 規範文「同じ `entityId`」と理由「同じ**組**」の食い違い | 実装は文面に忠実で、日次フェーズが動かない状態になった |
| W1-03  | 仕様の `List<PriceObservation>` が TDD01 §3.2「Actor別」と矛盾 | M0検証項目#5(誤爆率)が実行不能になる形 |
| W1-03  | 「`Now` は処理の前に更新する」が2通りに読める | エポックが永久に処理されない |

いずれも**実装は仕様に忠実**であり、直すべきは仕様だった。開発者のレビューを待たずに検出されている。

## なぜ ADR-0004 の予測が外れたか

ADR-0004 は「仕様の誤り」を一枚岩として扱っていたが、**2種類ある**:

1. **仕様が内部で破綻している**(規範文と理由の不一致、達成できない約束、上位文書との矛盾、曖昧な順序)
2. **仕様は整合しているが、作るべきものが間違っている**(ゲームデザインとして面白くない、ニーズの設計が違う)

レビュアーは docs とタスク仕様しか持たないが、**だからこそ1は見つかる**。文書間の食い違いは、文書だけを読む者に最もよく見える。ADR-0004 論点1 が「ドキュメントから読み取れない実装が自然に浮かぶ」と書いたのと同じ理屈が、仕様の内部矛盾にも働く。

2 は依然として開発者にしか判定できない。プロジェクトの意図を持っているのは開発者だけだからである。

## 検討した選択肢

1. **レビュアー憲章に「タスク仕様そのものの欠陥」を加え、対象を上記1に限定する**
2. ADR-0004 のまま維持し、仕様の欠陥は開発者のレビューで拾う
3. 憲章を変えず、設計セッションが自己点検する

## 決定

**選択肢1。** レビュアー憲章に項目を追加し、ADR-0004 論点4 の当該記述を**棄却する**:

- 棄却するのは「仕様そのものが間違っていることを検出できるのは開発者だけである」のうち、**上記1(仕様の内部破綻)に関する部分のみ**
- **2(作るべきものが正しいか)は引き続き開発者にしかできない。** ADR-0004 帰結の安全弁「守れていない領域(ゲームデザインの妥当性)では粒度を下げない」はそのまま有効
- ADR-0004 の他の決定(論点1〜3、論点5、WIP=1、三層の文書運用)は一切変更しない

## 理由

- 選択肢2は、既に検出できているものを捨てることになる。W1-03 の仕様欠陥は**開発者のレビュー前に**出ており、往復1回分を節約している
- 選択肢3は成立しない。仕様を書いたのは設計セッション自身であり、**書いた本人には食い違いが見えない**。W1-02 の過大な約束も W1-03 の規範文の誤りも、私(設計セッション)は自分では見つけられなかった
- ADR-0004 が「レビューはドキュメント品質の検査を兼ねる」(論点1)と既に書いており、仕様も docs の一部である。**今回の変更は論点1の帰結を論点4に反映させたにすぎない**とも読める

## 帰結(受け入れるトレードオフ)

- **開発者のレビュー粒度を下げられる範囲が広がる。** ただし広がるのは「仕様の内部整合」の分だけで、「作るべきものが正しいか」は変わらず開発者の担当である。この線引きを曖昧にすると、ADR-0004 帰結の安全弁が実質的に外れる
- **レビュアーの注意が分散する。** 見る対象がコードから仕様へ広がるぶん、1件あたりの深さは落ちうる。往復回数と見落としの発生で観察する
- **設計セッションが仕様を書き飛ばす誘因になりうる。** 「レビュアーが見つけてくれる」は、機械的ガードに対する「守ってくれる」と同じ堕落の形である。[タスク仕様の書き方](../tasks/README.md#タスク仕様の書き方)の規則は、レビュアーに渡す前に自分で潰すためのものであり、レビュアーはその後段である
