# ADR-0013: 変異は専用エージェントが使い捨て worktree で当て、測る者と書く者を分ける

| 項目 | 内容 |
| ---- | ---- |
| 状態 | 承認 |
| 日付 | 2026-09-20 |

## 背景

[02-task-spec](../process/02-task-spec.md)「変異テスト」は、**「核心」印のテストに実際に変異を当てて落ちることを確認する**ことを完了条件に含めている。他の完了条件(build / test / format)が機械の判定であるのに対し、**ここだけが自己申告である。**

**誰が当てるかは、どの憲章も決めていなかった。** 結果として消去法で実装者に落ちた。W2-08(#97 / PR #108)の生ログ `.pipeline/97-impl-20260919-234520.jsonl` で確認できる:

- implementer への起動プロンプト — 「完了条件のうち 6 件(#1・#9・#13・#16・#20・#29)に実際に変異を当てて落ちることを確認し…」
- reviewer 2巡目(網羅パス)への指示 — 「判定は机上ではなく実測でお願いします。`src/` に変異を当てて `dotnet test` …」(60 件)

**テストを書いた本人が、自分のテストの判別力を測っていた。** W2-08 で3つの形で表面化した([#110](https://github.com/stama72/visionary/issues/110)):

- **実測の主張だけが残った。** 1巡目の象限I-a 6件は**すべて「仕様が名指しした変異が実際には落ちない」**であり、うち1件(PR #108 別表 A-1)は doc コメントに「変異を当てて確認した」と**書かれていた**
- **revert 漏れが実害を出した。** implementer が「`git diff --stat src/` は空」と事実と異なる報告をし、**依頼した3変異のどれでもない**変異(`sellableStock` に世帯在庫を足す。すぐ上の doc コメントと矛盾する)が残っていた。オーケストレータ側の `git status` で検出して revert した
- **並行走行の信号が鈍った。** 変異作業中は本体ツリーが常に汚れているため、「別プロセスの疑い」が2度出て**片方は本物・片方は誤報**だった([#109](https://github.com/stama72/visionary/issues/109))

**フェーズ2 のメインはコードを読み書きしない**([ADR-0009](0009-phase-scoped-sessions.md) 論点1)ので、オーケストレータが自分で当てる形も現行の規約では採れない。**「誰がやるか」が空席のまま、規約が要求だけしていた。**

## 論点1: 誰が変異を当てて測るか

> ステータス: 承認

### 検討した選択肢

1. **変異テスト専用エージェント(`mutator`)を新設する**
2. オーケストレータ自身が当てる(ADR-0009 論点1 に「変異の適用と revert だけ」の例外を足す)
3. 現状維持。implementer とレビュアーに、変異の diff とテスト出力の逐語を報告させて証拠とする
4. 変異テストツール(Stryker.NET 等)で機械化する

### 決定

**選択肢1。** `mutator` は**実測結果だけを出す**。**これは [ADR-0004](0004-ai-driven-development-workflow.md) 論点1「実装は必ず implementer が書く」の例外ではない** — 変異はリポジトリに残る成果物ではなく、**捨てるために当てる測定の道具**である(論点2 のとおり、残る先そのものが無い)。実装もテストも書かない。**変異を選ぶのは依頼側**(タスク仕様の表 / レビュアーの列挙 / フェーズ2)であり、`mutator` は選ばない。憲章の正は [`.claude/agents/mutator.md`](../../.claude/agents/mutator.md)。

### 理由

- **測定者と被測定者を分けることが、この issue が消しにきた唯一のものである。** implementer は「自分が書いたテストが落ちること」を確かめる立場にあり、落ちなかったときに*テストを直す*動機と*変異を選び直す*動機が同居する。分けると、`mutator` にとって「落ちない」は自分の失点ではなくなる
- **選択肢2 は、節約そのものを壊す。** 名指しの変異でも「どこに当てるか」を決めるには `src/` を開く。ADR-0009 論点1 が置いた「メインがコードを開いた時点で節約は消えている」に正面から当たる。網羅パスの 60 件を Opus の文脈で回すのは、費用の桁が違う
- **選択肢3 は、証拠を出す主体が被測定者のままである。** W2-08 で外れたのは証拠の形式ではなく**主張と事実の対応**であり(`git diff --stat` は空だと報告されたが空でなかった)、逐語を求めても同じ主体が書く以上、同じ形で外れうる
- **選択肢4 を却下したのは、問うている質問が違うためである。** ツールは変異を**自分で生成する**ので「このコードに当てて落ちないテストがどれだけあるか」を答える。本プロジェクトが問うているのは「**タスク仕様が名指しした実装ミスで、そのテストが落ちるか**」であり、[02-task-spec](../process/02-task-spec.md)「落ちるべき条件」の表に対応する変異は仕様が選んでいる。**仕様の表と対応が付かない結果は、レビューの入力にならない。**
  **却下理由に費用を挙げない。** 論点2 の実測(333 テストが 3 秒)からすると、数百の変異体を回しても十数分であり、費用は本プロジェクトの規模では障害にならない。**「速いマシンなら採れる」と読ませないために、ここは費用の話にしない。** ツールを CI に足す価値は別途ありうるが、**それは仕様が名指しした変異の実測の代わりにはならない**
- **これは仮説である**: 測定を分けると、W2-08 で「確認した」と報告されて実際には落ちなかった型の食い違いが、**doc コメントに書かれる前に `mutator` の報告として表に出る**。
  **検証条件は2つ**とも記録先を **PR 説明**(引き継ぎメモ #5 経由)とし、0 件でも「0 件」と書く。
    1. **`mutator` が報告した「当てた件数 / 期待と食い違った件数」。** W2-08 の同じ工程は「6 件すべて確認済み」と報告し、実際は 6 件とも落ちなかった
    2. **doc コメントに実測を主張する記述のうち、`mutator` の報告に対応が無いものの件数。** 1 件でもあれば論点3 が守られていない
  **レビュー1巡目の指摘件数とは比べない。** 帰結のとおり `mutator` はレビューが閉じた後に走るので、1巡目との比は構造的に取れない

## 論点2: 変異をどこのツリーに当てるか

> ステータス: 承認

### 検討した選択肢

1. **HEAD から使い捨ての worktree を切り、その中だけで当てて測り、worktree ごと捨てる**
2. 本体ツリーに当て、`git diff --stat src/` が空であることを成果物とする([#110](https://github.com/stama72/visionary/issues/110) の原案)
3. 変異をパッチとして当て、`git stash` で退避・復元する

### 決定

**選択肢1。** 置き場所は `.pipeline/mutation/<issue番号>/`(`.gitignore` 済み)。`mutator` は**本体の作業ツリーへ書かない**。

### 理由

- **revert 漏れが原理的に起きない。** 選択肢2 の「revert を成果物にする」は規律であり、**W2-08 でその自己申告が実際に外れた**。捨てる単位が worktree なら、戻し忘れても本体には何も残らない
- **本体の `git status` が汚れないので、並行走行の信号が鈍らない**(#109)。変異作業がある限り「汚れているのは誰のせいか」は判定できず、疑いの信号が使えなくなる
- **代償が実測で無いに等しかった。** 2026-09-20 の実測(`Visionary.sln` / 333 テスト): 使い捨て worktree でのコールド実行が **5 秒**、変異1件あたりの再ビルド + テストが **3 秒**。W2-08 の網羅パス 60 件でも機械時間は 3〜4 分である。`Visionary.Sim` が Godot 参照ゼロの純 C#([ADR-0001](0001-engine-and-simulation-architecture.md))であることが効いている
- **無人フェーズでも権限に弾かれない。** `pipeline.ps1` の許可一覧は `Bash(git:*)` と `Bash(dotnet:*)` を既に持つ。許可を広げる必要がない([#100](https://github.com/stama72/visionary/issues/100))
- **選択肢3 を却下したのは、`git stash` のスタックが worktree 間で共有されるためである。** 並行して走る別セッションの退避を取り違えると、**変異作業が他人の作業を消す**。#109 が消しにきた事故と同じ形になる
- **測定対象がコミット済みであることを要求する副作用は、利点として引き受ける。** worktree は HEAD から切るので、測るのは「コミットされた実装」である。作業中の未コミット状態を測って「確認した」と書けなくなる

## 論点3: 「変異を当てて確認した」と書けるのは誰か

> ステータス: 承認

### 検討した選択肢

1. **`mutator` の報告を出所とする記述だけが、実測を主張してよい**
2. 主張の出所を問わない(現状)

### 決定

**選択肢1。** doc コメントやコミット本文に変異と結果を書くのは、引き続きコードを書く implementer である(ADR-0004 論点1)。ただし**書いてよいのは、フェーズ2 から渡された `mutator` の報告の転記だけ**であり、渡されていない変異結果を書いてはならない。実測の日付を添える。

### 理由

- **[03-corrections](../process/03-corrections.md) の「機械が守っていると書く前に、実際に壊して落ちることを確かめる」と同じ性質の規則である。** 広い保証(象限I-b-1)は「もう見なくてよい」と読ませるので、外れていても踏んだ人が気付けない。「変異を当てて確認した」は**そのままこの型の記述**であり、W2-08 別表 A-1 は実際にこの形で外れた
- **書く主体を `mutator` に移す案は採らない。** テストの doc コメントを書くのは実装であり、`mutator` にコードを書かせると論点1 の分離が逆向きに崩れる
- 転記であることは、日付と変異の記述が `mutator` の報告と一致することで後から確かめられる。**報告そのものはフェーズ2 のセッションと `.pipeline/*.jsonl` にしか残らない**ため、doc コメント側が唯一の恒久的な記録になる

## 決定(まとめ)

| 誰が | 何をする |
| ---- | -------- |
| フェーズ1(タスク仕様) | **変異を選ぶ**(「核心」印のテストと、当てる変異の場所・内容・期待) |
| フェーズ2(オーケストレータ) | `mutator` を起動し、報告を受け、implementer へ**転記を頼む**。本体ツリーが clean であることを確認する |
| `mutator` | **使い捨て worktree で当てて測る**。実測結果だけを出す。選ばない・書かない |
| レビュアー | 網羅パスでは**経路を列挙するまで**。`src/` を書き換えない |
| implementer | 実装とテストを書く。**変異は当てない。** `mutator` の報告を転記する |

- **変異を当ててよいのは `mutator` だけである**(論点1)
- **当てる場所は使い捨て worktree であり、本体の作業ツリーではない**(論点2)
- **実測を主張してよいのは `mutator` の報告を出所とする記述だけである**(論点3)

運用の正は [02-task-spec](../process/02-task-spec.md)「変異テスト」と [01-review](../process/01-review.md)「網羅パス」、憲章は [`.claude/agents/mutator.md`](../../.claude/agents/mutator.md) が持つ。

## 帰結(引き受けるトレードオフ)

- **エージェントが1つ増え、フェーズ2 の起動回数が増える。** 1タスクあたり `mutator` 1〜2回(網羅パスを出すなら2回)と、転記のための implementer 1回である。**測定の独立性をこの回数で買う。** 転記の implementer 呼び出しはコードの論理を触らないので、レビューの巡を増やさない
- **測るのはコミット済みの HEAD なので、後から実装やテストが変われば実測は古くなる。** よって核心テストの実測は**レビューの巡が閉じた後に一度で行う**。途中で測ると、訂正でテストが変わったときに「実測の主張だけが残る」— 本 ADR が消しにきた形そのものになる
- **`mutator` の報告もまた自己申告である。** 分離が消したのは「テストを直す動機との同居」であって、報告の真実性を機械が保証するわけではない。**機械が見るのは本体ツリーが汚れていないことだけ**である(`pipeline.ps1` のフェーズ2 終了時検査)。`mutator` が使い捨て worktree の中で何を測ったかは、`.pipeline/*.jsonl` を読む以外に確かめる手段がない
- **`RED` の意味を広げるが、停止則は4つのままとする。** `DONE` 時に本体の作業ツリーが汚れていれば `pipeline.ps1` が `RED` で止める。**5つ目のコードを作らないのは、[ADR-0010](0010-phase-pipeline-and-halt-conditions.md) が停止則の本数そのものを決定にしているためである** — 汚れたツリーは「検証した状態と、次のフェーズが PR にする状態が違う」ことなので、`RED`(緑を確かめずに先へ進む)の内側に収まる。**代わりに、`RED` は自己申告と機械の混在になる。** 停止則の表([05-phase-sessions](../process/05-phase-sessions.md))はその区別を持つ
- **仕様が変異を選べないタスクでは、この工程がまるごと空振りする。** 「落ちるべき条件」を書けない仕様は変異も名指しできない。空振りは仕様側の欠陥の徴候として扱う([02-task-spec](../process/02-task-spec.md) 仕様品質の先行指標)
