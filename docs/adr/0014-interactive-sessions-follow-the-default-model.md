# ADR-0014: 対話セッションのモデルは既定(opus)に従い、fable は大規模な洗い直しにだけ手で選ぶ

| 項目 | 内容 |
| ---- | ---- |
| 状態 | 承認 |
| 日付 | 2026-09-21 |
| 決定者 | stama |

## 背景

[ADR-0012](0012-design-session-bundles.md) 論点3 は「**モデルはセッションではなく仕事で決める**」とし、`docs/` の設計を fable に割り当てた。却下理由は「**設計の時間は開発者が 7 割を占め、モデル単価の節約が効く場所ではない**」である。

この却下理由は **API 等価コスト($)の軸の主張**だった。**Max プランで制約なのは枠であって API $ ではない**ことは、その後 [#122](https://github.com/stama72/visionary/issues/122) 決定 2 が確定させた。枠で測ると同じ結論にならない。

### 実測1 — 枠を食っているのは fable の対話である

`scripts/usage-rates.py` の枠別 $ を、モデル別レート(fable $51 / opus $200 / sonnet $658 per 100%。[04「枠」](../process/04-issue-driven.md))で割り、**枠の % に直した**(2026-09-21 時点)。

| 枠頭 | 実測 util | fable の寄与 | opus の寄与 | sonnet の寄与 | fable の $ シェア |
| --- | ---: | ---: | ---: | ---: | ---: |
| 09-19 19:10 | 0.91 | **0.70** | 0.15 | 0.06 | 35% |
| 09-20 11:30 | 0.66 | **0.30** | 0.26 | 0.05 | 15% |
| 09-20 16:40 | 0.82 | **0.39** | 0.42 | 0.04 | 16% |

**09-19 の枠は、$ の 35% しか占めない fable が消費の 77% を作っていた。** 同じ $ を opus で使っていれば、この枠は 0.91 ではなく 0.39 で終わっている。

セッション単位でも同じ形が出る(設計セッションのみ。`--sessions` の実測)。

| セッション | モデル | 開発者ターン | API $ | 枠% | 枠%/ターン |
| --- | --- | ---: | ---: | ---: | ---: |
| [#85](https://github.com/stama72/visionary/issues/85) GDD02 洗い直し | fable | 21 | 52.5 | 103.8 | 4.9 |
| [#101](https://github.com/stama72/visionary/issues/101) 追随表 | fable | 3 | 14.8 | 29.3 | 9.8 |
| [#104](https://github.com/stama72/visionary/issues/104) プロセス設計 | fable | 7 | 16.0 | 31.7 | 4.5 |
| [#122](https://github.com/stama72/visionary/issues/122) 枠の規則 | fable | 6 | 12.0 | 23.8 | 4.0 |
| [#131](https://github.com/stama72/visionary/issues/131) 価格係数 | fable | 3 | 11.1 | 21.9 | 7.3 |
| #104 続き | **opus** | 5 | 7.4 | **3.7** | **0.74** |
| #122(途中で opus へ切替) | opus 主 | 8 | 11.0 | **8.6** | **1.1** |

**#104 は同じ設計タスクを両方のモデルで回した唯一の例で、opus のほうが API $ でも安い**(fable 7 ターン $16.0 / opus 5 ターン $7.4)。[#123](https://github.com/stama72/visionary/issues/123) が「`C_opus` が無いと下段の打ち手は決まらない」と書いた穴は、ここで埋まっている。

**なお、レート自体は予測どおりに出ている。** #123 の判定表は P_fable = $51 を LOO の範囲内($38〜71)と判定し、「04 の表を据え置く。ADR-0012 決定3 は維持」を返す。**本 ADR が覆すのは、レートが外れたからではない。却下理由が立っていた軸(API $)が、制約の軸(枠)ではないと分かったからである。**

### 実測2 — 対話セッションでは `model:` frontmatter が起動モデルを変えない

ADR-0012 は「対話セッションでの frontmatter の効き方」を**未実測のまま置いた**。2026-09-21 に測った。

| 観測 | 既定 | frontmatter | 起動したモデル | 言えること |
| --- | --- | --- | --- | --- |
| 2026-09-20 23:19 `/design 38` | fable | `fable` | fable | **何も言えない**(既定と同じ) |
| 2026-09-21 `/design`(既定は GUI で選択) | **opus** | `fable` | **opus** | frontmatter は GUI の選択に勝たない |
| 2026-09-21 `/_probe-sonnet`(使い捨て。既定は settings) | **opus** | `sonnet` | **opus** | **frontmatter は settings の既定にも勝たない** |

**1 件目は ADR-0012 が `claude -p` で一度踏んだ罠と同じ形である** — 「最初の実測は `model: fable` で行い、既定と同じなので証拠にならなかった」。今回も、既定を変えるまで気付かなかった。

**3 件目は 2 件目の後に追加で測った。** 2 件目だけでは「GUI の選択が特別に強いだけで、settings の既定には frontmatter が勝つ」可能性が残り、**その可能性が残る限り [`wrap.md`](../../.claude/commands/wrap.md) の `model: sonnet` を外せない**(手で `/wrap` を開く経路で機構として生きている場合があるため)。**運用に効く差があったので測った。** プローブは `model: sonnet` にした — 既定(opus)とも 2 件目の fable とも違うモデルなら、結果を読み違えようがない。

観測は**プロジェクト階層のコマンド 2 本・2 モデル・2 方向**である。**「モデルはセッション起動時に決まり、起動後に読まれるコマンドはそれを差し替えられない」と読むと両方の観測に合う**が、機構そのものを確かめる手段は手元に無い。

効く経路と効かない経路は次のとおり。

| 経路 | frontmatter / 指定 | 効くか |
| --- | --- | --- |
| パイプライン(`claude -p --model`) | CLI の `--model` | **効く**(`scripts/pipeline.ps1` L97 の実測) |
| サブエージェント(`.claude/agents/*.md`) | `model:` | **効く**(implementer が sonnet で走っている) |
| **対話セッションのコマンド(`.claude/commands/*.md`)** | `model:` | **効かない**(上の実測) |

## 論点1: 対話セッションのモデルをどう決めるか

> ステータス: 承認 / [ADR-0012](0012-design-session-bundles.md) 論点3 を覆す

### 検討した選択肢

1. **対話セッションは既定に従う。既定を opus とする。仕事別の割り当ては、機構がある場所(サブエージェント・パイプライン)にだけ残す**
2. 「設計 = opus」と、仕事別の表を書き直す(fable を opus に差し替える)
3. 対話でも frontmatter を効かせる経路を探し、見つかってから決める
4. #123 の単独走行(P_fable の確認)を待つ

### 決定

**選択肢1。** `~/.claude/settings.json` の `"model"`(および GUI の選択)が対話セッションのモデルであり、**既定を opus とする。** [`design.md`](../../.claude/commands/design.md) の `model: fable` は外す。

### 理由

- **枠%/ターンで 4〜9 倍、同一タスク(#104)で 8.6 倍の差がある。** 設計の律速が開発者の時間であることは変わらないが、**枠が切れれば開発者の時間も止まる。** ADR-0012 決定3 の却下理由は「モデル単価の節約」を API $ の意味で使っており、枠の意味では成り立たない
- **選択肢2 は、守る機構が無いまま規約だけを残す。** frontmatter が効かない以上、「この仕事は opus、あの仕事は fable」を対話セッションに対して機械で当てる手段は無い。**ADR-0012 論点3 自身が「根拠の無い規約を機械で守れない形で置かない」として当初の起案を退けており、同じ基準がここに当たる。** 選択肢1 は割り当てを**機構のある場所にだけ残す**ので、残った規則はすべて機械が守る
- **選択肢3 は #137 を調査タスクに変える。** 経路が見つかっても、得られるのは選択肢2 の成立だけである。**見つからなかったときに何も決まっていない**のが最も高くつく
- **選択肢4 は待っても打ち手が変わらない。** #123 の判定表は P_fable = $51 に対して「維持」を返す。**本 ADR の根拠はレートではなく却下理由の前提なので、確認の結果と独立している**
- **`design.md` の `model: fable` を外す理由は「opus に落とすから」ではない。** [06](../process/06-design-sessions.md) はこれを「既定が変わったときの保険」と書いていたが、**その保険は最初から効いていなかった。** 効かないものを保険として残すと、既定を変えたときに「保険があるから大丈夫」と読ませる
- **同じ理由が [`wrap.md`](../../.claude/commands/wrap.md) の `model: sonnet` にも当たるので、こちらも外す。** 対話では効かず、パイプライン経路では `pipeline.ps1` の `--model` が勝つ(同 L97 の実測)。**どちらの経路でも何も決めていない。** 残すと「フェーズ3 は `wrap.md` が sonnet を握っている」と読ませるが、握っているのはパイプラインだけである

## 論点2: fable をどの仕事で使うか

> ステータス: 承認

### 検討した選択肢

1. **大規模な既存コンテキストの修復・洗い直しにだけ使う。開発者が起動時に手で選ぶ**
2. 使わない(既定の opus だけで回す)
3. 「大きい設計タスク」で使う([#137](https://github.com/stama72/visionary/issues/137) 本文の候補)

### 決定

**選択肢1。** **既に書かれた文書やコードの山を横断して読み直し、食い違いを見つける仕事**には fable を選ぶ。#85(GDD02 の洗い直し)と #101(追随表)がこの型である。**通常の設計束 — 新しく決める仕事 — は既定の opus で回す。**

### 理由

- **#85 で切れたのは枠ではなく開発者の判断帯域であり、そこでは fable の質が開発の進行を助けた。** ADR-0012 決定3 の却下理由(設計のボトルネックは開発者の時間であり、モデル単価の節約が効く場所ではない)は、**この型の仕事では今も成り立っている。** 本 ADR は決定3 を全面的に覆すのではなく、**前提が成り立つ範囲を洗い直しへ狭める**
- **選択肢2(AI の推奨)を採らないのは、枠と判断帯域のどちらが律速かが仕事で変わるためである。** 洗い直しは読む量が決める量より大きく、**見落としの代償が後続の全タスクに乗る**(#101 は GDD → コードの追随漏れを拾う仕事だった)。枠%/ターンが最も悪い型でもあるが、**そこは 5 時間枠 1 つを明け渡す前提で走らせる**
- **選択肢3 の「大きさ」は基準にならない。** 大きさは毎回の判定を要求し、しかも #85 は「大きい」と「洗い直し」の両方に当てはまるので区別の役に立たない。**仕事の種類で切ると、着手前に決まる**
- **この例外は機械で守れない。** 下の帰結で引き受ける

## 決定(まとめ)

| 論点 | 決定 |
| ---- | ---- |
| 1 対話セッションのモデル | 既定に従う。**既定は opus。** 仕事別の割り当ては機構のある場所(サブエージェント・パイプライン)にだけ残す。`design.md` の `model: fable` を外す |
| 2 fable の使い所 | **大規模な既存コンテキストの修復・洗い直しにだけ、開発者が起動時に手で選ぶ** |

運用の正は [06-design-sessions](../process/06-design-sessions.md)「モデル」、枠の見込みは [04「枠」](../process/04-issue-driven.md)。

## 帰結(引き受けるトレードオフ)

- **論点2 の例外は機械で守れない。** 開発者が起動時に選ぶ手動の行為であり、選び忘れても機械は気付かない。許容できるのは**片側にしか倒れない**ためである — 忘れれば opus で走り、枠は軽いままで、失うのは質だけである。逆向き(洗い直しでないのに fable を選ぶ)は枠で気付く
- **対話セッションのモデルを仕事で振り分ける手段を、当面持たない。** 論点1 が機構の無い規約を置かないことを選んだ帰結である。frontmatter が対話でも効くようになれば、選択肢2 を再検討する余地が戻る
- **「対話では frontmatter が効かない」と言えるのは、プロジェクト階層のコマンドについてである。** 実測はコマンド 2 本・2 モデル・2 方向(GUI 選択と settings の既定の両方に勝たない)。**ユーザ階層(`~/.claude/commands/`)のコマンドは測っていない**が、そこに置かれたコマンドはこのリポジトリの運用に無い。**将来この挙動が変わったときに気付く機構は無い** — `design.md` と `wrap.md` から `model:` を外したので、変わっても何も動かないほうへ倒してある
- **枠%/ターンの比較は仕事の大きさで正規化していない。** 同一タスクでの比較は #104 の 1 例だけである。レート(fable $51 / opus $200)も #122 決定 3 の実測で、**P_fable は外挿**(fable 主体の枠が 1 つも無い)。#123 の確認で動くが、**動いても論点1 の根拠は動かない** — 根拠はレートの値ではなく、却下理由が立っていた軸だからである
- **ADR-0012 決定3 の検証条件「実装のフェーズ1 の API 等価コスト(fable のまま)」は、測る対象が消える。** フェーズ1 も対話セッションなので既定に従い、opus で走る。**ADR-0012 が「未決」として残した穴は、決めたのではなく埋まった**
