## 規則

| #  | 規則                                                                                                                                | 機械化の余地                       |
| -- | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| 1  | テスト表に**「この実装ミスで落ちる」列**を必ず埋める。埋められないテストは未完成であり、実装に渡してはならない                     | 列が空でないことは可。中身は不可   |
| 2  | **「宣言のみでよい」と書かない。** フィールド一覧を書けないなら、それは実装タスクではなく設計タスクである。決めるか、型ごとスコープ外にする | 不可(レビュー観点)               |
| 3  | 「作るもの」の各項目に **TDD/GDD の該当箇所を引用**する。引用できないものは新しい決定であり、先に TDD/GDD へ書く                    | リンクの有無は可                   |
| 4  | **保証を書くときは残る穴も書く。**「X で防ぐ。ただし Y は防げない」の形にする。防ぎきれないものを「不可能にする」と書かない          | 不可                               |
| 5  | **式と散文を突き合わせる。** 規範文と括弧内の理由、**および式と、その式が現れる節・引用先の節の散文**。食い違ったら狭い方を規範文に書き直す(下の「式と散文の突き合わせ」) | 不可                               |
| 6  | **順序・境界は具体例で固定する。** 例:「`Advance(3)` を `Tick.Zero` から呼ぶと処理は tick 0,1,2、終了時 `Now = 3`」                 | 不可                               |
| 7  | **呼び出し側を持たないコードを作るタスクでは、配線の列挙をテスト表と別立てで持つ**(下の「呼び出し側を持たないコード」)                | 不可                               |
| 8  | **既存コードを「変えない」と宣言するときは、その中の規則ごとに、従う現行の GDD/TDD の節を添える**(下の「変えないと宣言する既存コード」)。突き合わせていないなら「未確認」と書く | 不可。候補の列挙だけ `grep` が手伝う |

規則1と3だけが機械化の余地がある(列が空でないこと、引用リンクの有無)。**ただし現時点で docs の lint も CI ジョブも存在せず、実装予定も無い。** したがって8件とも今は人が守る規約である。

うち規則3・4・5 はレビュアー憲章(`.claude/agents/reviewer.md` §4)に象限I-b の項目としてあり、**規則8 は同 §5 が二次防衛線として持つ**(一次は表を書く設計セッションである)。**規則1・2・6・7 は、憲章では自己点検を代替できない** — 規則1・2・7 は憲章に項目が無く、**規則6(順序・境界)は [ADR-0008](../adr/0008-review-scope-narrowed-to-unnoticeable-defects.md) で象限II へ降格し、実装レビューの1巡目にしか残らない**(憲章 §3)。これは [ADR-0005](../adr/0005-reviewer-scope-includes-spec-defects.md) が「書いた本人には食い違いが見えない」と認めた経路そのものなので、弱い。**4件とも設計セッションが書く時点で守るしかない。**

> [ADR-0008](../adr/0008-review-scope-narrowed-to-unnoticeable-defects.md) の帰結節は同じ数を「規則1・2 の2件から**規則1・2・6 の3件**になる」と書いている。**あれは起案時点(2026-09-14)の数である。** 規則7 は W2-05 の実測から後に足した。ADR は凍るので数え直さない。

> [ADR-0004](../adr/0004-ai-driven-development-workflow.md) 論点2 が「**緑にすべきテストの一覧**を書く」と呼んでいるものの、現在の形が本書である。ADR は承認済みなので書き換えず、決定(仕様をテストのリストとして書く)はそのまま生きている。変わったのは目標の置き方だけである。

## なぜ「緑にすべきテスト」をやめたか

**節名そのものが失敗を誘発していた。**(当時この規則群はタスク仕様の1節だった) 「緑にすべき」は *通すこと* を目標に据える。型1の3件は、通ったが検出力を持たなかった — 実装者は仕様どおり緑にした。仕様が要求したのは緑であって検出力ではなかったからである。

目標を**「落ちるべき条件」**に置き換えると、この3件は書く段階で不備が露見する。「どんな実装ミスでこれが落ちるか」を書けないテストは、書けない時点で欠陥だと分かる。

**ただし節名の変更だけでは型2〜5は防げない。** 実際、型1以外の5件のほうが被害は大きかった(日次フェーズが動かない、M0検証項目#5が実行不能、エポックが永久に処理されない)。規則2〜6が要るのはこのためである。

## 式と散文の突き合わせ(規則5)

**当てる対は3つである。**

| 対 | 例 |
| -- | -- |
| 規範文 ↔ 括弧内の理由 | 「同じ `entityId` に対して2度」と書きながら、理由は「同じ**組**を2度開くと」 |
| **式 ↔ その式が現れる節の散文** | 式は1回の外出しか立たないのに、同じ節の散文は「区画が2つあれば**2回行き**」「往復移動時間の**合計**が T を超える外出はしない」 |
| **式 ↔ 引用先の節の散文** | `q = 線形解の購入量(GDD02b §5.2)` と引きながら、§5.2 は「**耐久は耐久値で解き、`CeilDiv(購入量, N × 1000)` で個数に直す**」と書いている |

**規則3(引用する)を満たしても、この突き合わせは終わらない。** W2-10 の3件は**いずれも引用してあった**。引用先が何と書いているかを問うていなかった。

**この規則は2つの工程で当てる。** 一次はタスク仕様を書くフェーズ1(本書)だが、**W2-10 の3件のうち2件は上位文書の側で生まれている**(欠陥1 は `c5fc2da` = フェーズ1 の GDD 編集、欠陥3 は `7464ad8` = 設計セッション)。**GDD / TDD に式を書く束でも当てる** — そちらの射程は [06-design-sessions](06-design-sessions.md) 仕事2 が持つ。

### 実測(W2-10、[#98](https://github.com/stama72/visionary/issues/98))

**パイプラインが3回止まり、3回とも欠陥はフェーズ1 のタスク仕様にあった。実装側の欠陥は0件。** 3件とも「**誤った式の正確な実装**」で、コードを直しても直らない。

| 欠陥 | 式が生まれた場所 | 何が起きたか |
| ---- | ---------------- | ------------ |
| **1** 2回目の外出が構造的に不可能 | **フェーズ1 自身**(`c5fc2da`) | 旧形は「行った区画の品目を需要リストから外して繰り返す」で2回目が立っていた。**機構を増分へ差し替え**、減算側だけ `自区画 → 既に居る区画` へ移し、**候補側を `d の最安店` のまま残した** |
| **3** 工具の余剰が 13,000 倍 | 設計セッション(`7464ad8`) | 引用先の GDD02b §5.2 が当時から単位変換を書いていたまま写した。フェーズ1 は**この行を編集しながら**単位だけ相続した |
| 2 `Errand.Surplus` が `int`、積む先が `long` | タスク仕様の内部 | 上位文書は無関係。同一文書 §5.6 との矛盾 |

**欠陥2 は規則にしない。** 同一文書の中で矛盾しており**読めば矛盾する**([03-corrections](03-corrections.md) が4規則を落としたときの判定で象限III)。実際 implementer が最初の読みで止めている。

### なぜ検算では出ないか

**検算は「した」。** GDD が用意した計算例の検算値が実数演算で書かれていた誤り(余剰 43 → 44、38 → 39)は、フェーズ1 が見つけて直している。**しかし検算したのはその1例だけで、それは「1回の外出・1品目・必需」のケースだった。**

| 欠陥 | 計算例の外のどこか |
| ---- | ------------------ |
| 1 | 外出**2回目** |
| 2 | **大きい値** |
| 3 | **別の用途**(耐久) |

**上位文書のカバレッジの穴をそのまま相続し、穴の中で検算して「確かめた」と判断していた。** 散文を当てるのは、**検算例の外へ出るための最も安い手段**である — 散文は例より広い範囲を主張しているので、例の外の挙動をそこだけが書いている。

### 距離0 — 書き換えている式そのものの中に旧機構が残る

**欠陥1 の型は、既存のどの規約も持っていなかった。** 既存の3つは全部「**別の場所に残った残滓**」を対象にしている。

| 規約 | 対象 | 欠陥1 に当たるか |
| ---- | ---- | ---------------- |
| 規則8(上の「変えないと宣言する既存コード」) | 既存コード、別ファイル | × |
| [04-issue-driven](04-issue-driven.md) の追随表 | **設計 issue**、別の節・別分冊 | × #98 は impl issue |
| [03-corrections](03-corrections.md) 規則2(却下理由の空洞化) | 却下理由。同じ変更が前提を崩す | △ 型は同じだが、対象が散文の却下理由であり、かつ「直すとき」の書 |

**機構を差し替えたら、等式の全項を新機構で読み直す。** 片側だけ移すと、式は文法的に正しく、テストは緑になり、**旧機構でしか意味を持たない項が残る。** これに専用の規則(「差し替えたら全項を読み直す」)を置かないのは、**差し替えれば散文と式が食い違い、上の突き合わせを通せば露見する**ためである。

> **ただし、散文が式より先に書かれている場合に限る。** 欠陥1 で照合相手になった散文(「区画が2つあれば**2回行き**」)は、式より先に `7464ad8` で書かれていた。**散文と式を同時に新規で書く束では照合相手が無く、この突き合わせは空振りする。** そのとき距離0 の型は素通りするので、専用の規則を足す判断が要る。**いまは足していない** — 空振りの実例がまだ無いためである。

**なぜ気付けないか**: 1回目だけを見ると両形の結果は一致する(増分が負でも「価値 ≤ 0 なら行かない」に吸収される)。**表に出る形は「2回行く日が一度も観測されない」だけである。**

### 機械で守れるか

**不可。** 自然言語の散文と式の突き合わせであり、意味の問題である。**引用の有無だけは規則3 が持つ**(リンクの有無は機械で見られる)が、引用先が何と書いているかは見られない。**人依存の規則を1本ぶん太らせることを承知で広げている** — 規則の本数は8本のまま増やしていない。

## 呼び出し側を持たないコード(規則7)

**純関数へ切り出すほど、誤りは関数の中から呼び出し側へ移動する。** 式の正しさはテスト表が押さえるが、「その式をどう呼ぶか」には行が立ちにくい。パイプラインに繋がっていれば統合テストが偶然守ってくれる配線が、**呼び出し側を持たないタスクではどこからも踏まれない。**

**実測(W2-05)**: `BuyerDemand` は W2-05 では誰も呼ばない。4巡で計16件の指摘が出て、**そのすべてがテストの判別力・網羅度であり、実装バグは0件だった。** 最後まで10件が「仕様どおりに書かれているが誰も確かめていない経路」として残り、[#37](https://github.com/stama72/visionary/issues/37) へ渡った。

したがってテスト表(「この実装ミスで落ちる」)とは**別立てで**次を書く。

- **入力の作り方** — その関数に渡す値を、誰がどう組み立てるか
- **添字・並び・単位の約束** — 取り違えても例外が出ない種類の契約
- **呼び出し順** — 同じ tick 内で何の後に呼ばれるか

**呼び出し側を後続タスクへ預ける判断そのものは妥当でありうる。** W2-05 が「`TradeSystem` に繋ぐ」を却下したのは正しかった。ただし**その却下は配線から統合テストの保護を外す。** 却下を書くときは代償も見積もる([05-phase-sessions](05-phase-sessions.md) 引き継ぎメモ #1)。

## 変えないと宣言する既存コード(規則8)

**「含まない」に挙げた既存コードは、宣言した時点で現行の GDD/TDD に従っているとは限らない。** 上位文書を書き直した後の実装タスクでは、書き直し前のコードが「一世代前の仕様の正確な実装」として残る。それを「変えない」と書くと、読者(implementer・レビュアー・次のフェーズ1)は確認をやめる。

**実測(W2-08、[#101](https://github.com/stama72/visionary/issues/101))**: 仕様は「`OfferPrice.UpdatedAcquisitionCost` は残す。呼び出し側(`TradeSettlement`)が生きており、本タスクの利潤上限が摩耗費の材料として読む」と書いた。呼び出し側の条件は W2-06 当時の GDD02(生産の入力だけ)のままで、現行の GDD02a §5.1(生産の入力と耐久)と食い違っていた。**W2 では耐久の約定が構造的に起きないので、テストも実測も踏まない。** 利潤上限の摩耗費が工具価格に応答しないまま「機構の帰結」として実測に紛れ込むところだった。レビュアーが偶然 GDD02a §5.1 を読みに行ったので見つかった。

したがって「含まない」で既存コードを「変えない」と書くときは、**コードの規則ごとに、それが従う現行の節を添える**([docs/tasks/README.md](../tasks/README.md) のテンプレート「スコープ」):

| 変えないコード(規則の単位) | 従う節(現行版) | 確認 |
| --------------------------- | --------------- | ---- |
| `TradeSettlement.Execute` の移動平均の更新条件 | GDD02a §5.1 | 一致 / **不一致(本タスクで直す・#N へ)** / 未確認 |

- **「一致」と書けるのは、現行版の節を読んでコードと突き合わせたときだけである。** していないなら「未確認」と書く — 狭い側に倒す([03-corrections](03-corrections.md) 規則1)。「未確認」が並ぶ表は、レビュアーに「ここを見よ」と告げる表として正しく働く
- **単位はファイルではなく規則である。** `TradeSettlement` を「変えない」と書いても、その中の条件1つが古い。ファイル単位の宣言は、中の規則ごとの食い違いを隠す
- **後続タスクが全面的に書き換える予定のコードも表に載せる。** 「#98 が書き換える」は所有者の宣言であって一致の確認ではない。中間状態で動く旧規則が、その間の実測を何色に染めるかは書いておく(W2-08 は `StoreChoice` の「移動費を目標在庫で割り戻す」旧規則が残ることを明記した)
- **表の候補を出すのは機械が手伝える。** コードの doc コメントは GDD の節を引用している(`GDD02a §5.1` など)ので、`grep -rn "GDD02a §5" src/` で「その節に従うと自称するコード」が列挙できる。**ただし引用は古い節番号のまま残っていることがある**([#85](https://github.com/stama72/visionary/issues/85) は296件の引用の書き換えを後続へ送った)ので、列挙は候補であって網羅ではない。**実測(2026-09-20)**: #97 以前の `TradeSettlement` は旧節番号 `GDD02 §8.1.1` を引いており、現行の `GDD02a §5` で `git grep` しても掛からない — **#101 の当該ケースそのものが、現行節番号の grep では候補に出ない。** 節番号を振り直した差分では逆向きに引く — 「現行の文書に見出しとして存在しない節を引く doc コメント」を列挙する([#112](https://github.com/stama72/visionary/issues/112) 着手時点(2026-09-20)の実測で master の 27 ファイル・112 件、`TradeSettlement` を含む。#101 時点の 21 ファイル・146 件から #97 のマージで減った。手順は `scripts/check-doc-citations.sh`)

**この表の親は設計 issue 側の追随表である**([04-issue-driven](04-issue-driven.md)「上位文書を書き換える設計 issue」)。GDD を書き換えた設計 issue が「変えた規則 → 実装している既存コード → 引き取る impl issue」を持っていれば、実装タスクの表はそこから写すだけで済む。持っていなければ、実装タスクのフェーズ1 が自分で現行版と突き合わせる。

## 変異テスト

**「核心」と印を付けたテストについては、実際に変異を当てて落ちることを確認し、完了条件に含める。** 1タスクあたり2〜3件を想定する。

**仕様が変異を選ぶ。** 「核心」印には、当てる**変異の場所と内容、期待(赤 / 緑)**まで書く。「このテストは核心」とだけ書くと、選ぶ仕事が下流のどこかへ落ち、**測る者が自分で選ぶ**状態に戻る。

| 誰が | 何をする |
| ---- | -------- |
| フェーズ1(この文書) | **変異を選ぶ** — 場所・内容・期待 |
| [`mutator`](../../.claude/agents/mutator.md) | **使い捨て worktree で当てて測る。** 選ばない・書かない |
| フェーズ2 | `mutator` を起動し、結果を裁き、implementer に**転記させる** |
| implementer | テストを書く。**変異は当てない。** 渡された報告を doc コメントへ転記する |

**当てた変異と結果を、テストの doc コメントかコミットメッセージに残す。** 残さないと、レビュアーは機械の判定結果を渡されない(ADR-0004 帰結)ため確認手段が無く、この完了条件は自己申告のみになって形骸化する。他の完了条件(build / test / format)が機械の判定なのに対し、ここだけ性質が違う点に注意する。

**書けるのは、`mutator` の報告を出所とする記述だけである**([ADR-0013](../adr/0013-mutation-measurement-separated.md) 論点3)。実測の日付を添える。**「変異を当てて確認した」は読者に確認をやめさせる記述**であり、外れていても踏んだ人が気付けない([03-corrections](03-corrections.md) と同じ型)。

**実測(W2-08、[#110](https://github.com/stama72/visionary/issues/110))**: 変異を当てていたのはテストを書いた implementer 自身だった。1巡目の象限I-a 6件は**すべて「仕様が名指しした変異が実際には落ちない」**で、うち1件(PR #108 別表 A-1)は doc コメントに「変異を当てて確認した」と**書かれていた**。**実測の主張だけが残り、実測は行われていなかった。** 同じ回で、依頼していない変異が本体ツリーに残ったまま「`git diff --stat src/` は空」と報告されている。

**測るのはレビューの巡が閉じた後、一度でよい。** 途中で測ると、訂正でテストが変わったときに実測が古くなる — 上と同じ「主張だけが残る」形になる。測る対象はコミット済みの `HEAD` である。

印を付けないテストは「落ちる条件」を書くだけでよい。全テストに変異を当てるのは、レビュー帯域ではなく実装時間を消費するため採らない。**機械時間は安い**(2026-09-20 の実測: 使い捨て worktree のコールド 5 秒、変異1件あたり 3 秒 / 333 テスト)**が、変異を選ぶのは人の仕事である。**

## 仕様品質の先行指標

ADR-0004 は「レビュー往復が2回を超えたらモデルではなく仕様を疑う」としているが、W1-03 では**1往復目で既に仕様側が原因**だった。指標として遅い。

**仕様の穴の数 = 実装エージェントが「止まって報告した件数」+「決めて報告した件数」** を先行指標とする。往復が発生する前に穴の数が見える。

- 独断で決めた件数だけを数えると、新しい「止まる基準」が守られるほど定義上0に近づき、**仕様の穴ではなくルール違反の数**しか測らなくなる
- 記録場所は**タスクのPR説明**とする。凍結後のタスク仕様には書かない(仕様は使い捨てで、指標は後から振り返る対象のため)
- **PR を書くのは別フェーズなので、[引き継ぎメモ](05-phase-sessions.md)を経由する。** implementer の報告はフェーズ2 のセッションにしか無く、`/clear` で消える。件数を数字で書かせるのは implementer 憲章の責務にしてある
- **「決めて報告」を受け取ったら、契約に触るものが混じっていないか事後に仕分ける。** 混じっていたら「止まるべきだった」側へ数え直し、引き継ぎメモに残す。**合計は動かない**(両方を足しているため)が、数え直さないと **`IMPL-BLOCKED` が鳴らなかったことと、契約級の決定が開発者の目を通らなかったこと**が見えない
- W1-03 の実績は5件(いずれも新基準では「止まるべき」側だった)
- W2-05 の実績は4件(止まって0件・決めて4件)。うち1件、`BuyerBudget.DerivedDemand` の配列の添字規約は `BuyerDemand` との**契約そのもの**で、取り違えても例外が出ない。結果は妥当だったが、**止まるべきだった側**である

## 実装は必ず implementer が書く

**`docs/tasks/` に仕様があるものが実装タスクであり、その実装は必ず implementer が書く。**([ADR-0004](../adr/0004-ai-driven-development-workflow.md) 論点1)**レビュー指摘の修正も含む**のは [ADR-0009](../adr/0009-phase-scoped-sessions.md) 論点3 が足した一点である。

**書いた本人が実装すると、仕様に穴があっても自分の頭から埋めてしまい表面化しない。** W2-01 はこれを踏み、先行指標が1回分採れなかったうえ、仕様の穴がレビューまで持ち越された([#65](https://github.com/stama72/visionary/issues/65))。

## 実装エージェントが判断に出会ったとき

**影響範囲で線を引く。**

- **止まる**:タスクの外から参照される型・API・データモデルに触れる判断。W1-03 でいえば `DomainEvent` の形と `Knowledge` の構造(後者は M0 検証項目#5 が実行不能になるところまで波及した)
- **決めて報告してよい**:タスク内部に閉じた実装細部。W1-03 でいえば `LedgerEntry` の共用体の平坦化
