# プロセス 04 — issue 運用

| 項目 | 内容 |
| ---- | ---- |
| 種別 | 育てる文書(現行の運用を持つ) |
| 関連 | [ADR-0006](../adr/0006-issue-driven-task-management.md)(決定と理由) / [ADR-0004](../adr/0004-ai-driven-development-workflow.md) 論点2・3 |

**本書は「今どう運用しているか」を持つ。なぜそうしたかは [ADR-0006](../adr/0006-issue-driven-task-management.md) が持ち、本書は再説明しない。**

## 切り分け — 何をどこに書くか

| 器 | 持つもの | 持ってはいけないもの |
| -- | -------- | -------------------- |
| **issue** | 進行・スコープ・優先順位・依存関係・**未決事項**・**更新履歴** | 設計判断、実装の詳細仕様 |
| **ドキュメント**(ADR / GDD / TDD / process) | 設計と意思決定。「なぜ」と「今の仕様」 | 未決事項、進捗、更新履歴 |
| **タスク仕様書**(`docs/tasks/`) | 実装の要件。「どう作るか」 | 設計判断(ADR / TDD へ)、進捗(issue へ) |

**議論の過程をどちらに置くかは「そのコンテキストは捨てられるか」で割る**([ADR-0004](../adr/0004-ai-driven-development-workflow.md) 論点1 の基準)。却下した案とその理由が**次の判断の入力になる**ならドキュメント。ならないなら issue / PR のコメント。

### 機械で守る境界

> **`docs/` に「未決定事項」を節見出しとして置かない。**

CI で次の正規表現を検証する。**番号付き見出しを捕まえることと、行末で閉じることの両方が要る**:

```
^#{2,4} *[0-9.]* *未決[定]?事項 *$
```

- **番号付きを捕まえる。** 現に `## 7. 未決定事項`(GDD01)、`## 6. 未決定事項`(GDD03・GDD05)、`## 7. 未決定事項`(TDD01)があり、`## 未決定事項` だけを見る素朴な grep は**6件中4件を素通りする**
- **行末で閉じる。** そうしないと本節や「未決事項の扱い」という**規約側の見出し**まで落ちる

**`docs/adr/` は対象外とする。除外リストではなく、性質の違いによる。** ADR は凍る文書であり、その「未決定事項」節は**起案時点で決めなかったことのスナップショット**である。凍っているので増えない。溜まるのは育てる文書の側であり、規約が守りたいのはそちらである。**ADR の未決事項も中身は issue へ移すが、節そのものは当時の記録として残す**(本文を書き換えないという [ADR の運用ルール](../adr/README.md)に従う)。

`- [ ]` そのものは禁じない。**完了条件のチェックリストとしては正当**だからである:

| 用途 | 可否 | 例 |
| ---- | ---- | -- |
| **完了条件**(満たしたら閉じる) | 可 | タスク仕様の「完了条件」、ADR の「波及(反映先)」 |
| **未決事項**(いつ決めるか未定) | **不可** | 「係数の初期値確定」「腐敗を入れるか」 |

見分け方は「**これは今のタスクを閉じるための項目か、それとも将来の別の作業か**」。後者なら issue である。

## 階層 — 3層

| 層 | 器 | 例 |
| -- | -- | -- |
| **マイルストーン / 段階** | GitHub **Milestone**(期日を持つ) | `M0-W2`, `M0-W3`, `M1` |
| **関心事** | **親 issue** | 「W2: 仮経済の実装」「W2: シム実験」 |
| **タスク** | **sub-issue** = 1タスク = 1タスク仕様書 = 1 PR | 「生産・消費システムを実装する」 |

**M0〜M4 の定義と Exit Criteria は [企画書 §6](../02-project-proposal.md) が持つ。** Milestone はそれに期日と進捗を与えるだけで、定義を複製しない。

**「W」は週ではなく段階である**([TDD01 §5.4](../04-tdd/01-sim-core-and-m0.md))。呼称は W1 起案時のまま残っているが、1つの段階が1週に収まる保証はない。期日は Milestone 側が持つ。

## ラベル

### 型(必ず1つ)

| ラベル | 内容 | 終わり方 |
| ------ | ---- | -------- |
| `type:design` | 設計のみ。文書を書いて終わる | 文書がマージされる |
| `type:impl` | 実装。タスク仕様書 → 実装 → レビュー | PR がマージされる |
| `type:experiment` | シム実験。条件を振り、判定関数で判定する | `summary.json` と判定が出る |
| `type:playtest` | テストプレイ | 所感メモが残る |
| `type:process` | 開発手法の改善 | 運用が `docs/process/` と `.claude/` に反映される |
| `type:marketing` | 市場調査・発信・ストア | 成果物か判断が残る |
| `type:risk` | リスク。監視対象 | **解消したか、顕在化して別 issue になったとき** |

### 優先順位(必ず1つ)

| ラベル | 意味 |
| ------ | ---- |
| `P0` | **今のマイルストーンのゲートを塞いでいる。** これが動かないと先の全てが無意味になる |
| `P1` | 今のマイルストーンに要る |
| `P2` | 先送り可。backlog |

**優先順位はラベルが正とする。** GitHub Projects を使う場合も、Projects 側のフィールドではなくラベルを見る — Projects を後で捨てても優先順位が失われないようにするため。

### 補助

| ラベル | 意味 |
| ------ | ---- |
| `needs-decision` | **開発者の判断待ち。** レビュー帯域をどこに割り当てるかは、まずこのラベルの一覧で決める |
| `blocked` | 依存待ち。本文に何を待っているかを書く |

## issue の書き方

**肥大化を止める規則を3つ置く。** 文書で起きたことは issue でも起きる([ADR-0006](../adr/0006-issue-driven-task-management.md) 帰結)。

1. **本文は箇条書き15行以内。** 設計はドキュメントへリンクする。issue に設計を書き始めたら、それは GDD / TDD / ADR に書くべき内容である
2. **閉じる条件を1行で書けないものは issue にしない。** 書けないなら、まだタスクではなく関心事である(親 issue にするか、分割する)
3. **テンプレートは2種だけに保つ。** `task`(型を選ぶ)と `decision`(判断待ち)。型ごとにテンプレートを増やさない

## 未決事項の扱い

未決事項を持つのは issue だけである。ただし**文書に書かれている `- [ ]` がすべて未決事項とは限らない**。移す前に4種へ仕分ける([ADR-0006](../adr/0006-issue-driven-task-management.md) 論点2):

| 種別 | 見分け方 | 行き先 |
| ---- | -------- | ------ |
| **値・閾値の初期値** | 構造は決まっていて、数値だけが調整対象 | **文書に残す。**`- [ ]` をやめ「調整軸」の表に書き換える |
| **他分冊へのルーティング** | 「→ 分冊06」のように所在を述べているだけ | **文書に残す。** リンク1文にする |
| **疑い(実データ待ちの予測)** | 「〜しうる」。観測する実験が既に決まっている | **その実験 issue の受入条件**へ畳み込む |
| **決定待ち・拡張案** | 上の3つに当てはまらない | **issue**(`decision` テンプレート) |

CLAUDE.md が「数値(閾値・係数)は初期値であり調整対象。固定すべきは構造と依存関係」と決めている以上、**1種目は未決事項ではない。** チェックボックスという文法が誤っているだけである。

## WIP

**開発者の判断を要するタスクの WIP = 1**([ADR-0006](../adr/0006-issue-driven-task-management.md) 論点4)。

| タスク | 上限 | 根拠 |
| ------ | ---- | ---- |
| 設計・ADR・ゲームデザイン(`type:design`) | **1** | 判断を全工程で食う。途中経過が成果物であり、並行すると保持すべき文脈が増える |
| 仕様が凍結済みの実装(`type:impl`) | **2** | 判断を末尾でだけ食う。前段はレビュアーエージェントが吸う |
| その他(`type:process` / `type:marketing`) | 別コンテキストなので上限に数えない | |

- **「仕様が凍結済み」とは、タスク仕様書がマージされ、実装エージェントに渡せる状態を指す。** 仕様を書いている最中は `type:design` として数える
- レビューが難航した、または前提として別タスクが必要だと判明したときは、**承認せずに凍結してよい**(ADR-0004 論点3)。凍結は issue を閉じずに `blocked` を付け、待っている issue を本文に書く
- **上限2は仮説である。** 「2本目が『レビュー中』のまま1週間を超えるか」で検証し、超えたら1へ戻す

## ライフサイクル

1. **立てる** — 型と優先順位を必ず付け、閉じる条件を1行で書く。**Milestone は P0 / P1 に付ける。P2(backlog)は付けなくてよい** — いつ着手するかが決まっていないことが P2 の意味だからである
2. **着手する** — Assignee を付け、ブランチを切る。ブランチ名は issue 番号を含める(`feat/12-production-system`)
3. **進める** — 進捗・判断・詰まりは**issue のコメント**に書く。文書側には書かない
4. **PR を出す** — 本文に `Closes #12` を書く。レビュアーエージェントを通してから開発者のレビューへ([01-review.md](01-review.md))
5. **閉じる** — PR のマージで自動的に閉じる。閉じる条件を満たしていない場合は閉じず、残りを sub-issue に割る

**完了したタスクの履歴は issue と PR に残る。** 文書側に完了報告を書かない。

## issue にしないもの

- **値・閾値の調整**(上記の仕分け1種目)
- **1つのコミットで終わる誤字・リンク切れの修正。** 見つけたその場で直す
- **まだ関心事の域を出ないもの。** 閉じる条件が書けないなら、親 issue として立てるか、`decision` として「何を決めるか」だけを書く
