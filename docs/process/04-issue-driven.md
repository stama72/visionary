# プロセス 04 — issue 運用

| 項目 | 内容 |
| ---- | ---- |
| 種別 | 育てる文書(現行の運用を持つ) |
| 関連 | [ADR-0006](../adr/0006-issue-driven-task-management.md)(決定と理由) / [ADR-0004](../adr/0004-ai-driven-development-workflow.md) 論点2・3 |

**本書は「今どう運用しているか」を持つ。なぜそうしたかは [ADR-0006](../adr/0006-issue-driven-task-management.md) が持ち、本書は再説明しない。**

## 切り分け — 何をどこに書くか

| 器 | 持つもの | 持ってはいけないもの |
| -- | -------- | -------------------- |
| **issue** | 進行・スコープ・優先順位・依存関係・**未決事項**・**更新履歴** | 設計判断、実装の詳細仕様 |
| **ドキュメント**(ADR / GDD / TDD / process) | 設計と意思決定。「なぜ」と「今の仕様」 | 未決事項、進捗、更新履歴 |
| **タスク仕様書**(`docs/tasks/`) | 実装の要件。「どう作るか」 | 設計判断(ADR / TDD へ)、進捗(issue へ) |

**議論の過程をどちらに置くかは「そのコンテキストは捨てられるか」で割る**([ADR-0004](../adr/0004-ai-driven-development-workflow.md) 論点1 の基準)。却下した案とその理由が**次の判断の入力になる**ならドキュメント。ならないなら issue / PR のコメント。

### 機械で守る境界

> **`docs/` に「未決定事項」を節見出しとして置かない。**

CI で次の正規表現を検証する。**番号付き見出しを捕まえることと、行末で閉じることの両方が要る**:

```
^#{2,4} *[0-9.]* *未決[定]?事項 *$
```

- **番号付きを捕まえる。** 現に `## 7. 未決定事項`(GDD01)、`## 6. 未決定事項`(GDD03・GDD05)、`## 7. 未決定事項`(TDD01)があり、`## 未決定事項` だけを見る素朴な grep は**6件中4件を素通りする**
- **行末で閉じる。** そうしないと本節や「未決事項の扱い」という**規約側の見出し**まで落ちる

**`docs/adr/` は対象外とする。除外リストではなく、性質の違いによる。** ADR は凍る文書であり、その「未決定事項」節は**起案時点で決めなかったことのスナップショット**である。凍っているので増えない。溜まるのは育てる文書の側であり、規約が守りたいのはそちらである。**ADR の未決事項も中身は issue へ移すが、節そのものは当時の記録として残す**(本文を書き換えないという [ADR の運用ルール](../adr/README.md)に従う)。

`- [ ]` そのものは禁じない。**完了条件のチェックリストとしては正当**だからである:

| 用途 | 可否 | 例 |
| ---- | ---- | -- |
| **完了条件**(満たしたら閉じる) | 可 | タスク仕様の「完了条件」、ADR の「波及(反映先)」 |
| **未決事項**(いつ決めるか未定) | **不可** | 「係数の初期値確定」「腐敗を入れるか」 |

見分け方は「**これは今のタスクを閉じるための項目か、それとも将来の別の作業か**」。後者なら issue である。

## 階層 — 3層

| 層 | 器 | 例 |
| -- | -- | -- |
| **マイルストーン / 段階** | GitHub **Milestone**(期日を持つ) | `M0-W2`, `M0-W3`, `M1` |
| **関心事** | **親 issue** | 「W2: 仮経済の実装」「W2: シム実験」 |
| **タスク** | **sub-issue** = 1タスク = 1タスク仕様書 = 1 PR | 「生産・消費システムを実装する」 |

**M0〜M4 の定義と Exit Criteria は [企画書 §6](../02-project-proposal.md) が持つ。** Milestone はそれに期日と進捗を与えるだけで、定義を複製しない。

**「W」は週ではなく段階である**([TDD01 §5.4](../04-tdd/01-sim-core-and-m0.md))。呼称は W1 起案時のまま残っているが、1つの段階が1週に収まる保証はない。期日は Milestone 側が持つ。

## ラベル

### 型(必ず1つ)

| ラベル | 内容 | 終わり方 |
| ------ | ---- | -------- |
| `type:design` | 設計のみ。文書を書いて終わる | 文書がマージされる |
| `type:impl` | 実装。タスク仕様書 → 実装 → レビュー | PR がマージされる |
| `type:experiment` | シム実験。条件を振り、判定関数で判定する | `summary.json` と判定が出る |
| `type:playtest` | テストプレイ | 所感メモが残る |
| `type:process` | 開発手法の改善 | 運用が `docs/process/` と `.claude/` に反映される |
| `type:marketing` | 市場調査・発信・ストア | 成果物か判断が残る |
| `type:risk` | リスク。監視対象 | **解消したか、顕在化して別 issue になったとき** |

### 優先順位(必ず1つ)

| ラベル | 意味 |
| ------ | ---- |
| `P0` | **今のマイルストーンのゲートを塞いでいる。** これが動かないと先の全てが無意味になる |
| `P1` | 今のマイルストーンに要る |
| `P2` | 先送り可。backlog |

**優先順位はラベルが正とする。** GitHub Projects を使う場合も、Projects 側のフィールドではなくラベルを見る — Projects を後で捨てても優先順位が失われないようにするため。

### 補助

| ラベル | 意味 |
| ------ | ---- |
| `needs-decision` | **開発者の判断待ち。** 付けるのは判断が要ることの表明だけであり、優先順位は `P*` が持つ |
| `blocked` | 依存待ち。本文に何を待っているかを書く |

**レビュー帯域の割り当て先は、ラベル単体ではなくクエリで出す。**

```
label:needs-decision label:P0,P1 -label:blocked
```

`needs-decision` の一覧そのものを見ると、**バックログで埋まって用途をなさない** — 導入初日の時点で6件中5件が P2、うち2件が `blocked` だった([issue #17](https://github.com/stama72/visionary/issues/17))。判断待ちであることと、**いま**判断する価値があることは別である。`P2` と `blocked` を落として初めて「今あなたが決めるべきもの」になる。

## issue の書き方

**肥大化を止める規則を3つ置く。** 文書で起きたことは issue でも起きる([ADR-0006](../adr/0006-issue-driven-task-management.md) 帰結)。

1. **本文は箇条書き15行以内。** 設計はドキュメントへリンクする。issue に設計を書き始めたら、それは GDD / TDD / ADR に書くべき内容である
2. **閉じる条件を1行で書けないものは issue にしない。** 書けないなら、まだタスクではなく関心事である(親 issue にするか、分割する)
3. **テンプレートは2種だけに保つ。** `task` と `decision`。型ごとにテンプレートを増やさない
4. **型は `type:*` ラベルだけが正。本文に書かない。** GitHub Issue Form の dropdown はラベルを付けないので、本文で型を聞くと**ラベルと本文の2か所に入って食い違う**([issue #16](https://github.com/stama72/visionary/issues/16))。テンプレートは型を聞かず、作成後にラベルを1つ付ける
5. **優先順位は `P2` が自動で付く。** 上げるのは `P0` / `P1` への付け替えという明示的な判断にする。既定を空にすると「付け忘れ」と「P2 と判断した」が区別できない
6. **空の issue は塞ぐ**(`blank_issues_enabled: false`)。閉じる条件とスコープを素通りさせないため

**型の自動付与は採らなかった。** dropdown の回答をラベルへ写す workflow を挟めば自動化できるが、**静かに壊れる機械を1つ増やす**ことになる(緑のまま効かなくなっても誰も気付かない)。2種に保つ以上、型は手で付ける。

## 上位文書を書き換える設計 issue

**GDD / TDD の規則を書き換える `type:design` の issue は、閉じる条件に「追随表」を含める。** 追随表は「変えた規則 → それを実装している既存コード → 引き取る impl issue」の3列で、issue の本文かコメントに置く(文書には置かない。進行の器は issue である)。

**docs 直下(コンセプトシート・企画書・世界観設定書)の規則を書き換える issue も同じ形で、向きが一段上がる** — 「変えた規則 → 追随する GDD / TDD の節 → 引き取る design issue」。[#68](https://github.com/stama72/visionary/issues/68) の ADR-0011「領主 → 市参事会」が最初の適用例で、波及節が「別 issue」とだけ書いた時点では GDD01 / 02 / 09 の「領主」16 箇所に引き取る issue が無かった。層の表は [06-design-sessions](06-design-sessions.md)。

| 変えた規則(現行版の節) | 実装している既存コード | 引き取る issue |
| ------------------------ | ---------------------- | -------------- |
| GDD02a §5.1 移動平均の更新対象に耐久を足す | `TradeSettlement.Execute` の更新条件 | [#97](https://github.com/stama72/visionary/issues/97) |

- **書くのは設計 issue を閉じる側である。** 何を変えたかを知っているのは書き換えた本人だけで、後続の impl issue のフェーズ1 は「変わった」こと自体を履歴を引かないと知れない。**書き換え前のコードは「一世代前の仕様の正確な実装」として残り、現行版だけを読むと正しく見える。** [#85](https://github.com/stama72/visionary/issues/85) は20件の決定と「W2-04〜06 の実装は全面的に仕様が変わる」という申し送りを持っていたが、粒度がファイルで、`TradeSettlement` の条件1つが漏れた([#101](https://github.com/stama72/visionary/issues/101))
- **単位は規則である。ファイルではない。** 1ファイルの中で1条件だけが反転していることがある
- **反転・削除・追加を全部載せる。** 「追加」は実装が無いので漏れにくい。「削除」は消えるべきコードが残る型([#97](https://github.com/stama72/visionary/issues/97) が `OfferPrice.UnitCost` を消したのがこれ)。**「反転」が最も見えにくい** — 現行版を読む限り正しい
- **引き取る issue が無い行は、その場で issue を立てるか、既存 issue の本文に足す。** 行き先の無い規則は誰も実装しない。#85 では 02a §5 の利潤の計測がこれで、#41 の本文に無いまま W2-08 の仕様が「#41 が書く」と書いていた
- **機械で守れない。** 規則とコードの対応は意味の問題である。手伝えるのは候補の列挙までで、向きが2つある([02-task-spec](02-task-spec.md) 規則8)。**順向き**: コードの doc コメントは節を引用しているので `grep -rn "GDD02a §5" src/` で「その節に従うと自称するコード」が出る。#85 型の書き換え(節番号の振り直しを伴う)では引用が古く、この向きは弱い(現行節番号では `TradeSettlement` が 0 件)。**逆向き**: 「現行の文書に存在しない節を引く doc コメント」を引く。振り直しのときこそ強く、実測(2026-09-20、master)では 21 ファイル・146 件が出て `TradeSettlement` も含まれた。代償は旧引用が残っている間の雑音で、その 21 ファイルは「#85 以前のコード」の一覧そのものでもある。**どちらの向きも候補であって一致の判定ではない。** 書き換えた側が、候補ごとに「現行の規則に従っているか」を読む

**この追随表が、実装タスクの「変えない既存コード」表([02-task-spec](02-task-spec.md) 規則8)の親である。** 親があれば子は写すだけで済む。無ければ、実装タスクのフェーズ1 が自分で現行版と突き合わせる。

## 未決事項の扱い

未決事項を持つのは issue だけである。ただし**文書に書かれている `- [ ]` がすべて未決事項とは限らない**。移す前に4種へ仕分ける([ADR-0006](../adr/0006-issue-driven-task-management.md) 論点2):

| 種別 | 見分け方 | 行き先 |
| ---- | -------- | ------ |
| **値・閾値の初期値** | 構造は決まっていて、数値だけが調整対象 | **文書に残す。**`- [ ]` をやめ「調整軸」の表に書き換える |
| **他分冊へのルーティング** | 「→ 分冊06」のように所在を述べているだけ | **文書に残す。** リンク1文にする |
| **疑い(実データ待ちの予測)** | 「〜しうる」。観測する実験が既に決まっている | **その実験 issue の受入条件**へ畳み込む |
| **決定待ち・拡張案** | 上の3つに当てはまらない | **issue**(`decision` テンプレート) |

CLAUDE.md が「数値(閾値・係数)は初期値であり調整対象。固定すべきは構造と依存関係」と決めている以上、**1種目は未決事項ではない。** チェックボックスという文法が誤っているだけである。

## WIP

**開発者の判断を要するタスクの WIP = 1**([ADR-0006](../adr/0006-issue-driven-task-management.md) 論点4)。

| タスク | 上限 | 根拠 |
| ------ | ---- | ---- |
| 設計・ADR・ゲームデザイン(`type:design`) | **1** | 判断を全工程で食う。途中経過が成果物であり、並行すると保持すべき文脈が増える |
| 仕様が凍結済みの実装(`type:impl`) | **2** | 判断を末尾でだけ食う。前段はレビュアーエージェントが吸う([ADR-0008](../adr/0008-review-scope-narrowed-to-unnoticeable-defects.md) 後も実装工程ではレビュアーを使う) |
| その他(`type:process` / `type:marketing`) | **数えない(暫定)** | 根拠は「別コンテキストだから」**ではない**。`type:process` も設計タスクであり([06](06-design-sessions.md))、[#104](https://github.com/stama72/visionary/issues/104) 自身が判断を全工程で食った。**食うかは型では決まらず**、同じ `type:process` でもパイプラインのスクリプト修正は食わない。**枠(トークン)の側は下の「枠」が見る。注意の側の上限は未実測** |

- **「仕様が凍結済み」とは、タスク仕様書がマージされ、実装エージェントに渡せる状態を指す。** 仕様を書いている最中は `type:design` として数える
- レビューが難航した、または前提として別タスクが必要だと判明したときは、**承認せずに凍結してよい**(ADR-0004 論点3)。凍結は issue を閉じずに `blocked` を付け、待っている issue を本文に書く
- **上限2は仮説である。** 「2本目が『レビュー中』のまま1週間を超えるか」で検証し、超えたら1へ戻す
- **上限の軸は「開発者の判断を全工程で食うか」であって、型ラベルではない**(ADR-0006 論点4)。表が型で書かれているのは数えやすさのためで、`type:process` の免除はその近似が崩れている箇所である。**枠(トークン)の制約は注意の制約とは別の原因なので、WIP に負わせない** — 枠は下の「枠」が持つ

## 枠

**5 時間枠(トークン)の制約は、WIP(注意)とは別の制約である。** 枠は「同時に走る本数」ではなく「走っているものの API 等価コストの合計」で減る([#122](https://github.com/stama72/visionary/issues/122) 決定 1)。ただし **$ あたりの重みはモデルで違う**(決定 3)。2026-09-19〜20 の Max 期 5 枠を、**枠頭(リセット直後 = 0%)からの累積**で解いた実測が下である。

| モデル | 枠の 100% に相当する API $ | 確からしさ |
| --- | ---: | --- |
| **fable** | **$51** | leave-one-out の範囲 $39〜72 |
| **opus** | **$200** | LOO の範囲 $133〜322 |
| **sonnet** | **$658** | **「opus より 3 倍ほど軽い」以上の精度は無い**(opus との共線性で LOO の幅が $135〜654 と大きい) |

**fable は opus の約 4 倍、sonnet の約 13 倍重い。** 100% が $145〜377 に見えていたのは、枠ごとのモデル構成が違ったためである(全体で R² = 0.988)。

1. **着手前に 5 時間枠の残りを見る。** 走っているものと着手するものの見込み(下表)の合計が残りを超えるなら着手しない
2. **パイプラインは残り 40% 未満なら起動しない。読むのは `pipeline.ps1` 自身で、足りなければ起動を拒否する**(終了コード 4。読めなかったときも拒否する)。途中で枠が切れたパイプラインはその場で死に、使った分が消える(#36 で $16、#37 で $30)。**`-From wrap` の再開だけは 10%** — フェーズ3 単独は枠の 0.2% しか使わず(実測 $1.07〜1.41 / 2〜5 分)、しかもここは**枠切れで死んだ後の再開路**である。**リセットまで 1 時間を切っていれば要求はさらに下がる** — 枠切れは「消費が残りに達する前にリセットが来るか」で決まり、リセットまで T 分ならこの枠で使うのは高々 `0.64 %/分 × T` だからである。閾値は `-MinRemaining` で変えられ、`0` は検査しない。**この数値と `scripts/pipeline.ps1` の既定が一致しているかは機械が見ていない**([#139](https://github.com/stama72/visionary/issues/139))
3. **基本形は「パイプライン 1 本 + fable 以外の対話セッション 1 本」で、この範囲は 1 の計算を省く。** fable の対話は 1 本で枠の 29〜103% を食うので、免除の外に置く([#122](https://github.com/stama72/visionary/issues/122) 決定 2 の打ち手。発火条件は決定 3 の実測で満たされた)。**fable の対話と並行してパイプラインを起動するときは、規則1 の計算をする** — 残りを読むのは haiku 1 呼び出しで、枠の 0.05% しか使わない。4 枠目が切れたら基本形をさらに狭める
4. **型ラベルは見ない。** WIP 表の `type:process` の免除は、枠には無い

| 走らせるもの | 見込み(枠の %) | 根拠(2026-09-19〜20、Max) |
| --- | ---: | --- |
| **設計・process(fable)** | **29〜103** | 3 本、$15〜53。**活動 1 時間あたり 16〜22** |
| **実装のフェーズ1(fable)** | **41** | 1 本、$21 |
| 実装のパイプライン(フェーズ2・3) | **6〜28**(中央値 14) | 7 走行、$20〜104。**implementer が sonnet なので $ の割に軽い** |
| 実装のフェーズ1(opus) | 3〜21 | 8 本、$6〜42 |
| 設計・process(opus) | 4〜8 | 3 本、$7〜16 |
| アドバイザー 1 巡(**対話での実測**) | fable 4〜11 / opus 1 | 8 本、$2〜6。**サブエージェント化後([#105](https://github.com/stama72/visionary/issues/105))は未実測** — 起動時の約 60K を払わないぶん下がるはずだが、測っていない |

**枠を食う順は「fable の対話 > パイプライン」である。** 9/20 に 5 時間枠を 3 時間で焼いたとき、並行 4 本のうち最大の消費者はパイプラインではなく fable の対話セッションだった。**レートも見込みも `python scripts/usage-rates.py` で測り直せる**(セッション別は `--sessions`)。数値は [#123](https://github.com/stama72/visionary/issues/123) の確認で動かす。**破ったことは「枠切れの回数」と「途中で死んだパイプラインの $」に出る。**

## ライフサイクル

1. **立てる** — 型と優先順位を必ず付け、閉じる条件を1行で書く。**Milestone は P0 / P1 に付ける。P2(backlog)は付けなくてよい** — いつ着手するかが決まっていないことが P2 の意味だからである
2. **着手する** — Assignee を付け、ブランチを切る。ブランチ名は issue 番号を含める(`feat/12-production-system`)
3. **進める** — 進捗・判断・詰まりは**issue のコメント**に書く。文書側には書かない
4. **PR を出す** — 本文に `Closes #12` を書く。**実装(`type:impl`)ならレビュアーエージェントを通してから**開発者のレビューへ。設計・プロセスなら開発者のレビューへ直接([01-review.md](01-review.md))
5. **閉じる** — PR のマージで自動的に閉じる。閉じる条件を満たしていない場合は閉じず、残りを sub-issue に割る

**完了したタスクの履歴は issue と PR に残る。** 文書側に完了報告を書かない。

## issue にしないもの

- **値・閾値の調整**(上記の仕分け1種目)
- **1つのコミットで終わる誤字・リンク切れの修正。** 見つけたその場で直す
- **まだ関心事の域を出ないもの。** 閉じる条件が書けないなら、親 issue として立てるか、`decision` として「何を決めるか」だけを書く
