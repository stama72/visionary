**指摘を受けて直すときの規則。** [02-task-spec.md](02-task-spec.md) が「最初に書くとき」の規則を持つのに対し、本書は「**直すとき**」の規則を持つ。

**規則は2つだけである。** どちらも「気付けない × 影響大」に当たる([ADR-0008](../adr/0008-review-scope-narrowed-to-unnoticeable-defects.md) 論点2)。訂正の失敗はほかにも起きるが、**残りは踏んだ人がその場で直せる**ので規約にしない([01-review.md](01-review.md)「気付いたら直す」)。

## 規則1 — 行き過ぎない。迷ったら狭い側に倒す

**訂正は実態まで戻す。広げすぎない。**

W1-04 で、「機械が守る範囲」の一覧が**実態より狭い**という疑いに対応した結果、**広げすぎて実態に無い保証を主張した**。同じ PR 内のテストが「素通りする」と明記している性質を、「機械化できた」側に置いていた。

**狭い誤りと広い誤りは、危険度が対称ではない。**

| 誤りの向き | 何が起きるか |
| ---------- | ------------ |
| 狭い(守れる範囲を小さく書く) | 委譲判断が過度に保守的になる。人が余分に見る |
| **広い**(守れない範囲を守れると書く) | **「テストが守っているから見なくてよい」と読ませる。誰も見なくなる** |

[ADR-0004](../adr/0004-ai-driven-development-workflow.md) が「サブエージェントに委ねられる範囲は機械的ガードの範囲に依存する」としている以上、この種の一覧は**委譲判断の入力**である。広い誤りは読者に確認をやめさせるので、**踏んでも気付けない。**

> **「機械化できた」と書く前に、実際に壊して落ちることを確かめる。** W1-04 の件は、`enum` を `long` 幅で・`Tick` を `int` 幅で書く実装に変えてもテストが全て緑のままであることを実測して初めて確定した。書いた時点では確かめていなかった。

同じ形は「型で不可能にする」「CI が止める」「アナライザが捕まえる」にも現れる。**主語が機械である保証は、全部この規則の対象である。**

### 壊すのは、運用者が実際に打つ入口から

**式が正しくても、配線が無ければ何も守っていない。**

[ADR-0010](../adr/0010-phase-pipeline-and-halt-conditions.md) の停止則 `SPEC-OUTSIDE` で踏んだ。文書3本を「これだけは機械も見ている」に書き換えた `1e9970f` は、`scripts/pipeline.ps1` を変更していなかった。**検証は本物だった** — 捨てコミットを作り、`src/` だけなら検出されず `docs/03-gdd/` なら検出されることを確かめている。確かめた対象が `git diff --name-only ...` という**式**であって、運用者が打つ `pwsh scripts/pipeline.ps1` という**入口**ではなかった。

この形が規則1 の中でとくに危ないのは、**検証ログが本物であるぶん、読み返しても穴が見えない**ことである。「壊して落ちることを確かめた」という記述に嘘は無い。

> **壊すのは、運用者が実際に打つコマンドからにする。** 内側の式を直接叩いた結果は、配線が通っている証拠にならない。

**そのために、高価な呼び出しだけを差し替えて配線を全部通す経路を用意する。** `pipeline.ps1` の `-DryRun` がこれにあたり、`claude` の起動だけを作り物に差し替えて、進捗表示・合図の読み取り・`SPEC-OUTSIDE` の検査は本番と同じ関数を通る。**用意しておくと、この規則が人の記憶ではなく実行可能物になる** — 後から誰でも、何度でも、入口から壊せる。

経路を作ったら**そこも壊しておく。** `-DryRun` 自体が新しい判定を素通りしていれば、通ったことは何の保証にもならない(実際 `56c376c` の時点で一度素通りしていた)。

## 規則2 — 却下理由の前提が崩れていないか確認する

**同じ変更の中で、自分が却下理由を反証していることがある。**

W1-04 で「汎用のフィールド単位凍結は `record struct` の位置引数と `init` プロパティが混在し誤検出が多くなるため採らない」と書いた。**その混在を一様に数えて成立するコードを、後の巡の訂正で自分が追加していた。** 却下理由は1巡目の訂正(`67eff46`)で書き、それを反証する `CountInstanceFields` は2巡目の訂正(`6e951bc`)で入った。

**これが「最初に書くとき」ではなく「直すとき」の規則である理由**: 執筆時に成り立っていた理由が、訂正で崩れた。

前提だけ崩れて理由が空白になると、再検討する人が**「無理だと結論が出ている」と読んで取り逃がす。** 却下理由そのものは残るので、**読んでも気付けない。**

[ADR の運用ルール](../adr/README.md)は「却下理由の前提が崩れたら、代替の却下理由を註記する」を**ADR について**定めている。**同じことが育てる文書と使い捨て文書にも要る。**

## 規約にしないもの

W1-04 のレビューは5巡を要し、2巡目以降の指摘のうち**8件は訂正が原因**だった。かつて本書はその8件から6つの規則を導いていたが、[ADR-0008](../adr/0008-review-scope-narrowed-to-unnoticeable-defects.md) の分類で**4つを落とした。**

| 落とした規則 | 落とした理由 |
| ------------ | ------------ |
| 訂正は上書きで行う(註記で足すのは ADR だけ) | 註記と本文が食い違えば**読めば気付く**。象限III |
| 訂正前の語で `grep` して残存を確認する | 取り残した N か所目は**読めば矛盾する**。象限III |
| 下流に注記を足す前に発生源を直す | 発生源が残ると同じ指摘が再生産されるが、**1件あたりは小さい**。象限IV |
| 派生する記述(件数・チェックリスト)を洗い出す | 件数のズレは**数えれば分かる**。象限III |

**これらが「守れば防げた」ことは事実である。だが守らせるコストのほうが、踏んだときに直すコストより大きかった。** 本書は 16,743字あり、そのうち「気付けない × 影響大」を守っていたのは上の2規則だけだった。**規約に書いても同型の失敗は繰り返し起きており、それは規約で防げるものではない。**

落とした4つに当たる不具合を見つけたら、**その場で直す。** issue にも別 PR にもしない([01-review.md](01-review.md))。

## 機械で守れるか

CLAUDE.md「新しい規約を作るときは『これは機械で守れるか』を必ず問う」に従う。

**規則1・2 とも不可。** いずれも意味の問題である。

- 規則1 は「その保証が実態と合っているか」であり、実態を知るには**壊して落ちるかを実測する**しかない。何を壊せばよいかは保証の内容ごとに違う
  - **ただし「入口から壊す」は、入口の側を用意できる。** `-DryRun` のような経路があれば、壊す手順そのものが実行可能物になる。**用意することは機械に守らせられないが、用意してあれば次からは安い** — 規則の中で唯一、道具で薄くできる部分である
- 規則2 は「却下理由の前提が、この変更のどこかに反証されていないか」であり、前提と反証は自然言語と実装コードにまたがる

**したがって本書の規則は全件が人依存である。** これを承知で残しているのは、**2件とも「書いた本人には構造上見えない」型**だからである([ADR-0005](../adr/0005-reviewer-scope-includes-spec-defects.md))。とくに規則1 は「もう見なくてよい」と読ませるので、書いた本人が最も見落とす。

W1-04 の8件も、**8件中7件はレビュアーが見つけた**(自己点検で捕まえたのは `8d88a8e` の1件だけ)。自己点検には委ねられない。

## 憲章との関係

規則1・2 はどちらも象限I-b の4類型に含まれる:

- 規則1 → **広い保証**
- 規則2 → **却下理由の空洞化**

**ただし本書の規則は設計セッションが守るためのものであり、レビュアーが見つけるのは二次防衛線である。** レビュアーが見つける限り巡は増える。
