**指摘を受けて直すときの作法。** [02-task-spec.md](02-task-spec.md) が「最初に書くとき」の規則を持つのに対し、本書は「**直すとき**」の規則を持つ。

W1-04 のレビューが5巡を要した。**巡を重ねた原因は指摘の質ではなく、訂正の質だった。**

| 巡 | 指摘 | うち「訂正が不完全・過剰」 |
| -- | ---- | -------------------------- |
| 1  | 7件 + 疑い3件 | 0件(すべて実質的な欠陥) |

## 規則

| #  | 規則                                                                                                                    | 機械化の余地 |
| -- | ----------------------------------------------------------------------------------------------------------------------- | ------------ |
| 1  | **訂正は上書きで行う。註記で足してよいのは凍る文書(ADR)だけ。** 育てる文書と使い捨て文書は本文を直す                | 不可         |
| 2  | **訂正の前に、同じ主張が何か所にあるかを数える。** 訂正後、**訂正前の語で grep して0件を確認する**                       | **可**       |
| 3  | **下流に注記を足す前に、発生源を直す。** 下流にだけ注記を足すと、発生源から次の下流が生まれる                            | 不可         |
| 4  | **派生する記述を洗い出す。** 件数・一覧・チェックリストは他の記述から派生している。元を変えたら派生も変える              | 一部可       |
| 5  | **訂正は実態まで戻す。行き過ぎない。迷ったら狭い側に倒す**                                                              | 不可         |
| 6  | **却下理由の前提が崩れていないか確認する。** 同じ変更で自分が反証していることがある                                      | 不可         |

### 規則1 — 訂正は上書きで行う

**ADR の註記運用を、凍らない文書へ持ち込まないこと。** これが件1の原因だった。

[ADR の運用ルール](../adr/README.md)が「本文の文言を変えず、註記を足す」としているのは、**決定を保存する必要がある**からである。後から「なぜこうなっているのか」を再検討する人に、当時の判断をそのまま見せる必要がある。

育てる文書(GDD / TDD / 本ディレクトリ)と使い捨て文書(タスク仕様)にはその必要がない。**誤りを残す理由が無い。** 註記を足して本文を残すと、註記を読み飛ばした読者に旧主張がそのまま届く。

**例外**: 訂正の経緯そのものが後の判断の入力になる場合は、上書きしたうえで註記を添えてよい。W1-04 の「テストで落とせないと書いたが誤りだった」は、**なぜそう誤ったか**(曖昧化の条件を要素型の一致と取り違えた)が W2 で同じ判断をするときの入力になるため、上書き + 註記とした。

### 規則2 — 同じ主張が何か所にあるかを数える

件4・5・6 の3件がこれである。W1-04 では、同じ主張が**4層**に散っていた:

```
タスク仕様の表のセル
タスク仕様の散文
BannedSymbols.txt(永続する規約ファイル)
テスト/実装の doc コメント
```

毎回1〜2か所を取り残した。

**訂正後に、訂正前の語で `grep` して0件を確認する。** これは実際にレビュアーが5巡目で行い、「訂正前の語『公開区画』はリポジトリ全体に残存なし」と報告した手順である。**設計セッションが先にやれば、その巡は不要になる。**

> **精度が要るのは、読者が到達する場所である。** 件5 では `BannedSymbols.txt` を直してテストのクラス doc を残したが、**優先順位が逆だった**。区画を足した開発者はテストの失敗メッセージからそのファイルへ来る。`BannedSymbols.txt` は能動的に開く保証がない。
>
> 訂正先を1つしか選べないなら、**読者が事故のときに必ず開くほう**を選ぶ。

### 規則3 — 発生源を直す

件3。「doc コメントが `long.Parse` を指すが実際は `TryParse`」という指摘に対し、私は仕様に「doc コメントの API 名は実際に呼ぶものと一致させる」というメタ規則を足した。**発生源は仕様の規範文が `long.Parse` と書いていたことであり、そこは直していなかった。**

メタ規則を足すのは、発生源を直したうえで「同じ間違いを繰り返さないため」に行う。**発生源を直す代わりにはならない。**

### 規則4 — 派生する記述を洗い出す

件2。「核心」印を3件→4件にしたとき、完了条件のチェック項目が「テスト2・3・12」のまま残った。

W1-04 で派生関係にあったもの:

- テストの件数(「テスト12件が全て緑」)← テスト表の行数
- 完了条件の変異テスト項目 ← 「核心」印の付いた行
- 当てるべき変異の一覧 ← 同上
- `BannedSymbols.txt` の「機械化できたもの」一覧 ← テストの実体

**元を変えたら派生も変える。** 数え上げ系は特に取り残しやすい。

### 規則5 — 行き過ぎない。迷ったら狭い側

件7。「機械が守る範囲」の一覧が**実態より狭い**という疑いに対応した結果、**広げすぎて実態に無い保証を主張した**。

**狭い誤りと広い誤りは、危険度が対称ではない。**

| 誤りの向き | 何が起きるか |
| ---------- | ------------ |
| 狭い(守れる範囲を小さく書く) | 委譲判断が過度に保守的になる。人が余分に見る |
| **広い**(守れない範囲を守れると書く) | **「テストが守っているから見なくてよい」と読ませる。誰も見なくなる** |

[ADR-0004](../adr/0004-ai-driven-development-workflow.md) が「サブエージェントに委ねられる範囲は機械的ガードの範囲に依存する」としている以上、この一覧は委譲判断の入力である。**迷ったら狭い側に倒す。**

**「機械化できた」と書く前に、実際に壊して落ちることを確かめる。** 件7 は、`enum` を `long` 幅で・`Tick` を `int` 幅で書く実装に変えてもテストが全て緑のままであることを実測して初めて確定した。書いた時点では確かめていなかった。

### 規則6 — 却下理由の前提が崩れていないか

3巡目の指摘D。「汎用のフィールド単位凍結は `record struct` の位置引数と `init` プロパティが混在し誤検出が多くなるため採らない」と書いたが、**同じ PR で追加したコードがまさにその混在を一様に数えて成立していた**。却下理由が、自分の書いたコードに反証されていた。

[ADR の運用ルール](../adr/README.md)は「却下理由の前提が崩れたら、代替の却下理由を註記する」を**ADR について**定めている。**同じことが育てる文書と使い捨て文書にも要る。** 前提だけ崩れて理由が空白になると、再検討する人が「無理だと結論が出ている」と読んで取り逃がす。

## 機械で守れるか

CLAUDE.md「新しい規約を作るときは『これは機械で守れるか』を必ず問う」に従う。

| 規則 | 判定 | 内容 |
| ---- | ---- | ---- |
| 2 | **可(未実装)** | 訂正前の語の `grep` は人が打つ手順として書ける。壊れた内部リンク(件1)は docs の lint で機械化できる |
| 4 | 一部可(未実装) | 「テストN件」と実際のテスト数の突き合わせは書ける。一覧の網羅性は不可 |
| 1, 3, 5, 6 | 不可 | いずれも意味の問題 |

**現時点で docs の lint も CI ジョブも存在せず、実装予定も無い**([02-task-spec.md](02-task-spec.md) と同じ状況)。したがって6件とも今は人が守る規約である。

**規則2の `grep` だけは、道具なしで今日から実行できる。** 7件のうち3件(件4・5・6)を直接防ぎ、件1の残存本文も検出する。**投資対効果が最も高いのはここである。**

## レビュアー憲章との関係

規則1〜6のうち、**憲章([`.claude/agents/reviewer.md`](../../.claude/agents/reviewer.md) §2c)に項目があるのは全件である。**

これは [02-task-spec.md](02-task-spec.md) の規則1・2 が「憲章に無く、設計セッションの自己点検だけに依存している」状態とは対照的である。そちらは [ADR-0005](../adr/0005-reviewer-scope-includes-spec-defects.md) が「書いた本人には食い違いが見えない」と認めた経路そのもので弱い、と自己評価している。

**訂正の失敗は、まさにその「書いた本人には見えない」型である。** 件1〜7 はすべて設計セッション(開発者)が起こし、すべてレビュアーが見つけた。**自己点検に委ねてはならない。** したがって憲章に入れた。

> ただし本書の規則は**設計セッションが守るためのもの**であり、レビュアーが見つけるのは二次防衛線である。レビュアーが見つける限り巡は増える。**巡を減らすのは設計セッション側の順守だけである。**
