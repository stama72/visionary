## レビュアー憲章の所在

**憲章そのものの正は [`.claude/agents/reviewer.md`](../../.claude/agents/reviewer.md) である。** 本書はその本文を複製しない。

理由は憲章が**実行される設定**だからである。詳細は [README「実行される仕様」](README.md#実行される仕様という位置づけ)。

ADR-0004 決定(まとめ)にも憲章のリストがあるが、**あれは起案時点(2026-08-27)のスナップショット**である([ADR-0005](../adr/0005-reviewer-scope-includes-spec-defects.md))。現行を知りたいときは `.claude/agents/reviewer.md` を読む。

同じことが [`.claude/agents/implementer.md`](../../.claude/agents/implementer.md) と [`.claude/commands/learn.md`](../../.claude/commands/learn.md) にも当てはまる。

## 規律

- **どの変更も、開発者のレビューの前にレビュアーエージェントを必ず通す。タスク仕様を持たない文書のみの変更も含む。** 例外を作らない。小さい変更ほど「今回は要らない」と判断しがちだが、その判断自体が開発者のレビュー帯域(ADR-0004 がボトルネックと認めた工程)を先に消費する
- レビュアーは**実装とは独立したコンテキスト**で読む。したがって実装を担当したセッション/エージェントの説明を渡さない。渡した時点で「ドキュメントから読み取れない実装」が見えなくなり、レビューがドキュメント品質の検査を兼ねるという設計(ADR-0004 論点1)が壊れる
- **レビュアーに機械の判定結果を渡さない**(ADR-0004 帰結)。ビルド・テスト・フォーマットが緑であることだけ伝え、再判定させない
- 指摘への対応は3択:**直す / 直さないと決めて理由を残す / issue へ落とす**。黙って見送らない

## スコープの関門

**指摘が正しいことと、今直すべきことは別である。**

レビュアーは指摘ごとに**ブロッカーか非ブロッカーか**を分類する(憲章 §0)。分類ごとに既定の処置が違う:

| 分類 | 既定の処置 |
| ---- | ---------- |
| **ブロッカー** — (a) ゲートを脅かす、または (b) **この変更自体が誤った記述を「正」として確定させる**(参照先の誤り、規範文と理由の食い違い、達成できない保証、上位文書との矛盾。とくに凍る ADR に入るもの) | 直す |
| **非ブロッカー** — どちらでもない | **issue へ落とす。**「直す」を既定にしない |

**軸が2本ある理由。** (a) だけだと、[ADR-0005](../adr/0005-reviewer-scope-includes-spec-defects.md) がレビュアーに与えた守備範囲(内部破綻の検出)の指摘が**構造上すべて非ブロッカーに落ちる** — 文書の食い違いは M0 の GO判断3項目を脅かさないからである。**(a) は「今やる必要があるか」、(b) は「今しか直せないか」を見ている。** M0 の Exit Criteria が定性的であるぶん、当面は (b) のほうが実効的に働く([ADR-0006](../adr/0006-issue-driven-task-management.md) 論点5)。

**既定を反転させることが要点である。** [reviewer.md](../../.claude/agents/reviewer.md) の観点はすべて「正しいか」を問うており、「今のマイルストーンに要るか」を問う観点を持たない。したがって正しい指摘はすべて「直す」対象になり、**正しい指摘を無限に出せる文書では原理的に収束しない**。この既定のまま [GDD02](../03-gdd/02-economy.md) は8巡を要した([ADR-0006](../adr/0006-issue-driven-task-management.md) 背景)。

**落とす先が無ければ「直さない」は選べない。** 本書は以前から上の3択を持っていたが、3つ目の実体が無かった。issue がその実体である。

**分類が割れたときだけ開発者が判断する。** (b) は文書間の照合なのでエージェントが担える。(a) は M0 のあいだ参照点が定性的なので、割れやすいのはこちらである。

## 停止則 — レビューを何巡で打ち切るか

> **前巡の修正が原因のブロッカーが2巡続いたら、その文書のレビューを打ち切り、実装へ渡す。**

**件数ではなく出自で判定する。** GDD02 のレビュー5〜8巡目のブロッカーは 9 → 7 → 3 → 4 件と減衰していたが止まらなかった。**6巡目の7件と7巡目の3件は、前巡の修正が新たに作った、または不十分だったもの**である。件数の減衰を停止則にすると、この自己触媒的なループを検出できない。出自で置けば GDD02 は7巡目で止まっていた。

**閾値が「2巡」なのは件数とは無関係である。** 1巡なら偶発的な訂正ミスと区別できず、3巡は GDD02 が実際に費やした巡数を超える。**「訂正が訂正を生む状態に入った」ことの最小の証拠が2巡連続である**、というのが根拠であり、上の件数はその状態が起きたことの記録にすぎない。

打ち切るときは:

- **残る指摘を issue に落としてから打ち切る。** 落とさずに打ち切ると、この停止則はただの品質低下になる
- 文書に「この版で打ち切った」と**理由つきで**記録する。GDD02 v0.15 の冒頭がその形である
- **次にその文書をレビューする機会は、実装とタスク仕様に対してであって、文書に対してではない**

## 2巡目以降に渡すもの

レビュアーは独立コンテキストで読む(上の規律)。**その独立性のせいで、2巡目以降は前巡の情報を持たない。** 憲章 §2c は「訂正が追記になっていないか」「訂正前の語で `grep` して残存を確認せよ」と求めるが、**何がどう指摘され、どう直されたかを渡さなければ実行できない。**

2巡目以降は以下を渡す:

- **対象のコミット範囲**(前巡のレビュー対象以降)。「どこからが訂正か」が確定する
- **前巡の指摘一覧と、それぞれへの対応方針**(受け入れ / 部分受け入れ / 穴として宣言のみ / 対応せず)。対応せずと決めたものは理由も
- 機械の判定結果は**渡さない**(上の規律のまま)。ただし設計セッションが変異を当て直したなど、**再現不要と伝えたい検証**があれば「確認済みなので再確認不要」と明示する

これは「実装の説明を渡さない」規律([ADR-0004](../adr/0004-ai-driven-development-workflow.md) 論点1)と矛盾しない。**渡すのは自分の指摘の履歴であって、実装の意図ではない。** レビュアーが失うコンテキストは「なぜそう実装したか」であり、そこは保たれる。

**収束のために、2巡目以降は判定も求める。** 「指摘が無ければ無しと明言せよ」「マージ可なら明言せよ」「非ブロッキングの精度の問題は『マージ可。ただし以下』の形で分けよ」。求めなければ、レビュアーは指摘を出し続けることしかできない。W1-04 が5巡を要した原因の一つがこれである([03-corrections.md](03-corrections.md))。

## 開発者のレビューとの分担

レビュアーエージェントが見るのは「**仕様の内部が破綻していないか**」まで。「**作るべきものが正しいか**」(ゲームデザインの妥当性、ニーズ設計の是非)は開発者にしか判定できない(ADR-0005)。

この線引きを曖昧にすると、ADR-0004 帰結の安全弁 —「開発者のレビュー精度を下げられる範囲は、機械的ガードとレビュアーが守れている範囲まで」— が実質的に外れる。
