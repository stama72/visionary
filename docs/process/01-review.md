## 方針 — 効率と質の両立

**レビューの守備範囲は「気付けない × 影響大」に限る。**([ADR-0008](../adr/0008-review-scope-narrowed-to-unnoticeable-defects.md))

| | 影響大 | 影響小 |
| --- | --- | --- |
| **気付けない** | **象限I — 見る** | 象限IV — 見ない |
| **気付ける** | 象限II — 1巡目のみ | 象限III — 見ない |

**「気付けるか」は品質の基準ではなく、放置コストの基準である。** 気付ける欠陥の放置コストは「踏んだときに直す手間」で有限だが、気付けない欠陥は踏んだことすら分からないので上限がない。レビューに払う価値があるのは後者だけである。

## 工程ごとの分担

| 工程 | 誰が見るか |
| ---- | ---------- |
| **実装**(コードとテスト) | [レビュアーエージェント](../../.claude/agents/reviewer.md) → 開発者 |
| **テストの判別力**(変異が落ちるか) | [`mutator`](../../.claude/agents/mutator.md) が実測する([ADR-0013](../adr/0013-mutation-measurement-separated.md)) |
| **設計・プロセス・文書のみ** | **設計セッションが呼ぶ** — 専門家([`adviser-economy`](../../.claude/agents/adviser-economy.md))が先、全般([`adviser`](../../.claude/agents/adviser.md))が最後に残りを拾う → 開発者。束ごとに差分へかける([06-design-sessions](06-design-sessions.md)) |

**[`reviewer`](../../.claude/agents/reviewer.md) は実装工程にだけ使う。** 設計・プロセス工程には使わない([ADR-0008](../adr/0008-review-scope-narrowed-to-unnoticeable-defects.md) 論点3)。**役を名指しするのは、設計・プロセス工程もエージェントで回すようになったためである**([#105](https://github.com/stama72/visionary/issues/105))。「エージェントは実装専用」ではない — 工程ごとに別の憲章を持つエージェントが当たる。

**実装工程のレビューは[フェーズ2](05-phase-sessions.md)が回す。** レビュアーを起動するのも、指摘を implementer に渡すのもフェーズ2 のセッションである。

アドバイザーは敵対的レビューではない。論点整理とスコープ整理を行い、**象限I-b の4類型**(広い保証 / 参照点の誤り / 上位文書との矛盾 / 却下理由の空洞化)だけを必ず報告する。結論は開発者が出す。

**報告する巡は2つで、3巡目は呼ばれても打ち切る**(実装レビューは3つ)。基準は同じ「後から気付けるか」で、2巡目に残るのは**気付けないものと、訂正で新しく入った決定**だけである。**役ごとの対応表は各憲章が持つ**(本書は複製しない)。1巡短いのは、設計はレビューで詰めきれず、使ってみることでしか詰まらないためである(下の「打ち切って実装へ渡す」)。

**2巡目の指摘への訂正は、誰も見ない。** 承知のうえで打ち切っている — 受け皿は「気付いたら直す」と、次のタスクでその文書を使うことである。**巡の本数を決めているのは、この受け皿があるかである。** したがって **ADR を含む束は打ち切らない**(下の「ADR だけは打ち切れない」。凍結後は踏めないので受け皿が無い)。その束の3巡目以降は2巡目の範囲のまま続ける。

## 「気付いたら直す」

> **象限III・IV を報告しない代わりに、踏んだ人がその場で直す。**

**これが範囲外を放置できる条件である。** この規約が無ければ、[ADR-0008](../adr/0008-review-scope-narrowed-to-unnoticeable-defects.md) の決定は単なる品質低下になる。

- リンク切れ、表記揺れ、古い件数、取り残した N か所目 — **見つけたら、そのとき直す**
- **issue を立てない。** 立てる手間のほうが直す手間より大きい
- **別 PR にしない。** 触っているブランチで直してよい
- 直すのが5分を超えるなら、そのときだけ issue へ落とす

## 実装レビューの規律

- レビュアーは**実装とは独立したコンテキスト**で読む。実装を担当したセッション/エージェントの説明を渡さない。渡した時点で「ドキュメントから読み取れない実装」が見えなくなり、レビューがドキュメント品質の検査を兼ねるという設計([ADR-0004](../adr/0004-ai-driven-development-workflow.md) 論点1)が壊れる
- **機械の判定結果を渡さない**(同 帰結)。ビルド・テスト・フォーマットが緑であることだけ伝え、再判定させない
- 指摘への対応は3択:**直す / 直さないと決めて理由を残す / issue へ落とす**。黙って見送らない。**直したものはコミット本文が持ち、直さないと決めたものは[引き継ぎメモ](05-phase-sessions.md)が持つ** — 直さないとコミットが発生せず、記録先が無いままになる
- **象限I は直す。象限II は開発者が決める**(直すか issue か)

## 減衰と打ち切り

**巡が進むほど、報告してよい象限を狭める。** **巡と象限の対応表は [`reviewer.md`](../../.claude/agents/reviewer.md) §0b が持つ**(本書は憲章の本文を複製しない。上の「憲章の所在」)。4巡目で打ち切る。

**何巡目かは起動時に渡す。** 渡さなければレビュアーは1巡目として扱う。

**落とすのは件数ではなく種類である。** 件数を閾値にすると「軽微な指摘を大量に出す巡」が素通りする。[GDD02](../03-gdd/02-economy.md) のレビューはブロッカーが 9 → 7 → 3 → 4 件と減衰していたが止まらなかった([ADR-0006](../adr/0006-issue-driven-task-management.md) 背景)。

**3巡目に I-a だけを残す理由。** 訂正で新たに書いたテストが「緑のまま壊れる」型の欠陥を持つことが実際にあった(W1-04 2巡目の3件)。訂正由来を一律に落とすと、ここが取りこぼされる。

**「打ち切って実装へ渡す」の「実装へ渡す」は、その文書を使い始めることである。**([ADR-0006](../adr/0006-issue-driven-task-management.md) 論点5)コードなら実装、プロセス文書なら次のタスクで実際に運用してみること、GDD / TDD なら下流のタスク仕様を書き始めることが対応する。**レビューで詰めきれない部分は使ってみることでしか詰まらない**、という前提の規則なので、レビュー対象が実装を持たなくても行き先は定義できる。

**ADR だけは打ち切れない。** 本文を後から直せないため「不完全なまま渡して後で直す」が使えない。ADR は残る指摘を全件反映してから凍結する([ADR-0007](../adr/0007-m1-scale-follows-economic-model.md) 冒頭の註記が実例)。

打ち切るときは:

- **残る指摘を issue に落としてから打ち切る**
- 実装なら PR の説明に、文書なら本文に「この版で打ち切った」と理由つきで記録する。**実装では、PR を書くのは別フェーズなので[引き継ぎメモ](05-phase-sessions.md)を経由する**
- **巡ごとの件数は 0 件の巡も記録する。** 0 件の巡はコミットが発生しないため、記録しないと「その巡が無かった」ことになる

## 網羅パス — 渡し方を変える1巡

**欠陥の出所に列挙可能な境界が見えたら、探すのをやめて数え上げる。**

渡し方は「`X` が外部とやりとりする全経路を列挙し、各経路に当てるべき変異を書き出せ」の形にする。レビュアーは読んで見つけるのではなく、**有限のリストを埋める。**

**列挙はレビュアー、実測は [`mutator`](../../.claude/agents/mutator.md) である**([ADR-0013](../adr/0013-mutation-measurement-separated.md))。レビュアーが出すのは**経路と、当てる変異と、期待**までで、当てない。**机上で「落ちるはず」と埋めさせない** — 外れても誰も気付かないことが、この巡が測っている対象そのものである。W2-08 では60件の実測をレビュアーに委託しており、変異作業のあいだ本体ツリーが汚れて並行走行の検出が鈍った([#109](https://github.com/stama72/visionary/issues/109) / [#110](https://github.com/stama72/visionary/issues/110))。

- **起動条件は「列挙可能な境界が見えたこと」である。** 同一類型が続いたことではない。続いたことは境界に気付く**きっかけ**ではあるが、条件ではない
- **境界が引けない対象へ出さない。** レビュアーは全体を読み直すだけになる
- **巡を1つ消費する。** 網羅を出すなら、**探索の巡を1つ削って充てる。** 上限4も、巡ごとの減衰も動かさない
- **減衰表はそのまま当たる。** 実測が出す「この経路の変異が落ちない」は定義上 I-a(緑のまま壊れる)なので、3巡目でも通る。**充てられるのは2巡目か3巡目である** — 1巡目は境界がまだ見えず、4巡目は打ち切りのままだからである

**実測(W2-05)**: 探索の1〜3巡で計6件。**上限を1つ超えた4回目**を網羅へ切り替えたところ、同じ類型を10件まとめて出した。10件は全件に変異を当てて283件が緑のまま通ることを確認しており、直さずに [#37](https://github.com/stama72/visionary/issues/37) へ引き継いだ(`d9f380e`)。

**巡の本数を動かさないのは、[ADR-0008](../adr/0008-review-scope-narrowed-to-unnoticeable-defects.md) 論点4 が「巡数と象限の対応は機械的に決まる」を選択理由に挙げているためである。** 網羅パスを巡の外へ置くと、巡が進むかどうかがフェーズ2 の裁量になり、この選択理由のほうが崩れる。`REVIEW-EXHAUSTED` は元から自己申告なので([05-phase-sessions](05-phase-sessions.md))、**機械の歯止めが無いぶん、規則の側で緩めない。** 変えてよいのは1巡の渡し方だけで、巡の本数ではない。

**代償は探索が1巡減ることである。** W2-05 の運用に当てはめれば、探索を2巡に留めて3巡目を網羅に充てることになり、**探索が出した6件のうち何件かは出ない。** 上限内で網羅の10件を取れるほうが大きい、という取引を引き受ける。

## 2巡目以降に渡すもの

レビュアーは独立コンテキストで読むため、**2巡目以降は前巡の情報を持たない。** 以下を渡す:

- **何巡目か**(減衰の判定に要る)
- **対象のコミット範囲**(前巡のレビュー対象以降)
- **前巡の象限I の指摘と、それぞれへの対応方針**(受け入れ / 対応せず + 理由)。**象限II 以下は渡さない** — 2巡目以降は報告対象外なので、渡すと注意を逸らす

機械の判定結果は渡さない(上の規律のまま)。

これは「実装の説明を渡さない」規律と矛盾しない。**渡すのは指摘の履歴であって、実装の意図ではない。**

## 開発者のレビューとの分担

レビュアーエージェントが見るのは「**仕様の内部が破綻していないか**」まで。「**作るべきものが正しいか**」(ゲームデザインの妥当性、ニーズ設計の是非)は開発者にしか判定できない([ADR-0005](../adr/0005-reviewer-scope-includes-spec-defects.md))。

**象限II(気付ける × 影響大)の検出器は実装であって、レビューではない。** 規範文の食い違いも、順序の曖昧さも、マイルストーンの順序反転も、実装すれば必ず踏む。**先に小さく実装して踏むほうが安い。** これを文書レビューで先取りしようとしたことが、GDD02 が 1,488行・8巡になった原因である([ADR-0008](../adr/0008-review-scope-narrowed-to-unnoticeable-defects.md) 論点2)。
