## 方針 — 効率と質の両立

**レビューの守備範囲は「気付けない × 影響大」に限る。**([ADR-0008](../adr/0008-review-scope-narrowed-to-unnoticeable-defects.md))

| | 影響大 | 影響小 |
| --- | --- | --- |
| **気付けない** | **象限I — 見る** | 象限IV — 見ない |
| **気付ける** | 象限II — 1巡目のみ | 象限III — 見ない |

**「気付けるか」は品質の基準ではなく、放置コストの基準である。** 気付ける欠陥の放置コストは「踏んだときに直す手間」で有限だが、気付けない欠陥は踏んだことすら分からないので上限がない。レビューに払う価値があるのは後者だけである。

## 工程ごとの分担

| 工程 | 誰が見るか |
| ---- | ---------- |
| **実装**(コードとテスト) | [レビュアーエージェント](../../.claude/agents/reviewer.md) → 開発者 |
| **設計・プロセス・文書のみ** | [`/advise`](../../.claude/commands/advise.md)(任意)→ 開発者 |

**レビュアーエージェントは実装工程にだけ使う。** 設計・プロセス工程には使わない([ADR-0008](../adr/0008-review-scope-narrowed-to-unnoticeable-defects.md) 論点3)。

`/advise` は敵対的レビューではない。論点整理とスコープ整理を行い、**象限I-b の4類型**(広い保証 / 参照点の誤り / 上位文書との矛盾 / 却下理由の空洞化)だけを必ず報告する。結論は開発者が出す。

## 「気付いたら直す」

> **象限III・IV を報告しない代わりに、踏んだ人がその場で直す。**

**これが範囲外を放置できる条件である。** この規約が無ければ、[ADR-0008](../adr/0008-review-scope-narrowed-to-unnoticeable-defects.md) の決定は単なる品質低下になる。

- リンク切れ、表記揺れ、古い件数、取り残した N か所目 — **見つけたら、そのとき直す**
- **issue を立てない。** 立てる手間のほうが直す手間より大きい
- **別 PR にしない。** 触っているブランチで直してよい
- 直すのが5分を超えるなら、そのときだけ issue へ落とす

## 実装レビューの規律

- レビュアーは**実装とは独立したコンテキスト**で読む。実装を担当したセッション/エージェントの説明を渡さない。渡した時点で「ドキュメントから読み取れない実装」が見えなくなり、レビューがドキュメント品質の検査を兼ねるという設計([ADR-0004](../adr/0004-ai-driven-development-workflow.md) 論点1)が壊れる
- **機械の判定結果を渡さない**(同 帰結)。ビルド・テスト・フォーマットが緑であることだけ伝え、再判定させない
- 指摘への対応は3択:**直す / 直さないと決めて理由を残す / issue へ落とす**。黙って見送らない
- **象限I は直す。象限II は開発者が決める**(直すか issue か)

## 減衰と打ち切り

**巡が進むほど、報告してよい象限を狭める。**

| 巡 | 報告してよい象限 |
| -- | ---------------- |
| 1  | I + II |
| 2  | **I のみ** |
| 3  | **I-a のみ**(緑のまま壊れる) |
| 4  | 打ち切り |

**何巡目かは起動時に渡す。** 渡さなければレビュアーは1巡目として扱う。

**落とすのは件数ではなく種類である。** 件数を閾値にすると「軽微な指摘を大量に出す巡」が素通りする。[GDD02](../03-gdd/02-economy.md) のレビューはブロッカーが 9 → 7 → 3 → 4 件と減衰していたが止まらなかった([ADR-0006](../adr/0006-issue-driven-task-management.md) 背景)。

**3巡目に I-a だけを残す理由。** 訂正で新たに書いたテストが「緑のまま壊れる」型の欠陥を持つことが実際にあった(W1-04 2巡目の3件)。訂正由来を一律に落とすと、ここが取りこぼされる。

打ち切るときは:

- **残る指摘を issue に落としてから打ち切る**
- 実装なら PR の説明に、文書なら本文に「この版で打ち切った」と理由つきで記録する

## 2巡目以降に渡すもの

レビュアーは独立コンテキストで読むため、**2巡目以降は前巡の情報を持たない。** 以下を渡す:

- **何巡目か**(減衰の判定に要る)
- **対象のコミット範囲**(前巡のレビュー対象以降)
- **前巡の象限I の指摘と、それぞれへの対応方針**(受け入れ / 対応せず + 理由)。**象限II 以下は渡さない** — 2巡目以降は報告対象外なので、渡すと注意を逸らす

機械の判定結果は渡さない(上の規律のまま)。

これは「実装の説明を渡さない」規律と矛盾しない。**渡すのは指摘の履歴であって、実装の意図ではない。**

## 開発者のレビューとの分担

レビュアーエージェントが見るのは「**仕様の内部が破綻していないか**」まで。「**作るべきものが正しいか**」(ゲームデザインの妥当性、ニーズ設計の是非)は開発者にしか判定できない([ADR-0005](../adr/0005-reviewer-scope-includes-spec-defects.md))。

**象限II(気付ける × 影響大)の検出器は実装であって、レビューではない。** 規範文の食い違いも、順序の曖昧さも、マイルストーンの順序反転も、実装すれば必ず踏む。**先に小さく実装して踏むほうが安い。** これを文書レビューで先取りしようとしたことが、GDD02 が 1,488行・8巡になった原因である([ADR-0008](../adr/0008-review-scope-narrowed-to-unnoticeable-defects.md) 論点2)。
