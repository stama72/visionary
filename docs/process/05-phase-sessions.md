| 項目     | 内容                                                                 |
| -------- | -------------------------------------------------------------------- |

**1タスクを3つのフェーズに切る。** なぜそう切るかは [ADR-0009](../adr/0009-phase-scoped-sessions.md) が、**フェーズ2・3 を機械が繋ぐこと**は [ADR-0010](../adr/0010-phase-pipeline-and-halt-conditions.md) が持つ。本書は**今どう運用するか**を持つ。

## 3つのフェーズ

| | フェーズ1 設計 | フェーズ2 実装とレビュー | フェーズ3 文書更新と PR |
| --- | --- | --- | --- |
| 起動 | 既定のメインセッション | [`/impl`](../../.claude/commands/impl.md) | [`/wrap`](../../.claude/commands/wrap.md) |
| モデル | `~/.claude/settings.json` の既定(**opus**。[ADR-0014](../adr/0014-interactive-sessions-follow-the-default-model.md) / [06](06-design-sessions.md)「モデル」) | Opus(実装は Sonnet の implementer) | **Sonnet**(**パイプラインの `--model` が握る**。[`wrap.md`](../../.claude/commands/wrap.md) 側には何も無い) |
| 成果物 | タスク仕様の凍結 | 緑のコードとコミット | PR と切り出した issue |
| 終わり方 | 引き継ぎメモを書き、**パイプラインを背景起動して止まる** | 引き継ぎメモに追記し `PIPELINE: DONE` | PR を作り `PIPELINE: DONE` |

**フェーズ2 のメインはコードを読み書きしない。** 実装も、レビュー指摘の修正も implementer に渡す。ここが崩れると、実装を Sonnet に逃がした節約がそのまま消える。

**例外は象限I-b(仕様そのものの欠陥)だけ。** 仕様の訂正は設計判断なので、メインが仕様を直してから implementer に渡す。

## 引き継ぎメモ

**`docs/tasks/W<段階>-<連番>-<スラッグ>.handoff.md`。** ファイル名とテンプレートは [docs/tasks/README.md](../tasks/README.md)。

### 書くもの — 5件だけ

| # | 項目 | どのフェーズで書くか |
| - | ---- | -------------------- |
| 1 | **却下した設計案と理由**(ADR に載らない大きさのもの)と、**却下によって失われる保護** | 1 |
| 2 | **implementer の件数** — 止まって報告した / 決めて報告した | 2 |
| 3 | **直さないと決めたレビュー指摘と、その理由** | 2 |
| 4 | **巡ごとの件数**(0件の巡を含む)と、打ち切ったならその理由。**網羅に充てた巡があれば、その境界も**([01-review](01-review.md)) | 2 |
| 5 | **`mutator` の件数** — 当てた変異の数と、**期待と食い違った数**(0件なら「0件」)。[ADR-0013](../adr/0013-mutation-measurement-separated.md) の検証条件で、記録先は PR 説明である | 2 |

#### 却下の代償を1行で書く

**却下理由は「なぜ採らないか」しか書かないので、失うものは別に書かないと消える。**

W2-05 は「`BuyerDemand` を `TradeSystem` に繋ぐ」を却下した。**却下の判断そのものは妥当だった**(計算結果を誰も読まないので、用途を落としても緑のまま)。だが代償 — **配線が統合テストの保護を受けない** — は見積もられていなかった。結果、4巡16件の指摘がすべてテストの判別力・網羅度に費やされ、10件が未検証のまま [#37](https://github.com/stama72/visionary/issues/37) へ渡った([02-task-spec](02-task-spec.md) 規則7)。

### 書かないもの

**既にどこかに残るものは書かない。** 器を作ると全部書きたくなるので、書かない側を先に決めてある。

| 書かないもの | 既にどこに残るか |
| ------------ | ---------------- |
| 型・シグネチャ・テスト表・編集してよい文書・スコープ外にした判断 | タスク仕様 |
| **採った**設計の理由 | コードの doc コメントと TDD(implementer 憲章が要求している) |
| 直したレビュー指摘の内容と対応 | コミット本文 |
| **設計フェーズ内で自分で捕まえた仕様の誤りと、直した内容** | **仕様を凍結するコミットの本文**(下記) |
| 当てた変異と結果 | doc コメントかコミット([02-task-spec](02-task-spec.md))。**`mutator` の報告そのものは `.pipeline/*.jsonl` にしか残らない**ので、件数だけメモの #5 が持つ |
| build / test / format の結果 | フェーズ3で再実行できる |

#### 設計フェーズ内で捕まえた仕様の誤り

**フェーズ1 が自分で見つけて直した仕様の誤りは、仕様を凍結するコミットの本文に書く。** 仕様は最終形しか見せないので、書かなければ消える。

メモに入れないのは、**フェーズ内で完結し、後のフェーズへ判断を引き継がない**ためである。メモは境界を越える情報の器である。

コミット本文を選ぶのは、消えるのを防ぐだけが理由ではない。[02-task-spec](02-task-spec.md) の先行指標「仕様の穴の数」は、いま **implementer が突き当たった穴しか数えられない** — 設計フェーズが自分で塞いだ穴は、塞がれたことで指標から消える。コミット本文に書けば `git log` で数えられる。

### メモに入れないが、記録する1件

**「引き継ぎメモの不足で、後のフェーズが止まった・判断をやり直した回数」は PR 説明の検証節に書く**(0 件でも「0 件」と書く)。[ADR-0009](../adr/0009-phase-scoped-sessions.md) の検証条件である。

メモに足さないのは、**書く主体がフェーズ3 だけで、フェーズをまたがない**ためである。メモは境界を越える情報の器である。

### 寿命

**使い捨て層。フェーズ3 で PR 説明へ転記し、同じブランチの最後のコミットで削除する。** add と delete が同じ PR に入るので、差分には現れず master にも残らない。正は PR 説明である。

## フェーズをまたぐときの手順

**フェーズ1 は、仕様を凍結したら自分でパイプラインを背景起動して終わる。**

```powershell
pwsh scripts/pipeline.ps1 -Issue 35
```

`claude -p "/impl 35"` → `claude -p "/wrap 35"` を**別プロセス**で順に回す。プロセスが別なのでコンテキスト窓も別で、`/clear` と同じ隔離になる。

**打つのがフェーズ1 なのは、開発者が打つ形だと「終わったので次を打つ」待ちがそのまま残るためである。** それを無くすのが [ADR-0010](../adr/0010-phase-pipeline-and-halt-conditions.md) の目的で、同 ADR 論点1 の選択肢2 も「フェーズ1 のセッション(または素のシェル)がスクリプトを起動し」と書いている。

**待っている間にフェーズ1 が使うターンは 0 である。** W2-04(#35)の実測で、36分の待ちに対してターン 0(背景実行のツール呼び出し1件でブロックし、完了で起こされる)。起こされた後の事後検証6ターンぶんは $2.68 で、build / test / format の独立再実行を1回増やすぶんに当たる。**選択肢3(サブエージェント連鎖)を却下した理由 — 親が子の報告を読んでコンテキストが育つ — は、背景実行のブロッキング呼び出しには当たらない。**

開発者が手で打ってもよい。停止則に当たった後の再開はそうなる。

**Git Bash からは呼べない。** MSYS が先頭の `/` を `C:/Program Files/Git/...` に変換し、スラッシュコマンドとして解決されない。PowerShell から回すこと。

### パイプラインが走っている間、本体の worktree はパイプラインのものである

**無人フェーズは `git commit` / `git checkout` / `gh pr create` を回している。** 同じ作業ツリーを開発者が同時に触ると、コミットに巻き込まれるか、`git checkout` で消える。

パイプライン以前は「1タスク = 開発者が張り付く1時間」だったので、この衝突は起こりえなかった。**無人フェーズ中に開発者が空くのは [ADR-0010](../adr/0010-phase-pipeline-and-halt-conditions.md) の狙いどおりだが、空いた開発者が行く先を決めていなかった。**

したがって次を規律とする。

- **パイプライン実行中、本体の `visionary/` は触らない。** 並行して進める別タスクは **worktree を分ける**
- 本体で待つのが自然なのは、パイプラインを起動したフェーズ1 のセッション自身だけである(完了で起こされ、build / test / format と PR を独立に確認する)
- **5 時間枠の残りは `pipeline.ps1` 自身が起動時に読み、足りなければ起動を拒否する**(終了コード 4。[04「枠」](04-issue-driven.md) 規則2)。フェーズ1 は打つ前に自分で読まなくてよいが、**拒否されたらリセット時刻を開発者に報告して止まる**(拒否の理由とリセット時刻は標準出力とデスクトップ通知の両方に出る)。`/usage` は CLI の UI なのでセッションからは読めないが、haiku の 1 呼び出し($0.11 = 枠の 0.05%)で同じ値が取れる(実測 2026-09-20)。**規則1 のために自分で残りを見たいとき**は、この 1 行で読む:

  ```
  claude -p --model haiku --output-format stream-json --verbose "OK" | grep -o '"five_hour":{"utilization":[0-9.]*,"resetsAt":[0-9]*' | tail -1
  ```

  `utilization` が 0.60 を超えていれば残り 40% 未満。`resetsAt` は Unix 秒

W2-04 と #68(世界観と正式タイトル)が 21:12〜21:16 に重なったが、#68 が `.claude/worktrees/` にいたため衝突しなかった。**成立したのは worktree が分かれていたからで、WIP の数え方が守ったのではない。**

#### いまはこれを機械が守っている

**W2-08(#97)で規約は破れた。** 走行中のフェーズ2 に重ねて新しいセッションが立ち、本体ツリーへ 3 回書き込み、`git checkout` で implementer が当てたばかりの変異を消した。**ログの中では原因不明の環境問題として記録された**([#109](https://github.com/stama72/visionary/issues/109))。規約しか無いものは、こう破れて、破れたことも見えない。

| 部品 | 何をするか |
| ---- | ---------- |
| `scripts/pipeline-lock.ps1` | ロック `.pipeline/<issue>.lock`(PID と起動時刻)の読み書き。**生きている = その PID が今も居て起動時刻も一致する** |
| `scripts/pipeline.ps1` | 起動時にロックを取り、終了時(`exit` を通っても)に外す。**生きているロックがあれば起動を拒否する**(終了コード 3) |
| `scripts/check-budget-threshold.sh` | 枠ガードの閾値の**写しが正からずれていないか**を CI で見る([#139](https://github.com/stama72/visionary/issues/139))。正は `pipeline.ps1` の `$DefaultMinRemaining` で、写しは [04「枠」](04-issue-driven.md) 規則2 / CLAUDE.md / **この節の haiku 1 行**(使用率 0.60 の側も突き合わせる)。**数値が取れなければ落とす**(fail-closed)なので、文面を書き換えると数値が正しくても落ちる — そのときは検査の錨を直す |
| `scripts/pipeline.ps1` の枠ガード | 起動時に **5 時間枠の残りを haiku 1 呼び出しで読み、足りなければ起動を拒否する**(終了コード 4)。**読めなければ拒否する**(fail-closed)。閾値は `-MinRemaining`、`0` で検査しない。壊して確かめる口は `-DryRun -DryRunProbe short\|near-reset\|fail` |
| `scripts/pipeline-guard.ps1` + `.claude/settings.json` | `PreToolUse` フック。生きているロックがある間、**本体ツリーへの書き込みを止める**(`Edit` / `Write` と、書き込む形の `Bash` / `PowerShell`) |

素通しする経路は4つ:**パイプライン自身のセッション**(`pipeline.ps1` が渡す `VISIONARY_PIPELINE_ISSUE`)/ **worktree の中**(`.claude/worktrees/`)/ **読み取り**(`git status` や `Grep` は止めない — 走行中の様子を見にいけなくなる)/ **`.pipeline/` への書き込み**(ロックの回収路。ここを止めると、誤って居座ったロックを Claude のセッションから外せなくなる)。

#### 何が止まらないか

**これは「絶対に衝突しない」ではなく「うっかりが止まる」である。** 止まらないものを数え上げておく。

| 止まらないもの | なぜ |
| -------------- | ---- |
| **相対パスで本体へ届く `Bash` / `PowerShell`** — `git -C ../../.. checkout` / `dotnet --project ../..` | `Edit` / `Write` は対象ファイルを見るが、**シェルは cwd と「コマンドに現れる本体の絶対パス」しか見ていない。** 抜け道は無限にあるので、機械を厚くせず境界を書く側に倒した |
| **ホーム相対の絶対パス** — `cat > ~/game_dev/visionary/...` | Git Bash が `~` を `$HOME` へ展開して本体に届くが、照合は単純な文字列一致なので `C:\...` / `C:/...` / `/c/...` のどれにも当たらない。**上の行と違い、これは意図した境界ではない** — 展開後は絶対パスであり、綴りが 1 つ決まっている([#152](https://github.com/stama72/visionary/issues/152))。2026-09-21 に `cat >` と `Edit` の両方で素通しを実測した。`/cygdrive/c/...` も同じく当たらない(この環境では出ない綴り) |
| **フックを承認していないセッション** | フックは**開発者が1回承認するまで動かない。** 承認は設定の内容にひもづくので、`.claude/settings.json` を1文字変えると未承認に戻りうる |
| **判定に失敗したとき** | フックは例外をすべて素通しに倒す(判定の失敗で開発が止まるほうが高くつく)。**黙って素通しはしない** — `.pipeline/guard-failures.log` に1行残る。`exit 0` のフックの標準出力は transcript(ctrl+o)にしか出ないので、画面だけに頼ると守る側が静かに壊れる |
| **Claude のセッション以外** | 素のターミナルや他のエディタからの書き込みはフックを通らない |
| **走行中に枠が切れること** | 枠ガードは**起動時の 1 点しか見ない。** 起動後に別のセッションが枠を食えば、通した判定は外れる。走行中の監視は置いていない(枠切れの死は生ログの `is_error` に出る) |
| **週次(`seven_day`)の枠** | ガードが**判定に使うのは 5 時間枠だけ**である(週次は残りを**表示するだけ**)。とくに「リセットが近ければ要求を下げる」の前提(リセットで utilization が 0 に戻る)は**週次には成り立たない** — そして緩和がいちばん効く局面(5 時間枠を焼き切った直後)は、週次も高い局面である。閾値の根拠が無いので判定に入れていない([#141](https://github.com/stama72/visionary/issues/141) / 校正は [#123](https://github.com/stama72/visionary/issues/123)) |

逆に、**本体に居るセッションが worktree を絶対パスで触る**のは止まる(cwd が本体なので)。対称ではない。

実測(2026-09-20、17 ケース): 本体への `Write` / `Edit` / `git checkout` / `Remove-Item`、**worktree から本体を絶対パスで触る `git -C <本体> checkout` と `sed -i <本体のパス>`** が `exit_code 2` で止まり、worktree 内の操作・相対パスの `git commit`・読み取り・`.pipeline/` のロック回収・`VISIONARY_PIPELINE_ISSUE` を持つセッションは通ることを確認した(ここが通らないとパイプライン自身が死ぬ)。**このうち `git -C <本体>` は最初の実装で素通ししていた** — 書き込み判定の正規表現が `git checkout` の形しか見ておらず、動詞の前に大域オプションが挟まる形を落としていた。

**逆向きの誤りも1つあった。** リダイレクトを「`>` の後ろに非空白」で見ていたため、`grep ... 2>&1` のような**読み取りだけのコマンドが止まっていた**(2026-09-21 に #132 の作業中、worktree から走行中を覗く経路で 2 回踏んだ)。**ハンドルの合流(`>&1` / `>&2`)と捨て先(`/dev/null` / `$null`)を除外**し、`>> file` の追記は止まる側に残した。実測 7 ケース(`2>&1` / `2>/dev/null` / `*> $null` / 素の読み取りが通り、`> file` / `>> file` / `git checkout .` が `exit_code 2` で止まる)。

**Git Bash 形式の絶対パス(`/c/Users/...`)は素通ししていた**(2026-09-21、[#138](https://github.com/stama72/visionary/issues/138))。走行中の本体へ `cat > /c/Users/.../_probe.md` が通り、untracked を 1 本残した。照合していたのが `C:\...` と `C:/...` の 2 形だけだったためで、**この環境の `Bash` は Git Bash なので、これは抜け道の 1 例ではなく主要な経路が 1 つ抜けていた。** 綴りは `$mainRoot` から機械的に作って足した。

**穴は 2 か所にあった。** コマンド文字列を見る側(`Bash` / `PowerShell`)だけでなく、**`Edit` / `Write` の `file_path` を見る側も同じ形で抜けていた** — `[IO.Path]::GetFullPath('/c/Users/x')` は例外にならず、カレントドライブ直下の `C:\c\Users\x` を返すので、本体ツリーへの前方一致から**静かに**外れる。`Write` はこの綴りを受けて実際の場所に書く(実測)。判定の前に Windows 形へ直す。**綴り替えを効かせるのは Windows のホストだけである** — 本体が `/c/` 以下にある Linux ホストでは、本物のパスを `C:\...` へ変えてしまい、逆に守りが消える([#146](https://github.com/stama72/visionary/issues/146) でホストが増える)。

実測(2026-09-21、15 ケース): 使い捨ての git リポジトリに生きたロックを置き、フックへ直接イベントを流した。`/c/...` 形の `cat >` / `sed -i` / `rm` / `git -C <本体> checkout` と `Edit` の `file_path`(大文字ドライブ `/C/...` を含む)が `exit_code 2` で止まり、**carve-out は新しい綴りでも保たれる** — `/c/.../.claude/worktrees/` 配下・`/c/.../.pipeline/`(ロックの回収路)・読み取りだけの `grep`・本体の外・worktree 内のローカル書き込みは通る。`C:\...` / `C:/...` の既存 2 形も止まったままである。**あわせて、同じハーネスで `~` 形が素通しすることを 2 ケース測った**(上の表の行。#152)。

#### 走行中かどうかは目で判断しない

```powershell
pwsh scripts/pipeline.ps1 -Status
```

走っていれば issue 番号・フェーズ・PID・生ログを出して終了コード 1、走っていなければ 0 を返す。**停止の唯一の証拠はプロセスが消えることである。** オーケストレータの「止まりました」も、生ログ `.pipeline/*.jsonl` の末尾も、停止の証拠にならない(下記)。止めたいときは `Stop-Process -Id <PID>` であって、オーケストレータに頼むことではない。

### 停止則 — 4つだけ

| コード | 条件 | 判定 |
| ------ | ---- | ---- |
| `SPEC-OUTSIDE` | 象限I-b の訂正が**タスク仕様の外**(GDD / TDD / ADR)に及ぶ | **機械** + 自己申告 |
| `IMPL-BLOCKED` | implementer が「止まって報告」した | 自己申告 |
| `REVIEW-EXHAUSTED` | レビュー4巡目到達 / implementer が2回試して緑にならない | 自己申告 |
| `RED` | build / test / format が赤のまま先へ進みそう。**`DONE` 時に本体の作業ツリーが汚れている場合も含む** | 自己申告 + **機械**(作業ツリー) |

**差分で見えるものは機械が見ている。** フェーズ2 が `PIPELINE: DONE` を出しても、**フェーズ2 起動直前の `HEAD` から見て `docs/03-gdd/` `docs/04-tdd/` `docs/adr/` に差分があれば止める。** 基準が `master` でないのは、フェーズ1 が仕様を凍らせるときに GDD を直すのが正当な仕事で、その変更が既にブランチ上にあるためである。フェーズ3 は文書を触るのが仕事なので検査しない。

**`RED` も一部を機械が見る。** フェーズ2 が `DONE` を出した時点で `git status --porcelain` が空でなければ止める。拾うのは2つ — **コミットし忘れ**(検証した状態と PR になる状態が違う)と、**戻し忘れた変異**である。後者は W2-08 で実際に残った([#110](https://github.com/stama72/visionary/issues/110))。`.pipeline/` と `.claude/worktrees/` は `.gitignore` 済みなので、[ADR-0013](../adr/0013-mutation-measurement-separated.md) の使い捨て worktree 自身は現れない。

**この検査が見るのは、`DONE` を出した瞬間に残っている汚れだけである。** 次はいずれも素通しする:

- 走行中に本体へ変異を当てて、**戻した**場合(#110 の「変異作業中は並行走行の信号が鈍る」は、この検査では消えない)
- 変異を**コミットしてしまった**場合
- `HALT` で終わった場合(検査は `DONE` の枝にしかない)
- **開発者が手で `/impl` を回したとき**(`pipeline.ps1` を通らない)

**「変異が使い捨て worktree の中に閉じている」ことを機械は確かめていない。** そこは [`mutator`](../../.claude/agents/mutator.md) 憲章の規律である。

止まると**デスクトップ通知が飛び**、スクリプトは終了コード 2 で終わる。**`PIPELINE: DONE` も `HALT` も出さずに終わったフェーズは、停止扱いにする**(`NO-SENTINEL`)。フェーズが殺された・落ちた場合も合図が残らないので、同じ扱いになる。

**止まったら `.pipeline/<issue>-<フェーズ>-<時刻>.jsonl` を読む**(Git 管理外)。1イベント1行の JSONL で、**走っている間ずっと伸びる** — 走行中に何をしているかも、途中で死んだ場合にどこまで進んでいたかも、ここに残る。画面にも tool_use が1行ずつ流れる。

#### 停止したら、制御はパイプラインを起動したフェーズ1 に戻る

`pipeline.ps1` は停止時に `exit 2` で終わるので、**背景起動したフェーズ1 のセッションが「異常終了」として起こされる。新しいフェーズ1 を立てる必要は無い。** W2-08 では立ててしまい、走行中のツリーに 2 人の書き手が居る状態を作った([#109](https://github.com/stama72/visionary/issues/109))。

#### `NO-SENTINEL` は原因を1行で名指しする

同じ `NO-SENTINEL` でも中身が違う。W2-07(#96)の1回目はネットワーク断、2回目は**サブエージェントの打ち切り**で、**生ログを開くまで区別がつかなかった**([#100](https://github.com/stama72/visionary/issues/100))。`Get-NoSentinelDetail` が生ログから次を見分けて、通知の本文に載せる。

| 跡 | 意味 |
| -- | ---- |
| `Background tasks still running after … terminating` | **サブエージェントを待ち切れずに打ち切られた。** 合図を出す前に終わっている |
| 最終 `result` の `permission_denials` が非空 | 権限で拒否されたツール呼び出しが残っている |
| `is_error` / `api_error_status` | フェーズが異常終了した |
| `result` イベントが無い | 殺された / 落ちた / 中断 |

**打ち切りの上限は `pipeline.ps1` が `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` で 1 時間に広げてある。** 非対話モード(`claude -p`)はサブエージェントが走っている間は待つが、**待ちがアイドルのまま 10 分続くと走っているものを止め、部分結果を捨てる。** W2-07 の2回目がそれで、オーケストレータの「完了通知を待ちます。」がそのまま最終メッセージになった。無限待ちにしないのは、ハングが通知も出さずに居座るほうが高くつくためである。

**これは打ち切りを遅らせるだけで、ハングを見分けてはいない。** 実行基盤を替えれば上限そのものが要らなくなる可能性があり、[#146](https://github.com/stama72/visionary/issues/146)(デスクトップ PC で走らせる)に申し送ってある。

止まらないもの(implementer の「決めて報告」/ レビュー1〜3巡の指摘と修正 / 気付いたことの issue 化)の根拠は [ADR-0010](../adr/0010-phase-pipeline-and-halt-conditions.md) 論点2。

### 合図は最後の `result` にしか意味が無い

**`result` はターンの終わりであって、プロセスの終わりではない。** サブエージェントを走らせたままオーケストレータがターンを閉じると、そこにも `result` が出る。W2-08 の1回目のフェーズ2 は `result` を 4 件出しており、**合図を含むのは最後の1件だけ**、他の3件は「implementer に渡しました。完了を待ちます。」だった。その間もサブエージェントは走り続け、コミットまで行っている。

- **`pipeline.ps1` の判定は壊れていない** — `Get-PhaseResultText` は最後の `result` だけを読む
- **壊れているのは人間に見えている合図のほうである。** 走行中の画面(`Write-PhaseProgress`)にも「待ちます」が流れるし、開発者の問いかけへの返答も「止まりました」になる。**オーケストレータはサブエージェントを止める手段を持っていない**ので、「止めました」は答えられない答えである
- したがって**停止の確認は `-Status`(= PID の生存)に一本化する**

### 手で回すとき

停止則に当たった後の再開や、パイプラインを使わない場合は、**開発者が `/clear` してから** `/impl <issue番号>` `/wrap <issue番号>` を開く。フェーズ3 だけやり直すなら `pwsh scripts/pipeline.ps1 -Issue 35 -From wrap`。

**`/clear` は機械で守れない。** 忘れても何も壊れないが、節約も起きない。パイプラインを通す限りこれは起きない — 境界がプロセス境界になるためである。

**モデルも自分で選ぶ。上の表の Sonnet を握っているのはパイプラインの `--model` だけである** — 手で開けば `/impl` も `/wrap` も既定(opus)で走る。`wrap.md` に `model:` を置いても対話では効かないので、[ADR-0014](../adr/0014-interactive-sessions-follow-the-default-model.md) で外した。**フェーズ3 を sonnet で回したいなら、開くときに自分で選ぶ。**

## 何が「実装タスク」か

**`docs/tasks/` に仕様があるものが実装タスクであり、その実装は必ず implementer が書く。**([ADR-0009](../adr/0009-phase-scoped-sessions.md) 論点3)

仕様を書くまでもない規模なら、そもそも実装タスクではない — [02-task-spec](02-task-spec.md) 規則2(「宣言のみでよい」と書かない)の裏返しである。

**設計・プロセス・文書のみの変更は、この3フェーズに乗らない。** レビュアーではなく [`/advise`](../../.claude/commands/advise.md) と開発者が見る([01-review](01-review.md))。**進め方は [06-design-sessions](06-design-sessions.md) が持つ** — 束ごとに決めて書いてコミットし、引き継ぎメモは書かない。フェーズ1 と設計タスクの境界(却下する選択肢があるか)も同書。
