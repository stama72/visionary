# プロセス 05 — フェーズごとにセッションを切る

| 項目     | 内容                                                                 |
| -------- | -------------------------------------------------------------------- |
| 種別     | 育てる文書(現行の運用を持つ)                                        |
| 関連     | [ADR-0009](../adr/0009-phase-scoped-sessions.md)(3フェーズ) / [ADR-0010](../adr/0010-phase-pipeline-and-halt-conditions.md)(連鎖と停止則) / [ADR-0004](../adr/0004-ai-driven-development-workflow.md) 論点1・論点2 |

**1タスクを3つのフェーズに切る。** なぜそう切るかは [ADR-0009](../adr/0009-phase-scoped-sessions.md) が、**フェーズ2・3 を機械が繋ぐこと**は [ADR-0010](../adr/0010-phase-pipeline-and-halt-conditions.md) が持つ。本書は**今どう運用するか**を持つ。

## 3つのフェーズ

| | フェーズ1 設計 | フェーズ2 実装とレビュー | フェーズ3 文書更新と PR |
| --- | --- | --- | --- |
| 起動 | 既定のメインセッション | [`/impl`](../../.claude/commands/impl.md) | [`/wrap`](../../.claude/commands/wrap.md) |
| モデル | `~/.claude/settings.json` の既定(**opus**。[ADR-0014](../adr/0014-interactive-sessions-follow-the-default-model.md) / [06](06-design-sessions.md)「モデル」) | Opus(実装は Sonnet の implementer) | **Sonnet**(**パイプラインの `--model` が握る**。[`wrap.md`](../../.claude/commands/wrap.md) 側には何も無い) |
| 成果物 | タスク仕様の凍結 | 緑のコードとコミット | PR と切り出した issue |
| 終わり方 | 引き継ぎメモを書き、**パイプラインを背景起動して止まる** | 引き継ぎメモに追記し `PIPELINE: DONE` | PR を作り `PIPELINE: DONE` |

**フェーズ2 のメインはコードを読み書きしない。** 実装も、レビュー指摘の修正も implementer に渡す。ここが崩れると、実装を Sonnet に逃がした節約がそのまま消える。

**例外は象限I-b(仕様そのものの欠陥)だけ。** 仕様の訂正は設計判断なので、メインが仕様を直してから implementer に渡す。

## 引き継ぎメモ

**`docs/tasks/W<段階>-<連番>-<スラッグ>.handoff.md`。** ファイル名とテンプレートは [docs/tasks/README.md](../tasks/README.md)。

### 書くもの — 5件だけ

| # | 項目 | どのフェーズで書くか |
| - | ---- | -------------------- |
| 1 | **却下した設計案と理由**(ADR に載らない大きさのもの)と、**却下によって失われる保護** | 1 |
| 2 | **implementer の件数** — 止まって報告した / 決めて報告した | 2 |
| 3 | **直さないと決めたレビュー指摘と、その理由** | 2 |
| 4 | **巡ごとの件数**(0件の巡を含む)と、打ち切ったならその理由。**網羅に充てた巡があれば、その境界も**([01-review](01-review.md)) | 2 |
| 5 | **`mutator` の件数** — 当てた変異の数と、**期待と食い違った数**(0件なら「0件」)。[ADR-0013](../adr/0013-mutation-measurement-separated.md) の検証条件で、記録先は PR 説明である | 2 |

#### 却下の代償を1行で書く

**却下理由は「なぜ採らないか」しか書かないので、失うものは別に書かないと消える。**

W2-05 は「`BuyerDemand` を `TradeSystem` に繋ぐ」を却下した。**却下の判断そのものは妥当だった**(計算結果を誰も読まないので、用途を落としても緑のまま)。だが代償 — **配線が統合テストの保護を受けない** — は見積もられていなかった。結果、4巡16件の指摘がすべてテストの判別力・網羅度に費やされ、10件が未検証のまま [#37](https://github.com/stama72/visionary/issues/37) へ渡った([02-task-spec](02-task-spec.md) 規則7)。

### 書かないもの

**既にどこかに残るものは書かない。** 器を作ると全部書きたくなるので、書かない側を先に決めてある。

| 書かないもの | 既にどこに残るか |
| ------------ | ---------------- |
| 型・シグネチャ・テスト表・編集してよい文書・スコープ外にした判断 | タスク仕様 |
| **採った**設計の理由 | コードの doc コメントと TDD(implementer 憲章が要求している) |
| 直したレビュー指摘の内容と対応 | コミット本文 |
| **設計フェーズ内で自分で捕まえた仕様の誤りと、直した内容** | **仕様を凍結するコミットの本文**(下記) |
| 当てた変異と結果 | doc コメントかコミット([02-task-spec](02-task-spec.md))。**`mutator` の報告そのものは `.pipeline/*.jsonl` にしか残らない**ので、件数だけメモの #5 が持つ |
| build / test / format の結果 | フェーズ3で再実行できる |

#### 設計フェーズ内で捕まえた仕様の誤り

**フェーズ1 が自分で見つけて直した仕様の誤りは、仕様を凍結するコミットの本文に書く。** 仕様は最終形しか見せないので、書かなければ消える。

メモに入れないのは、**フェーズ内で完結し、後のフェーズへ判断を引き継がない**ためである。メモは境界を越える情報の器である。

コミット本文を選ぶのは、消えるのを防ぐだけが理由ではない。[02-task-spec](02-task-spec.md) の先行指標「仕様の穴の数」は、いま **implementer が突き当たった穴しか数えられない** — 設計フェーズが自分で塞いだ穴は、塞がれたことで指標から消える。コミット本文に書けば `git log` で数えられる。

### メモに入れないが、記録する1件

**「引き継ぎメモの不足で、後のフェーズが止まった・判断をやり直した回数」は PR 説明の検証節に書く**(0 件でも「0 件」と書く)。[ADR-0009](../adr/0009-phase-scoped-sessions.md) の検証条件である。

メモに足さないのは、**書く主体がフェーズ3 だけで、フェーズをまたがない**ためである。メモは境界を越える情報の器である。

### 寿命

**使い捨て層。フェーズ3 で PR 説明へ転記し、同じブランチの最後のコミットで削除する。** add と delete が同じ PR に入るので、差分には現れず master にも残らない。正は PR 説明である。

## どこで走らせるか

**実装タスクはデスクトップで、文書だけの仕事はラップトップで走らせる。** 両方が本体ツリーを持つ([#146](https://github.com/stama72/visionary/issues/146) 決定1)。

| | ラップトップ | デスクトップ |
| --- | --- | --- |
| 本体ツリー | 持つ | 持つ |
| [`/design`](06-design-sessions.md)(設計・プロセス・文書のみ) | **ここで開く** | 開いてよい |
| **実装タスクのフェーズ1** | 開かない | **ここで開く**(ssh で入って `claude --bg` で。下記) |
| `pipeline.ps1` | 打たない | **ここで打つ**(フェーズ1 が背景起動する) |
| 電源 | 移動中に閉じる | **AC ではスリープも休止もしない**(`powercfg` の `STANDBYIDLE` / `HIBERNATEIDLE` が AC = 0) |

分ける理由は、**パイプラインが止まらない条件に「起動したマシンが生きていること」が入っている**ためである。ロック `.pipeline/<issue>.lock` は PID の生存で判定し、停止の証拠もプロセスが消えることだけである(下記「走行中かどうかは目で判断しない」)。移動中に閉じるマシンでこれを回すと、**停止則のどれにも当たっていないのに死ぬ。**

**フェーズ1 をパイプラインと同じマシンに置くのは、[ADR-0010](../adr/0010-phase-pipeline-and-halt-conditions.md) を無傷で残すためである。** フェーズ1 は仕様を凍結したら**自分で背景起動して終わる**(下記)。これが開発者の「終わったので次を打つ」待ちを消している唯一の仕掛けなので、**フェーズ1 と `pipeline.ps1` の間にマシン境界を入れない。**

**`/design` だけラップトップに残るのは、文書の仕事がパイプラインを起動しないからである。** 束ごとにコミットして終わるので、マシンを分けても ADR-0010 に触れない。

### フェーズ1 は背景セッションで開く

**デスクトップで実装タスクのフェーズ1 を開くときは、机の前にいても `claude --bg` で生やし、`claude attach <id>` で繋ぐ**([#146](https://github.com/stama72/visionary/issues/146) 決定8)。素の `claude` で開かない。**入るのは ssh からである**(下記「入口は ssh に一本化する」)。**`/design` は対象外** — パイプラインを起こさないので、切れて失うのは端末だけである。

**素の `claude` で開いた回に失うのは、セッション1つではなく「停止で起こされる先」と「`DONE` 時の独立確認」である。** フェーズ1 は仕様を凍結したら背景起動して待つ。端末が切れてフェーズ1 ごと死ぬと、**`pipeline.ps1` が `exit 2` で終わっても起こされる相手が居ない**ので、停止の受け取りが手で見に行く形に戻る(下記「停止したら、制御はパイプラインを起動したフェーズ1 に戻る」)。**`DONE` 時に build / test / format と PR を独立に確認する**役も落ちる — **フェーズ3 も build / test / format は再実行するが、その出力と PR を別プロセスから独立に見るのはフェーズ1 だけである。** **`claude --resume` が戻すのは会話だけで、どちらも戻らない。**

**停止通知そのものは届く。** 出しているのは `pipeline.ps1` 自身で、フェーズ1 の生死に依らないからである(下記「出先で停止を知る経路」)。**ただし素の `claude` が死んだとき、その下の `pipeline.ps1` まで道連れになるかは測っていない。** 下の表で切り離された子は生き残っているので走り続ける側が濃いが、確かめてはいない。**落ちる側なら通知も出ずに走行が消える。**

**条件付きにしない**(「出先から繋ぐときだけ `--bg`」)。外れるのが**離席を決める前に開いてしまった回**、つまりちょうど必要な回になる。

**機械は拒否しないが、打った瞬間に気付ける。** `pipeline.ps1` は起動時に自分の祖先を辿り、**3値で答える**([#146](https://github.com/stama72/visionary/issues/146) 決定12)。`--bg` のマーカーが見つかれば黙り、根まで辿って見つからなければ警告し、**読めない祖先に当たったら「判定できませんでした」と出す。**

**`unknown` で黙らないのは、ssh の前景がちょうどその形を通るからである。** 非昇格から SYSTEM 持ちの `sshd` を見ると `CommandLine` が空で返り、**そこから上は辿れない。** 黙る設計にすると、**いちばん守りたい形が沈黙で「合格」に見える。**

**拒否にしないのは、判定が「不明」を返すからである。** 拒否にすると、正しく打った回が止まる。**判定が2値になれば、拒否にするかを再検討してよい。**

**警告は画面にしか出ない。** 生ログにも issue コメントにも入らないので、**「後から分かる」ではなく「打った瞬間に気付ける」までである** — 破った回は端末が死ぬ回なので、後から読む先が無い。

**ssh を切っても生き残ることは実測済みである**(2026-09-23、`claude 2.1.268`)。ssh で入り、**クライアントを強制終了**して測った — **蓋を閉じるより厳しい形である。** クライアント殺しは TCP を即座に閉じるので sshd がその場でセッションを畳むが、蓋を閉じた場合は keepalive が切れるまで畳まれない。

| ssh セッションで生やした形 | 切断すると | 現実で対応するもの |
| --- | --- | --- |
| **前景(pty に繋がる)** | **死ぬ** | 素の `claude`、手で打つ `pipeline.ps1` |
| 切り離した子(`Start-Process`) | 生きる | — |
| **`claude --bg` のセッションと子・孫** | **生きる** | フェーズ1 と、その下のパイプライン |

**sshd は自分のセッションのプロセスは畳んでいる。** 畳まれないのは、そこから切り離された側である。`--bg` が切り離されているのは、デーモンが **`WmiPrvSE.exe` を親として**起きるからで、起動したシェルは親でも祖先でもない。**走行中で測っている** — セッションは `bash.exe` の子・孫を抱えた `status: busy` の状態だった。

**入り直した ssh からは、そのセッションが見える。** `claude agents` に出るので `claude attach <id>` で戻せる。

走行中かどうかの確認は、これまでどおり `pipeline.ps1 -Status`(= PID の生存)が持つ。`claude agents` が見せるのはセッションの生死であって、パイプラインの生死ではない。

#### 入口は ssh に一本化する — 机の前でも `ssh localhost`

**フェーズのセッションは、机の前にいても ssh で入ってから `--bg` で開く**([#146](https://github.com/stama72/visionary/issues/146) 決定13)。**手で開く `/impl` `/wrap` も、手で打つ `pipeline.ps1` も同じである。**

**理由は、デーモンがユーザーごとに1つしか無いからである。** `--bg` のセッションを抱えるデーモンはパイプ名を共有しており、**ssh 発のものが Session 0 に居ると、console 側は見えない・止められない・新しく作れない**(実測 2026-09-23)。

```
console から claude --bg → Couldn't reach the background service (45s)
claude daemon status     → not running / control.sock: unreachable
claude daemon stop --any → no daemon running   ← 実際には Session 0 に生きている
```

**`claude daemon status` は console から嘘をつく。** 放っておくと、**出先から ssh でフェーズ1 を開いた翌日、机で `--bg` を開けない。** 非対称を消す方法は「常に同じ側に居る」ことだけなので、ssh 側に寄せた。**代償は、机の前でも毎回パスワードを打つことである**(鍵認証は [#189](https://github.com/stama72/visionary/issues/189))。

**ssh のログオンは Session 0(サービス側)に入る。** 机の前の console は Session 1 である。**この境界は、同じユーザーでも越えられない。**

| | |
| --- | --- |
| **見えない** | console の `claude agents` に、ssh 発の `--bg` セッションは**出ない**(`claude logs` は `ECONNREFUSED`)。逆向き(ssh から console のセッション)は見える |
| **止められない** | 非昇格の console から Session 0 のプロセスは**アクセス拒否**で止められない。**机の前から、ssh 発のパイプラインを手で止められない** |
| **デスクトップ通知が消える** | Session 0 から `NotifyIcon` のバルーンを出しても**例外は出ないのに、画面には出ない**(実測)。`Send-Notification` の `catch` が発火しないので `Write-Warning` すら残らない |

**したがって、出先から ssh で起動したパイプラインの通知は issue コメントの1経路である**(下記「出先で停止を知る経路」の2経路は、**机の前で console から起動したときの話**)。**出先へ届く経路そのものは無傷**なので、通知の実装を Session 0 でも届く形に直すのは [#188](https://github.com/stama72/visionary/issues/188) に置いた。

### 出先からデスクトップへ繋ぐ経路

**到達はオーバーレイ(Tailscale)、シェルは Windows の OpenSSH Server である**([#146](https://github.com/stama72/visionary/issues/146) 決定3・決定9)。出先からはデスクトップへ ssh で入り、そこでフェーズ1 を `--bg` で生やす。

**役割が2つに分かれているのは、Tailscale SSH が Windows をサーバ側にできないからである**(サーバ側は Linux と macOS のみ。[Tailscale SSH](https://tailscale.com/kb/1193/tailscale-ssh))。**オーバーレイが買うのは到達性だけで、認証とシェルは ssh 側に残る。**

ルータのポート開放ではなくオーバーレイなのは、**攻撃面ではなく到達性で選んでいる**ためである。大学のネットワークは着信だけでなく発信も絞ることがあり、「着いてから通らないと分かる」失敗は出先で詰む。オーバーレイなら直結が塞がれても中継(443/TCP)に落ちる。**したがってこの経路は、出先のネットワークが中継を通すことに依存する。**

### 出先で停止を知る経路

**パイプラインの通知は2経路に出る。デスクトップ通知と、対象 issue へのコメントである。** 停止則・枠ガード・鮮度ガード・完了のすべてが同じ関数を通る。**ただし ssh から起動した場合、実際に出るのは issue コメントだけである**(上記「入口は ssh に一本化する」)。

**デスクトップ通知だけでは届かない。** 実装タスクを走らせるマシンは無人だからである(そのマシンがスリープしないことは、無人であることの裏返しでもある)。そのままだと「出先から起動 → 数分で `IMPL-BLOCKED` → 気付くのは帰宅後」になり、[ADR-0010](../adr/0010-phase-pipeline-and-halt-conditions.md) が消した待ちが形を変えて戻る。

**issue コメントが出先へ届く経路は、GitHub の「自分の更新」メール通知である**(実測 2026-09-22)。**GitHub Mobile のプッシュ通知ではない** — プッシュは直接メンション / アサイン / レビュー依頼 / デプロイ承認依頼の4種だけで、**issue コメントは対象外**である([Configuring notifications](https://docs.github.com/en/subscriptions-and-notifications/get-started/configuring-notifications))。したがって**この経路は GitHub の設定「自分の更新をメールに含める」に依存する。** 切れば静かに届かなくなる。

**`claude -p` の外側で `gh` を打つので、Remote Control が `claude -p` に届くかどうかには依存しない。**

**スマホはこの通知の受け口だけである**([#146](https://github.com/stama72/visionary/issues/146) 決定10)。Tailscale も ssh クライアントも置かない。**したがって出先でスマホだけを持っているとき、分かるのは「止まった」「終わった」までで、「まだ生きているか」は分からない。**

**通知が出るのは、`pipeline.ps1` が生きていて `gh` が通ったときである。** 保証できるのはここまでで、内訳は3つに分かれる。

- **乗る** — フェーズ2・3 のサブエージェント待ちは1時間で打ち切られ、`NO-SENTINEL` として停止扱いになって通知に乗る(下記)。**この上限が掛かるのは `claude -p` で走るフェーズ2・3 だけで、`--bg` のフェーズ1 には掛からない**
- **出ない(プロセスが消える形)** — フェーズ1 の道連れ・マシンの再起動。`Send-Notification` は**両経路とも fail-open** で、`gh` が打てなければ警告が**無人の画面**に出るだけである。**しかも故障は相関する** — `NO-SENTINEL` の実例(下記 W2-07 の1回目)はネットワーク断で、`gh` も打てない状況である
- **出ない(生きたまま進まない形)** — 筆頭は **`--bg` のフェーズ1 が権限プロンプトで黙る経路**で、このとき `pipeline.ps1` はまだ起動していないので**ロックも通知も無く、`-Status` は「走っていない」と答える。見分ける手は `claude logs <id>` だけで、それには ssh が要る** — スマホには置かない。**未測である**

埋めるとしたら [#186](https://github.com/stama72/visionary/issues/186) だが、**出先は主に大学でそこにはラップトップがある**ので、足りないのは通学中だけと見ている。

### 本体ツリーが2つあると何が起きるか

**「本体ツリーは1つ」という前提は、マシンをまたいでは成り立たない。** `.pipeline/` は `.gitignore` 済みで、ロックも `PreToolUse` フックも**そのマシンの中しか見ていない。**

開く穴は4つで、機械が塞ぐのは1つである。

| 穴 | 塞げるか |
| -- | -------- |
| **デスクトップの本体が `origin/master` より遅れたままパイプラインを打つ** | **塞ぐ。** 鮮度ガードが起動を拒否する(終了コード 5)。遅れた本体で実装すると、**一世代前の GDD / TDD / 既存コードを正確に前提にした結果**が残り、出来上がりを読んでも正しく見える。束1 の作業中に実際に 18 コミット(W2-15 一式)遅れていた。**見ているのは HEAD が `origin/master` を含むかだけで、ブランチ上のタスク仕様の新旧は見ていない** |
| **コミットしていない作業が片方のマシンに取り残される** | **塞げない。** 束ごとにコミットする規律([06](06-design-sessions.md))だけが防波堤である |
| **ラップトップの `/design` が、デスクトップのフェーズ3 が master に入れた文書更新より古い本体で、同じ GDD / TDD を書く** | **塞げない。** `/design` は `pipeline.ps1` を通らないので鮮度ガードが当たらない。**別の節を触れば git は綺麗にマージする**ので、一世代前の文書を正確に編集した結果が残る — 鮮度ガードが塞ぐ失敗と同じ形である。**入口で `git pull` するのを規律とする**([06](06-design-sessions.md)「束」)。**遅れに上限は無い** — `master` を動かしているのはデスクトップのフェーズ3 なので、ラップトップを数日開かなければ遅れは実装タスク数本ぶんになる |
| 2台で同時に `pipeline.ps1` を打つ | 機械は止めない(ロックが互いに見えない)。**WIP の規律**([04](04-issue-driven.md))が先に効く |

## フェーズをまたぐときの手順

**フェーズ1 は、仕様を凍結したら自分でパイプラインを背景起動して終わる。**

```powershell
pwsh scripts/pipeline.ps1 -Issue 35
```

`claude -p "/impl 35"` → `claude -p "/wrap 35"` を**別プロセス**で順に回す。プロセスが別なのでコンテキスト窓も別で、`/clear` と同じ隔離になる。

**打つのがフェーズ1 なのは、開発者が打つ形だと「終わったので次を打つ」待ちがそのまま残るためである。** それを無くすのが [ADR-0010](../adr/0010-phase-pipeline-and-halt-conditions.md) の目的で、同 ADR 論点1 の選択肢2 も「フェーズ1 のセッション(または素のシェル)がスクリプトを起動し」と書いている。

**待っている間にフェーズ1 が使うターンは 0 である。** W2-04(#35)の実測で、36分の待ちに対してターン 0(背景実行のツール呼び出し1件でブロックし、完了で起こされる)。起こされた後の事後検証6ターンぶんは $2.68 で、build / test / format の独立再実行を1回増やすぶんに当たる。**選択肢3(サブエージェント連鎖)を却下した理由 — 親が子の報告を読んでコンテキストが育つ — は、背景実行のブロッキング呼び出しには当たらない。**

開発者が手で打ってもよい。停止則に当たった後の再開はそうなる。

**Git Bash からは呼べない。** MSYS が先頭の `/` を `C:/Program Files/Git/...` に変換し、スラッシュコマンドとして解決されない。PowerShell から回すこと。

### パイプラインが走っている間、本体の worktree はパイプラインのものである

**無人フェーズは `git commit` / `git checkout` / `gh pr create` を回している。** 同じ作業ツリーを開発者が同時に触ると、コミットに巻き込まれるか、`git checkout` で消える。

パイプライン以前は「1タスク = 開発者が張り付く1時間」だったので、この衝突は起こりえなかった。**無人フェーズ中に開発者が空くのは [ADR-0010](../adr/0010-phase-pipeline-and-halt-conditions.md) の狙いどおりだが、空いた開発者が行く先を決めていなかった。**

したがって次を規律とする。

- **パイプライン実行中、本体の `visionary/` は触らない。** 並行して進める別タスクは **worktree を分ける**
- 本体で待つのが自然なのは、パイプラインを起動したフェーズ1 のセッション自身だけである(完了で起こされ、build / test / format と PR を独立に確認する)
- **5 時間枠の残りは `pipeline.ps1` 自身が起動時に読み、足りなければ起動を拒否する**(終了コード 4。[04「枠」](04-issue-driven.md) 規則2)。フェーズ1 は打つ前に自分で読まなくてよいが、**拒否されたらリセット時刻を開発者に報告して止まる**(拒否の理由とリセット時刻は標準出力・デスクトップ通知・issue コメントに出る)。`/usage` は CLI の UI なのでセッションからは読めないが、haiku の 1 呼び出し($0.11 = 枠の 0.05%)で同じ値が取れる(実測 2026-09-20)。**規則1 のために自分で残りを見たいとき**は、この 1 行で読む:

  ```
  claude -p --model haiku --output-format stream-json --verbose "OK" | grep -o '"five_hour":{"utilization":[0-9.]*,"resetsAt":[0-9]*' | tail -1
  ```

  `utilization` が 0.60 を超えていれば残り 40% 未満。`resetsAt` は Unix 秒

- **本体が `origin/master` を含まなければ起動を拒否する**(終了コード 5)。**拒否されたフェーズ1 は `git pull` せず、開発者へ返して止まる。** ブランチには凍結済みのタスク仕様が乗っているので、rebase か merge かの判断が要る — **機械に負わせない。**

W2-04 と #68(世界観と正式タイトル)が 21:12〜21:16 に重なったが、#68 が `.claude/worktrees/` にいたため衝突しなかった。**成立したのは worktree が分かれていたからで、WIP の数え方が守ったのではない。**

#### いまはこれを機械が守っている

**W2-08(#97)で規約は破れた。** 走行中のフェーズ2 に重ねて新しいセッションが立ち、本体ツリーへ 3 回書き込み、`git checkout` で implementer が当てたばかりの変異を消した。**ログの中では原因不明の環境問題として記録された**([#109](https://github.com/stama72/visionary/issues/109))。規約しか無いものは、こう破れて、破れたことも見えない。

| 部品 | 何をするか |
| ---- | ---------- |
| `scripts/pipeline-lock.ps1` | ロック `.pipeline/<issue>.lock`(PID と起動時刻)の読み書き。**生きている = その PID が今も居て起動時刻も一致する** |
| `scripts/pipeline.ps1` | 起動時にロックを取り、終了時(`exit` を通っても)に外す。**生きているロックがあれば起動を拒否する**(終了コード 3) |
| `scripts/check-budget-threshold.sh` | 枠ガードの閾値の**写しが正からずれていないか**を CI で見る([#139](https://github.com/stama72/visionary/issues/139))。正は `pipeline.ps1` の `$DefaultMinRemaining` で、写しは [04「枠」](04-issue-driven.md) 規則2 / CLAUDE.md / **この節の haiku 1 行**(使用率 0.60 の側も突き合わせる)。**数値が取れなければ落とす**(fail-closed)なので、文面を書き換えると数値が正しくても落ちる — そのときは検査の錨を直す |
| `scripts/pipeline.ps1` の枠ガード | 起動時に **5 時間枠の残りを haiku 1 呼び出しで読み、足りなければ起動を拒否する**(終了コード 4)。**読めなければ拒否する**(fail-closed)。閾値は `-MinRemaining`、`0` で検査しない。壊して確かめる口は `-DryRun -DryRunProbe short\|near-reset\|fail` |
| `scripts/pipeline.ps1` の鮮度ガード | `-From impl` のとき、起動時に `git fetch origin master` して、**本体が `origin/master` を含まなければ起動を拒否する**(終了コード 5。[#146](https://github.com/stama72/visionary/issues/146))。**fetch できなければ拒否する**(fail-closed)。**逃げ口は置いていない** — フェーズ本体は `claude -p` なので、ネットワークが無ければどのみち走らない。壊して確かめる口は、使い捨て worktree を `HEAD~1` に置いて打つこと。**開発者が手で `/impl` を回すときは当たらない**(`pipeline.ps1` を通らない)— 停止則の後の再開路がそれで、`master` が動いている可能性がいちばん高い場面である |
| `scripts/pipeline-guard.ps1` + `.claude/settings.json` | `PreToolUse` フック。生きているロックがある間、**本体ツリーへの書き込みを止める**(`Edit` / `Write` と、書き込む形の `Bash` / `PowerShell`) |

素通しする経路は4つ:**パイプライン自身のセッション**(`pipeline.ps1` が渡す `VISIONARY_PIPELINE_ISSUE`)/ **worktree の中**(`.claude/worktrees/`)/ **読み取り**(`git status` や `Grep` は止めない — 走行中の様子を見にいけなくなる)/ **`.pipeline/` への書き込み**(ロックの回収路。ここを止めると、誤って居座ったロックを Claude のセッションから外せなくなる)。

#### 何が止まらないか

**これは「絶対に衝突しない」ではなく「うっかりが止まる」である。** 止まらないものを数え上げておく。

| 止まらないもの | なぜ |
| -------------- | ---- |
| **相対パスで本体へ届く `Bash` / `PowerShell`** — `git -C ../../.. checkout` / `dotnet --project ../..` | `Edit` / `Write` は対象ファイルを見るが、**シェルは cwd と「コマンドに現れる本体の絶対パス」しか見ていない。** 抜け道は無限にあるので、機械を厚くせず境界を書く側に倒した |
| **任意コードの実行** — `dotnet fsi probe.fsx` / `python` / `node` / `pwsh -c` | 止めているのは**書き込む形のコマンド**であって、スクリプトの中で何を書くかは追えない。**`dotnet new` は止まる**(出力先の指定によらずファイルを作るので、動詞だけで書き込み判定として成立する)。`dotnet fsi` を足すと同じ理屈が上のすべてに及ぶので足していない — 憲章(`reviewer.md` / `mutator.md`)の文言で受ける([#134](https://github.com/stama72/visionary/issues/134))。**動詞が引用符の中にしか出ない形は下の行が持つ**(#166 で狭まったので、別に数え上げる) |
| **動詞が引用符の中にしか現れない書き込み** — `bash -c "rm <本体>/docs/x.md"` / `pwsh -c "Remove-Item x"` / `"rm" -rf docs` | 書き込み判定は**引用符を潰してから**当てる([#166](https://github.com/stama72/visionary/issues/166))。書き込み判定は早期 `exit 0` で、**cwd 判定にも絶対パスの照合にも上流**にあるので、**そこを通らなければどちらにも届かない。****`cwd` が本体のセッションでも止まらない**(`bash -c "rm docs/x.md"` は素通しする。実測)— **#109 の実害は「2つ目のセッションが本体ツリーで `git checkout` を打った」形で絶対パスを必要としないので、開いた穴の主たる面はこちらである。** worktree から本体を絶対パスで名指しする形(`bash -c "rm <本体>/docs/x.md"`)も同じく素通しする。**#166 で狭まった側である。** 順序を入れ替えて守る側に倒すと、実測された偽陽性が戻る(`mutator` M-7 で 3 件)ので、境界を書く側に倒した。**ハーネスが `expect = 0` の 2 件で固定している**(1 件目が「cwd が本体でも止まらない」、2 件目が「絶対パスの照合にも届かない」)— 落ちたら**塞がないと決めたものを塞いだ**ということで、この行と #166 の決定ログを直す |
| **フックを承認していないセッション** | フックは**開発者が1回承認するまで動かない。** 承認は設定の内容にひもづくので、`.claude/settings.json` を1文字変えると未承認に戻りうる |
| **判定に失敗したとき** | フックは例外をすべて素通しに倒す(判定の失敗で開発が止まるほうが高くつく)。**黙って素通しはしない** — `.pipeline/guard-failures.log` に1行残る。`exit 0` のフックの標準出力は transcript(ctrl+o)にしか出ないので、画面だけに頼ると守る側が静かに壊れる |
| **Claude のセッション以外** | 素のターミナルや他のエディタからの書き込みはフックを通らない |
| **走行中に枠が切れること** | 枠ガードは**起動時の 1 点しか見ない。** 起動後に別のセッションが枠を食えば、通した判定は外れる。走行中の監視は置いていない(枠切れの死は生ログの `is_error` に出る) |
| **週次(`seven_day`)の枠** | ガードが**判定に使うのは 5 時間枠だけ**である(週次は残りを**表示するだけ**)。とくに「リセットが近ければ要求を下げる」の前提(リセットで utilization が 0 に戻る)は**週次には成り立たない** — そして緩和がいちばん効く局面(5 時間枠を焼き切った直後)は、週次も高い局面である。閾値の根拠が無いので判定に入れていない([#141](https://github.com/stama72/visionary/issues/141) / 校正は [#123](https://github.com/stama72/visionary/issues/123)) |

逆に、**本体に居るセッションが worktree を絶対パスで触る**のは止まる(cwd が本体なので)。対称ではない。

実測(2026-09-20、17 ケース): 本体への `Write` / `Edit` / `git checkout` / `Remove-Item`、**worktree から本体を絶対パスで触る `git -C <本体> checkout` と `sed -i <本体のパス>`** が `exit_code 2` で止まり、worktree 内の操作・相対パスの `git commit`・読み取り・`.pipeline/` のロック回収・`VISIONARY_PIPELINE_ISSUE` を持つセッションは通ることを確認した(ここが通らないとパイプライン自身が死ぬ)。**このうち `git -C <本体>` は最初の実装で素通ししていた** — 書き込み判定の正規表現が `git checkout` の形しか見ておらず、動詞の前に大域オプションが挟まる形を落としていた。

**逆向きの誤りは2つあった。** リダイレクトを「`>` の後ろに非空白」で見ていたため、`grep ... 2>&1` のような**読み取りだけのコマンドが止まっていた**(2026-09-21 に #132 の作業中、worktree から走行中を覗く経路で 2 回踏んだ)。**ハンドルの合流(`>&1` / `>&2`)と捨て先(`/dev/null` / `$null`)を除外**し、`>> file` の追記は止まる側に残した。実測 7 ケース(`2>&1` / `2>/dev/null` / `*> $null` / 素の読み取りが通り、`> file` / `>> file` / `git checkout .` が `exit_code 2` で止まる)。

**2つ目は引用符である**(2026-09-21、[#166](https://github.com/stama72/visionary/issues/166))。書き込み判定の列挙は語境界もアンカーも持たずコマンド文字列全体に当たるので、**検索パターンとして書いた動詞が書き込み判定を通していた** — `grep -n "Remove-Item|prune|…" scripts/pipeline.ps1` が走行中に 2 回止まった。`grep` / `rg` / `Select-String` / `echo` すべてに当たる形で、**発火する場所が偏っている**(走行中に `pipeline*.ps1` を読みに行くのは、まさに別セッションがやる作業である)。**引用符で囲まれた区間をプレースホルダ 1 文字へ潰してから照合する。**

- **潰す先を空白にすると偽陰性が開く。** `git -C "<本体>" checkout` は `(-C\s+\S+\s+)*` の `\S+` を満たさなくなり、**書き込み判定ごと外れる**。非空白 1 文字なら引数が在ったことだけが残る(ハーネスがこのケースを持つ)
- **剥がした文字列の行き先は書き込み判定だけである。** 本体の絶対パスの照合は剥がす前に当てているので、`rm "<本体>/docs/x.md"` は止まったままである。**`.pipeline` の回収路判定も剥がす前だが、こちらは極性が逆で、素通しを広げる側である** — 「剥がす前に当てる = 守りが消えない」という一般則ではない
- **対応が取れなければ元の文字列に落とす**(素通しではない)。エスケープ(`\"`)は見ていない — 見ないほうが不揃いな引用符が「対応が取れない」に落ちる

**壊して確かめた**(2026-09-21、`mutator` が 8 件、#166)。プレースホルダを空白にする / 対応が取れないときの落とし先を剥がした文字列に変える / 剥がすのをやめる / 単引用符を引用符として扱わない / 絶対パスの照合を剥がした後の文字列に当てる は、**いずれも赤**になった(**期待と食い違った件は 0 件**)。**プレースホルダを空白にする変異は 2 か所を落とす** — `git -C "<本体>" checkout` だけでなく `echo x > "docs/x.md"` も落ちる(リダイレクト判定の `>\s*…\S` も非空白を 1 つ要求する)。**「空白に潰すと偽陰性が開く」は 1 か所の話ではなかった。**

**穴を塞ぐ向きに倒すと #166 が戻ることも測った。** 書き込み判定を剥がす前の文字列にも当てる変異(`-and $cmd -notmatch $writeish`)は、**意図した境界の 2 件だけでなく、#166 が塞いだ偽陽性を 3 件落とす**(`grep` / `Select-String` / 単引用符の入れ子)。**「順序を入れ替えると偽陽性が戻る」は推論ではなく実測である。**

**読み取り専用の頭を白紙化する案(`grep` / `rg` / … を先に素通し)は却下した。** `grep x && rm y` の穴を塞ぐ自然な手は「区切り文字を含むなら白紙化しない」だが、**実測された `grep` のパターン自身が引用符の中に `|` を持つ** — 区切りが引用符の内か外かを知るには結局引用符を見ることになる(#166 決定1)。

**あわせて停止メッセージを直した。** 「worktree を分けてください」しか言わないため、**既に分けている読み手が指示どおりにしても直らなかった**(ガードが見ているのは worktree の有無ではなく**セッションの cwd** である)。読むだけなら `Grep` / `Read` ツールがフックを通らないことと、cwd ごと移る必要があることを書く(#166 決定2)。

**Git Bash 形式の絶対パス(`/c/Users/...`)は素通ししていた**(2026-09-21、[#138](https://github.com/stama72/visionary/issues/138))。走行中の本体へ `cat > /c/Users/.../_probe.md` が通り、untracked を 1 本残した。照合していたのが `C:\...` と `C:/...` の 2 形だけだったためで、**この環境の `Bash` は Git Bash なので、これは抜け道の 1 例ではなく主要な経路が 1 つ抜けていた。** 綴りは `$mainRoot` から機械的に作って足した。

**穴は 2 か所にあった。** コマンド文字列を見る側(`Bash` / `PowerShell`)だけでなく、**`Edit` / `Write` の `file_path` を見る側も同じ形で抜けていた** — `[IO.Path]::GetFullPath('/c/Users/x')` は例外にならず、カレントドライブ直下の `C:\c\Users\x` を返すので、本体ツリーへの前方一致から**静かに**外れる。`Write` はこの綴りを受けて実際の場所に書く(実測)。判定の前に Windows 形へ直す。**綴り替えを効かせるのは Windows のホストだけである** — 本体が `/c/` 以下にある Linux ホストでは、本物のパスを `C:\...` へ変えてしまい、逆に守りが消える([#146](https://github.com/stama72/visionary/issues/146) でホストが増える)。

実測(2026-09-21、15 ケース): 使い捨ての git リポジトリに生きたロックを置き、フックへ直接イベントを流した。`/c/...` 形の `cat >` / `sed -i` / `rm` / `git -C <本体> checkout` と `Edit` の `file_path`(大文字ドライブ `/C/...` を含む)が `exit_code 2` で止まり、**carve-out は新しい綴りでも保たれる** — `/c/.../.claude/worktrees/` 配下・`/c/.../.pipeline/`(ロックの回収路)・読み取りだけの `grep`・本体の外・worktree 内のローカル書き込みは通る。`C:\...` / `C:/...` の既存 2 形も止まったままである。**あわせて、同じハーネスで `~` 形が素通しすることを 2 ケース測った**(#152 で閉じた。下記)。

**ホーム相対の絶対パス(`~/...`)も素通ししていた**(2026-09-21、[#152](https://github.com/stama72/visionary/issues/152))。Git Bash も PowerShell も `~` を `$HOME` へ展開して本体に届くのに、照合していたのが `C:\` / `C:/` / `/c/` の 3 形だけだった。**#138 とまったく同じく、穴は 2 か所にあった** — コマンド文字列を見る側と、`Edit` / `Write` の `file_path` を見る側である。**綴りを作る場所を `Get-MainTreeNeedle` 1 か所に寄せ**、`/cygdrive/c/...`(この環境では出ない綴りだが、同じ材料から 1 行で作れる)も足した。あわせて **`dotnet new` を書き込み判定に足した** — 無人のレビュアーが `dotnet new console -o .probe` を通し、本体ツリーに `.probe/` を残していた([#134](https://github.com/stama72/visionary/issues/134))。

**実測の手順を 3 回作り直したので、残すことにした**(#152 決定2)。`scripts/check-pipeline-guard.ps1` が 49 ケースを持ち、CI の `Pipeline guard` ジョブが回す。使い捨ての git リポジトリを **`$HOME` の下に**作り(`~` 形のため)、生きたロックを置いてフックへ直接イベントを流す。**CI(Ubuntu)が守るのはホスト非依存の範囲だけである** — 綴り替え(`C:\` / `C:/` / `/c/` / `/cygdrive/`)は Windows でだけ効く設計なので skip され、**skip の件数と理由が出力に出る**(緑を「全部守られている」と読ませないため)。**2026-09-21 の CI 実測は 29 PASS / 0 FAIL / 10 SKIP**(39 件版。#166 で足した 11 件はいずれも綴り替えを使わないので Ubuntu でも走る) — `~` 形の本体のケースは Ubuntu でも走る(HOME 展開は綴り替えではない)ので、#152 が塞いだ穴そのものは CI が見ている。全件を走らせるには Windows の開発機で `pwsh scripts/check-pipeline-guard.ps1` を打つ。

**このハーネスは、書いた当日に実バグを 1 件捕まえている。** 文字クラスが `[\/]` に潰れており(生成時に `\\` が 1 つになった)、`~/` は止まるのに **`~\` だけが素通しする片側の穴**になっていた。両方書いたつもりでいる目には映らない形である。

**壊して確かめた**(2026-09-21、`mutator` が 7 件)。`~` の綴りを消す / `ConvertFrom-HomePath` の呼び出しを消す / 文字クラスを `[\/]` に潰す / `/cygdrive` の剥がしを消す / `dotnet new` を `-o` 付きだけにする / `dotnet new` の行を消す は、いずれも**赤**になった。**1 件だけ緑のままだった** — `Get-MainTreeNeedle` に `/cygdrive` の綴りを足す行は、消してもハーネスが 39 件緑のままである。`/cygdrive/c/X` は `/c/X` を部分文字列として含み、照合が `IndexOf` なので**素の Git Bash 綴りだけで当たる**ためで、**この行は機械が守っていなかった。消した**(#152 決定3)。**同じ綴りでも `Edit` / `Write` 側は事情が違う** — あちらは `GetFullPath` に食わせる前に剥がす必要があり、消すと落ちる。当てるまで見えなかった差である。

#### 走行中かどうかは目で判断しない

```powershell
pwsh scripts/pipeline.ps1 -Status
```

走っていれば issue 番号・フェーズ・PID・生ログを出して終了コード 1、走っていなければ 0 を返す。**停止の唯一の証拠はプロセスが消えることである。** オーケストレータの「止まりました」も、生ログ `.pipeline/*.jsonl` の末尾も、停止の証拠にならない(下記)。止めたいときは `Stop-Process -Id <PID>` であって、オーケストレータに頼むことではない。

### 停止則 — 4つだけ

| コード | 条件 | 判定 |
| ------ | ---- | ---- |
| `SPEC-OUTSIDE` | 象限I-b の訂正が**タスク仕様の外**(GDD / TDD / ADR)に及ぶ | **機械** + 自己申告 |
| `IMPL-BLOCKED` | implementer が「止まって報告」した | 自己申告 |
| `REVIEW-EXHAUSTED` | レビュー4巡目到達 / implementer が2回試して緑にならない | 自己申告 |
| `RED` | build / test / format が赤のまま先へ進みそう。**`DONE` 時に本体の作業ツリーが汚れている場合も含む** | 自己申告 + **機械**(作業ツリー) |

**差分で見えるものは機械が見ている。** フェーズ2 が `PIPELINE: DONE` を出しても、**フェーズ2 起動直前の `HEAD` から見て `docs/03-gdd/` `docs/04-tdd/` `docs/adr/` に差分があれば止める。** 基準が `master` でないのは、フェーズ1 が仕様を凍らせるときに GDD を直すのが正当な仕事で、その変更が既にブランチ上にあるためである。フェーズ3 は文書を触るのが仕事なので検査しない。

**`RED` も一部を機械が見る。** フェーズ2 が `DONE` を出した時点で `git status --porcelain` が空でなければ止める。拾うのは2つ — **コミットし忘れ**(検証した状態と PR になる状態が違う)と、**戻し忘れた変異**である。後者は W2-08 で実際に残った([#110](https://github.com/stama72/visionary/issues/110))。`.pipeline/` と `.claude/worktrees/` は `.gitignore` 済みなので、[ADR-0013](../adr/0013-mutation-measurement-separated.md) の使い捨て worktree 自身は現れない。

**この検査が見るのは、`DONE` を出した瞬間に残っている汚れだけである。** 次はいずれも素通しする:

- 走行中に本体へ変異を当てて、**戻した**場合(#110 の「変異作業中は並行走行の信号が鈍る」は、この検査では消えない)
- 変異を**コミットしてしまった**場合
- `HALT` で終わった場合(検査は `DONE` の枝にしかない)
- **開発者が手で `/impl` を回したとき**(`pipeline.ps1` を通らない)

**「変異が使い捨て worktree の中に閉じている」ことを機械は確かめていない。** そこは [`mutator`](../../.claude/agents/mutator.md) 憲章の規律である。

止まると**通知が2経路に出て**(デスクトップ通知と issue へのコメント。下記「どこで走らせるか」)、スクリプトは終了コード 2 で終わる。**`PIPELINE: DONE` も `HALT` も出さずに終わったフェーズは、停止扱いにする**(`NO-SENTINEL`)。フェーズが殺された・落ちた場合も合図が残らないので、同じ扱いになる。

**止まったら `.pipeline/<issue>-<フェーズ>-<時刻>.jsonl` を読む**(Git 管理外)。1イベント1行の JSONL で、**走っている間ずっと伸びる** — 走行中に何をしているかも、途中で死んだ場合にどこまで進んでいたかも、ここに残る。画面にも tool_use が1行ずつ流れる。

#### 停止したら、制御はパイプラインを起動したフェーズ1 に戻る

`pipeline.ps1` は停止時に `exit 2` で終わるので、**背景起動したフェーズ1 のセッションが「異常終了」として起こされる。新しいフェーズ1 を立てる必要は無い。** W2-08 では立ててしまい、走行中のツリーに 2 人の書き手が居る状態を作った([#109](https://github.com/stama72/visionary/issues/109))。

#### `NO-SENTINEL` は原因を1行で名指しする

同じ `NO-SENTINEL` でも中身が違う。W2-07(#96)の1回目はネットワーク断、2回目は**サブエージェントの打ち切り**で、**生ログを開くまで区別がつかなかった**([#100](https://github.com/stama72/visionary/issues/100))。`Get-NoSentinelDetail` が生ログから次を見分けて、通知の本文に載せる。

| 跡 | 意味 |
| -- | ---- |
| `Background tasks still running after … terminating` | **サブエージェントを待ち切れずに打ち切られた。** 合図を出す前に終わっている |
| 最終 `result` の `permission_denials` が非空 | 権限で拒否されたツール呼び出しが残っている |
| `is_error` / `api_error_status` | フェーズが異常終了した |
| `result` イベントが無い | 殺された / 落ちた / 中断 |

**打ち切りの上限は `pipeline.ps1` が `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` で 1 時間に広げてある。** 非対話モード(`claude -p`)はサブエージェントが走っている間は待つが、**待ちがアイドルのまま 10 分続くと走っているものを止め、部分結果を捨てる。** W2-07 の2回目がそれで、オーケストレータの「完了通知を待ちます。」がそのまま最終メッセージになった。無限待ちにしないのは、ハングが通知も出さずに居座るほうが高くつくためである。

**これは打ち切りを遅らせるだけで、ハングを見分けてはいない。** 実行基盤を替えれば上限そのものが要らなくなる可能性があり、[#146](https://github.com/stama72/visionary/issues/146)(デスクトップ PC で走らせる)に申し送ってある。

止まらないもの(implementer の「決めて報告」/ レビュー1〜3巡の指摘と修正 / 気付いたことの issue 化)の根拠は [ADR-0010](../adr/0010-phase-pipeline-and-halt-conditions.md) 論点2。

### 合図は最後の `result` にしか意味が無い

**`result` はターンの終わりであって、プロセスの終わりではない。** サブエージェントを走らせたままオーケストレータがターンを閉じると、そこにも `result` が出る。W2-08 の1回目のフェーズ2 は `result` を 4 件出しており、**合図を含むのは最後の1件だけ**、他の3件は「implementer に渡しました。完了を待ちます。」だった。その間もサブエージェントは走り続け、コミットまで行っている。

- **`pipeline.ps1` の判定は壊れていない** — `Get-PhaseResultText` は最後の `result` だけを読む
- **壊れているのは人間に見えている合図のほうである。** 走行中の画面(`Write-PhaseProgress`)にも「待ちます」が流れるし、開発者の問いかけへの返答も「止まりました」になる。**オーケストレータはサブエージェントを止める手段を持っていない**ので、「止めました」は答えられない答えである
- したがって**停止の確認は `-Status`(= PID の生存)に一本化する**

### 手で回すとき

停止則に当たった後の再開や、パイプラインを使わない場合は、**開発者が `/clear` してから** `/impl <issue番号>` `/wrap <issue番号>` を開く。フェーズ3 だけやり直すなら `pwsh scripts/pipeline.ps1 -Issue 35 -From wrap`。

**手で回すときも、ssh で入って `--bg` のセッションの中から打つ**([#146](https://github.com/stama72/visionary/issues/146) 決定11・決定13)。**`/impl` `/wrap` を手で開く場合も、`pipeline.ps1` を直に打つ場合も同じである。** 上の「フェーズ1 は背景セッションで開く」と同じ規律である。**ここを外に置くと、いちばん踏みやすい経路に同じ穴が開いたまま残る** — 停止則に当たった後の再開は、出先で起きる場面だからである。**前景で打ったプロセスが ssh の切断で死ぬことは実測してある**(上記「フェーズ1 は背景セッションで開く」の表)。

**`/clear` は機械で守れない。** 忘れても何も壊れないが、節約も起きない。パイプラインを通す限りこれは起きない — 境界がプロセス境界になるためである。

**モデルも自分で選ぶ。上の表の Sonnet を握っているのはパイプラインの `--model` だけである** — 手で開けば `/impl` も `/wrap` も既定(opus)で走る。`wrap.md` に `model:` を置いても対話では効かないので、[ADR-0014](../adr/0014-interactive-sessions-follow-the-default-model.md) で外した。**フェーズ3 を sonnet で回したいなら、開くときに自分で選ぶ。**

## 何が「実装タスク」か

**`docs/tasks/` に仕様があるものが実装タスクであり、その実装は必ず implementer が書く。**([ADR-0009](../adr/0009-phase-scoped-sessions.md) 論点3)

仕様を書くまでもない規模なら、そもそも実装タスクではない — [02-task-spec](02-task-spec.md) 規則2(「宣言のみでよい」と書かない)の裏返しである。

**設計・プロセス・文書のみの変更は、この3フェーズに乗らない。** [`reviewer`](../../.claude/agents/reviewer.md) ではなく**アドバイザー**と開発者が見る([01-review](01-review.md))。**進め方は [06-design-sessions](06-design-sessions.md) が持つ** — 束ごとに決めて書いてコミットし、引き継ぎメモは書かない。フェーズ1 と設計タスクの境界(却下する選択肢があるか)も同書。
