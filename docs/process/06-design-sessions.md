**設計タスクは実装の3フェーズ([05](05-phase-sessions.md))に乗らない。本書はその進め方を持つ。** なぜそう決めたか(却下した案と理由、実測)は [ADR-0012](../adr/0012-design-session-bundles.md) が持ち、本書は再説明しない。枠づけは [`/design`](../../.claude/commands/design.md)(**実行される仕様**。本書はその本文を複製しない)。

## 何が「設計タスク」か

**`docs/` の規則・仕様・設定を書き換える仕事。成果物は文書である。** `type:design` と `type:process` がこれに当たる。層が違っても進め方は変えない — 変わるのは**規則を変えたとき何が追随するか**だけである。

| 層 | 文書 | 規則を変えたとき追随するもの | 引き取る issue |
| -- | ---- | ---------------------------- | -------------- |
| **docs 直下** | コンセプトシート・企画書・世界観設定書 | GDD / TDD の節 | `type:design` |
| **GDD / TDD** | `03-gdd/` `04-tdd/` | コード(doc コメントが節を引く) | `type:impl` |
| **ADR** | 選択肢と理由。層ではなく、上のどの層の決定にも付く | 波及節が持つ | — |
| **process** | `docs/process/` と `.claude/` | 運用。次のタスクで回して確かめる | — |

**実装タスクのフェーズ1(凍った GDD からタスク仕様を書く)は本書の対象ではない。** そちらは [05](05-phase-sessions.md) が持ち、既定のセッション(モデルは下の「モデル」のとおり opus)で回す。境界は「**却下する選択肢があるか**」([ADR の切り分け](../adr/README.md)の問い1 と同じ基準)である。

- 選択肢が無い — 実装が要る決定の追記、節番号の追随、実態合わせ — はフェーズ1 の中で GDD / TDD を直してよい(05 が「フェーズ1 が仕様を凍らせるときに GDD を直すのは正当な仕事」と書いている範囲)
- **選択肢がある — 規則の反転・削除・新設 — は設計タスクである。** フェーズ1 の途中で出たら、issue を分けて `/design` で回す([#28](https://github.com/stama72/visionary/issues/28) が実例)

## 仕事の5分割と分担

| # | 仕事 | 誰が | どう出すか |
| - | ---- | ---- | ---------- |
| 1 | **スコープ決め = issue を立てる** | **開発者が持ち込み、AI が精査してまとめる** | 持ち込みは指摘・アイディア・作成指示のどれでもよい。AI は文書と既存 issue を読み、[04](04-issue-driven.md) の切り分け(issue か文書か / 閉じる条件を1行で書けるか / 型 / 依存 / 重複)に当てて本文を組み、**優先順位とマイルストーンも置いて立てる。立ててから報告し、開発者が却下・書き直す**(下記の例外)。**入力は変わらない** — 持ち込みと、束の途中で出た残る論点。issue の種を自分で探しに行くことはしない。**どのセッションでも起きる** — `/design` の中に限らず、実装フェーズの途中で出た論点も、束の途中で出た残る論点も、ここへ来る |
| 2 | **論点出し** | **矛盾・穴・数値の検証は AI。何を作りたいか・何を重視するかは開発者** | AI は各論点に「**今決めるべきか / 実装すれば分かるか**」を付けて出す([ADR-0004](../adr/0004-ai-driven-development-workflow.md) 論点4 / [`adviser`](../../.claude/agents/adviser.md)「先に踏む」)。**数値と式**は実験に回す前に恒等式や連立方程式で解き、計算根拠の表を添える。**式を書くとき・書き換えるときは [02-task-spec](02-task-spec.md) 規則5 を当てる** — 式は同じ節の散文と引用先の節の散文に照らし、**照合相手が無い節(式・散文・帰結が同じ束で生まれた節)では代わりに代入して2周ぶん回す**。上位文書の式の欠陥は、下流のタスク仕様が正確に相続して「誤った式の正確な実装」になる(W2-10 / [#98](https://github.com/stama72/visionary/issues/98) の3件のうち2件はここで生まれた)。新しく設計の余地があるものは 3 へ、既存の決定の帰結だけのものは 4 へ |
| 3 | **案とトレードオフ** | AI | 案ごとにトレードオフを1行ずつ並べ、**推奨を1つ言う**。開発者が案を足したら、**開発者の案も含めて**並べ直す |
| 4 | **決定** | 開発者 | 「決めて報告 / 止まって報告」の線引きは下記 |
| 5 | **文書化** | **設計セッション自身**。機械的な波及だけ [`propagator`](../../.claude/agents/propagator.md)(sonnet) | 下記「文書化の分担」 |

**1 は精査であって転記ではない。** 持ち込みが既に決まっていることの再発見だったり、issue ではなく文書に書くべきものだったり、閉じる条件が書けない関心事だったりする。それを文書と既存 issue に当てて判定するのが AI の仕事で、開発者はその結果を見て立てる。

**2 と 3 は一度に言い切らない。** 開発者の1ターンは平均14分の読解と入力を伴う([ADR-0012](../adr/0012-design-session-bundles.md) 背景の実測)。論点を短く出し、掘るところを聞いてから深く入る — アドバイザーの憲章が「1回の呼び出しで言い切ろうとしない」で置いたのと同じ規律である。

## 決めて報告 / 止まって報告 — 仕事4 の AI 側

implementer と同じ2種に分ける([`implementer.md`](../../.claude/agents/implementer.md))。**違いは、開発者に選択肢を出して待つ(止まって報告)か、自分で決めて束の終わりに列挙する(決めて報告)かである。決めて報告した件は開発者が却下できる** — 事前の許可ではなく、事後の拒否権として置く。

**設計セッションが自分で決めてよいのは、次の2つを両方満たすものだけ**である。

| 条件 | 満たさない例 |
| ---- | ------------ |
| **却下する選択肢が無い**(他に選びようのない帰結、整合のための修正)。**上位文書の規則の反転・削除には常に選択肢がある**(反転しない、という選択肢) | 「A でも B でもよい」を A に倒す / 移動平均の更新対象に耐久を足す([#101](https://github.com/stama72/visionary/issues/101) 型) |
| **開発者が置いた数値・優先順位・スコープを動かさない**。**「置いた」は既に置かれたものを指す** — 新規 issue に初期値を置くことは当たらない | 校正値を「計算が合わないので」変える / 開発者が `P1` にした issue を `P2` に下げる |

**条件1 には例外が1つある — 仕事1(issue を立てる)は、選択肢があっても止まらない。** issue を立てること自体も、優先順位とマイルストーンを置くことも、**立ててから報告する**([ADR-0012](../adr/0012-design-session-bundles.md) 論点6)。止まると「立てるか」と「どう立てるか」で往復が2回に割れる。**立てた件は束の終わりに列挙し、開発者が閉じる・書き直す** — 論点5 の事後の拒否権と同じ扱いである。**一度開発者が置いた優先順位を動かすのは条件2 で止まる。**

**例示に「新設」を挙げていないのは、process 文書では全文が規則で常に発火し、件数が指標でなくなるためである**([ADR-0012](../adr/0012-design-session-bundles.md) 論点5)。**緩めているのではない** — 却下する選択肢がある新設は条件1 の本文が捕まえる。上の §「何が設計タスクか」が**フェーズ1 との境界**で「反転・削除・新設」を挙げているのとは別の判定である(あちらは層をまたぐ振り分け、ここは同じセッションの中で止まるかどうか)。

どちらかが外れたら止まり、選択肢とトレードオフを出す。**迷ったら止まる側に倒す** — 止めすぎの代償は1往復だが、進めすぎの代償は設計判断が記録なく入ることである。

**件数を束ごとに数え、決定ログに残す。** 決めて報告した件は1行ずつ列挙する。

## 決定ログ — 決めたその場で issue に書く

**対象 issue のコメントに、番号付きで追記する。** [#85](https://github.com/stama72/visionary/issues/85) の「決定 1〜20」と [#104](https://github.com/stama72/visionary/issues/104) がその形である。

| 書く時点 | 開発者が「承認」と言った**直後、文書を書く前** |
| --- | --- |
| **書くもの** | 決めたこと / **却下した選択肢と理由** / 前提(崩れると何が倒れるか)/ 決めて報告・止まって報告の件数 |
| 書かないもの | 採った案の中身そのもの(文書が持つ)/ 進捗 |
| ADR に載る大きさの却下案 | ADR へ。ログはそれ以外を持つ |

文書を書く前に書くのは、**セッションが途中で死んでも決定が残る**ためである。決定ログが常に最新なら、死んだセッションは束の途中からでも作り直せる。

## 束 — セッションを切る単位

**1束 = 論点の集まりを決め、文書に書き、コミットするまで。** sub-issue があればそれが束である([#85](https://github.com/stama72/visionary/issues/85) の #86〜#91)。

**束の終わりで次の3条件を満たす。** 満たしたら、そこでセッションを切ってよい。

1. 文書がコミットされている
2. 決定ログが issue にある
3. 残る論点が issue(本文かコメント)に書かれている。**開発者が仕事2 で述べた「何を重視するか」のうち、まだ決定に消費されていないものもここに含める** — 決定に載る前に切ると、これだけは文書にも決定ログにも無い

**切るかどうかは束ごとに開発者が選ぶ。引き継ぎメモは書かない。** 何がどこに残るかは次のとおりで、境界で消える情報が無い(棚卸しは [ADR-0012](../adr/0012-design-session-bundles.md) 論点1):

| 情報 | どこに残るか |
| ---- | ------------ |
| 採った案 | 文書(コミット済み) |
| 却下した案と理由・前提 | 決定ログ(ADR 級なら ADR) |
| 残る論点 | issue |
| 開発者が述べた「何を重視するか」で、まだ決定に消費されていないもの | issue(境界の条件3) |
| アドバイザーの指摘と対応 | コミット本文 |
| 決めて / 止まって報告の件数 | 決定ログ |

切る目安は3つ。**次の束がこの束の却下案を入力にしない** / 翌日にまたぐ / コンテキストが重い(切って読み直す代償は起動時の約 60K)。

**切っても切らなくても、3条件は束の終わりに満たす。** 切らない選択は「引き継ぎを省く」ではなく「同じ条件を満たしたうえで続ける」である。

## アドバイザー — 束ごとに差分へかける

束の文書を書いたら**設計セッション自身がアドバイザーを呼び**、指摘は 2(論点出し)へ戻す。設計は行き来する工程なので、これは差し戻しではなく巡回である。

**開発者が指摘をコピペで運ぶ形はやめた**([#105](https://github.com/stama72/visionary/issues/105))。往復の時間だけでなく、**並行タスクとの取り違え事故が実際に起きた**(2026-09-21)。設計セッションの外で書いた差分にかける入口だけが [`/advise`](../../.claude/commands/advise.md) に残る。

### 誰を呼ぶか

**専門家が先、全般が最後に残りを拾う。** 専門家は差分の内容に応じて**必要なものだけ**呼ぶ。

**(c) を呼ぶのは任意ではなく必須である。** 以前の `/advise` は「任意」で、開発者が回すかを選んでいた([#105](https://github.com/stama72/visionary/issues/105) 決定8)。**前提は 1 巡が枠の 1% であること** — 束ごとに常時払える値だから必須にできる。**ここが動いたら、必須かどうかを見直す**([04「枠」](04-issue-driven.md)の見込みは #123 の確認で動く)。

| | 役 | 憲章 | 呼ぶ条件 |
| - | -- | ---- | -------- |
| **(a)** | 経済アドバイザー | [`adviser-economy`](../../.claude/agents/adviser-economy.md) | 差分が経済の設計に触れているとき |
| **(c)** | 全般アドバイザー | [`adviser`](../../.claude/agents/adviser.md) | **常に。設計・プロセスのどちらの束でも**。残り全部を拾う |

**(b) ゲーム理論アドバイザーはまだ置いていない。** シムにプレイヤーの概念が無く(`grep -rn "Player" src/` = 0 件)、検査対象が存在しないためである([#157](https://github.com/stama72/visionary/issues/157) が W5 に置く)。**W2〜W4 にプレイヤーの選択を扱う設計が入ったら、この前提は崩れる。**

**エージェント定義はセッション起動時に読まれる。** `.claude/agents/` に新しく置いた役は、**置いた束と同じセッションからは呼べない**(#105 の束で踏んだ)。その束だけは憲章ファイルを読ませる形で代替し、次のセッションから通常の呼び方に戻る。**代替のあいだは憲章の `tools:` と `model:` が効かない** — 機械の歯止めが指示に落ちるので、呼ぶ側が「変更しない」「どのモデルで読むか」を指示で埋める。

**代替で回すか、呼び出しを次の束へ送るかは束が選ぶ。** [#125](https://github.com/stama72/visionary/issues/125)([`propagator`](../../.claude/agents/propagator.md))は送った — **歯止めを `tools:` に置いた役では、`tools:` が効かない代替で回しても、置いた歯止めを一度も検証しないまま閉じることになる**ためである。

**(a) の指摘と、それぞれへの対応方針を (c) に渡す。** (c) は独立な検査ではなく**相補**の役なので、渡さないと同じ指摘が重なる。渡すのは**指摘の履歴であって設計の意図ではない**([01-review](01-review.md)「2巡目以降に渡すもの」と同じ線引き)。

### 巡と打ち切り

**何巡目かを起動時に渡す。渡さなければアドバイザーは1巡目として扱う。**

**「この論点を掘れ」と呼び直す回は巡に数えない。** サブエージェントは1回の呼び出しで返って終わるので、`/advise` が対話で持っていた「短く出して、掘るところを聞いてから深く入る」の後半は呼び直しでしか実現できない。数えると、掘った時点で残りが打ち切りだけになる。**歯止めは「掘り下げでは新しい指摘を出さない」** — 出したらその回を巡として数える(憲章にも書いてある)。

**報告する巡は2つである。3巡目は呼ばれても打ち切る** — 表の行は3つあるが、**3行目は巡ではなく歯止め**(押されても何も出さずに返すため)である。基準は「後から気付けるか」で、2巡目に残るのは**気付けないものと、訂正で新しく入った決定**だけ。役ごとの対応表は各憲章が持つ(本書は複製しない)。実装レビュー(報告3巡)より1つ短い理由は [01-review](01-review.md) にある。

**2巡目の指摘への訂正は、誰も見ない。** 承知のうえで打ち切っている。**「2巡かけたから見てある」とは書かない** — 受け皿は「気付いたら直す」と、次のタスクでその文書を使うことである。

**ただし ADR を含む束は打ち切らない。巡の本数を決めているのは、打ち切った後の受け皿があるかである。** 既定の束は打ち切っても次のタスクでその文書を使って踏むが、**ADR は本文を後から直せないので凍結後に踏めない**([01-review](01-review.md)「ADR だけは打ち切れない」)。**設計束は ADR を書ける**(上の層の表)ので、この例外は本書の対象に当たる。**その束の3巡目以降は、2巡目の範囲のまま続ける**(1巡目の範囲には戻さない)。

**アドバイザーにかける前にコミットする。** 訂正を別のコミットに分けないと、2巡目の範囲(前巡のレビュー対象以降)に**訂正が入らない**。フェーズ2 が「コミットしてからレビューする」のと同じ形である([#105](https://github.com/stama72/visionary/issues/105) の束で踏んだ — 1巡目の訂正が1巡目の対象と同じコミットに畳まれ、2巡目から見えなくなった)。

- 対応は3択 — 直す / 直さないと決めて理由を**決定ログ**に残す / issue へ落とす。**黙って見送らない**([01-review](01-review.md) と同じ)
- 打ち切るときに残る指摘は issue へ落とす(同)

### モデル — 既定は opus、上げるのは証拠が出たときだけ

**アドバイザーの既定は opus である。主な根拠は費用ではない** — **アドバイザーの価値の源泉は独立したコンテキストであって、モデルの生の力ではない**([`reviewer`](../../.claude/agents/reviewer.md) と同じ機構)。レートが動いてもこの根拠は倒れない。

**費用はそれを補強する。** fable は opus の約4倍重く([04「枠」](04-issue-driven.md))、束ごとに払うには重い。**ただし 04 の見込みは対話での実測で、サブエージェント化後は未実測である**(同)。**実測が出たら、この節は費用の側から見直してよい。**

**名指しで引けず、系列全体を並べないと判定できない観点だけを上げる。** アドバイザーは差分の外を読んでよく、`grep` や節の名指しで引けるものは自分で引く。**上げるのは「どこかに〜が無いか」の形でしか書けない問いだけ**である。専門家アドバイザーはそれを指摘に混ぜず「**差し戻し要求**」として分けて返し、**何を並べれば判定できるかを名指しする**(憲章が持つ)。

**差し戻し要求は入れ子の2段で解く。**

| 段 | 何をするか | モデル |
| -- | ---------- | ------ |
| **1** | **同じ専門家を、名指しされた範囲を渡して呼び直す** | **opus** |
| **2** | 1 で「それでも判定できない」と返ったものだけ、もう一度呼び直す | **fable** |

**段1 を置くのは、名指しの多くが数節に収まるからである。** 「02c §4 と 02d §3 の調整経路を並べる」は2節であり、fable の条件([ADR-0014](../adr/0014-interactive-sessions-follow-the-default-model.md) 論点2「文書やコードの**山を横断**して読み直す」)に届かない。**境界を動かすのではなく、その内側を狭めている。**

- **上げる先はサブエージェントであって、fable の対話セッションではない。** 下の「モデル」表の「fable の対話は 1 本で枠の 29〜103% を食う」はここには当たらない
- **1束につき fable は1回まで。** 上げた先がさらに上げることはしない
- **上げる前に枠の残りを見る**([04 規則1](04-issue-driven.md))。足りなければ上げず、その観点を issue へ落とす
- **差し戻しの解決は巡に数えない。** 新しい検査ではなく、1巡目が出しきれなかった観点の続きだからである。返ってきた指摘は**その巡のもの**として扱う

**開発者に「fable へ上げますか」と聞かない。** 束の頭ではまだ判定材料が揃っておらず、聞けば本節が消したはずの往復が別の名前で戻る。**条件が本書で凍っているので、各回の「上げるか」は選択肢の無い帰結である**(上の「決めて報告 / 止まって報告」条件1)。

## 文書化の分担 — 本文は設計セッション、機械的な波及は `propagator`

**GDD / TDD / ADR / process の本文は設計セッション自身が書く。** 「気付けない × 影響大」の4類型は文言の中で生まれるので、却下案を持つ者が書く。

**機械的な波及だけをサブエージェント(Sonnet)に出す。** 判定は「**却下した選択肢を知らなくても正しく書けるか**」である。

**当てるのは [`propagator`](../../.claude/agents/propagator.md) である。出してよい3種(参照の付け替え / 追随表の候補列挙 / 件数・索引・一覧の更新)と、手順と、返し方は憲章が持つ** — 本書は複製しない([README「実行される仕様」](README.md#実行される仕様という位置づけ))。[#125](https://github.com/stama72/visionary/issues/125) が置くまでは**範囲とモデルだけが決まっていて機構が無く**、汎用のサブエージェントに範囲を都度渡していた([ADR-0012](../adr/0012-design-session-bundles.md) 論点3 の「フェーズ1 = Opus に機構が無かった」と同じ穴である)。

**憲章の `tools:` から `Bash` と `Write` を落としてある。** 「コマンドを実行しない」「新しいファイルを作らない」を文言ではなく**機械の側**に置くためである。`tools:` はツール名単位でしか効かないので、「`Bash` は grep と git だけ」のような制限は機械の歯止めにならない。**`git log` が要る調べものは、設計セッションが引いて渡す。**

**呼ぶときに層を指定する。** 文書は寿命で四層に分かれ、ADR は凍り `docs/tasks/` は PR とともに終わるので、**波及を当ててよい層は束ごとに違う**([`f9adf1f`](https://github.com/stama72/visionary/commit/f9adf1f) は「ADR と `docs/tasks` は触らない」と指定して回った)。指定が無ければ `propagator` は当てずに候補を返す。**ただしこれは憲章の文言による歯止めであって、機械ではない** — `Edit` は全層に届くので、上の `tools:` の話はここには及ばない。

**候補と判定を分ける。** 追随表の候補列挙は出してよいが、「現行の規則に従っているか」の一致判定は設計セッションが読む。上位の層の規則を書き換えた束では、**追随表を束の終わりに書く**(閉じる条件。[04-issue-driven](04-issue-driven.md)「上位文書を書き換える設計 issue」)。向きは上の層の表のとおり — **docs 直下なら「変えた規則 → 追随する GDD / TDD の節 → 引き取る design issue」、GDD / TDD なら「変えた規則 → 実装している既存コード → 引き取る impl issue」**。

## モデル

**対話セッションは既定に従う。既定は opus。** 理由は [ADR-0014](../adr/0014-interactive-sessions-follow-the-default-model.md)。

| 仕事 | モデル | 機構 |
| ---- | ------ | ---- |
| 設計セッション(仕事 1〜5。`docs/` の全層) | **opus** | `~/.claude/settings.json` の `"model"`(と GUI の選択)。**コマンドの `model:` frontmatter は対話セッションでは効かない**([ADR-0014](../adr/0014-interactive-sessions-follow-the-default-model.md) 背景の実測2。このため `design.md` と `wrap.md` から `model:` を外した) |
| **大規模な既存コンテキストの修復・洗い直し** | **fable** | **無い。開発者が起動時に手で選ぶ**([ADR-0014](../adr/0014-interactive-sessions-follow-the-default-model.md) 論点2)。既に書かれた文書やコードの山を横断して読み直し、食い違いを見つける仕事がこれに当たる([#85](https://github.com/stama72/visionary/issues/85) の GDD02 洗い直し、[#101](https://github.com/stama72/visionary/issues/101) の追随表)。**新しく決める仕事は通常の設計束であり、opus で回す** |
| 実装タスクのフェーズ1(凍った GDD → タスク仕様) | **opus** | 同じく既定。対話セッションなので上と同じ経路である |
| 機械的な波及([`propagator`](../../.claude/agents/propagator.md)) | sonnet | サブエージェントの `model`(**効く**) |
| **アドバイザー**([`adviser`](../../.claude/agents/adviser.md) / [`adviser-economy`](../../.claude/agents/adviser-economy.md)) | **opus**。差し戻し要求だけ **fable** へ上げる(上の「アドバイザー」の「モデル」) | サブエージェントの `model`(**効く**) |
| フェーズ2・3 | 05 のまま(opus / implementer は sonnet / `/wrap` は sonnet) | パイプラインの `--model`(**効く**) |

**fable を選んだら、枠の免除は外れる。** fable の対話は 1 本で枠の 29〜103% を食う([04「枠」](04-issue-driven.md) 規則3 と見込み表)。**5 時間枠 1 つを明け渡す前提で走らせる。**

**レートは [#123](https://github.com/stama72/visionary/issues/123) の確認で動くが、動いても ADR-0014 論点1 の根拠は動かない** — 根拠はレートの値ではなく、ADR-0012 決定3 の却下理由が立っていた軸(API 等価コスト)が制約の軸(枠)ではなかったことだからである。

## 検証条件の記録先

**本書の運用は仮説である。検証条件は [ADR-0012](../adr/0012-design-session-bundles.md) の帰結が持つ。** 記録先は次の設計タスクの PR 説明で、0 件でも「0 件」と書く。

**アドバイザーについては、次の「経済に触れる設計束」の PR 説明が2つを持つ**([#105](https://github.com/stama72/visionary/issues/105) 決定11。あちらは (a) を一度も動かさずに閉じた)。

- **(a) の「差し戻し要求」が空振りしなかったか。** 空振りするなら、上げる経路(上の「モデル」)は一度も発火しない
- **段2(fable)が発火したか。** 数束回して 0 件なら、**自己申告が壊れているのか、段2 が要らないのか**を判別する。0 件でも「0 件」と書く
- **(a) の指摘を (c) に渡したとき、(c) が重ねなかったか**(上の「誰を呼ぶか」)

**機構そのものは、次の設計束の PR 説明が持つ**(層を問わない。**機構の検証に経済の差分は要らない**ので、上の3つとは記録先が別になる。いまの予定は [#126](https://github.com/stama72/visionary/issues/126))。

- **アドバイザーをエージェントとして実際に呼べたか。** #105 の束は憲章ファイルを読ませる代替で回しており、`tools:` と `model:` が効いた状態は**まだ一度も動いていない**(上の「誰を呼ぶか」の註)
- **巡の数え方が回ったか** — 掘り下げと差し戻しの解決を数えず、報告2巡で打ち切れたか
- **コミットを先に置く手順で、2巡目が1巡目の訂正を見られたか**(上の「巡と打ち切り」)
- **[`propagator`](../../.claude/agents/propagator.md) を実際に呼べたか。** [#125](https://github.com/stama72/visionary/issues/125) の束は定義を置くだけで閉じておらず(同じセッションからは呼べない。上の「誰を呼ぶか」の註)、**`tools:` から `Bash` を落とした歯止めが効いたかは、最初の呼び出しまで分からない**
- **`propagator` が範囲の外を返したか** — **当てた件数と、変えずに返した件数の両方**。0 件が続いたら範囲が広すぎて判定を巻き込んでいないかを疑い、**逆に全件を返してきたら、呼ぶ利得がゼロになっている**(設計セッションが全部当て直すことになる)
- **歯止めのせいで仕事が回らなかったか。** [`f9adf1f`](https://github.com/stama72/visionary/commit/f9adf1f) 級(155 件)が `Bash` 無しの `Edit` の逐次適用で回るかは**未実測**である。**最初の呼び出しは数件の波及に当てる**
