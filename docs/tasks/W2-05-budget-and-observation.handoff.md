## 却下した設計案(フェーズ1)

- **`相場基準` を `OfferPrice` から `MarketReference` へ切り出し、売り手と買い手で共有する** — 採らない。`OfferPrice.TryMarketReference` を買い手からそのまま呼ぶ。クラス名だけを見ると買い手が売り手の式を呼んでいるように読めるが、[GDD02 §8.1.1](../03-gdd/02-economy.md) は `相場基準` を提示価格の節の中で定義しており、**移すと文書の節構成とコードの置き場所がずれる**。加えて #35 のテスト12〜20(9件)を巻き込む改名になり、**挙動が1ビットも変わらない差分でレビュー帯域を使う**。[ADR-0008](../adr/0008-review-scope-narrowed-to-unnoticeable-defects.md) の「今のマイルストーンの Exit Criteria を脅かすか」で仕分けて、脅かさない側と判定した

- **`BuyerDemand` を `TradeSystem` に繋ぎ、予算を毎日計算して捨てる** — 採らない。「4つの基礎値がすべて実行される」を**パイプラインで**満たす形だが、**計算結果を誰も読まない**ので、用途を1つ落としても在庫も資金も動かず緑のままになる。#37 が店の選択を入れるまで、**式が正しいことを主張できるのはテストの期待値だけ**である。実行されている見た目を作るより、テスト表で4用途すべてを通すほうが検出力が高い

- **`予想在庫` を `ExpectedStock(現在庫, 予定消費, 予定生産投入)` という引数付きの関数にする** — 採らない。M0 のパイプラインでは順5 の時点で当日の消費も生産投入も済んでおり、**2つの引数は常に 0 になる**。常に 0 の引数は「埋めるべき穴」に見えてしまい、**#37 が何かを入れたくなる**。代わりに [GDD02 §8.2.2](../03-gdd/02-economy.md) に「M0 では `予想在庫 = 現在庫` になる」を書き、**理由(パイプラインの順序)を文書側に置いた**。日内スケジュールが入ったときに GDD の註ごと外す

- **耐久財の目標在庫を品目別の表(`DurableTargetStockPermille[itemId]`)にする** — 採らない。`ToolTargetStockPermille` の単一値にする。M0 の耐久財は工具だけであり([GDD02 §13.1](../03-gdd/02-economy.md) が「工具以外へ広げるのはスコープ膨張の回避」と明記)、**9欄のうち意味を持つのが1欄の表**になる。`InitialToolStock` / `ProductionRunsPerToolWear` が既に工具名指しの欄であり、そちらと揃えた。**1個あたりの耐久値も品目別に持てない**(`N` は §5.3 の工具固有の定数である)ので、表にしても半端になる

- **`DemandPurpose` の値を [GDD02 §6.2.1](../03-gdd/02-economy.md) の走査順(必需 → 生産の入力 → 耐久 → 嗜好)に振る** — 採らない。値は [GDD02 §8.2.1](../03-gdd/02-economy.md) の表の順のままにし、走査順は `HouseholdDemand.Lines` の並びが持つ。`enum` の値に走査順を兼ねさせると、**後から用途を1つ足したときに決済順が黙って変わる**。`Occupation` / `RandomStream` / `StateHasher` の区分タグで既に「値は振り直さない」規律があり、そこへ順序の意味を載せると規律同士が衝突する

- **観測の生成を `Knowledge` 専用のシステム(順9 相当)として独立させる** — 採らない。順5 `TradeSystem` の末尾に置く。[GDD06 §3.1](../03-gdd/06-trade-and-negotiation.md) の観測は「その日に**買い物で**訪れた区画」に依存し、それを知っているのは #37 の店選択である。別システムにすると訪問区画を `World` の状態として渡すことになり、**1日限りの中間値のためにハッシュ対象の区分が1つ増える**。`SimScheduler` が `RandomStream` の重複登録を拒むので、順5 に2つのシステムは置けない([TDD01 §3.1](../04-tdd/01-sim-core-and-m0.md))

- **`Knowledge` を「(品目, 売り手) ごとに最新1件」に畳んで持つ** — 採らない。追記して保持期間で失効させる。畳むと1 NPC あたり最大 `品目数 × 売り手数` に固定できて魅力的だが、[GDD01 §4.5](../03-gdd/01-trust-and-conversation.md) の不当価格の「気づき」は**取引tick近傍にどの観測を持っていたか**を見る([TDD01 §3.4](../04-tdd/01-sim-core-and-m0.md) の誤爆率の後段計算)。W4(#45)の入力を、いま測っていない都合で先に捨てることになる。保持期間7日・視界内の売り注文が高々10件なら、1 NPC あたり70件で頭打ちになる

### 根の構造(A〜J に共通) — issue に必ず持っていくこと

**個別に10件潰すのではなく、テスト世界の縮退を3つ解くほうが根治的である。** 4巡目の実測によれば:

1. **世帯の同一視**: テスト世界が `Id = 0`・`HeadNpcId = 0`・`Occupation = Miller(0)` で三者が同じ値 → **B・J** が通る
2. **母数の同一視**: 耐久・嗜好の `BaseValue` を assert するテストが `WorkingCapital = 0` → `surplus == LiquidFunds` → **A** が通る
3. **時間と用途の縮退**: 季節係数が全季節 1000‰ → **E** が通る。嗜好の行は `BaseValue` しか assert されていない → **C・D** が通る

**`WorkingCapital > 0` かつ `Id ≠ HeadNpcId ≠ 職業添字` かつ嗜好に在庫と消費量を持つ世帯を1つ用意すれば、A・B・C・D は1本のテストでまとめて赤にできる**(E は季節係数を非一様にする必要がある)。

### この類型が3巡連続で出た理由(#37 と、今後のタスク仕様へ)

**`BuyerDemand` は本タスクでは誰も呼ばない**(却下案「`BuyerDemand` を `TradeSystem` に繋ぐ」を採らなかった帰結)。**パイプラインに繋がっていれば統合テストが偶然守ってくれる配線を、ここでは全部テスト表が明示的に列挙するしかなかった。** 却下の判断自体は妥当だが(計算結果を誰も読まないので用途を落としても緑のまま)、**その代償の大きさは仕様凍結時に見積もられていなかった。** 「誰も呼ばないコードを作るタスク」では、テスト表に**配線の列挙**を式の検証とは別立てで持たせる必要がある。

### 1. 同一類型が続いたら「探す」から「数え上げる」へ切り替える([01-review](../process/01-review.md))

**実測**: 1〜3巡目は「読んで見つける」渡し方で計6件。4巡目に「`Build` が外部とやりとりする全経路を列挙し、各経路の変異が283件で落ちるか判定せよ(判定できないものは実際に変異を当てて確かめよ)」へ変えたところ、**同じ類型を10件まとめて出した。**

**論点**: 01-review は「巡ごとに報告してよい象限を狭める」を持つが、これは**減衰対策の軸**である。今回効いたのは**別の軸** — 欠陥が単一の構造的原因から出ていると分かった時点で、探索を網羅に切り替えること。規則にできるか(例: 同一類型が2巡続いたら、3巡目は網羅を指示する)。

**注意**: 網羅を指示できたのは「`BuyerDemand.Build` の配線」という**有限に数え上げられる境界**があったからである。境界が引けない対象へ同じ指示を出すと、レビュアーは全体を読み直すだけになる。**切り替えの条件は「同一類型が続いたこと」ではなく「列挙可能な境界が見えたこと」かもしれない。**

### 2.「誰も呼ばないコードを作るタスク」のテスト表([02-task-spec](../process/02-task-spec.md))

**`BuyerDemand` は本タスクでは誰も呼ばない**(却下案「`TradeSystem` に繋ぐ」を採らなかった帰結。却下の判断自体は妥当)。**パイプラインに繋がっていれば統合テストが偶然守ってくれる配線を、ここでは全部テスト表が明示的に列挙するしかなかった。** 4巡で計16件の指摘が出て、**そのすべてがテストの判別力・網羅度であり、実装バグは0件**だった。

**論点**: タスク仕様のテスト節は「式が正しいか」を落ちるべき条件として書けているが、**「その式をどう呼ぶか」には行が立ちにくい。** 純関数へ切り出すほど、誤りは関数の中から**呼び出し側へ移動する**(象限I-b の #12 がその実例)。**呼ばれないコードを作るタスクでは、配線の列挙を式の検証とは別立てで持たせる**規則が要るのではないか。

**あわせて**: 却下案を書くときに**その代償の大きさ**も見積もる。今回、却下理由(「計算結果を誰も読まないので用途を落としても緑のまま」)は正しかったが、**代償(配線が統合テストの保護を受けない)は見積もられていなかった。**

### 3. 件数を断定する書き方が「列挙が完了した」保証として読まれる([03-corrections](../process/03-corrections.md))

**実例**: フェーズ2 のオーケストレータが書いた「R1 別表が埋めたのは**5経路のうち3つ**」が、「配線は全部で5つで埋め切った」と読まれた。実際には10件残っていた。**「3つ埋めた」は安全だが「5つのうち3つ」は全体集合を主張する。**

**しかもこれを、同じ文書で `process/03` を引いて R1-7 の主張を狭めた直後に、隣の段落で犯している。** 規則を知っていることと、書いている最中に踏まないことは別である。

**論点**: 03-corrections は「広い誤りは『見なくてよい』と読ませる」を持つが、**分母を書く行為がその広い誤りになる**ことは明示されていない。「塞いだものを数えてよい。残りが無いことは、実際に数え上げたときだけ主張してよい」を足せるか。

### 4. implementer の「決めて報告」に、止まるべきだった1件が混じる([02-task-spec](../process/02-task-spec.md))

**止まって報告 0件 / 決めて報告 4件**だったが、そのうち1件(`DerivedDemand` の配列の**添字規約**)は**`BuyerDemand` と `BuyerDemand` の契約そのもの**であり、取り違えても例外が出ない種類の決定だった。結果は妥当だったが、**先行指標としては「止まるべきだったが止まらなかった1件」**である。

**論点**: 「止まって報告した件数」を仕様品質の先行指標として使うなら、**決めて報告した内容を事後に仕分ける**必要がある(契約に触るものは止まるべきだった側へ数え直す)。指標が「implementer がどれだけ止まったか」ではなく「仕様にどれだけ穴があったか」を測るように。
