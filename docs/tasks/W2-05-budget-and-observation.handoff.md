# W2-05 引き継ぎメモ

**この文書は PR 説明へ転記して削除する。**

## 却下した設計案(フェーズ1)

- **`相場基準` を `OfferPrice` から `MarketReference` へ切り出し、売り手と買い手で共有する** — 採らない。`OfferPrice.TryMarketReference` を買い手からそのまま呼ぶ。クラス名だけを見ると買い手が売り手の式を呼んでいるように読めるが、[GDD02 §8.1.1](../03-gdd/02-economy.md) は `相場基準` を提示価格の節の中で定義しており、**移すと文書の節構成とコードの置き場所がずれる**。加えて #35 のテスト12〜20(9件)を巻き込む改名になり、**挙動が1ビットも変わらない差分でレビュー帯域を使う**。[ADR-0008](../adr/0008-review-scope-narrowed-to-unnoticeable-defects.md) の「今のマイルストーンの Exit Criteria を脅かすか」で仕分けて、脅かさない側と判定した

- **`BuyerDemand` を `TradeSystem` に繋ぎ、予算を毎日計算して捨てる** — 採らない。「4つの基礎値がすべて実行される」を**パイプラインで**満たす形だが、**計算結果を誰も読まない**ので、用途を1つ落としても在庫も資金も動かず緑のままになる。#37 が店の選択を入れるまで、**式が正しいことを主張できるのはテストの期待値だけ**である。実行されている見た目を作るより、テスト表で4用途すべてを通すほうが検出力が高い

- **`予想在庫` を `ExpectedStock(現在庫, 予定消費, 予定生産投入)` という引数付きの関数にする** — 採らない。M0 のパイプラインでは順5 の時点で当日の消費も生産投入も済んでおり、**2つの引数は常に 0 になる**。常に 0 の引数は「埋めるべき穴」に見えてしまい、**#37 が何かを入れたくなる**。代わりに [GDD02 §8.2.2](../03-gdd/02-economy.md) に「M0 では `予想在庫 = 現在庫` になる」を書き、**理由(パイプラインの順序)を文書側に置いた**。日内スケジュールが入ったときに GDD の註ごと外す

- **耐久財の目標在庫を品目別の表(`DurableTargetStockPermille[itemId]`)にする** — 採らない。`ToolTargetStockPermille` の単一値にする。M0 の耐久財は工具だけであり([GDD02 §13.1](../03-gdd/02-economy.md) が「工具以外へ広げるのはスコープ膨張の回避」と明記)、**9欄のうち意味を持つのが1欄の表**になる。`InitialToolStock` / `ProductionRunsPerToolWear` が既に工具名指しの欄であり、そちらと揃えた。**1個あたりの耐久値も品目別に持てない**(`N` は §5.3 の工具固有の定数である)ので、表にしても半端になる

- **`DemandPurpose` の値を [GDD02 §6.2.1](../03-gdd/02-economy.md) の走査順(必需 → 生産の入力 → 耐久 → 嗜好)に振る** — 採らない。値は [GDD02 §8.2.1](../03-gdd/02-economy.md) の表の順のままにし、走査順は `HouseholdDemand.Lines` の並びが持つ。`enum` の値に走査順を兼ねさせると、**後から用途を1つ足したときに決済順が黙って変わる**。`Occupation` / `RandomStream` / `StateHasher` の区分タグで既に「値は振り直さない」規律があり、そこへ順序の意味を載せると規律同士が衝突する

- **観測の生成を `Knowledge` 専用のシステム(順9 相当)として独立させる** — 採らない。順5 `TradeSystem` の末尾に置く。[GDD06 §3.1](../03-gdd/06-trade-and-negotiation.md) の観測は「その日に**買い物で**訪れた区画」に依存し、それを知っているのは #37 の店選択である。別システムにすると訪問区画を `World` の状態として渡すことになり、**1日限りの中間値のためにハッシュ対象の区分が1つ増える**。`SimScheduler` が `RandomStream` の重複登録を拒むので、順5 に2つのシステムは置けない([TDD01 §3.1](../04-tdd/01-sim-core-and-m0.md))

- **`Knowledge` を「(品目, 売り手) ごとに最新1件」に畳んで持つ** — 採らない。追記して保持期間で失効させる。畳むと1 NPC あたり最大 `品目数 × 売り手数` に固定できて魅力的だが、[GDD01 §4.5](../03-gdd/01-trust-and-conversation.md) の不当価格の「気づき」は**取引tick近傍にどの観測を持っていたか**を見る([TDD01 §3.4](../04-tdd/01-sim-core-and-m0.md) の誤爆率の後段計算)。W4(#45)の入力を、いま測っていない都合で先に捨てることになる。保持期間7日・視界内の売り注文が高々10件なら、1 NPC あたり70件で頭打ちになる
