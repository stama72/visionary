# 実装タスク仕様と状態管理

設計セッションが実装エージェントに渡す作業指示と、進行中タスクの状態一覧。運用は [ADR-0004](../adr/0004-ai-driven-development-workflow.md) による。

## 状態一覧

**同時に「進行中」なのは常に1つ**(ADR-0004 論点3)。完了したタスクは表から削除する(履歴は Git にある)。

| タスク                                                         | 状態   | ブランチ                    | worktree            |
| -------------------------------------------------------------- | ------ | --------------------------- | ------------------- |
| [W1-03: World と Clock/スケジューラ](W1-03-world-and-scheduler.md) | 進行中 | `feat/world-and-scheduler`  | `visionary/`(本体) |

W1 の残り(着手前・未採番): 決定論ハッシュと2プロセス検証。

状態は **進行中 / レビュー中 / 凍結 / 完了** の4つ。

### レビューの規律

- **どのタスクも、開発者のレビューの前にレビュアーエージェントを必ず通す。** 例外を作らない。小さい変更ほど「今回は要らない」と判断しがちだが、その判断自体が開発者のレビュー帯域(ADR-0004 がボトルネックと認めた工程)を先に消費する
- レビュアーは**実装とは独立したコンテキスト**で読む。したがって実装を担当したセッション/エージェントの説明を渡さない。渡した時点で「ドキュメントから読み取れない実装」が見えなくなり、レビューがドキュメント品質の検査を兼ねるという設計(ADR-0004 論点1)が壊れる
- **レビュアーに機械の判定結果を渡さない**(ADR-0004 帰結)。ビルド・テスト・フォーマットが緑であることだけ伝え、再判定させない
- 指摘への対応は3択:**直す / 直さないと決めて理由を残す / 別タスクとして切り出す**。黙って見送らない

### 状態遷移の規律

- **レビューを終えて初めて、次に取り組むタスクを選べる。** レビュー中を放置して新しいタスクを進行中にしない
- レビューが難航した、または前提として別タスクが必要だと判明したときは、**承認せずに凍結してよい**。デッドロックを避けるための逃げ道であり、使うことをためらわない
- 新しいタスクで**勝手にセッションを開かない**。まずメインセッションに相談し、専門性が違うと判断されたときだけサブセッションへ一時的に移る(その間メインは凍結)
- **メインに戻るときは、サブセッションのタスクを完了か凍結して閉じる**

### この表の更新について

**master へ直接コミットする。** worktree をまたいで共有する必要があり、ブランチ上で更新すると他のツリーからは古い表しか見えないため。ADR 番号の予約([docs/adr/README.md](../adr/README.md))と同じ扱い。

## タスク仕様の位置づけ

**使い捨て文書**として扱う(ADR-0004 論点2)。

- 実装完了(PRマージ)時点で**凍結**し、以後は更新しない
- 実装後の正は**コードと TDD**。この文書は当時の指示であって、現在の仕様ではない
- したがって実態合わせ改訂(TDD01 §5.4 W6)の対象外
- レビュアーエージェントは、この文書を「仕様との過不足」を判定する根拠に使う

書くのは「どう作るか」。「何を作るか」と「なぜそうするか」は GDD・TDD・ADR が持ち、ここでは**リンクするだけ**にする。ここに設計判断を書き始めたら、それは ADR か TDD に書くべき内容である。

## タスク仕様の書き方

W1-02・W1-03 で、**仕様が原因の問題が8件**出た。その分類から作った規則である。

| 型                                     | 件数 | 実例                                                                     |
| -------------------------------------- | ---- | ------------------------------------------------------------------------ |
| **テストの検出力を要求していない**     | **3** | 参照ベクトルの縮退、テスト6の空虚、テスト11の無力                        |
| 上位文書との矛盾を自分で作った         | 2    | `List<PriceObservation>`(TDDは「Actor別」)、「型で不可能にする」という過大な約束 |
| 規範文と理由の不一致                   | 1    | 「同じ `entityId`」と書きながら理由は「同じ**組**を2度開くと」            |
| 空白の委譲                             | 1    | 「型の宣言のみでよい」→ 実装エージェントの独断5件                        |
| 順序・境界の曖昧                       | 1    | 「`Now` は処理の前に更新する」→ エポックが永久に処理されない             |

> **当初この表は9件・型1を4件とし、「テスト10の制約回避」を型1に含めていた。誤りである。**
> テスト10 が2つのシステムに別々の entityId を与えたのは、規範文の誤り(型3)に従った実装が
> そうしないと例外になったからで、「緑という目標設定」が原因ではない。節名を変えても実装者は
> 同じ例外に突き当たり同じ回避をする。これを防ぐのは規則5であって規則1ではない。
> 1つの根本原因を型1と型3に二重計上していた。
>
> また「何も検証しないテスト」という言い方は、参照ベクトル(縮退点でも安定性は主張していた)には
> 過大である。真に空虚だったのはテスト6とテスト11の2件。

### 規則

| #  | 規則                                                                                                                                | 機械化の余地                       |
| -- | ----------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| 1  | テスト表に**「この実装ミスで落ちる」列**を必ず埋める。埋められないテストは未完成であり、実装に渡してはならない                     | 列が空でないことは可。中身は不可   |
| 2  | **「宣言のみでよい」と書かない。** フィールド一覧を書けないなら、それは実装タスクではなく設計タスクである。決めるか、型ごとスコープ外にする | 不可(レビュー観点)               |
| 3  | 「作るもの」の各項目に **TDD/GDD の該当箇所を引用**する。引用できないものは新しい決定であり、先に TDD/GDD へ書く                    | リンクの有無は可                   |
| 4  | **保証を書くときは残る穴も書く。**「X で防ぐ。ただし Y は防げない」の形にする。防ぎきれないものを「不可能にする」と書かない          | 不可                               |
| 5  | **規範文と括弧内の理由が、違う語を使っていないか突き合わせる。** 食い違ったら狭い方を規範文に書き直す                                | 不可                               |
| 6  | **順序・境界は具体例で固定する。** 例:「`Advance(3)` を `Tick.Zero` から呼ぶと処理は tick 0,1,2、終了時 `Now = 3`」                 | 不可                               |

規則1と3だけが機械化の余地がある(列が空でないこと、引用リンクの有無)。**ただし現時点で docs の lint も CI ジョブも存在せず、実装予定も無い。** したがって6件とも今は人が守る規約であり、規則2・4・5・6 はレビュアー憲章にも同じ項目を置いてある。

> [ADR-0004](../adr/0004-ai-driven-development-workflow.md) 論点2 が「**緑にすべきテストの一覧**を書く」と呼んでいるものの、現在の形がこの節である。ADR は承認済みなので書き換えず、決定(仕様をテストのリストとして書く)はそのまま生きている。変わったのは目標の置き方だけである。

### なぜ「緑にすべきテスト」をやめたか

**節名そのものが失敗を誘発していた。** 「緑にすべき」は *通すこと* を目標に据える。型1の3件は、通ったが検出力を持たなかった — 実装者は仕様どおり緑にした。仕様が要求したのは緑であって検出力ではなかったからである。

目標を**「落ちるべき条件」**に置き換えると、この3件は書く段階で不備が露見する。「どんな実装ミスでこれが落ちるか」を書けないテストは、書けない時点で欠陥だと分かる。

**ただし節名の変更だけでは型2〜5は防げない。** 実際、型1以外の5件のほうが被害は大きかった(日次フェーズが動かない、M0検証項目#5が実行不能、エポックが永久に処理されない)。規則2〜6が要るのはこのためである。

### 変異テスト

**「核心」と印を付けたテストについては、実際に変異を当てて落ちることを確認し、完了条件に含める。** 1タスクあたり2〜3件を想定する。

**当てた変異と結果を、テストの doc コメントかコミットメッセージに残す。** 残さないと、レビュアーは機械の判定結果を渡されない(ADR-0004 帰結)ため確認手段が無く、この完了条件は自己申告のみになって形骸化する。他の完了条件(build / test / format)が機械の判定なのに対し、ここだけ性質が違う点に注意する。

印を付けないテストは「落ちる条件」を書くだけでよい。全テストに変異を当てるのは、レビュー帯域ではなく実装時間を消費するため採らない。

### 仕様品質の先行指標

ADR-0004 は「レビュー往復が2回を超えたらモデルではなく仕様を疑う」としているが、W1-03 では**1往復目で既に仕様側が原因**だった。指標として遅い。

**仕様の穴の数 = 実装エージェントが「止まって報告した件数」+「決めて報告した件数」** を先行指標とする。往復が発生する前に穴の数が見える。

- 独断で決めた件数だけを数えると、新しい「止まる基準」が守られるほど定義上0に近づき、**仕様の穴ではなくルール違反の数**しか測らなくなる
- 記録場所は**タスクのPR説明**とする。凍結後のタスク仕様には書かない(仕様は使い捨てで、指標は後から振り返る対象のため)
- W1-03 の実績は5件(いずれも新基準では「止まるべき」側だった)

### 実装エージェントが判断に出会ったとき

**影響範囲で線を引く。**

- **止まる**:タスクの外から参照される型・API・データモデルに触れる判断。W1-03 でいえば `DomainEvent` の形と `Knowledge` の構造(後者は M0 検証項目#5 が実行不能になるところまで波及した)
- **決めて報告してよい**:タスク内部に閉じた実装細部。W1-03 でいえば `LedgerEntry` の共用体の平坦化
