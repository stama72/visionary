## 却下した設計案(フェーズ1)

- **`Need.Id` を内容から導く**(`Id = ((世帯Id × 理由数) + 理由) × 品目数 + 品目`)— 状態もカウンタも要らず、`World.Needs` の削除・並べ替えに**構造的に**強い。採らないのは、**失効した組が後日また立ったときに同じ Id が返る**からである。M0 には `Promise` を作る処理が無いので今は害が出ないが、順6 を足した日に「失効した Need を指していた約束が、別の Need を静かに指す」が成立する。**この却下で失う保護**: 状態が1欄(`World.NextNeedId`)増え、ハッシュの入力・初期化・保存の経路がそのぶん増える。**添字参照に戻る事故を防いでいるのはテスト13・14 だけである**
- **遠方在庫を順4 で判定し直す**(`Ledgers` から「前日その品目を買ったか」を読み、目標在庫と予想在庫を順4 で解き直す)— `HouseholdState` に欄を増やさずに済む。採らないのは、**目標在庫と予想在庫の式が `BuyerDemand` と2か所になる**からである([02-task-spec](../process/02-task-spec.md) 規則5。`Recipe.CapacityRuns` が同じ理由で1か所に寄せてある)。**この却下で失う保護**: 順5 と順4 の間に「順5 が毎日正しく書いている」という暗黙の契約ができる。**契約を守るのはテスト20〜24 だけで、型も例外も守らない**(`int[]` の添字と単位の取り違えは黙って通る)
- **困窮を破産中フラグだけで立てる**([GDD02b §4](../03-gdd/02b-consumption-and-household.md)「判定の規範は §3.3 の破産中フラグ」をそのまま読む)— 引用に最も忠実で、条件が1つで済む。採らないのは、**フラグが在庫を見ないと §3.3 自身が明記している**からで、Need(= 不足の表面化)としては広すぎる。**この却下で失う保護**: 今日から食えなくなった世帯の困窮 Need が1日遅れる(フラグが前日ベースのため)。**[GDD02 §8](../03-gdd/02-economy.md)-2 (a) を「困窮 Need の件数」で代替できなくなった** — (a) が測るのはフラグそのものである(GDD02b §8.1 に書いた)
- **`LaborCapacity` を切り出さず、順4 で設備係数と労働力合計‰を綴り直す** — `ProductionSystem` に一切触らずに済み、差分が小さい。採らないのは規則5(同上)。**この却下で失う保護**: `ProductionSystem.RunOneHousehold` を書き換えるので、既存の `ProductionSystemTests` が守る範囲の外(構成員の走査順・`max(0, …)`)に手が入る。**見張りはテスト25 だけである**
