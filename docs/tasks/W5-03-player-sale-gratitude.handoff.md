## 却下した設計案(フェーズ1)

4件とも開発者の裁定(2026-10-28)。

- **用途を GDD02b §3.2 の走査順だけで決める** — 薪は暖房(必需)へ回り、台詞が語った生産停止の Need が残る。**失う保護**: 規則が1本で済む単純さ。採った案は理由ごとの優先順と走査順の2段になり、優先順の取り違えはテスト #9 だけが捕まえる
- **コマンドが NeedId を指定する** — #263 のコマンドと UI に選択が乗り、検証が1つ増える。**失う保護**: プレイヤーが用途を明示的に選べること(どの困りごとに応えたかを自分で決める表現)。M0 では Need の一覧から品目を選ぶだけになる
- **朝0時の予算を World に控えて読む** — 状態とハッシュの欄が増え、同じ日に先に売った分が予算に映らない。**失う保護**: 日中に予算が動かないこと。採った案では、同じ日に別の品目を先に売ると(買い手の流動資金が減って)後の品目の予算が下がりうる。1日1回の制約は (世帯, 品目) 単位なので、品目をまたいだ予算の変化は塞いでいない
- **Need を満たした取引だけに段階を出す** — 資金で切られた取引に段階が出ず、資金の乏しい戸ほど反応が消える。**失う保護**: 「Need を満たした」という GDD01 §3.6 冒頭の語の字義どおりの読み。採った案では、1個だけ売っても段階が出る(数量を絞って感謝だけ集める経路は、Need の差し引きで残量が減るので同じ Need には翌日以降しか届かない)

- **(訂正2)付け替えの翌日の古い遠方在庫を、販売の側で `NoNeed` として断る** — 開示した困りごとに売れない食い違いが残る。開発者の裁定で Need の生成側を直した。**失う保護**: 差分が #253 の新規コードの中で閉じること。採った案は既存の `NeedGenerationSystem` を変え、行の有無の条件が `Build` と `HasDemandLine` の2か所に書かれる(一致はテスト #17 だけが見る)

## 停止(フェーズ2・2回目)

1巡目の I-b-1 で `SPEC-OUTSIDE`。**手順5 の「Need があるのに需要の行が無いのはモデルの欠陥」は誤り。** 職業付け替えの翌日に正常系で踏む: 前日 18時に資金不足で入力を買えず `UnfilledPurchase` が積まれる → 0時に `HouseholdSystem` が付け替え(`UnfilledPurchase` は消さない)→ 同じ 0時の `NeedGenerationSystem` が旧入力品目に遠方在庫の Need を立てる(開示される)→ プレイヤーが値を出すと、新職業のレシピで組んだ `Build` に行が無く `InvalidOperationException`。そのうえ手順4 の記録が残ったまま例外が上がる。付け替え先にも行がある品目(薪)は落ちず、黙って用途が変わる。直し先の候補(Need 生成で旧入力を落とす / `NoNeed` に寄せる / 結果値を足す / #263 に握らせる)は、いずれも GDD06 §6.1 か GDD02b §8.1・GDD06 §3.1 に及ぶ。
