## 却下した設計案(フェーズ1)

- **窓口を `World.Market` に実体化する** — [GDD02d §2.1](../03-gdd/02d-external-market-and-money.md) が決定として却下済み。`Market` のキーは売り手**世帯**であり、実体化すると決定論ハッシュに「`Market` は含める / 窓口は含めない」の二重定義が生まれる。**どちらに実装しても同一設定の2回実行は一致するので CI が検出しない** — 却下理由はこの「検出できなさ」に立っており、いまも生きている
- **窓口の当日価格を全世帯に見せる**(所在が公開なら価格も公開)— [GDD06 §3.1](../03-gdd/06-trade-and-negotiation.md) が「所在は公開、価格は距離 R の外からは見えない」と明記している。見せると隅の世帯が外部売値の季節変動を先読みでき、情報の摩擦が窓口の側から抜ける。代わりに未知価格の見積もりを **1** と決めた([GDD02d §2.2](../03-gdd/02d-external-market-and-money.md) に追記)
- **窓口の未知価格の見積もりを 0 にする** — 「最も楽観的な下限」としては 0 が自然だが、`BuyerBudget.Decide` と `TradeSettlement.FundsCap` が「実効価格は 1 以上」で投げる。**検査を緩める側に倒すと、床が 0 の品目で `PurchaseQuantity` の除算に到達する経路が開く**
- **輸出を段5a の外出の計画へ畳む** — 余剰はその日の世帯間取引が確定するまで決まらない([GDD02d §2.3](../03-gdd/02d-external-market-and-money.md)「確定したあと」)。畳むと持ち込む量を予測する別の規則が要る
- **`TradeSettlement.Execute` に `null` の売り手を通して窓口を表す** — 売り手側の在庫・資金・帳簿を動かす枝が `if (seller != null)` だらけになり、世帯間の約定の不変条件が読めなくなる。別メソッド2本(`ExecuteImport` / `ExecuteExport`)にした
- **`BandMultiplier` を実測に合わせて引き上げ、シードを足す** — 発散は [#120](https://github.com/stama72/visionary/issues/120) の守備範囲であり、本タスクで帯を緩めると #120 の検出器が先に鈍る。**シード1・20 倍のまま据え置き、実測を doc コメントに 1 行残す**

### 2巡目を網羅パスに充てた判断と、その結果

1巡目の象限I 2 件が**同じ型**だった — 「仕様のテスト表が『この実装ミスで落ちる』と数えた実装ミスが、そのテストを実際には落とさない」。この型は**列挙可能な境界**(テスト表の行 × 各行が挙げた実装ミス)を持つので、[01-review](../process/01-review.md)「網羅パス」に従って**2巡目を探索ではなく全数の突き合わせに充てた**。

**結果: 挙がっていた実装ミス 44 件のうち 3 件が、そのテストを落とさなかった。** 1巡目が探索で見つけた 2 件に対し、網羅は 3 件を確定させたうえで**残り 41 件が実際に落ちることも確定させた**。3巡目の象限I-a が 0 件だったのは、この網羅が効いたためと読んでいる。

**巡を1つ消費する判断は正しかった。** I-a-1(輸出の相場基準の売り手側 / 買い手側の取り違え)は探索では出にくい — **仕様が2か所で「取り違えても例外は出ない」と名指ししていたのに検出器が1件も無く、しかも段6 を踏む既存テストが全て初日で `TrySeller` と `TryBuyer` がともに false を返すため、差が構造的に出なかった。**

### M-5 の実測 — 仕様が予告した issue は**立てない**

**タスク仕様は M-5 について「緑のままなら、耐久の換算がどこからも守られていないという実測である — 直さずに [#37](https://github.com/stama72/visionary/issues/38) の後継として issue へ落とす」と事前に決めていた。実測は赤(5 件)だったので、この issue は立てない。**

落ちた 5 件のうち **`TradeSystemTests.ErrandPlannerAndSettlementAgreeOnQuantity` は耐久の換算を直接見ている意図的な検出器である。** つまり #37 申し送り1・3 が心配していた「耐久の換算に守りが無い」状態は、**#98 以降すでに解消していた**。

**この経緯自体がフェーズ2 の失敗の記録でもある。** 2巡目のレビューを受けてフェーズ2 が仕様の別表に「耐久の換算には現時点で検出器が無い」と書き、3巡目がそれを反証し(R-6 の前提表明が拘束している)、実測がさらに主たる守り手を別に見つけた。**「検出器が無い」は「機械が守っている」と同じく読者に確認をやめさせる記述であり、実測の前に書いてよいものではなかった**([process/03](../process/03-corrections.md))。訂正は `39e367a` に残してある。
