## 却下した設計案(フェーズ1)

| 案 | 却下の理由 |
| -- | ---------- |
| **検出器を CI ジョブとして回す** | 開発者の判断。GDD の節番号を振り直した PR が、コード側の引用を直すまで赤になる。#101 が踏んだ経路を機械が塞ぐ効果はあるが、その代償を**いまは**取らない。**検出器は置くので、後から CI に載せる判断だけが残る** |
| **検出器の対象を `GDD02*` と `GDD06` に限る**(issue の閉じる条件の文言どおり) | 2026-09-20 の実測で、古い引用は `GDD02 §*` の 112 件だけ。`TDD01`(143 引用)・`GDD08`・`GDD06` には 1 件も無い。**全文書へ広げても結果が同じなので、広げるコストが 0 である。** 将来 TDD01 の節を振り直したときに拾える |
| **継続引用(`GDD02 §6.1・§9`)を無条件に直前の文書 Id へ引き継ぐ** | `GDD02d §4.3 の条件(a)〜(e)、#96 タスク仕様 §8` を `GDD02d §8` と誤検出した(`M0CalibrationTests.cs:9`)。**0 件を要求する検査では偽陽性のほうが有害である。** 引き継ぎを `タスク仕様` / `ADR-` / `#<数字>` で打ち切る規則に変えて 0 になった |
| **行をまたいで文書 Id を引き継ぐ**(`StateHasher.cs` の `§3.8` のような形を解決する) | 誤帰属の危険が、取りこぼし 35 件より大きい。**`UNRESOLVED` として件数だけ出す**ことにして、解決は放棄した。スクリプト冒頭の「残る穴」に書く |
| **表C(規則ごと古いコメント)の散文も本タスクで直す** | 直すと、規則を引き取る #98 / #38 / #39 の入力が消える。#112 が「式や規則は触らない」と決めている。**代償は、引用先だけが現行を指す中間状態がしばらく残ること** — 仕様の表C とフェーズ3 の issue コメントが、その間の唯一の目印である |
