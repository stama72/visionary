## フェーズ1 の裁定(フェーズ2 からの差し戻し)

**フェーズ2 が挙げた2つの読み(値 / 配線)は、計測でどちらも棄却された。** 真因は3つめにある — **W2 では耐久の需要が構造的に立たない。**

- **配線は正しい。** `TradeSystem` に一時プローブを入れて実測したところ、`基礎値 == ApplyPermille(流動資金, 比率‰)` が毎日一致した。母数は GDD02 §8.2.1 どおり流動資金であり、引き継ぎ表 A は踏まれていない
- **値でもない。** 耐久の予算比率を 10‰ → 1000‰(流動資金の100%)にし、30日 → 150日にしても**工具の約定は0件**
- **真因**: 工具の摩耗は生産回数でしか進まない(1生産 = 1摩耗)。W2 は1次産品に売り手が居ない(#38)ので**生産が初期入力5日分で止まり、摩耗も5で止まる**。需要が立つには摩耗15回が要る。実測でも `予想在庫` が day5 から day149 まで 25 耐久値で凍結していた

**帰結として、引き継ぎ表 A はパイプラインでは原理的に検出できない**(母数を `surplus` にしても約定0件のままで挙動が変わらない)。**旧 #22 は A の検出器として置かれていたが、判別力を持ち得ない場所にあった。**

裁定は3つ:

1. **旧 #22 を分ける。** 嗜好(ビール)は `PreferenceIsActuallyBought` としてパイプラインに残す(現状緑)
2. **A の検出器を単体へ移す**(新 #29 `DurableBaseValueIsMeasuredOnLiquidFundsNotSurplus`)。**必要運転資金 > 0 の世帯で `SurplusFunds < LiquidFunds` を確かめたうえで母数を見る** — この確認が判別力そのものである(既存 `DurableAndPreferenceReadTheirOwnBudgetRatio` は必要運転資金0の世界なので A を素通りさせる)
3. **「工具が実際に買われる」は #38 の Exit Criteria へ移す。** 耐久の予算比率‰ の当否も #38 の後でなければ測れない(#28 へ実測つきで送った)

**タスク仕様の自己矛盾も解消した。** 完了条件「落ちるべき条件のテストが全て緑」と例外「30日回しても1件も買われないなら止まって報告する」は、耐久側が仕様から外れたことで同時に満たせるようになった。

## フェーズ2 が裁けなかった点(→ フェーズ1。**上の裁定で決着済み**)

**テスト #22 の耐久が0件になる原因が、2つの読みに割れる。どちらに倒すかが設計判断であり、修正先はいずれもタスク仕様の外にある。**

| 読み | 原因 | 修正先 | 所有 |
| ---- | ---- | ------ | ---- |
| 値 | `BudgetRatioPermilleByPurpose[Durable] = 10‰` が M0 の初期流動資金200・工具の実効価格48 に対して構造的に小さい(1%×338 ≒ 3 ≪ 48)| `WorldDefinition.M0` の初期値 | **#28**(軸は GDD02 §13.2)|
| 配線 | 耐久の予算の**母数が余剰資金**になっている | `BuyerBudget` | **#36**(引き継ぎ表 **A**)|

**implementer は「値」と断じたが、テスト #22 は仕様上まさに引き継ぎ表 A の検出器として置かれている**(「耐久の母数を余剰資金にする → 運転資金で潰れた世帯が恒久に工具を買えない」)。implementer 自身の報告も「嗜好/耐久の予算は必ず余剰資金 ≦ 流動資金に縛られる」と述べており、**症状は A の記述と一致する**。「係数が小さい」のか「母数が誤っている」のかの切り分けは GDD02 §8.2.1・§8.2.3 の意味論の判定である。

**あわせて、タスク仕様が自己矛盾している(象限I-b)。** 完了条件「28件すべて緑」と、同じ節の例外「30日回しても1件も買われないなら直さずに止まって報告する」は同時に満たせない。**#22 は嗜好(ビール)と耐久(工具)を1つのテストに同居させているため、ビールが通っても赤のまま**である。この2つを分けるかどうかもフェーズ1 の判断。
