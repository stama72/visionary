## 却下した設計案(フェーズ1)

- **統合テストで `StateHasher` の値を定数にピン留めする(黄金ハッシュ)** — #36 から引き継いだ配線10件(A〜J)は、どれもハッシュを変える。ピン留めすれば全件まとめて落とせる。**採らないのは、赤の意味が読めなくなるためである** — #28 が初期値を1つ動かすだけで赤くなり、「配線が壊れた」のか「値を変えた」のかを区別できない。**値に依存しない結果(嗜好と耐久が買われる / 知識が R の外へ広がる / 帳簿が突合する)で代替した**(テスト #20・#22・#23)。この理由は #28 が値を動かす限り生き続ける。
- **「必需を資金不足で買えなかった」件数の記録を #39 へ回す** — 本タスクのスコープ(店の選択と帳簿の突合)には無い。**採らないのは、#39 が Trade の決済ループに配線を足すことになるためである** — #39 は `Household`(順3)のタスクであり、順5 を触らない。W2-05 で問題になった「仕様だけが守っている配線」を、フェーズをまたいでもう一度作ることになる。切り詰めが起きる場所でその場で数えるほうが、テストも同じ場所で書ける。

## フェーズ2 が裁けなかった点(→ フェーズ1)

**テスト #22 の耐久が0件になる原因が、2つの読みに割れる。どちらに倒すかが設計判断であり、修正先はいずれもタスク仕様の外にある。**

| 読み | 原因 | 修正先 | 所有 |
| ---- | ---- | ------ | ---- |
| 値 | `BudgetRatioPermilleByPurpose[Durable] = 10‰` が M0 の初期流動資金200・工具の実効価格48 に対して構造的に小さい(1%×338 ≒ 3 ≪ 48)| `WorldDefinition.M0` の初期値 | **#28**(軸は GDD02 §13.2)|
| 配線 | 耐久の予算の**母数が余剰資金**になっている | `BuyerBudget` | **#36**(引き継ぎ表 **A**)|

**implementer は「値」と断じたが、テスト #22 は仕様上まさに引き継ぎ表 A の検出器として置かれている**(「耐久の母数を余剰資金にする → 運転資金で潰れた世帯が恒久に工具を買えない」)。implementer 自身の報告も「嗜好/耐久の予算は必ず余剰資金 ≦ 流動資金に縛られる」と述べており、**症状は A の記述と一致する**。「係数が小さい」のか「母数が誤っている」のかの切り分けは GDD02 §8.2.1・§8.2.3 の意味論の判定である。

**あわせて、タスク仕様が自己矛盾している(象限I-b)。** 完了条件「28件すべて緑」と、同じ節の例外「30日回しても1件も買われないなら直さずに止まって報告する」は同時に満たせない。**#22 は嗜好(ビール)と耐久(工具)を1つのテストに同居させているため、ビールが通っても赤のまま**である。この2つを分けるかどうかもフェーズ1 の判断。
