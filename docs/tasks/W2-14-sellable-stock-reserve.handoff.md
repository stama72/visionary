## 却下した設計案(フェーズ1)

- **`TradeSettlement` に番人を置かない(呼び出し側の切り詰めだけで担保する)** — 採らない。段5b と `StoreChoice` の2経路を直しても、**将来 工房在庫を直接読む呼び出し側が生えたときに機械が止めない。** #148 の追随表が約定の減算を「最終的な担保」と呼んでいるのは、そこが在庫を動かす唯一の場所だからである。引数1つと既存テストの修正がその代償
- **不変条件テスト(60日走行で鍛冶の工房在庫が常に ≥ 1)だけで担保する** — 採らない。上と同じ理由に加え、**60日走行は踏まれた経路しか見ない** — 番人は踏まれた瞬間にその場で落ちる
- **検出器の下限を「全品目で毎日1件以上」に広げる** — 採らない。**完売由来の 0 件**(食料など需要の強い品目で正当に起きる)で赤くなり、留保と無関係な理由で検出器が鳴る
- **検出器の下限を日数比率(例: 60日中58日)で置く** — 採らない。#148 の**訂正9 が明示的に反転させた向き**へ戻る。0 件の日は検出したい事象そのものである
- **ヘルパーに `Recipe` を渡す形** — 採らない。別世帯のレシピを渡す取り違えが型で防げない。`(definition, household, itemId)` なら職業から引くので混ざらない(#39 の職業付け替えにも自動で追随する)
- **留保量で設備と入力を合算する形** — 採らない。[GDD02c §1.3](../03-gdd/02c-price-and-budget.md) は排他の分岐で書いており、M0 に該当品目が無い。合算は**新しい決定**であって実装の裁量ではない

### 止まって報告した内容(1件)

**テスト11 `SmithProductionRecoversOverSixtyDays` が5シードすべてで赤。原因は留保ではなく、1次産品(鉄鉱石・木炭)の供給が60日もたないこと。**

留保そのものは仕様どおり効いており、テスト1〜10・12 は緑。鍛冶の工具在庫は60日間一度も 0 にならず 4〜7 で安定する(#148 の紙の予測「留保1 + 閾在庫3 = 4」とおおむね一致)。しかし鍛冶は day 7〜8 で鉄鉱石・木炭を使い切り、以後 生産回数 0 が60日目まで続く。

### 切り分けの実測(シード1。フェーズ2 が追加で指示したもの)

| 測ったこと | 結果 |
| ---------- | ---- |
| day 8〜60 に `world.Market` へ鉄鉱石・木炭の売り注文が立った日数 | **鉄鉱石 0/53日・木炭 0/53日**(全日0件) |
| 同期間の鍛冶2戸の所持金 | ゼロではない(household2 は大半10・時折70〜590 / household3 は大半8〜68・時折884) |
| 同期間の鍛冶の帳簿 `Purchase` に鉄鉱石・木炭が現れた件数 | **0件** |

**供給側の断絶であって、需要側(資金不足・走査順)ではない。** 鍛冶は買いに行く以前に、市場に売り注文が無い。

master(留保なし)との比較:

| | master | 本ブランチ(留保あり) |
| - | ------ | ---------------------- |
| 工具在庫が最初に 0 になる日 | day 1 | **60日中一度も 0 にならない** |
| 生産回数が最初に 0 になる日 | day 2 | day 8 |
| 鉄鉱石が最初に 0 になる日 | day 8 | day 7 |
| 木炭が最初に 0 になる日 | day 8 | day 7 |

**原材料の枯渇は留保が作った経路ではない**(master でも day 8)。留保が変えたのは工具在庫が 0 にならないことと、それに伴い生産0 の発生が day 2 → day 8 に遅れたことだけである。
