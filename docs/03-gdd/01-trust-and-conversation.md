## 0. この文書の位置づけ

信用システムと会話システムは、本作のUSP「信用が資本になる」と「情報を足で稼ぐ」を実装する中核であり、**コアループの2工程(歩く・聞く / 商う)を直接支える**。両者は不可分(会話が信用を生み、信用が会話の内容を変える)なため、1つの分冊にまとめる。

数値はすべて**初期値であり、M0〜M2の調整対象**である。ここで固定したいのは数値ではなく、システムの構造と依存関係。

## 1. 設計方針

1. **会話それ自体に意味を持たせる**。情報を得るための手段としてだけの会話は作業になる。話しかける・話を聞く行為そのものが信用という蓄積を生むことで、会話が目的にもなる
2. **信用は中世商業のリアリティである**。掛け売り・手形・評判で回っていた当時の商業を、メカニクスとして再現する。ファンタジーの好感度システムではなく、経済の構成要素として設計する
3. **効果は4点に限定する**。信用が「なんとなく色々に効く」状態は、プレイヤーが因果を追えずGuild 3化する。効き先を絞り、プレイヤーが「信用を上げると何が起きるか」を明確に予測できるようにする
4. **数値は見せない**。信用は本来目に見えないもの。数値ではなくTierと相手の態度で伝える(§2.7)
5. **シミュレーションへの組み込みは段階的に**。まずプレイヤー⇔NPC間で成立させ、NPC同士への拡張は制御可能性を確認してから行う(§2.9)

## 2. 信用システム

### 2.1 データモデル

```
TrustScore
  from    : NpcId           // 信用を寄せる側
  to      : ActorId         // 信用を寄せられる側(プレイヤー or NPC)
  value   : int  [0, 100]   // 信用スコア
  lastMet : Tick            // 最後に接触したtick
```

- v1.0の必須スコープは `to = プレイヤー` のみ。`to = NPC` はフルスコープ(§2.9)
- NPC 100体 × プレイヤー = 100レコード。フルスコープでも 100×100 = 10,000レコードで、疎行列として保持すれば問題ない規模

### 2.2 信用が影響する4つの効果

**この4つ以外に信用を効かせない。** 拡張したくなった場合はこの表に追記し、影響の全体像を1箇所で把握できる状態を保つ。

| # | 効果                     | 内容                                                                         | 実装上の形                                                                                                                                                                                                |
| - | ------------------------ | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 | **取引相手の選好** | 同条件なら信用のある相手から買う。多少高くても信用を優先する                 | NPCの購買評価で実効価格`p' = p × (1 - α × trust/100)` を用いる(α初期値0.2 = 信用MAXで実質2割引の魅力)。**p' は相手選びの効用比較にのみ使う評価値であり、実際の支払額には影響しない**(§2.2.1) |
| 2 | **交渉価格の幅**   | 信用があるほど価格交渉で動かせる幅が広い                                     | 交渉可能レンジ`±(base + β × trust/100)`%(base 3%, β 12% → 信用MAXで±15%)                                                                                                                          |
| 3 | **掛け売りの可否** | 信用が一定以上で後払い・信用取引が解禁。上限額は信用と相手の支払余力で決まる | Tier「常連」以上で解禁。与信枠は動的(§2.2.2)                                                                                                                                                             |
| 4 | **情報開示の深さ** | 信用に応じて話す内容が深くなる。世間話→相場の実数→他人の事情→秘密         | 会話トピックの解禁条件(§3.2)                                                                                                                                                                             |

#### 2.2.1 効果1と効果2の関係(二重適用の禁止)

取引価格に実際に影響するのは**効果2のみ**。効果1の実効価格 p' は、NPCが複数の取引相手候補を比較するときの効用計算にだけ使う内部評価値であり、支払額そのものは動かさない。信用が高いと「選ばれやすく」なり(効果1)、選ばれた後の交渉で「動かせる幅が広く」なる(効果2)——役割を分けることで、信用が価格に二重に効くことを防ぐ。

なお、交渉が実際にどう妥結するか(提示・応答のフロー、NPCの留保価格、妥結額の決定)は本分冊のスコープ外とし、**分冊06「取引・交渉システム」で定義する**。本分冊が保証するのは「信用は交渉可能レンジの広さにのみ効く」という境界条件まで。

#### 2.2.2 与信枠は動的に決まる

掛け売りの上限額をグローバル係数だけで決めると、支払余力のない世帯が掛けに応じて破産する(素材代金や弟子の給金が払えなくなる)。与信枠は**信用と支払余力の両方で制約**する:

```
与信枠 = min( γ × trust,  max(0, 流動資金 − k × 直近の固定支出見込み) )
```

- 流動資金・固定支出は**世帯**の家計モデル([GDD02b §3](02b-consumption-and-household.md))から取得する。**家計の主体は個人ではなく世帯である**([GDD08 §2](08-household-and-decision.md))。**M0 の固定支出は仕入れだけである** — 給金は [GDD10](10-employment.md)、税は [GDD09](09-treasury-and-tax.md) でどちらも M0 のスコープ外
- k は安全率(初期値1.5)。「固定支出の1.5季(45日)分は手元に残す」という保守的な商人の感覚
- これにより「信用はあるが金がない相手は掛けに応じない」という自然な挙動が、家計モデルから導かれる

### 2.3 信用の増減(一覧)

約束(クエスト)まわりの式の定義と記号は§2.8。**全計算式の結果は小数点以下切り上げ。**

| 分類 | 行為                              | 変化                                  | 備考                                                                         |
| ---- | --------------------------------- | ------------------------------------- | ---------------------------------------------------------------------------- |
| 会話 | 挨拶(自動)                        | +1                                    | 1日1回。話しかけると自動で発生(§3.1)                                        |
| 会話 | 会話評価:自分のニーズを言えた     | +1                                    | 会話終了時に判定(§3.5)。同一ニーズにつき1回                                 |
| 会話 | 会話評価:自分に関係ある噂を話せた | +2                                    | 1つ以上で+2。1日1回(§3.5)                                                   |
| 会話 | プレゼント                        | +2〜+8                                | 相手のニーズに合致するほど大きい([idea/001](../idea/001-コアループ.md) §4.2) |
| 約束 | 約束する                          | +max(2, 0.2B)                         | = +2〜+4(§2.8)                                                              |
| 約束 | ニーズの充足(納品)                | +B                                    | B = 5〜20(§2.8)                                                             |
| 約束 | 履行ボーナス(期限内完了)          | +0.5B × 残り日数/L                   | 早く納めるほど大きい(§2.8)                                                  |
| 約束 | **不履行ペナルティ**        | **−min(30, 5 + 1.5B × e/L)**  | 破棄・自動破棄。早く謝るほど軽い(§2.8)                                      |
| 約束 | 期限延長ペナルティ                | −min(30, 0.75B × (e延長 + e完了)/L) | 延長を使った場合、完了時に必ず付く(§2.8)                                    |
| 取引 | 不当な価格での売りつけ            | −5〜−15                             | 乖離幅に比例。判定原則と納得感の設計は§4.5                                  |
| 経過 | 期間経過による減衰                | スコアは不変                          | 効果1〜3の適用が段階的に鈍る。最大半減(§2.5)                                |

### 2.4 非対称性の原則

**信用は築くのに時間がかかり、失うのは一瞬。** 不履行ペナルティの上限(−30)を単発の獲得(最大+20)より大きく設定しているのはこのため。これは中世商業のリアリティであると同時に、「約束を軽く扱えない」という緊張感がゲームプレイの重みを作る。

同時に、§2.8の式は「早く謝るほど軽い」よう設計されており、**誠実さを行動で示す手段**がプレイヤーに常に残されている。回復不能にはしない——信用0に落ちても、時間と誠実な取引で再建できる(プレイヤーが詰む状態を作らない)。

### 2.5 信用の減衰モデル

長期間会わないNPCの信用が下がるかどうか。定期的に顔を出さないといけない「作業感」の問題に直結する。

#### 上限の減衰

スコア自体は下がらないが、会わない期間が1週間経つことに効果1〜3の適用が最大3回、20%ずつ段階的に鈍る。再会話1回(同日中は再カウントしない)で10%ずつ回復。回復タイミングは話しかけた瞬間。よって、少なくとも1回分は回復してから効果が適用される。最大まで減衰(40%)の状態->話しかける->50%に回復->取引交渉開始(効果1が50%効く)。この1回分が効くことにより、上記の設定では実質的に2週目の減衰は半分の10%で済み、最大でも効果は半分までしか減衰しないことになる。なお、減衰期間、減衰幅、回復幅についてはバランス調整をする可能性がある。

- 全員を周回するのではなくて、維持対象を大商人中心に絞るように促す設計意図。
- 減衰幅を半分までにとどめること(ペナルティの軽減)、減衰のスピードを速めること、回復に必要な会話の回数を増やすこと(維持コスト、機会費用の増加)で、大半のNPCについては減衰のペナルティが会話の手間(機会費用)を超えることがない状況を作る。
- プレイヤーが効果を維持するインセンティブを持つのは、取引額の大きな一部の大商人だけ。全員を周回するよりも、彼らに集中して手間をかける方が有利な状況を作る。大商人と会食などを設定して定期的に会うことを促す設計にする。
- 逆にそれ以外の相手については、最大でも半減に抑えることで、「放置しても致命傷にはならない」という安心感をプレイヤーに与える。
- 情報収集(効果4)については一旦適用外とする。クエストが詰まるストレスを避ける。

将来の拡張アイデア(維持コストの個性化、派閥とトレードオフ、外注化、前兆の可視化)は [idea/005](../idea/005-信用・会話システム.md) に蓄積する。

### 2.6 信用Tier

閾値はすべて初期値(調整対象)。トピック・機能の解禁条件はTierで指定する(数値を直接参照しない)。

| Tier         | 閾値(仮) | 概要                                                 |
| ------------ | -------- | ---------------------------------------------------- |
| 他人         | 0〜19    | 初対面。世間話と現金取引のみ                         |
| 顔見知り     | 20〜39   | ニーズを聞ける                                       |
| 常連         | 40〜69   | 相場を尋ねられる。掛け売り解禁。オフィス訪問可       |
| 信頼する相手 | 70〜89   | 他人のことを聞ける。私的な食事。背景・事情の開示     |
| 盟友         | 90〜100  | 秘密と大口案件の入口(v1.0では最小限の専用コンテンツ) |

### 2.7 表示方針:信用は隠しステータス

**数値は開示せず、プレイヤーに見せるのはTierのみ。** 本来、信用とは目に見えないものであり、その特徴を再現してこそ、道徳や思いやりを行動で示すという心のこもった体験が実現できる。

- 増減の手応えは数値ポップアップではなく、NPCの態度・台詞・演出の変化で返す
- 信用を得られることが報酬になる場合は、定性ラベルでの表記を許容する(例:「報酬:◯◯コイン、信用(小)」)
- 減衰などの状態変化も、噂話やNPCの素振りといった間接的なシグナルで察知させる(具体案は[idea/005](../idea/005-信用・会話システム.md)④)
- 内部数値は開発ビルドのデバッグ表示でのみ可視化する(バランス調整用)

### 2.8 約束(クエスト)のライフサイクル

**M1 から入れる。** M0 は約束を持たず、困りごとは通常の取引で解く(§6.1。プレイヤーが売り手になる取引の扱いは [#103](https://github.com/stama72/visionary/issues/103))。

#### 成立

```
ニーズ開示(§3.2)
  → NPC「この依頼、受けてくれるかね?」
      → はい: 約束成立(クエスト生成、期限が確定)
      → いいえ: 何もなし(信用変化なし。ニーズは開示済みのまま残る)
```

#### 記号の定義

- **B(基本値)**:ニーズの緊急度・規模に比例。5〜20
- **t0**:約束した日付 / **t1**:期限の日付
- **L(クエストの長さ)**= t1 − t0。1以上
- **e(経過日数)**= 判定時点 − t0
- 全計算式の結果は小数点以下切り上げ。日数の条件判定も切り上げ
- 信用変化のグラフ: https://www.desmos.com/calculator/hkgrl9vgtx

#### 信用変化の式

| 事象                   | 変化                                      |
| ---------------------- | ----------------------------------------- |
| 約束する               | +max(2, 0.2B)                             |
| ニーズの充足(納品)     | +B                                        |
| 約束履行のボーナス     | +0.5B × (t1 − 完了日)/L                 |
| 約束不履行のペナルティ | −min(30, 5 + 1.5B × e/L)                |
| 期限延長のペナルティ   | −min(30, 0.75B × (e延長時 + e完了時)/L) |

#### 状態遷移のルール

- **早期の謝罪破棄**:期限前ならいつでも、NPCに直接謝ってクエストを破棄できる。不履行ペナルティは謝罪時点の e で計算されるため、**早く謝るほど軽い**。約束したその日のうちなら固定値5に収まる
- **期限の延長**:e が 0.25L〜1L の間、根拠となる情報(サプライヤーとの商談の記録、材料不足の噂、船の遅れの噂など。§4.3の出来事知識・§4.4の帳簿)と共に難航を説明すれば、期限を最大1.25L(t0起点)まで延長できる。代償として**約束履行のボーナスは消失**し、本来の期限に間に合ったかに関係なく、**完了時に期限延長のペナルティが付く**。これによりクエスト完了時の信用収支は概ね−5〜+10に低下する。延長後に破棄した場合は通常どおり不履行ペナルティを適用する
- **自動破棄**:期限までに完了されなかったクエストは自動的に破棄される。不履行ペナルティ(e = L)は即時反映され、**プレイヤーが謝りに来るまで悪い噂が広められ続ける**(継続的な悪影響。噂の最小実装は§7)。期限を破ってしまった場合でも、早く謝りに行った方がよい
- **NPC都合のキャンセル**:クエストが有効な間、NPCはそのニーズを他の手段で満たそうとしない。期限内に意図せず満たされてしまった場合(例:よその船が偶然その品を大量に持ち込んだ)、NPCはプレイヤーを直接訪ねてきて、**ペナルティなしのキャンセル**を告げる。期限の延長をしていなければ、プレイヤーへの補償として約束履行のボーナスが与えられる

### 2.9 スコープとフォールバック

| 段階                     | 内容                                                                                              | 判定                 |
| ------------------------ | ------------------------------------------------------------------------------------------------- | -------------------- |
| **必須**           | プレイヤー⇔NPC間の信用。効果1〜4すべて                                                           | v1.0必須             |
| **フルスコープ**   | NPC同士の信用も経済シミュレーションに組み込み、取引相手選好・交渉価格に反映                       | M0で制御可能性を検証 |
| **フォールバック** | フルスコープが破綻した場合、NPC同士の信用は廃し、プレイヤー関連の取引条件と会話発生条件のみに縮小 | M0で判定             |

フルスコープの懸念は**バランス調整の困難さ**:信用が取引相手選好に効くと、経済が「最適な取引相手」ではなく「関係の履歴」で回り始め、価格形成が意図せず硬直または発散しうる。M0のヘッドレス実行で、信用ありモデルとなしモデルの価格系列を比較して判断する。

## 3. 会話システム

### 3.1 会話の構造

会話はトピック選択式。自由入力やフルボイスの分岐ドラマは作らない(工数)。

```
話しかける → 自動挨拶(信用+1、1日1回。相手の機嫌・近況の断片)
  → トピック一覧 → 選択 → 応答 → (一覧に戻る) → 会話終了
  → 会話評価(§3.5)
```

**挨拶はトピックではない**。話しかけた時点で自動的に交わされ、その後にメニューが開く。

**下の解禁条件は M1 からの仕様である。** M0 は Tier を持たないので、「ニーズを聞く」は常時開き、Tier で閉じるトピックと「依頼の報告」は置かない(§6.1)。

| トピック         | 解禁条件                 | 得られるもの                                               |
| ---------------- | ------------------------ | ---------------------------------------------------------- |
| 世間話           | 常時                     | 街の噂、天候・行事の情報                                   |
| ニーズを聞く     | Tier「顔見知り」以上     | ニーズの開示(§3.2)→約束の成立へ(§2.8)                   |
| 商談(売る/買う)  | 常時(条件は信用依存)     | 取引。交渉幅・掛け売りは効果2・3に従う。妥結の詳細は分冊06 |
| 相場を尋ねる     | Tier「常連」以上         | 品目の価格情報(§4.1の知識に加算)                          |
| 他人のことを聞く | Tier「信頼する相手」以上 | 他NPCのニーズ・事情・紹介(§4.2の知識に加算)               |
| 依頼の報告       | 依頼受注中               | 納品・謝罪・期限延長の申し出(§2.8)                        |

このトピック一覧はメニュー型の暫定仕様。プレイヤーの発言を選択肢として選ぶRPG風UI+動的ネスト構造に置き換える案があり([idea/007 会話UX](../idea/007-会話UX.md))、採否は分冊05(UI/UX)で決定する。**会話疲れは本作最大のリスクであり、会話UXの設計は最重要課題**である。

### 3.2 ニーズの開示

**ニーズは手書きクエストではなく、シミュレーション状態から発生する**([idea/001](../idea/001-コアループ.md) §1)。会話は、シムの内部状態を人間の言葉として開示するインターフェースである。

```
シム状態(在庫不足/金銭不足/労働力不足/建設意欲/イベント/病気…)
    ↓ ニーズ生成
Need { 種別, 対象世帯, 品目, 数量, 期限, 緊急度, 理由 }
    ↓ 台詞化(§3.3)
「うちの娘が夏に結婚するんだが、花嫁衣装の布が手に入らなくてね」
```

信用Tierによって開示の深さが変わる:

- 顔見知り:ニーズの存在と品目のみ(「布が要る」)
- 常連:数量・期限・予算まで(「夏までに3反、200まで出せる」)
- 信頼する相手:背景・事情まで(「実は蓄えが乏しくて、掛けで頼めないか」)

**M0 の開示は「顔見知り」に数量を足した水準に固定する**(「布が3反要る」)。予算・期限・背景は見えず、開示する理由も取引で解ける3つに限る(§6.1)。

開示のあと、NPCは「依頼を受けてくれるか?」と問う。受諾すれば約束成立、断れば何も起きない(§2.8)。

### 3.3 台詞生成パイプライン

**全NPCに手書き台詞は不可能**(NPC 100体 × ニーズ種別 × 状況)。テンプレート+パラメータ差し込みで生成する。

```
DialogueTemplate
  needType   : NeedType      // ニーズ種別
  occupation : Occupation    // 職業(パン屋、鍛冶屋…)
  personality: Personality   // 性格(寡黙、饒舌、卑屈、尊大…)
  trustTier  : TrustTier     // 信用段階
  gratitude  : Gratitude     // 感謝の段階(§3.6。取引の後の台詞にだけ使う)
  text       : string        // "{item}が{qty}ばかり要るんだ。{deadline}までに何とかならんか"
```

- **M0 では `trustTier` の軸は使わず、`gratitude` の軸が台詞の差の主役になる。** 信用が無いので Tier は全員同じである(§6.1)。感謝の段階は3つなので、取引の後の台詞は3系統あれば済む

- 差し込みパラメータ:`{item} {qty} {deadline} {budget} {reason} {npcName} {playerTitle}`
- **暦の制約**:1年 = 4季 × 30日で月の概念を持たない(仕様は [GDD03 §1](03-seasons-and-city.md)、理由は [ADR-0003](../adr/0003-calendar-structure.md))。台詞に「来月」「◯ヶ月後」を使えない。期限は**季節名**(「夏までに」)・**季節の相対表現**(「来季までに」)・**日数**(「十日のうちに」)のいずれかで表現する。商品や状況によって適切な表現は変わる。**M0 は期限を開示しない**(§6.1)ので、`{deadline}` の展開規則は期限に値を入れる M1 で確定する([#256](https://github.com/stama72/visionary/issues/256))
- **手書きは主要NPCに限定**:領主/市参事会、司教・修道女、主要な取引先数名。ストーリーを担うキャラクターのみ
- 品質リスク:テンプレートは繰り返しが目立つと世界が死ぬ。同一条件に複数バリエーションを持たせ、ランダムではなく**未使用のものを優先**して選ぶ(反復感の軽減)

#### 3.3.1 M0 の台詞(**決定**。仮仕様)

**M0 の会話は6種類の台詞でできている。** 1回の会話は、挨拶 → 世間話 → 開示(Need が無ければ「困りごとは無い」)の順に進み、プレイヤーが Need の品目を売りに出したら取引の台詞が続く。

| 種類 | 出る場面 | 照合する条件(テンプレート側の軸) | 差し込めるパラメータ |
| ---- | -------- | ---------------------------------- | -------------------- |
| 挨拶 | 会話の頭。毎回 | 職業 | なし |
| 世間話 | 挨拶の後。毎回 | 職業・季節 | `{season}` |
| 開示 | その NPC の世帯が開示する Need(§6.1 の3理由)ごとに1行 | 職業 | `{item}` `{qty}`(**両方を必ず含む**) |
| 困りごとは無い | 開示する Need が1つも無いとき | 職業 | なし |
| 取引の成立 | プレイヤーの値が通ったとき | 職業・**感謝の段階**(§3.6) | `{item}` `{qty}` |
| 取引の不成立 | プレイヤーの値が予算を上回ったとき([GDD06 §6.1](06-trade-and-negotiation.md)) | 職業 | `{item}` |

- **世間話は季節と職業だけを材料にする。** 自分の仕事の不調(生産が止まった・工具が切れた)を語らせない — 語らせると Need の理由が開示され、評価額の読み合い(§3.6)の手がかりになる。§6.1 が背景を見せないのと同じ理由である
- **挨拶に時間帯の言葉(おはよう・こんばんは)を入れない。** 時間帯を軸に持たないからである
- **差し込みの展開**: `{item}` は品目の表示名、`{qty}` は漢数字と品目ごとの助数詞(「工具を二本」の「二本」)、`{season}` は季節名(春・夏・秋・冬)。**表示名・助数詞・季節名はテンプレートと同じ台詞の資料が持ち、シムの型には持たせない**([GDD03 §1](03-seasons-and-city.md) の季節の表示名と同じ)。§3.3 の残りのパラメータ(`{deadline} {budget} {reason} {npcName} {playerTitle}`)は M0 では使わない — 前の3つは §6.1 が見せず、後の2つは M0 に名前と肩書きが無い
- **信用段階の軸は持たない**(M0 は全員「顔見知り」相当。§6.1)。**性格の軸は型にだけ置き、M0 のテンプレートはすべて「指定なし」にする** — シムの NPC がまだ性格を持たないからである

**照合**: テンプレートの軸は「指定なし」か1つの値を持つ。**指定なしの軸は何にでも当たり、値のある軸はその値にだけ当たる。** **ただし取引の成立のテンプレートは段階を必ず指定する** — 指定なしにすると、渋々にも深い感謝にも同じ台詞が出る。候補は、すべての軸が当たるテンプレートの**和集合**である — 職業を指定したものだけに絞らない。絞ると、職業別の台詞を1本足すたびに共通の台詞が全部消え、変化がかえって減る。

**選び方(未使用を優先する)**: 使用回数は NPC ごと・テンプレートごとに数える。

1. 候補のうち、その NPC での使用回数が最小のものだけを残す
2. 残りが2つ以上なら、その NPC が同じ種類で直前に使ったテンプレートを除く(一巡した直後に同じ台詞が続くのを防ぐ)
3. 残りから系統 `Dialogue`([TDD01 §3.1](../04-tdd/01-sim-core-and-m0.md))の乱数で1つ選ぶ。乱数を使うのは、同じ職業の NPC が全員同じ順で台詞を巡らないようにするためである

**一巡するまで同じ台詞は出ない。** 候補が N 本あれば、候補が変わらない限り(季節・職業が同じ間)、同じ NPC と N 回話すまで重複しない。したがって §6.2 #3(同一 NPC と10回会話)の反復感は、**候補の本数と、本数が尽きた後の巡り方**で決まる。

決定の経緯は [#46](https://github.com/stama72/visionary/issues/46) のフェーズ1。

**このパイプラインの品質はM0の検証項目**(企画書 §6 / コンセプトシート GO判断)。テンプレートで「人間らしさ」が出せない場合、NPC数を削って手書き比率を上げる方向に縮小する。

| 自分のニーズに協力を約束してもらえた | +max(2, 0.2B) | §2.8「約束する」と同一の加点(二重加算しない)                                             |

### 3.6 感謝(**決定**。M0 から)

**最小構成要素「困りごとを取引で解決し、感謝される」の「感謝」である**([ADR-0015](../adr/0015-roadmap-rebuilt-from-minimal-element.md) 論点1)。M0 の取引は信用の無い一回限りのゲームで、吹っかけが支配戦略になりうる。それに対抗する梃子を感謝の側に置く。

**感謝が出るのは、NPC が開示している Need(§6.1 の3理由)の品目を、プレイヤーが売って満たした取引だけである。** 困りごとと関係の無い販売には出ない — 出すと、パンを配り歩くだけで感謝が貯まり、「困りごと」が効かなくなる。

```
評価額 = min( ApplyPermille(基礎値, 在庫圧力‰) , 利潤上限 )   ← GDD02c §2.1 の予算から現金上限だけを外したもの
                                                               利潤上限が無い用途では第1項だけ
s‰     = CeilDiv( 1000 × (評価額 − 価格) , 評価額 )          ← 余剰の比率。成立した取引では 0 以上
段階   = s‰ < 150 → 渋々 / 150 ≤ s‰ < 400 → 感謝 / 400 ≤ s‰ → 深い感謝
         (境目 150‰ = 15%、400‰ = 40%。初期値)
```

- **評価額から現金上限を外す。** 現金上限は払えるかどうかの制約で、いくらなら妥当かという評価ではない([GDD02c §2.1](02c-price-and-budget.md) の役割分担と同じ)。入れると困窮した NPC ほど感謝が小さくなり、資金の調整で感謝が黙って変わる。**利潤上限は残す** — 生産の入力では、利潤上限が評価そのもの(派生需要)だからである。**代償として、現金上限で頭を押さえられた NPC には、上限いっぱいの値で売っても感謝が出る。** 例: 工具の相場基準 290 で評価額は 1.8 × 290 ≈ 522。工具に回せる金が 300 の戸に 300 で売ると、s ≈ 425‰ で深い感謝になる。困窮していなくても起きる。工具切れと生産停止の現金上限の母数は「流動資金 − 必需の取り置き」で、破産中より手前で閉じるからである。しかも、金のある戸は自分で買って Need が消えるので、プレイヤーが届く Need はこの帯に偏りうる。**帯の広さは式からは出ないので、[#253](https://github.com/stama72/visionary/issues/253) が「感謝した取引のうち、現金上限が予算を決めていた割合」を記録する**
- **余剰の絶対額ではなく比率で切る。** 品目ごとに価格帯が違うので、絶対額で切ると段階の意味が品目で変わる
- **段階は粗く、3つにとどめる。** 細かくすると、1回の取引から評価額を逆算できてしまい、予算を見せない理由(§6.1 の値踏みの読み合い)が崩れる。粗すぎると、段階の中では値を上げても感謝が下がらず、境目を掴んだプレイヤーはその幅まで何も失わずに吹っかけられる。**3段階では、中段の中で最大およそ相場の 0.45 倍ぶん吹っかけても段階が変わらない**(下の q = 1.8 の場合)。台詞の費用も段階の数に比例する(§3.3)
- **読み合いの源は、Need の種類ごとの評価額の違いである。** 価格と評価額を、その NPC の相場基準 m の倍数でそれぞれ μ・q と置くと、s = 1 − μ/q になる。q の値は Need の理由で変わる。工具切れは在庫 0 なので q = 1.2(許容乖離)× 1.5(在庫圧力)= 1.8 で固定。遠方在庫は、耐久・必需の品目なら 1.2〜1.8 である。生産停止(と入力の品目の遠方在庫)は利潤上限で頭打ちになり、採算が残らなければ 1 を下回る。**ただし利潤上限は、前日に出力を売っていない日・入力の相場を知らない日・赤字の日には min から落ち([GDD02c §2.3](02c-price-and-budget.md))、そのとき q は第1項の 1.8 まで跳ぶ。** 止まった工房はこれに当たりやすい。赤字の工房ほど深く感謝するのは予算の規則の性質で、M1 で扱う([#254](https://github.com/stama72/visionary/issues/254))。[#253](https://github.com/stama72/visionary/issues/253) が「生産停止の取引のうち、利潤上限が落ちていた割合」を記録する。在庫圧力も利潤上限もプレイヤーからは見えない。**q = 1.8 は許容乖離(1200‰)と在庫圧力の上限(1500‰)の積なので、この2つは感謝の帯も決めている**([GDD02c §3](02c-price-and-budget.md))。そのため、同じ値でも相手によって段階が変わる。q = 1.8 では、相場どおり(μ ≤ 1.08)で深い感謝、相場の 1.53 倍を超えると渋々になる

**向きは価格 → 感謝だけである。感謝は価格にも、取引相手の選好にも効かせない。** 効かせると信用の縮小版が M0 に入る([ADR-0015](../adr/0015-roadmap-rebuilt-from-minimal-element.md) 論点1)。感謝の礼として噂や他の困りごとを渡すこともしない。情報は次の取引の有利さに直結するので、同じことになる。**したがって感謝は、見え方だけで成り立つ報酬である。** 伝える経路は台詞(§3.3 の感謝の軸)と、表情・効果音程度の演出、それに数値の無い記録([GDD05 §2](05-ui-ux.md))である。

**評価額と段階は数値としては見せない。** 見せると予算の開示と同じになる(§6.1)。プレイヤーは台詞と演出から推し量る。**断られた値から予算を絞り込む経路は [GDD06 §6.1](06-trade-and-negotiation.md) が1日の中では塞ぐ**(同じ (世帯, 品目) に値を出せるのは1日1回まで。単位は予算と同じ世帯である)。段階を粗くしても、そこを塞がなければ予算は読まれる。**日をまたいで残る Need では、1日1回ずつ絞り込める** — 塞いでいるのは1日の中だけである。どれだけ効くかは [#103](https://github.com/stama72/visionary/issues/103) が Need の持続日数とともに測る。

決定の経緯は [#245](https://github.com/stama72/visionary/issues/245) の決定1〜7。

## 4. 知識モデル

信用の効果4「情報開示の深さ」と情報の非対称性の基盤。**プレイヤーとNPCの双方が、同型の知識レコードを持つ**。プレイヤーは全知の相場表を持たず、NPCも全知ではない。

### 4.1 価格知識

```
PriceObservation
  item      : ItemId
  location  : LocationId
  price     : int
  observedAt: Tick     // 観測時刻(鮮度)
  source    : Direct | Heard   // 自分で見たか、聞いた話か
```

- プレイヤーの「相場感」は観測記録の集合であり、鮮度が落ちた情報は不確実なものとして表示する(UI表現は分冊05)
- この非対称性こそが「情報を足で稼ぐ」というUSPの実体

### 4.2 人物・コミュニティ知識

```
PersonFact
  about     : NpcId | CommunityId  // 対象(人物、家族、通り、職業、組織…)
  kind      : FactKind             // 家族構成/職業/人間関係/人柄/近況…
  source    : Direct | Heard
  observedAt: Tick
```

- 効果4の「他人の事情」は、この知識の受け渡しとして実装する
- 会話の動的ネスト構造([idea/007](../idea/007-会話UX.md))の質問候補は、この知識の有無から生成する——相手の家族について何も知らなければ「家族は何人いるの?」という一段広い質問だけが出る

### 4.3 出来事知識(噂の実体)

```
EventKnowledge
  event     : EventId   // 出来事(船の遅延、豊作、事故、婚礼…)
  source    : Direct | Heard
  observedAt: Tick
```

- 噂システムの通貨。§3.5の「噂を話せた」判定、§2.8の期限延長の根拠、不履行後の「悪い噂」もすべてこの型で表現する

### 4.4 帳簿(取引履歴)

```
LedgerEntry
  counterparty : ActorId
  direction    : Purchase | Sale      ← 買ったのか売ったのか
  item, qty    : 品目と数量
  unitPrice    : int
  tick         : 取引時刻
  terms        : Cash | Credit(返済期日)
```

- プレイヤー・NPC双方が保持。掛け売りの管理(効果3)、不当価格の判定(§4.5)、期限延長の根拠(商談の記録)に使う
- **`direction` を持つのは、1つの約定を買い手と売り手が1行ずつ記帳するためである。** 帳簿は資金の増減と一致する([GDD02b §3](02b-consumption-and-household.md))ので、向きが無いと帳簿から流動資金を復元できない。**数量の符号では表さない** — 数量は個数であり、負の個数は在庫の式に紛れ込むと止まらない

### 4.5 不当な価格の判定(納得感の設計)

**問題**:後から気づかれて信用が下がる仕様は、プレイヤーから見ると「知らない間にNPCを怒らせた」体験になる。プレイヤー自身が相場を知らなかった・勘違いしていた場合は理不尽であり、取引後に街全体で相場が下落した場合の判定基準も曖昧。

**設計原則(B案)**:

1. **時点固定**:判定基準は「取引時点の公正価格」。帳簿のtickを基準に、取引時点近傍の価格観測から公正価格を推定する。**取引の後に相場が下落しても不当にはならない**
2. **相手の知識**:NPCが取引tick近傍の観測(observedAtが取引時点に近いPriceObservation)を後から入手したときにのみ「気づく」
3. **閾値バンド**:乖離が閾値(仮:公正価格+20%)以内はペナルティなし。プレイヤー自身の相場観の誤差を許容する遊びを持たせる
4. **顕在化イベント**:気づいたNPCはサイレントに減点せず、次の対面で問い質してくる(あるいは態度が変わる)。プレイヤーは謝罪+差額の返金や値引きで関係を修復でき、突っぱねればペナルティ確定。「知らない間に怒っていた」を「向き合える出来事」に変える

**M0〜M1での比較実験**:

| 案  | 内容                                                 |
| --- | ---------------------------------------------------- |
| A案 | 即時サイレント減点(v0.1仕様)                         |
| B案 | 上記4原則                                            |
| C案 | ペナルティなし(不当な取引は信用が「上がらない」だけ) |

測定指標:**誤爆率**(プレイヤーの手持ち知識では公正だった取引が罰せられた割合。プレイヤーのPriceObservationとシムログの突き合わせで算出)+プレイテスト所感。誤爆率は判定式そのものには使わない(プレイヤーの心を読む挙動は不自然)が、調整の計測指標として使う。

## 5. ニーズ解決フロー(コアループとの接続)

[idea/001](../idea/001-コアループ.md) §1.1で定義された流れを、本システムの用語で再記述する:

1. **耳を傾ける**(会話:ニーズを聞く)→ Need の開示。会話評価+1(§3.5)
2. **約束する**(§2.8)→「受けてくれるか?」に応えて約束成立。+max(2, 0.2B)
3. **考える**(プレイヤーの判断)→ 手持ち/仕入れ/誰かに作らせるかの選択
4. **キーパーソンを探す**(会話:他人のことを聞く、街歩き)→ 供給者の発見。信用Tierが探索効率を左右する
5. **関係を築く**(会話・取引の積み重ね)→ 供給者側の信用を上げる
6. **説得する**(商談・交渉)→ 効果2・3が効く。妥結の詳細は分冊06
7. **履行する** → +B+履行ボーナス。都市の状態が変化

**この7工程が本作の「クエスト」であり、M1 からはそのすべての工程で信用が効く。** 信用システムはコアループの装飾ではなく、骨格である。**ただし M0 は信用を持たずに、この流れの最小形(聞く → 考える → 探す → 取引する)だけで成り立つかを確かめる**(§6.1)。信用は、成り立った最小形を繰り返しゲームへ広げる増幅器として入る([ADR-0015](../adr/0015-roadmap-rebuilt-from-minimal-element.md) 論点1)。

## 6. 段階ごとのスコープと検証項目

### 6.1 M0 は信用と約束を持たない

**M0 は信用も約束(§2.8)も持たない**([ADR-0015](../adr/0015-roadmap-rebuilt-from-minimal-element.md) 論点1)。M0 が確かめるのは最小構成要素「困りごとを取引で解決し、感謝される」であり、信用はそれを繰り返しゲームへ広げる増幅器として M1 で入れる。本書の信用・約束・Tier の記述は M1 からの仕様である。M0 では次のように読み替える。

| 本書の記述 | M0 での扱い |
| ---------- | ----------- |
| 信用の増減(§2.3)・Tier(§2.6)・4つの効果(§2.2) | 持たない。挨拶による信用+1(§3.1)も無い |
| 約束(§2.8)と「依頼の報告」トピック(§3.1) | 持たない。困りごとは、聞いた後で品を持ってきて売る**通常の取引**で解く |
| トピックの解禁条件(§3.1) | Tier で閉じない。**「ニーズを聞く」は常時開いている**。「相場を尋ねる」「他人のことを聞く」は M0 に置かない |
| 開示の深さ(§3.2) | **「顔見知り」相当に固定し、数量を足す**。見えるのは品目と数量で、予算・期限・背景は見えない |
| 開示する Need の理由([GDD02b §8.1](02b-consumption-and-household.md)) | **取引で解ける3つ(生産停止・工具切れ・遠方在庫)だけ**。「増産できない」(足りないのは労働)と「困窮」(床値を割る)は、シムの中では立つが開示しない |
| 感謝(§3.6) | **M0 から入る。** 信用の代わりに、吹っかけへの梃子を担う。価格・取引相手の選好には効かない |
| ニーズ解決の7工程(§5) | 信用が効く工程は無い。**2 約束する・5 関係を築く**は M0 に無く、残る工程は通常の取引で進む |

**予算を見せないのは、値踏みの読み合いを残すためである**(常連相当に固定すると、吹っかけるか感謝されるかは意識的な選択になるが、読み合いが消える)。**数量を見せるのは、運ぶ量を決められないと、余りを床値で窓口に流す損が稼ぎに混ざるためである。** **数量から予算を逆算できないことを前提にしている**([#243](https://github.com/stama72/visionary/issues/243) 決定24)。困窮の Need を助ける体験は、M1 の同情([世界観設定書 §4](../02b-world-setting.md))が持つ。決定の経緯は [#243](https://github.com/stama72/visionary/issues/243) の決定11・12・24・26。

### 6.2 検証項目

**項目の番号は [TDD01 §5.1](../04-tdd/01-sim-core-and-m0.md) から引かれているので振り直さない。** M0 に残るのは1と3で、残りは M1 で検証する。

| # | 段階 | 検証内容                              | 判定基準                                                                     |
| - | ---- | ------------------------------------- | ---------------------------------------------------------------------------- |
| 1 | M0 | 最小構成要素の面白さ(ニーズ発見→充足のループが面白いか) | グレーボックスで**1時間**(ゲーム内の約6日)遊んで「次のニーズを探したい」と思えるか。**観察項目: プレイヤーが吹っかけたか**(信用の無い一回限りの取引では、吹っかけが支配戦略になりうる) |
| 2 | M1 | 信用のシム組み込みは制御可能か        | 信用あり/なしで36,000日分(300ゲーム年)ヘッドレス実行し、価格が発散・硬直しないか(§2.9)      |
| 3 | M0 | テンプレート台詞の品質                | 同一NPCと10回会話して反復感が許容範囲か                                      |
| 4 | M1 | 4つの効果の因果がプレイヤーに見えるか | 「信用を上げると何が良くなるか」をテスターが説明できるか(数値非開示の前提で) |
| 5 | M1 | 不当価格判定の納得感                  | §4.5のA/B/C比較。誤爆率とテスター所感でB案の妥当性を判定                    |
| 6 | M1 | 約束の信用式の手触り                  | §2.8の式で「早く謝ると軽い」「延長は保険になる」が体感できるか              |

**1時間にするのは、日ごとの状況変化を体験させるためである。** 1日 = 実時間10分([GDD05 §1](05-ui-ux.md))なので、15分ではゲーム内の約1.5日にしかならない。M0 の経済の検証地平を30日にした根拠([GDD02 §7](02-economy.md))も、この1時間に乗っている。
