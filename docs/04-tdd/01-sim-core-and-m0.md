## 0. この文書の位置づけ

ADR-0001の決定(Godot 4 + C#、シムは純C#ライブラリ `Visionary.Sim`)を、**M0の検証項目(GDD01 §6)を実行できるアーキテクチャ**に落とす。M0の目的は面白さと制御可能性の実証であって製品コードの完成ではない。したがって本書の設計は「検証実験を速く・再現可能に回せること」を最優先し、v1.0で作り直す前提の箇所は明示的にプレースホルダと宣言する(§3.6)。

## 2. ソリューション構成

```
Visionary.sln
├─ src/
│  ├─ Visionary.Sim/          # 純C#(net8.0)。Godot参照ゼロ。本書の主題
│  ├─ Visionary.Sim.Runner/   # CLI実験ハーネス(コンソールアプリ)。§4
│  └─ Visionary.Game/         # Godot 4プロジェクト。M0ではグレーボックスのみ
└─ tests/
   └─ Visionary.Sim.Tests/    # xUnit。単体・プロパティ・決定論回帰・シナリオ
```

依存方向は `Game → Sim ← Runner / Tests` の一方向。`Sim` から外への依存は標準ライブラリのみ(JSONシリアライズ含む)。

`Visionary.Game` は W5(グレーボックス着手)で作成する。それ以外は作成済みで、CI(§2.1)が通っている状態。

### 2.1 CI(GitHub Actions)

`.github/workflows/ci.yml` に2ジョブ。ランナーはUbuntu — `Visionary.Sim` がGodot非依存(ADR-0001)であることの継続的な証明を兼ねる:

| ジョブ   | 内容                                                        | 失敗が意味すること         |
| -------- | ----------------------------------------------------------- | -------------------------- |
| `sim`    | restore → build(Release) → test。結果をtrxでアーティファクト化 | 壊れている                 |
| `format` | `dotnet format --verify-no-changes --severity warn`          | 整えれば直る               |

- **警告をエラーとして扱う**(`Directory.Build.props`)。ADR-0001が挙げた「AIが幻覚APIや古いAPIを生成するリスク」をコンパイル段階で機械的に弾く一次防衛線
- 決定論の回帰テスト(§1-1)はW1で `sim` ジョブに載る。36,000日実行をCIのどこまで組み込むかは§7の未決定事項
- 改行コードはLFに統一(`.gitattributes` + `.editorconfig`)。Windows開発・Ubuntu CIでフォーマット判定が食い違うのを防ぐ
- **SDK版は `global.json` で 8.0.424 に固定**(`rollForward: latestPatch`)。CI は `global-json-file` で同じ値を読むため、版の定義は1箇所に閉じる

`global.json` を置く理由は、当初想定した「フィーチャーバンドが上がってアナライザが増える」ではない。**.NET 8 は既に maintenance フェーズで、8.0.424 が最後のフィーチャーバンド**であり、そのドリフトはもう起きない。実際の理由は次の2点:

- **EOL が 2026-11-10** であり、M0(2026-10上旬)の直後、M1(2026-12末)の途中にあたる。ランナーイメージから .NET 8 SDK が落ちた日に、こちらの変更ゼロでCIが赤くなる
- 固定してあれば、`global.json` を書き換えるという**明示的な操作**として .NET 10 への移行が起きる。SDKが入っていない環境では明確なエラーで止まる(これは意図した挙動)

なお **SDK版とターゲットフレームワークは別物**である。.NET 10 SDK で `net8.0` の成果物はビルドできるため、Godot が `net8.0` を要求していてもツールチェーンだけ先に上げられる。移行時期は§7の未決定事項。

## 3. Visionary.Sim 中核設計

### 3.1 時間とスケジューラ

ADR-0002のとおり、`Tick` = ゲーム内1時間(long、単調増加)。システムは実行周期を宣言してスケジューラに登録する:

```
ISimSystem
  Cadence : EveryTick | Daily(hour) | Weekly(dayOfWeek, hour)
  Step(World world, SimContext ctx)   // ctx = 乱数ソース、イベント発行、設定
```

- 日次フェーズの実行順序は§3.3の表で固定(登録順ではなく明示順)。順序自体が仕様である
- 暦(1年 = 4季 × 30日 = 120日)の**仕様は [GDD03 §1](../03-gdd/03-seasons-and-city.md)**、選定理由は [ADR-0003](../adr/0003-calendar-structure.md)。`Tick` は暦の定数に依存せず、`GameDate` が読み替えを担う

#### 乱数と系統

**鍵は (マスターシード, 系統, tick, エンティティ) から導出する。** ADR-0002 の「フラグを切り替えても他系統の消費列が変わらない」という約束は、系統ごとに1本の長い列を持つ実装では**フラグを含む系統の内部で必ず破れる**(引く回数が変わればそれ以降が全部ずれる)。組ごとに独立した短い列を開くことで、影響をその組の中に閉じ込める。実装は `Visionary.Sim.Randomness`。

導出は3段。**この順序が仕様**である(段を入れ替えたり XOR を加算に変えたりすると、同一シードでも別の世界が生成される):

```
k = (ulong)masterSeed
k = Mix(k ^ (ulong)stream)
k = Mix(k ^ (ulong)tick)
k = Mix(k ^ (ulong)entityId)     // エンティティ非依存の用途は entityId = -1
```

系統(`RandomStream`)は §3.3 のパイプラインの各システムに**高々1つ**割り当てる。**1対1でも、順序どおりでもない** — `WorldGen` と `Dialogue` はパイプラインに無い。**逆に `Metrics`(順10)は乱数を引かないが、系統は持つ** — `ISimSystem.Stream` は系統を**システムの識別子**として使い(`SimScheduler` が重複登録を拒否する)、借用を型で不可能にしている。したがってパイプラインに登録される以上、乱数を引かないシステムも一意の系統を名乗る必要がある。値は **`Metrics = 13`**(`OpportunityCost = 12` とともに W2 で追加する)。W2 で追加する `OpportunityCost` はパイプライン先頭(順0)でありながら値は末尾の 12 である(§3.3)。値は鍵導出に直接使うため仕様であり、振り直さない。0 は既定値との衝突を避けるため使わない。生成器は SplitMix64 を自前で持つ — `System.Random` が禁止銘柄であることに加え、**.NET の乱数実装はバージョン間で変わった前例があり**、標準ライブラリではランタイム更新をまたいだ再現性を保証できないため。マスターシードは `long` 全域(負も可)。

**機械で守れていない残りの危険:**

| 危険 | 壊れ方 | 現状の守り |
| ---- | ------ | ---------- |
| **系統の借用** | 別系統の鍵で開くと、その系統が同じtickに開く列と**完全に同一の値**になる。判定同士が完全相関するのに消費列はズレないので、A/B比較の差分に現れず**発見の手がかりが無い** | `SimContext` が「現在のシステムの系統」しか開けない口を提供する。**ただしアセンブリ内からは防げない** — 実際のシステムは `Visionary.Sim` 内にあり `internal` が素通しなので、`CurrentStream` / `Now` を書き換えれば借用できる。ここはレビュー |
| **`Step` の外からの利用** | `SimContext` は class なので、システムが保持して後から `OpenRandom` を呼べる。直前のシステムの系統で静かに開く | `Step` を抜けたら `CurrentStream` を無効値に戻し、無効値での `OpenRandom` を例外にする |
| **二重オープン** | 同じ組を2度開くと同じ値から始まる | `SimContext` が同一tick内の重複オープンを検出して例外にする(W1-03) |
| **NPC の処理順** | 走査順を変えても、乱数の鍵が NPC ごとに独立で状態変更が可換なら結果が一致してしまう。順序の破れが結果に現れない | W1 時点では `src` に NPC を走査するコードが無く、**機械では守れていない**。W2 でシステムが入ってからのレビュー観点。`World.Npcs` が Id 昇順の配列であることだけはテストで固定済み |
| **値コピー** | `ref` を付けずに `RandomSequence` を渡すとコピーが独立に進み、同じ値が2度返る | `ref struct` はヒープ脱出しか禁じられない。**引数には必ず `ref` を付ける**という規約でしか守れない |

> W1-02 のタスク仕様は「借用を型で不可能にする」と書いたが、**`RandomSource` 単体ではそれを達成できない**(呼び出し側が系統を選ぶ以上、鍵を渡せば誰でも開ける)。仕様側の約束が過大だった。構造的に閉じられるのは `SimContext` を経由させる W1-03 であり、そこでも「値コピー」は残る。

**tick が鍵に入ることの副作用:** 日次フェーズの実行時刻(§3.3)を変えると全スコープの鍵が変わり、世界が総入れ替えになる。**実行時刻の変更は係数調整ではなく世界の再ロールである。** M0 の A/B フラグは実行時刻を変えないので当面は問題にならない。

- **`Advance(n)` は現在tickから n 個を処理する。** `Tick.Zero` から `Advance(3)` を呼ぶと処理されるのは tick 0・1・2 で、終了時 `Now = 3`。tick 3 は次回の `Advance` で処理される。先にtickを進めてから処理する実装にすると、エポック(1年 春1日 0時)が永久に処理されず `Daily(hour: 0)` が春1日を飛ばす。Godot 側のポンプ(§3.5)もこの契約に従う
- **`Cadence` に既定値は無い。** `EveryTick` / `Daily` / `Weekly` のいずれかで明示的に構築する。未設定のまま `SimScheduler` に渡すと構築時に `ArgumentException`。既定値をいずれかの周期に割り当てると、初期化を忘れたシステムが黙ってその周期で走る — 実行周期はtickを通じて乱数の鍵に入るため、周期の取り違えは A/B 比較の前提そのものを壊す
- **`Weekly` cadence は `dayIndex % 7 == n` の日と定義する。** 週は暦の一部ではなく単なる7日周期であり(GDD03 §1.3)、季節の境界をまたいで漂う。`GameDate` にも `Calendar` にも曜日を持たせず、曜日を表す型も作らない

**検証地平は日数で表す。** ADR-0003で1年が120日になったため、「100年」という言い方をやめる:

| 単位     | 値                                  |
| -------- | ----------------------------------- |
| 検証地平 | **36,000日**(= 300ゲーム年)        |
| tick数   | 864,000                             |
| 日次処理 | 36,000回                            |
| 週次処理 | 約5,140回(週は7日。暦とは独立)     |

日数を基準に据えるのは、暦の定数を変えるたびに性能予算と統計的検出力が黙って変わるのを防ぐため。以降、本書で「1年」と書く場合は120日を指す。

### 3.2 世界状態(データモデル)

`World` は全状態を保持する単一の集約。GDD01のデータモデルをそのまま写す:

> **本書では `World` の内訳を「区分」と呼ぶ。** GDD02 以降の「**区画**」は**都市の空間的な区画**(3×3 の9区画、[GDD02 §4.3](../03-gdd/02-economy.md))を指し、別概念である。

| 区分        | 内容                                                                | GDD対応    |
| ----------- | ------------------------------------------------------------------- | ---------- |
| Clock       | 現在tickのみ。暦は`GameDate`による読み替えで、状態として持たない | ADR-0003  |
| Npcs        | Id、世帯Id、階層(親方/職人/徒弟)、熟練度                            | §2.2.2 / GDD08 §2.2 |
| Households  | Id、**区画Id(不変)**、職業、世帯主NpcId、構成員NpcId列、流動資金、世帯在庫、工房在庫、**仕入れ移動平均単価**、**破産中フラグ**(int 0/1)、**工具の累積摩耗**(‰人日)、**当日の消費不足量**(品目別)、**当日の「必需を資金不足で買えなかった」件数**、**当日の生産量(実行回数)**、**前日の外出の労働損失‰** | [GDD02a §1〜§3](../03-gdd/02a-production.md) / [GDD02b §1・§3](../03-gdd/02b-consumption-and-household.md) / [GDD06 §2](../03-gdd/06-trade-and-negotiation.md) / GDD08 §2.2 |
| Market      | 品目 × **売り手世帯**の提示価格。Id昇順の疎構造                  | GDD02c §1 |
| TrustLedger | `TrustScore{from, to, value, lastMet}` の疎マップ                 | §2.1      |
| Needs       | `Need{種別, **対象世帯**, 品目, 数量, 期限, 緊急度, 理由}`         | §3.2      |
| Promises    | 約束(クエスト)。`{need, t0, t1, B, 状態(有効/延長中/完了/破棄)}`  | §2.8      |
| Knowledge   | **NpcId 別**の`PriceObservation` / `PersonFact` / `EventKnowledge` | §4.1〜4.3 |
| Ledgers     | **世帯Id 別**の`LedgerEntry`(取引履歴)                            | §4.4 / GDD08 §2.2 |
| EventLog    | ドメインイベントの追記専用列(§3.4)                                 | —         |

- 状態はすべてint/long(ADR-0002)。シリアライズ可能なプレーンデータとし、ロジックを持たせない
- **`Npcs` は「性格」と「役割」を持たない。** かつて本表の Npcs 行に挙げていたが、§3.8 の含める表と対で落とした。**性格**は M0 に読む処理が無い — 使わない状態を器に残すと「ハッシュに入れ忘れた穴」を先に作ることになる。**役割**は、それを読む唯一の処理である [GDD08 §7.2](../03-gdd/08-household-and-decision.md)(買いに行く者 = `argmin(機会費用)`)が、M0 では機会費用を**職業 × 階層の固定値**として引く([GDD08 §9](../03-gdd/08-household-and-decision.md))ため、役割を状態として持たなくても決まる。**時間配分と家事も §9 が M0 の対象外としている**ので、役割を要求する処理は他に無い。**どちらも戻すときは §3.8 の含める表と対で足すこと**
- **熟練度は持つ。ただし M0 では読まない。** [GDD08 §9](../03-gdd/08-household-and-decision.md) は熟練度を M0 の対象外とし、§4.2 の生産性式も M0 では使わない(生産量は [GDD02a §2](../03-gdd/02a-production.md) の労働力ベースの式が持つ)。**それでも器として先に持つのは、同節の「構造を先に固定し、値の由来を後から差し替える」方針による。** **上の「使わない状態を器に残さない」が熟練度に及ばないのは、その理由が「ハッシュに入れ忘れた穴を先に作る」ことにあるからである** — 熟練度は §3.8 の含める表に載っており、穴にならない。**読む処理を足すときは §9 の M0 スコープ表を先に直すこと**
- **Id は非負の `int` とする。文字列 Id を使わない。** int であることは状態ハッシュの入力を int/long に限る規約(§3.8)から、非負であることは乱数の `RandomSource.NoEntity = -1` を番兵に使うことから来る
- **提示価格は `Market` が持つ。** 世帯の属性ではなく「市場に出ている売り注文」であり、同一世帯が複数品目を売る以上どのみち品目別の入れ物が要る。家計モデル(GDD02)と混ぜない。**売り手は世帯である** — 在庫・職業・帳簿を世帯へ移した以上、売り注文の主体も世帯になる
- **`Market` は「前日の提示価格」の保管場所を兼ねる。** [GDD02c §1](../03-gdd/02c-price-and-budget.md) の `相場基準` は自分の前日の提示価格を含むが、**更新前の `Market` の値がそれである**ので専用のフィールドを足さない。**その日の提示価格は全売り手ぶんを前日の値から算出してから一括で書き込む**(売り手ごとに読んでは書くと世帯 Id の処理順が結果を変え、ADR-0002 の列挙順規約に違反する)
- **約定価格の真実は `LedgerEntry`。** `TradeExecuted` イベントはその複製であって真実ではない。`EventLog` はハッシュ対象外(§3.8)なので、約定価格をそちらに置くと契約が自己矛盾する
- **`LedgerEntry` は売買の向きを持つ。** [GDD01 §4.4](../03-gdd/01-trust-and-conversation.md) が `direction` を持つのは、**1つの約定を買い手と売り手が1行ずつ記帳する**ためである。帳簿は資金の増減と一致する([GDD02b §3](../03-gdd/02b-consumption-and-household.md))ので、向きが無いと帳簿から流動資金を復元できない。**数量の符号で表さない** — 数量は個数であり、負の個数は在庫の式に紛れ込むと止まらない
- **都市外市場([GDD02d](../03-gdd/02d-external-market-and-money.md))は `World` の区分を持たない。** 外部価格は品目ごとの定数に季節係数を掛けた導出値であり、在庫・資金・帳簿を持たない無限の相手方である。**状態が無いのでハッシュにも乗らない**(§3.8)
- **`Market` にも載らない。** [GDD02d §2](../03-gdd/02d-external-market-and-money.md) の決定により、都市外市場の売り注文は**実体化せず、買い手の店選択が外部価格から候補を合成する**。したがって `Market` のキーは売り手**世帯**のままでよい。**ただし窓口の観測を識別するために `PriceObservation` へ売り手 Id の欄を足し**(下記 §3.6 の仮決め表)、**既存の世帯 Id より大きい非負 int を1つ窓口に予約する**。**売り手 Id 昇順の走査(ADR-0002)では合成した候補が最後に来るので、実質コストが同値なら都市内の売り手が選ばれる**
- セーブ = `World` のJSONスナップショット+マスターシード+設定。M0はスナップショット方式のみ(イベントログからのリプレイはデバッグ用途に限定)

#### 経済主体は世帯である(W2 の区分変更)

**流動資金・在庫・帳簿は `NpcState` から `HouseholdState` へ移す**([GDD02b §3](../03-gdd/02b-consumption-and-household.md) / [GDD08 §2.2](../03-gdd/08-household-and-decision.md))。W1 の `NpcState.LiquidFunds` と `NpcState.Inventory` は廃止する。

| 何が | どこへ | なぜ |
| ---- | ------ | ---- |
| 流動資金 | **世帯** | 帳簿と突合するため。個人別に持つと一致しない(GDD08 §2.2) |
| 帳簿(`Ledgers`) | **世帯** | 同上。所有者Id = 世帯Id |
| 在庫 | **世帯**(消費財)と**工房**(生産の入出力)の**2本** | 下記 |
| 職業 | **世帯** | 工房に紐づく。[GDD02b §4](../03-gdd/02b-consumption-and-household.md) の破産時の職業付け替えが世帯単位で働く |
| 相場知識(`Knowledge`) | **個人** | 「その人が何を見たか」に依存する(GDD08 §2.2)。所有者Id = NpcId |
| 信用・熟練度・階層 | **個人** | 同上 |

> **`Knowledge` と `Ledgers` の所有者は違う。** [§3.6](#36-m0仮経済モデルプレースホルダ宣言) の仮決め表は両者を1行にまとめていたが、**知識は個人・帳簿は世帯**である。同じ「所有者Id を持たせる」でも指すものが違うので、型を共通化してはならない。

**在庫を2本に分けるのは構造的な要請である。** [GDD02c §2.1](../03-gdd/02c-price-and-budget.md) は目標在庫を用途別に定める(生産の入力は「1日分の使用量 × 仕入れ間隔」、必需の消費は「1週間分」など)。**薪のように消費財でも生産入力でもある品目**では、1本の在庫では目標在庫が一意に決まらず、在庫圧力(§8.2.2)が計算できない。パン屋が暖房用に持つ薪と焼成用に持つ薪は別勘定である。

**世帯の区画Id は不変**([GDD02 §4.3](../03-gdd/02-economy.md))。移住を作らないため、区画は初期配置で決まる定数であって状態遷移を持たない。

### 3.3 システムパイプライン(日次フェーズの実行順)

| 順 | システム             | 責務                                                                           | GDD対応            |
| -- | -------------------- | ------------------------------------------------------------------------------ | ------------------ |
| 0  | OpportunityCost      | 個体別の機会費用を**前日の確定値から**算出し、その日は固定(M0 は職業 × 階層の固定値) | GDD08 §5, §6.3   |
| 1  | Production           | 職業別の生産(レシピ1段)。在庫に加算                                            | [GDD02a](../03-gdd/02a-production.md) |
| 2  | Consumption          | 家族規模別の消費。在庫から減算(**0 で下げ止まる**)                             | [GDD02b §1](../03-gdd/02b-consumption-and-household.md) |

**`OpportunityCost` を先頭に置くのは循環を切るためである**([GDD08 §6.3](../03-gdd/08-household-and-decision.md))。機会費用は価格から出て、実質コストを通って取引に効き、取引が価格を動かす。1日の初めに前日の確定値から一度だけ算出して固定することで、当日の購入・生産・価格が当日の機会費用に影響しなくなる。

**M0 の `OpportunityCost` はシステムを持たない。** [GDD08 §9](../03-gdd/08-household-and-decision.md) が M0 の機会費用を **職業 × 階層の固定値**(`ApplyPermille(職業別の基準値, 階層係数‰)`)と決めた結果、この値は走行中ずっと定数であり、**前日の確定値から算出する対象が無い**(同節の検証項目2 が「M0 では実行しない」としているのはこのためである)。`World` の区分にすると、毎日同じ値を書き直す行が §3.8 のハッシュに1つ増える。**したがって M0 では `WorldDefinition` の定数から引く純関数とし、順0 にシステムを登録しない。** §5 の式で日々算出する v1.0 で順0 のシステムとして足す — そのとき `RandomStream` は下の規律どおり末尾の **12** を取る。**上の表の順0 の行を消さないのは、置き場所(パイプラインの先頭)が既に決まっているからである。**

> **`RandomStream` の値は末尾に足す。順序に合わせて振り直してはならない。** `OpportunityCost` はパイプラインの先頭(順0)だが、系統の値は既存11系統の後ろの **12** とする。`Metrics` も **13** を取る(乱数は引かないが、登録に一意の系統が要る。理由は §3.1)。**壊れ方は「系統の衝突」である。** 鍵導出は系統ごとに独立なので、`Production` を 2 から 3 へずらしても変わるのは Production の列だけだが、**その 3 は `Consumption` のものである**。同一tickに開いた2系統が完全に同一の値を返し、§3.1 の危険表が筆頭に挙げる**系統の借用**が起きる — 判定同士が完全相関するのに消費列はズレないので、**A/B比較の差分に現れず発見の手がかりが無い**。パイプラインの順序と系統の値は別物であり、一致させる必要はない。

プレイヤー起点の行為(会話・商談・納品・謝罪)はこのパイプラインの外で、コマンド(§3.4)として任意のtickに割り込む。

#### 順5 `Trade` の内部の段(**決定**)

**順5 だけは中に複数の段を持つ。** `SimScheduler` は同じ `RandomStream` の重複登録を拒む(§3.1)ので、値付け・買い物・観測を別システムに割れない。**段の順序は仕様である。**

| 段 | 何をするか | なぜその位置か |
| -- | ---------- | -------------- |
| 1 | 全売り手の新しい提示価格を求める(`Market` は読むだけ) | 自分の**前日の**提示価格が `相場基準` に要る([GDD02c §1](../03-gdd/02c-price-and-budget.md)) |
| 2 | `Market.Clear()` してから 1 の結果を一括で書く | 売り手ごとに読んでは書くと世帯 Id の処理順が結果を変える(§3.2) |
| 3 | 保持期間を過ぎた観測を失効させる | 段5 が読む「有効な記憶」を先に絞る |
| 4 | **全世帯ぶんの需要(基礎値・目標在庫・予想在庫・予算)を一括で作る** | 下記 |
| 5 | 世帯 Id 昇順に買い物(店の選択・約定・記帳)。訪れた区画を控える | 流動資金と販売在庫は共有資源なので順序が要る([GDD02b §3.2](../03-gdd/02b-consumption-and-household.md)) |
| 6 | 当日の提示価格から観測を生成し、世帯内で共有する | 生まれた観測が有効になるのは翌日([GDD06 §3.1](../03-gdd/06-trade-and-negotiation.md))。段5 の訪問区画がここの入力になる |

**段4 を段5 の中へ畳まない(需要は買い物の前に全世帯ぶん作る)。** 畳むと、先に決済した世帯の売上がその日のうちに自分の流動資金へ入り、**後から需要を作る世帯の基礎値(耐久と嗜好の母数は流動資金・余剰資金である)が世帯 Id の順序で変わる**。[GDD02b §3.2](../03-gdd/02b-consumption-and-household.md) が走査順に持たせた意味は「**どの購入が資金上限で切り詰められるか**」だけであり、**予算そのものが走査順の関数になると、区画間の価格差(§12-4)が機構の帰結か走査順の産物かを切り分けられなくなる**。[GDD08 §6.3](../03-gdd/08-household-and-decision.md) の1日遅延の成層化と同じ扱いである。

### 3.4 コマンドとドメインイベント

**コマンド**(外部→シム): `Talk`, `AskNeeds`, `ProposeTrade`, `AcceptPromise`, `Deliver`, `Apologize`, `RequestExtension`, `GiveGift` など。Godotのプレイヤー操作と、ヘッドレス実験のスクリプト化プレイヤー(§5.1)が**同じコマンドAPI**を使う。これにより「グレーボックスで人間が体験すること」と「ヘッドレスで測ること」の乖離を防ぐ。

**ドメインイベント**(シム→外部・ログ): `TradeExecuted`, `TrustChanged{from, to, delta, reason}`, `NeedCreated`, `PromiseBroken{e, penalty}`, `UnfairPriceSuspected{trade, detectorObservation}`, `PenaltyApplied` など。

- イベントは追記専用で、**判定に使った文脈(取引tick、判定時のNPC側観測、適用ポリシー)を自己完結で含む**。誤爆率(§5.2)はイベントログとプレイヤー知識スナップショットの突き合わせだけで後段計算できる
- Godot側の演出(態度変化、噂の素振り)も同じイベントを購読して駆動する(GDD01 §2.7の「数値を見せない」表現の供給源)

### 3.6 M0仮経済モデル(プレースホルダ宣言)

**品目・職業・価格形成の正は [GDD02](../03-gdd/02-economy.md) へ移った。** 本節に残るのは、GDD02 がまだ答えていない M0 限りの単純化だけである:

- **品目と職業は [GDD02 §2.2・§2.4](../03-gdd/02-economy.md) が正。** **9品目・都市5職業・10世帯**。**世帯構成は親方+徒弟の2人(初期値)で、NPC 20体**([GDD02 §2.4](../03-gdd/02-economy.md)「世帯構成と NPC 数」)。本節がかつて置いていた「品目5種・職業3類型」は破棄した
- **買い手の意思決定の正は [GDD02c §2](../03-gdd/02c-price-and-budget.md)(予算)と [GDD06](../03-gdd/06-trade-and-negotiation.md)(実質コストと店の選択)へ移った。** 本節がかつて置いていた「効用 = −実効価格」は破棄した — 選択は `argmin(実質コスト)` であり、実効価格に移動の機会費用が加わる
- **売り手の提示価格は [GDD02c §1](../03-gdd/02c-price-and-budget.md) が正。** 更新式は**確定済み**である。**相場基準は自分の前日の提示価格を含む** — 保管場所は `Market` 自身(§3.2)なので専用の状態は増えない。**初日は他の売り手の観測が0件で相場基準が立たないため原価下限がそのまま提示価格になる。** ただしそのためには**初期在庫の取得原価**を初期配置で与える必要がある([GDD02c §1](../03-gdd/02c-price-and-budget.md)) — 与えないと初日の原価が 0 になる。**初期価格そのものを別に決める必要は無い。** 板寄せ・オークションを作らないことだけは変わらない
- **貨幣のソースとシンクは [GDD02d](../03-gdd/02d-external-market-and-money.md) の都市外市場が正。** 1次産品の売り注文は中心区画(Id 4)について**買い手の店選択が外部価格から合成する候補**であり、`World` にも `Market` にも実体を持たない(§3.2)。都市生産品の余剰の買い取りは `Trade`(§3.3 順5、世帯間取引の確定後)として実装する。**状態が無いので区分もハッシュも増えない。****税・財政は M0 に無い**([GDD09](../03-gdd/09-treasury-and-tax.md))
- この単純化はThe Guild 3化(観測不能な複雑さ)の回避でもある。M0で価格が制御可能なら、複雑化はGDD02で慎重に積む

### 3.8 決定論ハッシュの契約

設計目標1(同一シード → 同一の状態ハッシュ)が比較する「状態ハッシュ」の契約。

#### アルゴリズムと入力の規約

- **`System.IO.Hashing` の `XxHash64` を使う。** Microsoft 公式で仕様が固定されており、選定理由を第三者に説明できる。`Visionary.Sim` に初めて実行時の外部依存が入るため、その方針は `Visionary.Sim.csproj` のコメントに書く
- **ハッシュ入力は `int` / `long` のみとする。`string` を一切入れない。** .NET Core の `string.GetHashCode()` と `System.HashCode` は**プロセス起動ごとにランダム化されたシード**を使うため、素直に書くと別プロセス間で値が一致しない。文字列を入力の領域に入れないことで根本的に回避する
- 上記は `BannedSymbols.txt` で機械的に強制する(`System.Object.GetHashCode` / `System.String.GetHashCode` / `System.HashCode` を禁止)。実測により、`record struct` の等値比較・`Dictionary` のキー利用・`override` 宣言は壊れず、**明示呼び出しだけが捕まる**ことを確認済み
- **Id は `int`**(§3.2)。文字列 Id を使わないのはこの規約の帰結でもある
- `enum` は基になる整数値として入れる。バイト列化の方法(エンディアンの固定など)は実装判断でよいが、**選んだ方法を1か所にコメントで固定する**
- 走査は **Id 昇順**(ADR-0002の列挙順規約)。順序非依存の畳み込み(XOR・加算)を使ってはならない — 順序の破れ自体が検出したいバグである

#### CIでの検証

- **別プロセスで2回実行して一致を検証する。** 同一プロセス内の2回では、値がビルドごとに変わっていても常に緑になり、回帰テストとして無意味になる
- **ゴールデン値(既知の期待ハッシュ値)はリポジトリに固定しない。** 係数調整のたびに更新が要り、「とりあえずハッシュを更新する」習慣がついて本物の破れを見逃す

#### 含める / 含めない

**判断基準は「シムの意思決定に関与するか」。** 関与しないものだけを除外し、除外の理由は調整耐性ではなく**性能と実装コスト**に置く。

| 含める                                                          | 含めない                                            |
| --------------------------------------------------------------- | --------------------------------------------------- |
| Clock(現在tick)                                                | `Metrics` のスナップショット(意思決定に関与しない) |
| Npcs(**世帯Id**・階層・熟練度)                                  | `EventLog` の全量(同上。かつ追記専用で巨大)       |
| **Households**(**区画Id**・職業・**世帯主NpcId**・**構成員NpcId列**・流動資金・世帯在庫・工房在庫・**仕入れ移動平均単価**・**破産中フラグ**・**工具の累積摩耗**・**当日の消費不足量**・**当日の「必需を資金不足で買えなかった」件数**・**当日の生産量**・**前日の外出の労働損失‰**) |                                     |
| Market(提示価格)                                               |                                                     |
| TrustLedger                                                     |                                                     |
| Needs                                                           |                                                     |
| Promises                                                        |                                                     |
| Knowledge **全部**(`PriceObservation` / `PersonFact` / `EventKnowledge`) |                                     |
| Ledgers                                                         |                                                     |

- `Knowledge` を全部含めるのは、§3.3-9 の Rumor(不履行後の悪い噂の限定伝播 = 家族・仕事仲間・近所という**集合を列挙して複製する**処理)が、**列挙順の破れが最も起きやすい系統**だから。ここを検出範囲の外に置くと回帰テストの目的と衝突する
- `Clock` を含めるのは、含めないと「同じ状態に違う時刻で到達した」を検出できないため
- **`Households` の走査は Household.Id 昇順**(ADR-0002 の列挙順規約)。区分タグ(`Section`)は既存の値を動かさず**末尾に 9 として足す** — `StateHasher` のコメントが既にこの規律を宣言している
- **世帯の区画Id はハッシュに含める。** 不変だが初期配置の一部であり、シードから決まる世界の同一性に属する
- **`破産中フラグ` を含めるのは、[GDD02b §3.3](../03-gdd/02b-consumption-and-household.md) の**②(順5 の値付けで原価下限を 500‰ へ下げる)と ④のゲート**を駆動する状態だからである。** 値付けと職業付け替えの両方を分岐させるので意思決定に直接関与する。**真偽値は `int` の 0/1 として持つ**(状態はすべて int/long とする §3.2 の規約と、ハッシュ入力を int/long に限る本節の規約の両方による。`bool` の例外を作らない)
- **`工具の摩耗カウンタ` と `当日の消費不足量` を含めるのは、どちらも在庫から復元できない状態だからである。** 摩耗は [GDD02a §3](../03-gdd/02a-production.md) のとおり工具在庫に対して端数を持ち越すので、在庫の個数だけでは次に工具が減る日が決まらない。消費不足は [GDD02b §1](../03-gdd/02b-consumption-and-household.md) の「在庫は 0 で下げ止まる」規約のせいで、消費後の在庫から不足の大きさが復元できない。**後者は毎日 順2 が全品目を上書きする当日限りの値である**が、順4 の Need 生成がそれを読む以上、意思決定に関与する状態である
- **`当日の生産量` と `前日の外出の労働損失‰` を含めるのも同じ理由である。** 生産量は順1 が毎日書き(0 の日も書く)、順3 の④のゲート「生産量が 0」([GDD02b §4.1](../03-gdd/02b-consumption-and-household.md))と順4 の Need が読む — 生産後の工房在庫からは「ちょうど使い切った」と「入力が無くて止まった」を区別できない。労働損失は順5 が当日の外出の合計を書き、翌日の順1 が労働力から引く([GDD02a §2](../03-gdd/02a-production.md))。在庫にも帳簿にも現れない
- **都市外市場([GDD02d](../03-gdd/02d-external-market-and-money.md))はハッシュに乗らない。** 外部価格は設定と暦から決まる定数であり、レシピ表・労働力係数・区画間距離と同じく**状態ではない**(§3.2)。**ハッシュが対象とするのは `World` の状態であって、世界の定義ではない** — 定義が違えば「別の設定」であり、値が違って当然である(下記のゴールデン値を固定しない判断と同じ理由)。**売り注文を `Market` に実体化しないと決めたので**(GDD02d §2)、`Market` を丸ごと含める規約とも衝突しない

> **この区分変更でハッシュ値は必ず変わる。** [§3.8 の「ゴールデン値を固定しない」判断](#ciでの検証)がここで効く — 比較するのは「同一シード・同一設定の2回実行」なので、区分が変われば値が変わって当然であり、更新すべきファイルは無い。

> **かつての判断基準「保持期間ポリシーに支配されない状態は含めない」は破棄した。** 理由は2つ。第一に、閉じた経済シムでは保持パラメータがほぼすべて最終的に価格へ染み出す(`PriceObservation` の保持本数を変えれば買い手の価格認識が変わり、取引が変わり、流動資金が変わる)ため、基準を適用しても何も分離できていなかった。第二に、ゴールデン値を固定しないと決めたことで心配自体が消えた — ハッシュは「同一シード・**同一設定**の2回実行」を比べるものであり、保持パラメータを変えたらそれは別の設定なので値が違って当然である。
>
> **将来ゴールデン値を導入したくなったら、この基準を再訪すること。**

### 4.1 設定とCLI

実験条件はJSON 1ファイルで完結させる(Git管理して実験の再現条件を履歴に残す):

```jsonc
// configs/m0-trust-ab.json(例)
{
  "masterSeeds": [1, 2, 3, ..., 10],       // 条件あたり10反復

```

```
vsim run --config configs/m0-trust-ab.json --out results/2026-09-xx/
vsim promise-table                # §2.8の式の感度表(B×L×謝罪日)を標準出力に表示
vsim dialogue-sample --npc <id> --repeat 10   # 同一NPC10回会話の台詞出力(§6-3レビュー用)
```

同一シード集合でフラグだけ変えた2条件は、共通乱数法(ADR-0002)によりペア比較として扱える。

### 5.2 判定基準の定量化

GDD01 §6-2「価格が発散・硬直しないか」を判定関数として定義する(閾値はすべて初期値、実データを見て調整):

**集計窓は日数で固定する**(120日)。ADR-0003で1年が120日になったため「年次」という語は使わず、窓長を明示する。36,000日の地平に対して300窓が取れる:

- **発散**: いずれかの品目の日次約定価格(中央値)が、初期価格比 [×0.1, ×10] の帯を出る。または120日窓の変動係数(CV)の対数が、窓を追うごとに有意に増加し続ける
- **硬直**: 直近120日の価格レンジがベース価格の±2%未満に収束したまま動かない。または取引相手スイッチ率が5%未満に固着(「関係の履歴」だけで経済が回り市場機能が死んだ状態)
- **判定**: 信用あり条件が、信用なし条件と同じ判定関数で発散も硬直も示さないこと。加えて取引集中度(HHI)・信用Giniの経時変化を目視確認し、勝者総取り化の兆候を記録する
- 破綻した場合の対応順: αを下げる → 効果1に上限を入れる → それでも不可ならフォールバック発動(GDD01 §2.9)

GDD01 §6-5「誤爆率」の定義:

```
誤爆率 = ペナルティが適用された取引のうち、
         取引tick時点のプレイヤー保有PriceObservationから推定した公正価格では
         乖離が閾値以内だった(=プレイヤー視点では公正だった)ものの割合
```

イベントログ(`UnfairPriceSuspected` / `PenaltyApplied`)とプレイヤー知識スナップショットの突き合わせで後段計算する。判定式そのものには使わない(GDD01 §4.5の原則)。

### 5.3 §2.8信用式のプロパティテスト(手触りの機械的検証)

「早く謝ると軽い」「延長は保険になる」を、体感より先にテストで固定する:

| プロパティ                        | 検証内容                                      |
| --------------------------------- | --------------------------------------------- |
| 不履行ペナルティは e に単調非減少 | 任意のB, Lで、謝罪が遅いほど重い              |
| 当日謝罪の下限                    | e=0なら固定値5に収まる                        |
| 早期謝罪 ≦ 自動破棄              | どの時点で謝ってもe=Lの自動破棄より軽い       |
| ペナルティ上限                    | いかなるB, L, eでも30を超えない               |
| 延長利用時の完了収支              | 概ね−5〜+10に収まる(GDD01 §2.8の意図)       |
| 延長して完了 > 破棄               | 延長が「保険」として常に破棄より得            |
| 切り上げの一貫性                  | 全式で天井関数が適用され、0デルタが発生しない |
