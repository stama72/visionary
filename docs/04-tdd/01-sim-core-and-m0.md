## 0. この文書の位置づけ

ADR-0001の決定(Godot 4 + C#、シムは純C#ライブラリ `Visionary.Sim`)を、**M0の検証項目(GDD01 §6)を実行できるアーキテクチャ**に落とす。M0の目的は面白さと制御可能性の実証であって製品コードの完成ではない。したがって本書の設計は「検証実験を速く・再現可能に回せること」を最優先し、v1.0で作り直す前提の箇所は明示的にプレースホルダと宣言する(§3.6)。

## 2. ソリューション構成

```
Visionary.sln
├─ src/
│  ├─ Visionary.Sim/          # 純C#(net8.0)。Godot参照ゼロ。本書の主題
│  ├─ Visionary.Sim.Runner/   # CLI実験ハーネス(コンソールアプリ)。§4
│  └─ Visionary.Game/         # Godot 4プロジェクト。M0ではグレーボックスのみ
└─ tests/
   └─ Visionary.Sim.Tests/    # xUnit。単体・プロパティ・決定論回帰・シナリオ
```

依存方向は `Game → Sim ← Runner / Tests` の一方向。`Sim` から外への依存は標準ライブラリのみ(JSONシリアライズ含む)。

`Visionary.Game` は W5(グレーボックス着手)で作成する。それ以外は作成済みで、CI(§2.1)が通っている状態。

### 2.1 CI(GitHub Actions)

`.github/workflows/ci.yml` に2ジョブ。ランナーはUbuntu — `Visionary.Sim` がGodot非依存(ADR-0001)であることの継続的な証明を兼ねる:

| ジョブ   | 内容                                                        | 失敗が意味すること         |
| -------- | ----------------------------------------------------------- | -------------------------- |
| `sim`    | restore → build(Release) → test。結果をtrxでアーティファクト化 | 壊れている                 |
| `format` | `dotnet format --verify-no-changes --severity warn`          | 整えれば直る               |

- **警告をエラーとして扱う**(`Directory.Build.props`)。ADR-0001が挙げた「AIが幻覚APIや古いAPIを生成するリスク」をコンパイル段階で機械的に弾く一次防衛線
- 決定論の回帰テスト(§1-1)はW1で `sim` ジョブに載る。100年実行をCIのどこまで組み込むかは§7の未決定事項
- 改行コードはLFに統一(`.gitattributes` + `.editorconfig`)。Windows開発・Ubuntu CIでフォーマット判定が食い違うのを防ぐ

## 3. Visionary.Sim 中核設計

### 3.1 時間とスケジューラ

ADR-0002のとおり、`Tick` = ゲーム内1時間(long、単調増加)。システムは実行周期を宣言してスケジューラに登録する:

```
ISimSystem
  Cadence : EveryTick | Daily(hour) | Weekly(dayOfWeek, hour)
  Step(World world, SimContext ctx)   // ctx = 乱数ストリーム、イベント発行、設定
```

- 日次フェーズの実行順序は§3.3の表で固定(登録順ではなく明示順)。順序自体が仕様である
- 100年実行の内訳: 876,000 tick、うち重い処理は日次36,500回+週次5,200回

### 3.2 世界状態(データモデル)

`World` は全状態を保持する単一の集約。GDD01のデータモデルをそのまま写す:

| 区画        | 内容                                                                | GDD対応    |
| ----------- | ------------------------------------------------------------------- | ---------- |
| Clock       | 現在tick、暦(年/季節/日/時)                                         | —         |
| Npcs        | Id、職業、性格、家計(流動資金・在庫・固定支出見込み)                | §2.2.2    |
| TrustLedger | `TrustScore{from, to, value, lastMet}` の疎マップ                 | §2.1      |
| Needs       | `Need{種別, 対象NPC, 品目, 数量, 期限, 緊急度, 理由}`             | §3.2      |
| Promises    | 約束(クエスト)。`{need, t0, t1, B, 状態(有効/延長中/完了/破棄)}`  | §2.8      |
| Knowledge   | Actor別の`PriceObservation` / `PersonFact` / `EventKnowledge` | §4.1〜4.3 |
| Ledgers     | Actor別の`LedgerEntry`(取引履歴)                                  | §4.4      |
| EventLog    | ドメインイベントの追記専用列(§3.4)                                 | —         |

- 状態はすべてint/long(ADR-0002)。シリアライズ可能なプレーンデータとし、ロジックを持たせない
- セーブ = `World` のJSONスナップショット+マスターシード+設定。M0はスナップショット方式のみ(イベントログからのリプレイはデバッグ用途に限定)

### 3.3 システムパイプライン(日次フェーズの実行順)

| 順 | システム             | 責務                                                                           | GDD対応            |
| -- | -------------------- | ------------------------------------------------------------------------------ | ------------------ |
| 1  | Production           | 職業別の生産(レシピ1段)。在庫に加算                                            | §3.6(仮経済)      |
| 2  | Consumption          | 職業・家族規模別の消費。在庫から減算                                           | 〃                 |
| 3  | Household            | 固定支出(仕入・給金・税)の支払い、流動資金の更新、支払不能の検出               | GDD01 §2.2.2      |
| 4  | NeedGeneration       | シム状態(在庫不足/過剰、金銭不足…)からNeedを生成・失効                        | GDD01 §3.2        |
| 5  | Trade                | NPC間取引: 売り手の提示価格更新→買い手の相手選好(効果1はここ)→約定→帳簿記帳 | GDD01 §2.2 効果1  |
| 6  | Promise              | 期限判定、自動破棄、NPC都合キャンセルの検出                                    | GDD01 §2.8        |
| 7  | Trust                | 当日発生した信用増減の適用(理由付き)。週次: 減衰カウンタ更新                   | GDD01 §2.3, §2.5 |
| 8  | UnfairPriceDetection | 取引tick近傍の観測入手による「気づき」判定(ポリシーA/B/C差し替え点)            | GDD01 §4.5        |
| 9  | Rumor(最小)          | 不履行後の悪い噂の限定伝播(EventKnowledgeの複製)                               | GDD01 §2.8, §7   |
| 10 | Metrics              | 日次メトリクスのスナップショット記録(シムの意思決定には一切関与しない)         | §4.2              |

プレイヤー起点の行為(会話・商談・納品・謝罪)はこのパイプラインの外で、コマンド(§3.4)として任意のtickに割り込む。

### 3.4 コマンドとドメインイベント

**コマンド**(外部→シム): `Talk`, `AskNeeds`, `ProposeTrade`, `AcceptPromise`, `Deliver`, `Apologize`, `RequestExtension`, `GiveGift` など。Godotのプレイヤー操作と、ヘッドレス実験のスクリプト化プレイヤー(§5.1)が**同じコマンドAPI**を使う。これにより「グレーボックスで人間が体験すること」と「ヘッドレスで測ること」の乖離を防ぐ。

**ドメインイベント**(シム→外部・ログ): `TradeExecuted`, `TrustChanged{from, to, delta, reason}`, `NeedCreated`, `PromiseBroken{e, penalty}`, `UnfairPriceSuspected{trade, detectorObservation}`, `PenaltyApplied` など。

- イベントは追記専用で、**判定に使った文脈(取引tick、判定時のNPC側観測、適用ポリシー)を自己完結で含む**。誤爆率(§5.2)はイベントログとプレイヤー知識スナップショットの突き合わせだけで後段計算できる
- Godot側の演出(態度変化、噂の素振り)も同じイベントを購読して駆動する(GDD01 §2.7の「数値を見せない」表現の供給源)

### 3.5 エンジン境界(SimHost)

```
SimHost
  Advance(int ticks)                 // シムを進める。Godotは1ゲーム時間ぶんずつポンプ
  Execute(ICommand cmd) : Result     // プレイヤー行為。検証エラーは例外でなくResultで返す
  DrainEvents() : IReadOnlyList<DomainEvent>   // 前回取得以降のイベント
  Query : ReadModels                 // UI用の読み取り専用ビュー(会話メニュー、Tier、帳簿…)
```

- シムからGodotへのコールバックはなし。Godotが毎フレームではなくゲーム時間の進行に合わせて `Advance` を呼び、イベントを消化する
- 会話中・取引UI表示中はゲーム時間を止める(M0の暫定仕様。ポーズ方針の最終決定は分冊05)

### 3.6 M0仮経済モデル(プレースホルダ宣言)

**GDD02(経済シミュレーション)は未着手**だが、M0の比較実験には最小の経済が必要。以下はM0限りの仮置きであり、GDD02執筆時に正式仕様で差し替える:

- 品目5種・1段レシピ(例: 穀物→パン、羊毛→布、木材、ビール、蝋燭)。NPC 30〜50体、職業は生産者/加工者/消費者の3類型+行商NPC数体
- 価格形成: **提示価格の在庫圧力調整**。売り手は在庫が目標水準を上回れば日次で値下げ、下回れば値上げ(ステップ±1〜5%、下限1)。板寄せ・オークションは作らない
- 買い手の相手選好: 効用 = −実効価格 `p' = p × (1 − α × trust/100)`(効果1)。信用なし条件では `p' = p`
- この単純化はThe Guild 3化(観測不能な複雑さ)の回避でもある。M0で価格が制御可能なら、複雑化はGDD02で慎重に積む

### 3.7 差し替え可能点(実験の可変軸)

比較実験の対象だけをインターフェースで分離し、それ以外は具象で直書きする(過剰な抽象化をしない):

| 差し替え点                  | 実装                                                             | 実験                |
| --------------------------- | ---------------------------------------------------------------- | ------------------- |
| `IPartnerSelectionPolicy` | 信用あり(α適用) / 信用なし(価格のみ)                            | GDD01 §2.9 (§6-2) |
| `IUnfairPricePolicy`      | A: 即時サイレント減点 / B: 4原則 / C: ペナルティなし             | GDD01 §4.5 (§6-5) |
| 係数セット                  | α, β, γ, k, 減衰パラメータ, B範囲(すべて‰整数、設定ファイル) | バランス調整全般    |

## 4. 実験ハーネス(Visionary.Sim.Runner)

### 4.1 設定とCLI

実験条件はJSON 1ファイルで完結させる(Git管理して実験の再現条件を履歴に残す):

```jsonc
// configs/m0-trust-ab.json(例)
{
  "masterSeeds": [1, 2, 3, ..., 10],       // 条件あたり10反復
  "durationYears": 100,
  "world": { "preset": "m0-small" },        // NPC数・品目・初期在庫
  "features": { "trustInPartnerChoice": true, "unfairPricePolicy": "B" },
  "coefficients": { "alphaPermille": 200, "betaPermille": 120, ... }
}
```

```
vsim run --config configs/m0-trust-ab.json --out results/2026-09-xx/
vsim promise-table                # §2.8の式の感度表(B×L×謝罪日)を標準出力に表示
vsim dialogue-sample --npc <id> --repeat 10   # 同一NPC10回会話の台詞出力(§6-3レビュー用)
```

同一シード集合でフラグだけ変えた2条件は、共通乱数法(ADR-0002)によりペア比較として扱える。

### 4.2 メトリクス出力

| ファイル         | 内容                                                         |
| ---------------- | ------------------------------------------------------------ |
| `prices.csv`   | 日次×品目の約定価格(中央値・最小・最大)と提示価格           |
| `trades.csv`   | 日次の取引件数、取引相手スイッチ率、取引集中度(HHI)          |
| `trust.csv`    | 信用分布の要約統計(平均、Gini)、Tier別人数                   |

分析はまずRunner内で完結させる(判定関数をC#で実装し `summary.json` に出す)。グラフ化が必要な場合のみ手元でCSVを可視化する。

### 5.2 判定基準の定量化

GDD01 §6-2「価格が発散・硬直しないか」を判定関数として定義する(閾値はすべて初期値、実データを見て調整):

- **発散**: いずれかの品目の日次約定価格(中央値)が、初期価格比 [×0.1, ×10] の帯を出る。または年次の変動係数(CV)の対数が経年で有意に増加し続ける
- **硬直**: 直近1年の価格レンジがベース価格の±2%未満に収束したまま動かない。または取引相手スイッチ率が5%未満に固着(「関係の履歴」だけで経済が回り市場機能が死んだ状態)
- **判定**: 信用あり条件が、信用なし条件と同じ判定関数で発散も硬直も示さないこと。加えて取引集中度(HHI)・信用Giniの経時変化を目視確認し、勝者総取り化の兆候を記録する
- 破綻した場合の対応順: αを下げる → 効果1に上限を入れる → それでも不可ならフォールバック発動(GDD01 §2.9)

GDD01 §6-5「誤爆率」の定義:

```
誤爆率 = ペナルティが適用された取引のうち、
         取引tick時点のプレイヤー保有PriceObservationから推定した公正価格では
         乖離が閾値以内だった(=プレイヤー視点では公正だった)ものの割合
```

イベントログ(`UnfairPriceSuspected` / `PenaltyApplied`)とプレイヤー知識スナップショットの突き合わせで後段計算する。判定式そのものには使わない(GDD01 §4.5の原則)。

### 5.3 §2.8信用式のプロパティテスト(手触りの機械的検証)

「早く謝ると軽い」「延長は保険になる」を、体感より先にテストで固定する:

| プロパティ                        | 検証内容                                      |
| --------------------------------- | --------------------------------------------- |
| 不履行ペナルティは e に単調非減少 | 任意のB, Lで、謝罪が遅いほど重い              |
| 当日謝罪の下限                    | e=0なら固定値5に収まる                        |
| 早期謝罪 ≦ 自動破棄              | どの時点で謝ってもe=Lの自動破棄より軽い       |
| ペナルティ上限                    | いかなるB, L, eでも30を超えない               |
| 延長利用時の完了収支              | 概ね−5〜+10に収まる(GDD01 §2.8の意図)       |
| 延長して完了 > 破棄               | 延長が「保険」として常に破棄より得            |
| 切り上げの一貫性                  | 全式で天井関数が適用され、0デルタが発生しない |

## 6. 技術リスク

| リスク                                       | 影響               | 対策                                                                                     |
| -------------------------------------------- | ------------------ | ---------------------------------------------------------------------------------------- |
| 決定論の破れ(浮動小数点・列挙順・系統外乱数) | 全実験の信頼性     | ADR-0002の規約+状態ハッシュ回帰テスト+レビュー観点をCLAUDE.mdに明記                      |
