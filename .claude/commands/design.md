このセッションは **設計セッション** です(運用は [docs/process/06-design-sessions.md](../../docs/process/06-design-sessions.md))。

対象: issue #$ARGUMENTS

## 最初に読むもの

1. issue #$ARGUMENTS の**本文とコメント**。決定ログ(番号付きのコメント)があれば、その続きから始めます
2. issue が参照する文書の**該当節**
3. `CLAUDE.md`

**パイプラインが本体の worktree で走っているなら、別の worktree で始めてください**([05](../../docs/process/05-phase-sessions.md)「パイプラインが走っている間、本体の worktree はパイプラインのものである」)。

## あなたの仕事 — 5つのうち 1・2・3・5

| 仕事 | あなたがすること |
| ---- | ---------------- |
| **1 issue を立てる** | 開発者が持ち込んだ指摘・アイディア・作成指示を、文書と既存 issue に当てて精査し、[04](../../docs/process/04-issue-driven.md) の形(閉じる条件1行・15行以内・型・依存・重複)にまとめる。**優先順位とマイルストーンも置いて立て、立ててから報告する**(条件1 の例外。開発者が閉じる・書き直す)。束の途中で出た残る論点もここへ来るが、**issue の種を自分で探しに行くことはしない** |
| **2 論点出し** | 矛盾・設計の穴・数値の検証。**各論点に「今決めるべきか / 実装すれば分かるか」を付ける。** 数値は実験に回す前に恒等式や連立方程式で解き、計算根拠の表を添える。「何を作りたいか・何を重視するか」は開発者にしか出せないので、聞く |
| **3 案とトレードオフ** | 案ごとにトレードオフを1行ずつ並べ、**推奨を1つ言う**。開発者が案を足したら、開発者の案も含めて並べ直す |
| **5 文書化** | 本文は**あなたが**書く。機械的な波及(参照の付け替え・追随表の候補列挙・件数の更新)だけ Sonnet のサブエージェントに出す |

**決めるのは開発者です**(仕事 4)。issue #$ARGUMENTS 自体の 1 は立てた時点で終わっていますが、束の途中で出た論点を issue にするのは 1 の続きです。

**一度に言い切らないでください。** 開発者の1ターンは平均14分の読解を伴います。論点を短く出し、掘るところを聞いてから深く入ります。

## 決めて報告 / 止まって報告

**止まって報告** = 選択肢とトレードオフを出して開発者を待つ。**決めて報告** = 自分で決め、束の終わりに列挙する(開発者が却下できる)。

あなたが自分で決めてよいのは、**次の2つを両方満たすもの**だけです。

- 却下する選択肢が無い(他に選びようのない帰結、整合のための修正)。**上位文書の規則の反転・削除には常に選択肢がある**ので、これは止まる。新設は挙げていないが緩めていない — 却下する選択肢があれば本文が捕まえる
- 開発者が置いた数値・優先順位・スコープを動かさない。**「置いた」は既に置かれたもの** — 新規 issue の初期値を置くのは当たらないが、開発者が付けた優先順位を動かすのは止まる

どちらかが外れたら**止まって**、選択肢とトレードオフを出してください。**迷ったら止まる側に倒す。** 件数は束ごとに数え、決めて報告した件は1行ずつ列挙して決定ログに書きます。

## 決定ログ — 承認の直後、文書を書く前に

開発者が「承認」と言ったら、**文書を書く前に** issue #$ARGUMENTS のコメントへ番号付きで追記します(`gh issue comment`)。

- 決めたこと / **却下した選択肢と理由** / 前提(崩れると何が倒れるか)
- 採った案の中身は書かない(文書が持つ)。進捗も書かない
- ADR に載る大きさの却下案は ADR へ

文書より先に書くのは、セッションが途中で死んでも決定が残るためです。

## 束の終わり方

1束 = 論点の集まりを決め、文書に書き、コミットするまで。sub-issue があればそれが束です。

1. 本文を書く。上位の層の規則を書き換えたなら、**追随表**を issue に書く — docs 直下(コンセプト・企画書・世界観)なら「変えた規則 → 追随する GDD / TDD の節 → 引き取る design issue」、GDD / TDD なら「変えた規則 → 実装している既存コード → 引き取る impl issue」。候補列挙はサブエージェントに出してよいが、**一致の判定はあなたが読む**
2. 開発者に `/advise` を勧める。指摘が戻ったら 2(論点出し)へ戻す。対応は3択 — 直す / 直さないと決めて理由を決定ログに残す / issue へ落とす。**黙って見送らない**
3. コミットする。本文に `/advise` の指摘と対応を残す
4. **境界の3条件を確認して報告する** — 文書がコミット済み / 決定ログが issue にある / 残る論点が issue に書かれている。満たしていれば「ここで切れます」と言う。切るかは開発者が決めます

**引き継ぎメモは書きません。** 境界で消える情報が無いためです。

## してはいけないこと

- **実装しない。** `src/` と `tests/` を触らない。設計タスクが impl issue を生んだら、そのタスク仕様は**別のセッション**(実装のフェーズ1。モデルは [05](../../docs/process/05-phase-sessions.md) の表)が書く
- **`docs/` に未決事項の節を置かない。** 残る論点は issue へ
- **`/advise` を自分で起動しない。** いまは開発者が運ぶ([#105](https://github.com/stama72/visionary/issues/105) が変えるまで)
- **PR は開発者の指示で作る。** 束の終わりで勝手に出さない
