このセッションは **フェーズ2 — 実装とレビュー** です([ADR-0009](../../docs/adr/0009-phase-scoped-sessions.md) / 運用は [docs/process/05-phase-sessions.md](../../docs/process/05-phase-sessions.md))。

対象: issue #$ARGUMENTS

## 最初に読むもの

1. 該当するタスク仕様(`docs/tasks/W*.md`)
2. 同じ名前の**引き継ぎメモ**(`docs/tasks/W*.handoff.md`)。フェーズ1 が却下した設計案がここにあります
3. `CLAUDE.md`

**タスク仕様は凍結済みの指示です。** 設計はフェーズ1 で終わっており、あなたは仕様を書き直す立場にありません。

## あなたはオーケストレータです

**自分でコードを読まない。書かない。修正もしない。** 実装も、レビュー指摘の修正も implementer に渡します。

これは好みではなく、このフェーズが存在する理由そのものです。実装の読み書きを Sonnet の implementer に逃がすことで初めてトークンが減ります。**あなたがコードを開いた時点で節約は消えています。**

**例外は1つだけ** — レビュアーが**象限I-b(タスク仕様そのものの欠陥)**を指摘したとき。仕様の訂正は設計判断なので、**あなたが仕様を直してから** implementer に渡します。

## してはいけないこと

- **PR を作らない。** フェーズ3 の仕事です
- **ADR / GDD / TDD を触らない。** 実態合わせはフェーズ3、仕様の変更はフェーズ1 です
- **タスク仕様を書き換えない。** レビューで追加したテストを**別表**として足すのは可(上の表は実装に渡した時点の指示であって最終形ではない、という区別を残すため)

## 進め方

1. **implementer を起動する。** 渡すのはタスク仕様へのパスと issue 番号だけ。引き継ぎメモは渡しません(却下案はあなたが判断に使うもので、実装者の入力ではありません)
2. **報告を受け、件数を数える。** 「止まって報告した件数」と「決めて報告した件数」。これが [02-task-spec](../../docs/process/02-task-spec.md) の**仕様品質の先行指標**です
3. **止まった点を裁く。** 仕様の穴なら、あなたが決めて仕様を直し、implementer に渡し直す。判断が設計に及ぶなら**そこで止まってください** — フェーズ1 に戻す案件です
4. `dotnet build -c Release`(警告0)/ `dotnet test -c Release` / `dotnet format --verify-no-changes --severity warn` が通っていることを確認する
5. **レビュアーを起動する。** 何巡目かを必ず渡す。2巡目以降は「何巡目か・対象のコミット範囲・前巡の象限I の指摘と対応方針」を渡す(象限II 以下は渡さない)。**機械の判定結果と実装の意図は渡さない**([01-review](../../docs/process/01-review.md))
6. **指摘への対応は3択。** 直す(= implementer に渡す)/ 直さないと決めて理由を残す / issue へ落とす。**黙って見送らない**
7. 4巡目で打ち切る。**残る指摘を issue に落としてから打ち切る**

## 終わり方 — 引き継ぎメモに追記して止まる

`docs/tasks/W*.handoff.md` に、**フェーズ3 が再構成できないものだけ**を足します。

- **implementer の件数**(止まった / 決めて報告した)。止まった内容も1行ずつ
- **直さないと決めた指摘と、その理由**
- **巡ごとの件数**(0件の巡を含む)と、打ち切ったならその理由

**既に残るものは書かないでください** — 直した指摘はコミット本文が、変異と結果は doc コメントかコミットが、検証結果はフェーズ3 の再実行が持ちます。

書いたら**止まってください**。PR も文書更新もここでは行いません。

## 終わり方 — 合図を出す

**最後の1行を、次のどちらかにしてください。**[ADR-0010](../../docs/adr/0010-phase-pipeline-and-halt-conditions.md) のパイプラインはこの行だけを見ています。開発者が手で回しているときも、同じ行が「`/clear` して `/wrap $ARGUMENTS` へ進んでよい」の合図になります。

| 出す行 | いつ |
| ------ | ---- |
| `PIPELINE: DONE` | 緑のコードとコミットが揃い、引き継ぎメモに追記した |
| `PIPELINE: HALT <コード> <1行の理由>` | 下の停止則に当たった |

### 停止則 — この4つは必ず止まる

| コード | 条件 | なぜ止めるか |
| ------ | ---- | ------------ |
| `SPEC-OUTSIDE` | 象限I-b の訂正が**タスク仕様の外**(GDD / TDD / ADR)に及ぶ | 仕様の外を直すのは設計判断で、フェーズ1 の仕事。ここを止めないと **GDD が黙って書き換わる**。W2-03 の GDD02 §5.2「所要労働」の定義訂正が実例。**これだけは機械も見ている** — `DONE` を出しても `docs/03-gdd/` `docs/04-tdd/` `docs/adr/` に差分があればパイプラインが止める |
| `IMPL-BLOCKED` | implementer が「止まって報告」した | [02-task-spec](../../docs/process/02-task-spec.md) の先行指標そのもの。仕様の穴が実装側から見えた瞬間である |
| `REVIEW-EXHAUSTED` | レビュー4巡目に到達した / implementer が2回試して build・test が緑にならない | 憲章が打ち切ると定めた境界。ここから先は回しても減衰しない |
| `RED` | build / test / format が赤のまま先へ進みそう | 対話なら人が気付く。無人だと気付く主体がいない |

**逆に、次は止まりません**(W2-02・W2-03 の実測で「後から追認できた」と確かめた範囲):

- implementer の「決めて報告」(W2-02 で4件・W2-03 で0件)
- レビュー1〜3巡の指摘と、その修正
- 気付いたことの issue 化 — **PR 時にまとめます**([`/wrap`](wrap.md))

**迷ったら止まる側に倒してください。** 止めすぎの代償は通知1回ですが、進めすぎの代償は設計判断が記録なく入ることです。
